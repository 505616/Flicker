# 构建单文件可执行程序

> 这份文档给**要自己构建**的人看。只想用的话，直接去 Releases 下载预编译产物即可。
>
> 相关文档：`架构决策.md` 第三、五章（为什么要单文件、怎么分发）、`行为与运行.md`（产物运行时的行为）

---

## 一、为什么要有这个

单文件程序是"自赠程序"功能的**完整形态**：

| 形态 | 对方拿到后要做什么 | 适用 |
|---|---|---|
| **单文件 `.exe`** | **双击**。什么都不用装 | ⭐ 首选 |
| 源码包 `.fkz` | 先装 Node.js 24+，再双击启动脚本 | 开发者、想看代码的人 |

没有单文件形态时，"把程序送给对方"这件事只完成了一半 ——
接收方还得去 Node 官网下载安装，绝大多数非技术用户会在这一步放弃。

单文件形态下，发送端**也不需要装 Node**。这是它最实际的价值。

## 二、构建

### 前置

| 要求 | 说明 |
|---|---|
| Node.js 24+ | 用 SEA（Single Executable Application） |
| 网络 | 首次注入需要下载 `postject`（构建期工具） |

### 命令

```powershell
node gen/build-sea.mjs              # 构建当前平台
node gen/build-sea.mjs --no-inject  # 只到 blob，方便排查
node gen/build-sea.mjs --keep       # 保留构建目录，便于事后检查
```

产物在 `dist/`：

```
dist/flicker-0.1.0-windows-x64.exe     约 90 MB
```

### 为什么是 90 MB

产物 = **一份完整的 Node 运行时**（本机 `node.exe` 为 89.2 MB）+ 内嵌的代码与资源。

这是"对方什么都不用装"的代价，也是最核心的取舍：用体积换零安装。
换成动态链接的 Node 会小很多，但就回到"对方得先装运行时"的老问题了。

## 三、流水线（每一步都验证，失败即停）

```
① 打包模块图       → app.cjs（CommonJS）
② 准备构建目录     → app.cjs / sea-entry.cjs / version.json / 各资源
③ 生成 SEA blob    → node --experimental-sea-config
④ 复制 Node 运行时 → 以它为基底
⑤ 注入 blob        → postject
⑥ 自检产物         → 真的跑一次 --version 与 --help
```

第 ⑥ 步不是可选的。构建工具出错不会让程序崩溃，只会产出一个跑不起来的产物 ——
所以在构建阶段就把它跑起来验一遍，比等到用户双击时才发现要好得多。

## 四、SEA 的三条硬限制（全部是实测踩出来的）

这三条决定了整个构建方案的样子，改动之前请先读完。

### 限制 1：只能有一个 JS 入口

SEA 只接受一个入口文件，而本项目有十个模块。
Node 的模块系统无法从内存里的 blob 解析 `./xxx.js`，所以必须先把模块图压成一个文件。

→ 这就是 `gen/bundler.mjs` 存在的原因。

**为什么不用 esbuild/rollup**：那会让"零第三方依赖"变成一句空话。
打包器只支持本项目实际用到的语法（静态 import/export、无循环依赖），
并且**宁可构建失败也不产出坏产物**。

### 限制 2：不按包边界解析，ES 模块加载不了

实测报错：

```
Warning: Failed to load the ES module: ...\main.js.
Make sure to set "type": "module" in the nearest package.json file
```

即使 `package.json` 里写了 `"type": "module"` 也一样 —— SEA 的模块加载器不看包边界。

→ 所以**产物入口必须是 CommonJS**（`entry/sea-entry.cjs`），
且打包产物的加载方式是"内嵌资产 + `module._compile`"，而不是 `require()` 一个文件。

顺带这也否决了一个看起来更优雅的方案：用 `package.json` 的 `imports` 条件映射
按条件选资源加载器（普通 Node 下完全可用）。在 SEA 里它不成立。

### 限制 3：`require()` 只认内置模块

实测报错：

```
Error [ERR_UNKNOWN_BUILTIN_MODULE]: No such built-in module: ...\app.cjs
```

→ `app.cjs` 也必须作为**内嵌资产**存进去，入口用 `sea.getAsset('app.cjs')` 取出源码再执行。

### 另一条容易踩的：`argv[1]` 不是空的

我原本以为 SEA 里 `process.argv[1]` 会是 `undefined`（脚本路径被嵌进去了）。
实测结果是：

```
argv1    : C:\...\app.exe     ← 可执行文件自身的路径，不是 undefined
execPath : app.exe
```

→ 判断"我是不是单文件形态"必须用官方的 `sea.isSea()`，
不能用 `argv`/`execPath` 去猜。入口把结果挂在 `globalThis.__flickerIsSea` 上，
其余代码通过 `assets.js` 的 `isSingleFile()` 读它。

## 五、打包器的五条约束

打包器用**拓扑序拼接**把模块合成一个文件。这带来五条必须遵守的约束，
每一条都有对应的测试用例盯着（`test/bundler.test.js`）：

| # | 约束 | 踩过的表现 |
|---|---|---|
| 1 | 入口的 shebang 会被剥掉 | 拼接后 shebang 跑到文件中段 → `Invalid or unexpected token` |
| 2 | 模块里**不能**用 `import.meta` | CommonJS 里没有这个对象，直接语法报错 |
| 3 | 语句剥离按行扫描，不按正则 | Windows CRLF 下正则跨行吞掉了整个 `manifest.js` |
| 4 | **不允许跨模块重名**的顶层声明 | `gift.js` 与 `run.js` 各自声明 `__dirname` → 撞名 |
| 5 | 入口的 `await main()` 会被转成 Promise 链 | 顶层 await 在 CommonJS 里非法 |

第 4 条值得展开：它**不是靠打包器改名绕过的**，而是把重复的东西收拢到一处
（`src/assets.js` 的 `rootDir()`）。重复声明本身就是问题，
让打包器去自动改名只会把问题藏起来。

打包器的自检也很严：剥掉注释后检查 `import.meta`、把产物交给 `node --check`
做真实语法检查。**误报和漏报都踩过**：
最初直接在原文里搜 `import.meta`，结果被注释里提到它误伤了。

## 六、跨平台构建

**必须在目标平台上构建。** SEA 的做法是把 blob 注入一份**该平台的原生 Node 运行时**，
所以：

| 想要 | 在哪里构建 |
|---|---|
| `flicker-x.y.z-windows-x64.exe` | Windows x64 |
| `flicker-x.y.z-macos-arm64` | Apple 芯片的 Mac |
| `flicker-x.y.z-macos-x64` | Intel 的 Mac |
| `flicker-x.y.z-linux-x64` | Linux x64 |

**不能交叉编译。** 发布时用 CI 的三个 runner 各构建一份，是最省事的做法。

> ⚠️ **除 Windows 外都还没实测过。** 构建脚本本身没有平台相关的分支
> （`postject` 支持 PE / ELF / Mach-O 三种格式），但"没实测"就是没实测 ——
> 与 `架构决策.md` 里 macOS/Linux 证书信任的状态一样，如实标注。
> 不过**证书生成这一块已经不再是平台相关**的：它是纯 JS（`src/x509.js` +
> `src/session-cert.js`），三平台跑的是同一份代码，CI 在 macOS/Linux 上会真的
> 执行它并用真实 TLS 握手验证。也就是说，第 8 项（三平台实测）里
> "证书生成"这一半已经由 CI 覆盖，"浏览器信任那一步"才需要真机。
>
> 另外 macOS 上未签名的产物会被 Gatekeeper 拦一次，
> 用户需要右键 → 打开（这个和源码模式下的 `.command` 是一样的处理）。

## 七、构建期唯一的外部工具：postject

`postject` 是注入 blob 的工具，也是整个项目**运行期零依赖**之外唯一的构建期依赖。

**为什么用它而不是自己实现注入**：注入要改写 PE / ELF / Mach-O 三种可执行格式，
自己写是一条容易出错的路，而且出错的表现是"产物偶尔跑不起来"，极难排查。
`postject` 是 Node 官方文档指定的工具。

它只在构建机器上出现，不进产物、不影响用户。构建脚本用 `npx --yes postject@1.0.0-alpha.6`
临时拉取，不写进 `dependencies`。

### 怎么调用它：不经过 shell

```js
// gen/npx.mjs —— 用当前 node 直接跑 npx 的 JS 入口
spawnSync(process.execPath, [npxCliPath, ...args], { shell: false })
```

原来的写法是 `spawnSync('npx', [...], { shell: true })`，能用，但有两个问题：

1. **Node 24 会打 `DEP0190` 警告**：参数被拼进命令行字符串，转义责任落到调用方头上。
   这里虽然只是本仓库路径，但"靠运气没出事"不是理由。
2. 走 shell 就要过 **cmd.exe 的解析规则**（引号、`^`、尾反斜杠），而本项目的目录叫
   `D:\闪传`、临时目录也可能带空格 —— 这些规则很容易踩。

而且这条路本来就绕：`npx` 是 `.cmd`/shell 包装，真正执行的仍是 `node <npm>/bin/npx-cli.js`。
我们手上就有 node（正在跑构建脚本的那个），直接跑它即可。

> ⚠️ **回退路径必须留着。** Windows 上从 Node 18.20 / 20.12 / 21.7 起
> （CVE-2024-27980 的修复），`spawn` **不允许**直接执行 `.cmd`/`.bat`，
> 不带 shell 会直接 `EINVAL` —— 所以"改成 `shell:false` + `npx.cmd`"那种修法是**坏的**。
> 找不到 `npx-cli.js` 时（某些发行版的 npm 布局不在候选里）就回退到 shell 写法，
> 让它打那条警告：**能用比没警告重要**。

## 八、验收

构建脚本自己会跑两步自检（`--version` 与 `--help`）。然后跑冒烟：

```powershell
node gen/smoke-sea.mjs
```

它验四件事，**第四件是 2026-10 补的，而且它才是最容易漏的那件**：

| # | 验什么 | 为什么 |
|---|---|---|
| ① | `--version` 输出版本号 | 产物是活的、版本注入成功（`0.0.0` 就是没注入） |
| ② | `--help` 有正常输出 | 代码与资源都打进去了 |
| ③ | `send --dry-run` 能扫出真实文件 | 内嵌资源完整（SEA 最容易出问题的地方） |
| ④ | **`--assets` 的指纹与磁盘一致** | 见下面 |

### ④ 为什么需要"内嵌资源指纹"

前三条**都通过，也不代表产物是新的**。测试读的是磁盘上的页面，
`--version` / `--help` / `--dry-run` 都不看页面内容 —— 所以"改了页面、
忘了重新构建"这件事，可以让整套测试加冒烟一起全绿，而 `dist/` 里躺着旧界面。

**2026-10 真的漏了一次**：那个 89.5 MB 的产物里连 `lang-switch` 这个字符串都搜不到
（等于没有 i18n、没有"单独清除"按钮、没有中继那几个 bug 的修复），
而当时 390 个用例全绿。**同一个坑后来还踩了第二次**，见下面"赠品源码包"。

做法是三个环节接上同一份实现（`gen/asset-digests.mjs`）：

```
构建时   digestAll()        → 把每个资源的 sha256 前 16 位写进内嵌的 version.json
运行时   flicker --assets   → 把这些指纹打印出来（源码模式没有记录，就现算）
冒烟时   compareDigests()   → 与磁盘上的文件逐项比对，不一致就失败并给出重建命令
```

**赠品源码包是同一类东西，要单独比。** 打包时把源码 + 中英文文档打成
`source-pack.fkz` 嵌进产物（见 `src/gift.js`），它**不是磁盘上的某个文件**，
而是"由整个源码树算出来的" —— 所以：

```
构建时   先打包，再 assetFingerprint(pack.bytes) → 记进同一个 version.json
运行时   --assets 多打一行 source-pack.fkz
冒烟时   compareSourcePack() → **现场再打一份包**，比指纹（与正式赠送走同一个 buildSourcePack）
```

不这么做的话，改了文档、没重新构建，症状是：测试全绿、页面也是新的，
**对方收到的赠品里却是旧文档** —— 而用户明确要求赠品里带文档。

```powershell
# 手工核对（等价于冒烟的第 ④ 步）
dist\flicker-0.1.0-windows-x64.exe --assets
node -e "import('./gen/asset-digests.mjs').then(m=>console.log(m.digestAll()))"
node _lab/verify-pack-digest.mjs     # 反向验证：往文档里加一行，这条判据必须报错
```

不一致时的报错长这样 —— 直接点出是哪个文件、两边的值、以及该跑哪条命令：

```
✗ 产物与源码**对不上** —— 这个二进制里内嵌的东西不是磁盘上现在这一版。
  web/station.html
      产物里：f28acb4bf5e836e4
      磁盘上：da5d963146dd9537
      产物里内嵌的是旧版
  请重新构建：node gen/build-sea.mjs
```

两个细节值得记下来：

- **`version.json` 里不许写构建时间。** 它进 blob、blob 进产物 —— 加了时间戳，
  同样的源码就产出不同的二进制，"可复现构建"就没了（`release.mjs` 正是靠
  "校验值一致 = 同一份源码构建的"来说话）。指纹是内容的纯函数，安全。
- **跑 `--assets` 时环境里要带 `FLICKER_NO_BROWSER=1`。** 万一遇到的是**不认识
  这个开关的旧产物**，它会把它当未知参数、一路走到"什么参数都不带 → 打开图形界面"，
  于是可能弹窗并且不退出。带上这个变量就不会弹窗，超时也会被明确报成"产物太旧"。

### 手工验证完整功能

```powershell
# 用产物发一个文件（不装证书、不开浏览器，纯命令行验证）
dist\flicker-0.1.0-windows-x64.exe send .\某个文件 --password=test --timeout=5s --no-cert-install --no-qr
```

**要确认的关键一行**是自赠程序那一行：

```
🎁 附带赠送程序：flicker-0.1.0-windows-x64.exe (89 MB)
   对方双击即可运行，不需要安装任何东西
```

如果它显示的是 `flicker-0.1.0-source.fkz`，说明产物**没识别出自己的单文件形态**；
如果版本号是 `0.0.0`，说明版本没被正确注入。

> 这两个都真实发生过：
> 版本号那个 bug 的成因是 `gift.js` 自己从磁盘读 `package.json` ——
> 单文件形态下没有那个文件，于是**静默**退回 `0.0.0`，
> 接收方会以为这是个很旧的版本。现在版本统一走 `assets.js` 的 `version()`。

## 九、发布打包

构建出产物之后，用 `gen/release.mjs` 整理成可发布的形态：

```powershell
node gen/build-sea.mjs        # ① 构建本平台产物 → dist/
node gen/release.mjs --check  # ② 先看齐不齐（不生成文件）
node gen/release.mjs          # ③ 生成 dist/release/
```

`dist/release/` 里会有：

| 文件 | 用途 |
|---|---|
| `flicker-<版本>-<平台>…` | 产物本身（从 dist/ 复制过来） |
| `flicker-<版本>-<平台>….zip` | 产物的压缩包（**推荐下载**：94.4 MB → 36.0 MB） |
| `SHA256SUMS` | 校验值，格式与 coreutils 一致（`sha256sum -c` 可直接用） |
| `RELEASE.md` | Release 说明：下载表、用法、**已知限制**、校验值、构建信息 |

### 为什么发 zip（以及为什么"减小体积"没戏）

产物 94 MB 里，**89.2 MB 是 Node 运行时本身**，我们自己的内容只有 **5.1 MB** ——
"把产物做小"最多省 5%，不值得做。真正能做的是**压缩下载量**：

| | 大小 |
|---|---|
| 未压缩（exe） | 94.4 MB |
| zip | **36.0 MB（38%）** |
| 省 | **62%** |

`.gz` 也能到这个数，但 **Windows 用户双击打不开 `.gz`**，`.zip` 双击就能解压 ——
格式上没有选择余地。原始产物**照样发**（不想解压的人直接下），
`RELEASE.md` 的下载表里给的"大小"是**下载大小**（zip），并写明原始文件也在。

ZIP 是**自己写的**（`gen/zip.mjs`）：`node:zlib` 只给 deflate 流、不管 ZIP 容器
（头、中央目录、CRC-32），而项目要求零运行时依赖、构建期也只允许 postject 一个第三方工具。
这个写入器只做我们要用的那一小块，但有三条判据：

| 判据 | 在哪 |
|---|---|
| **真实解压工具能解开**，解出来逐字节一致 | `node _lab/verify-zip.mjs`（Windows `Expand-Archive` / macOS·Linux `unzip`） |
| 独立写的解析器能读回；CRC 与 `zlib.crc32` 逐位一致 | `test/zip.test.js`（8 条，含两条反向验证） |
| 同一个输入压两次**逐字节相同** | 同上 —— ZIP 头里有时间字段，写"当前时间"就会毁掉可复现构建，所以固定成 1980-01-01 |

### `--check` 核对的是 release/ 里的副本，不只是 dist/

发布传上去的是 `dist/release/` 里那份**副本**，所以 `--check` 会逐项核对：

| 检查 | 防的是 |
|---|---|
| 每个产物都有一份副本、且哈希与 `dist/` 一致 | **产物重建了、忘了重跑 `release.mjs`** —— 名字一样、内容不同，只看 dist/ 的检查会报出新哈希，看起来一切正常，而发出去的是旧的那一个 |
| 每个产物的 **zip 在**，且**解开后里面的内容**与 `dist/` 逐字节一致 | 只比 zip 自己的哈希只能证明"压缩包没被改过"，**证明不了它装的是这一版产物** —— 用户解压后拿到的是旧程序，而检查看起来一切正常 |
| `SHA256SUMS` 里的值与 release/ 里的实际文件一致（**原始与 zip 都要有**） | 校验值算错/粘贴错。这比没有校验值更糟：用户对不上会以为文件被篡改 |
| `RELEASE.md` 在 | 少了它，下载页就没有已知限制那一节 |
| release/ 里没有 `dist/` 也没有的产物 | 上一版剩下的东西会被 `dist/release/*` 一起传上去 |

⚠️ `release/` **不存在**时不算失败（"刚构建完先看看缺哪些平台"是合法用法），
但会明确提示"还没有生成发布包" —— 免得把"检查通过"误读成"发布包是好的"。

> 这一条也是踩出来的：2026-10 出现过**两次**"dist/ 已重建、release/ 里还是旧副本"
> 的中间状态，两次都是靠手工比对哈希才发现的。现在 `test/release.test.js`
> 有 21 条用例盯着它（一致时通过、旧副本、校验值错、混进别的产物，
> 外加 3 条专治 zip：**旧产物打的 / 压缩包坏了 / zip 少了**）。

### 为什么校验值不是可选项

产物有 90 MB，**没有人会去读它的源码**。那么"你下载到的这个二进制确实来自这份源码"
就只能靠校验值 —— 手搓发布时最容易忘的就是它。

而且校验值算错比没有更糟：用户跑 `sha256sum` 对不上，第一反应是"这文件被篡改了"，
从此不再相信校验这件事。所以 `test/release.test.js` 里有一条用例
**独立算一遍再与 SHA256SUMS 比对**。

### 可复现构建：**同样的源码必须产出同样的字节**

校验值只有在"可复现"的前提下才有意义 —— 否则别人拿这份源码自己构建、
得到另一个哈希，会以为产物被动过手脚。所以构建里**不许有任何非确定性输入**。

2026-10 实测发现这条曾经不成立：连续两次构建的产物**差 7 个字节**，
diff 出来正是构建目录名里的时间戳：

```
…-1791953763234\sea-entry.cjs      ← 第一次
…-1791954696943\sea-entry.cjs      ← 第二次
```

原因是构建目录叫 `flicker-sea-build-<Date.now()>`，而**入口文件名会以绝对路径进 SEA blob**
（错误信息与堆栈里要显示它）。改成按平台命名（`flicker-sea-build-windows-x64`）之后：

```powershell
node gen/build-sea.mjs      # 第一次 → 02ef812404e2a7b6…
node gen/build-sea.mjs      # 第二次 → 02ef812404e2a7b6…   逐字节相同 ✓
```

两条机器判据守着它：`test/build-sea.test.js` 断言构建目录名里不许出现
`Date.now` / `Math.random` / `randomUUID`（已反向验过：加回时间戳立刻变红），
`test/asset-digests.test.js` 断言内嵌的 `version.json` 里不许有构建时间。

> 目录名确定之后，上一次的残留必须先删干净（`rmSync(BUILD)` 再 `mkdirSync`）——
> 否则残留文件会混进这次产物，而产物"看起来很新"。

### 为什么 RELEASE.md 会明确写出"缺哪些平台"

SEA **不支持交叉编译**（见 §六）。在一台 Windows 机器上打包，就只能产出 Windows 产物。
如果说明里不提这一点，用户在下载列表里反复找 Linux 版本，只会以为是自己没看到。

同理，说明里会带上**已知限制**（中继经手密文、macOS/Linux 未在真机验证、
Firefox 收大文件可能失败、关页面无法续传、弱密码风险）——
这些必须跟着产物一起发布，不能让用户以为"端到端加密"等于"什么都防"。

### 发布

脚本跑完会直接打印可以复制的命令：

```powershell
gh release create v0.1.0 dist/release/* `
  --title "闪传 Flicker v0.1.0" `
  --notes-file dist/release/RELEASE.md
```

> 缺平台的正确做法：**在那些平台上跑一遍构建**（或等 CI 的矩阵产出），
> 把产物都放进 `dist/` 后**重跑一次本脚本** —— 这样一次发布覆盖全部平台，
> 而不是先发一个只有 Windows 的版本再补。
