### 三个骗人的数字（都踩过，都补了机器检查）

**① 文档里的测试数量会悄悄过期。**
`README.md` 上写着"242 个用例"，实际已经 390；同一段还让人去跑
`npm run test:unit` / `npm run test:serial` —— 这两个脚本**从来不存在**
（真实的叫 `test:fast` / `test:parallel`）。数字看起来越精确，越没人怀疑它。
现在 `gen/run-tests.mjs` 会额外挂一个 TAP reporter 写进临时文件，
跑完拿 `# tests / # pass / # fail / # skipped` 去核对两份 README，
不一致就打印"哪一行、现在是多少、应该改成什么"。**只警告，不让测试失败** ——
测试数量每加一条用例就变，卡住 CI 只会逼人把这个数字删掉，那更糟。
（只有"本平台完整一轮"才核对：`--fast`、`--name-pattern` 跑的是另一套数字，拿它们比等于天天误报。）

**② 文件可以被写成"能打开但全是乱码"。**
用 Windows PowerShell 5.1 的 `Set-Content`（默认按 ANSI 写）改一个含中文和
破折号的 markdown，每个非 ASCII 字符的末字节都会变成 `?`
（`e2 80 94` → `e2 80 3f`）。文件照样能打开、能提交，**测试一条都不会失败** ——
只是在 GitHub 上破折号、勾号、中文文档名全花了。
所以 `gen/check-line-endings.mjs` 现在用 `TextDecoder(..., { fatal: true })`
严格解码每个文本文件：普通 `toString('utf8')` 只会悄悄塞 U+FFFD，**只有会抛错才可能当判据**。

**③ 文档里一堆"当前事实"的数字会一起过期。**
2026-10 用户说"看看文档里有没有错误"，一次揪出四类：i18n 文案条数（写着 171，实际 319）、
单文件产物大小（89.5 / 91 MB，实际 94 MB 出头）、文档份数（各 10 份，实际各 12 份）、
示例输出里的版本号（v1.0.0，实际 0.1.0）。它们有个共同点：**数字越具体，越没人怀疑**。
现在 `gen/check-doc-numbers.mjs` 把每条都算一遍再和文档对：i18n 条数、判据条数、
中英文档份数、示例里的版本号、最低 Node 版本；产物大小另由 CI 的 Windows job 在
`build-sea.mjs` 之后用 `--artifact` 核（±0.1 MB —— 赠品源码包里带着文档本身，改一次就浮动）。
它还故意要求"**至少有一处声明**"：哪天那句话被删掉，判据会报"没找到声明"而不是悄悄失效。
反向验证在 `test/doc-numbers.test.js`（8 条）：改坏数字要报出**文件与行号**、删掉句式要报错、
动"历史叙述里的老数字"不该有反应（否则就成了"扫所有数字"的坏判据）。

> 复原时顺手验证了这条判据的可靠性：把修复后的 `../README.md` 复制一份、
> 用当时那两步 PowerShell 操作（`Get-Content -Raw` + `Set-Content -NoNewline`）
> 再跑一遍，得到**同样的 12076 字节**和**同样的 `e2 80 3f` 破坏特征** ——
> 也就是说复原内容与原文件逐字节一致，不是"看起来差不多"。


### 三平台的实际能力边界（写清楚，不含糊）

| 能力 | Windows | macOS / Linux |
|---|---|---|
| 中继跨网络、协议、加密、限速、重试、打包 | ✅ | ✅ |
| 证书**生成**（`src/session-cert.js`，纯 JS） | ✅ | ✅ **代码路径全平台同一份**；真实 TLS 握手判据见 `test/session-cert.test.js`、`test/readiness.test.js` |
| 局域网端到端（需真实会话证书） | ✅ | ⏳ 生成与握手已就绪；**浏览器信任那一步未在真机验证** |
| 把 CA 装进**系统信任库**（`src/trust.js`） | ✅（`certutil`，已实测零警告） | ❌ macOS 必然弹认证对话框、Linux 必然要装额外软件包 —— 见下 |

Linux 的结论值得单独说一句，因为它不是"还没做"，而是**没有零依赖的做法**：
浏览器在 Linux 上不读系统 CA 目录，Chromium 读的是 NSS Shared DB
（M146 起 `~/.local/share/pki/nssdb`，之前是 `~/.pki/nssdb`），写入需要 `certutil`
（来自 `libnss3-tools` / `nss-tools`，**默认不装**），Firefox 另有自己的 profile 库。
依据：[Chromium 官方 `docs/linux/cert_management.md`](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/docs/linux/cert_management.md)。
macOS 的依据是 `man security` 里 add-trusted-cert 那一句：
"per-user Trust Settings, user authentication is required via an authentication dialog"。

所以这两个平台**继续默认 `--no-cert-install`**，程序会打印手动安装的确切命令
（`trust.manualTrustHint()`），但不代跑 —— 弹对话框和装软件包都不该发生在启动路径上。

**CI 的三个平台现在跑的是同一套 20 个测试文件。** 区别只在文件内部：
碰系统证书库的 3 个用例挂 `{ skipStore }`（见 `test/trust.test.js`），
其余**全都在 macOS/Linux 上真的执行** —— 包括证书生成、结构自检、真实 TLS 握手。
这是明确的边界，不是"跳过失败"。

### ✅ 已完成：链路抖动自动重连（5b，2026-10）

**这才是长传输最常见的失败原因。** 原来的代码里，一次瞬时网络错误
（Wi-Fi 抖动、手机切网、连接被重置、DNS 闪断）会直接终止整个传输 ——
几十 GB 前功尽弃。而"对方关掉程序"这种真正的致命错误反而少见。

两端都加了指数退避重试（400ms 起、翻倍、封顶 8s，带抖动）：

| 位置 | 修的是什么 |
|---|---|
| 发送端 `RelayClient._withRetry` | open / 清单 / 状态 / batch 全部走重试 |
| 接收端 `withRetry`（页面内） | `api()` 与中继取块全部走重试 |

**关键难点：batch POST 的失败语义是模糊的。** 请求可能已经在服务端成功，
只是响应在回程丢了。盲目重发会在房间尾部多出一批重复消息。
解法恰好来自协议本身 —— **序号由服务端分配**：重试前读一次 `nextSeq`，
涨到 `startSeq + count` 就说明上一次其实落库了，直接当成功返回。
（这个设计当初是为了解决并发撞车，在这里又额外买到一次"重试幂等"。）

分类判据：只重试瞬时故障（网络层异常、超时、5xx、429）；
`NO_ROOM` / `EXPIRED` / `GONE` / `BAD_SEQ` / 用户取消**一律立刻报错** ——
把不可恢复的错误拿去重试，只会让用户盯着屏幕白等四轮退避。

12 个新用例钉住这些行为，其中最关键的一条断言是
"**恰好只 POST 了一次**"（不是"重试成功了"，而是"重试没有造成重复投递"）。

### ⚠️ 为什么"跨会话断点续传"比预想的难 5 倍（第 5 项）

我原本估"半天：块范围存进 IndexedDB，重连时对账"。**实际动手时发现两个硬约束**，
它们在浏览器 API 层面无解，不是工程量大不大的问题：

**约束一：只有 Chromium 有可能做到。**
接收端有两条写盘路径：

| 路径 | 触发条件 | 重载页面后 |
|---|---|---|
| **流式写盘**（`showSaveFilePicker` → `createWritable`） | 仅 Chromium | 数据**在磁盘上**，只要文件句柄能恢复就还能续 |
| **内存 Blob**（收完再 `Blob` + `<a download>`） | Firefox / Safari / 降级路径 | 数据**只在内存里，重载即蒸发** —— 无从续起 |

所以"关掉页面接着传"在 Firefox / Safari 上**物理上做不到**。
而 FileSystemFileHandle 能否跨会话持久化、以及重开时权限如何重新获取，
是需要逐浏览器实测的不确定项。

**约束二：中继房间的 15 分钟 TTL。**
"关了页面过一会儿再回来"的场景里，发送端的房间很可能已经过期销毁。
续传需要发送端仍在运行、且房间还活着（或能重建并重新投递）。
这已经越过了"接收端自己记账"的范围，变成两端协商。

**结论与建议做法**（分两步，第一步就能拿到大部分价值）：

1. ✅ **第一步已完成（2026-10）：同一会话内的进度保留，做到文件粒度。**
   接收端按会话记录"已完整收到并通过整体校验"的文件下标
   （`DONE_FILES` / `fileDoneBytes` / `resetProgressFor()`，见 `web/receiver.html`），
   点"重试"时不再把前面几十个已经落盘的文件重传一遍。
   `test/receiver-page.test.js` 有一条用例专门钉住两条容易退化的判据：
   **必须按会话分开记**（换了源站/房间就清空 —— 沿用旧集合会跳过根本没收到的文件，
   用户拿到残缺目录，比"重传一遍"严重得多），
   **必须排在整体校验之后**（排在前面会把收到一半的文件也标记为完成）。
   这里**只做文件粒度**：`createWritable()` 是顺序写且每次调用截断文件，
   没有"从第 N 字节接着写"，所以块粒度在浏览器里做不到 —— 这不是工程量问题。
2. ❌ **第二步（真正跨会话）不做** —— **2026-10 用户决定**。原本要做的两件事（持久化
   FileSystemFileHandle + 发送端按接收端申报的进度重新投递）技术上不是不可行，
   代价是要**同时放宽三条已写进文档的承诺**（见 §六那张表最后一行）：
   - `行为与运行.md` §七写着「**不使用 Cookie、localStorage、IndexedDB** 保存任何传输相关信息」——
     "记住写到第几块"必须存进 IndexedDB，这条就不成立了（文件句柄也得存进去）；
   - 「**一次性的链接首次访问即失效**」—— 重开页面续传就得让同一个令牌再被接受一次；
   - 「**密码与会话密钥已随本页释放**」—— 接着解密要么留着会话密钥（违背这句），
     要么让用户重新输入一次密码（那"续传"就不再是无感的了）。
   另外它**只在流式写盘那条路上有可能**（Firefox / Safari 的数据只在内存里），
   还要和中继房间的 15 分钟 TTL 赛跑。
   **取舍**：这三条承诺是这个工具的核心卖点，换一次"断点续传"不值 ——
   所以保留承诺、明确不做，而不是先做出来再改文档说明。
   同会话内能做到的部分（断线自动重连、已完成文件跳过）**照旧全部有效**。

**"诚实地做不到"比"装作能做到"重要** —— 这条要写进用户手册。

## 三、打磨（5 项）

> ### ✅ 已完成（未列在编号里）：纯 JS 生成会话证书 —— 一次消掉最大的平台短板
>
> **原始问题**：证书信任只有 Windows 有实现（用 PowerShell 的
> `New-SelfSignedCertificate`）。macOS/Linux 上 `generateSession()` 直接抛
> `NOT_SUPPORTED`，**局域网模式完全不可用**，第 8 项（三平台实测）也无从谈起。
>
> **走过的弯路**：先打算用 `openssl` 命令行补上 macOS/Linux。放弃它的原因有两个：
> ① macOS 自带的是 **LibreSSL**（参数与 OpenSSL 有差异），Linux 各发行版不一定装了
> 命令行 openssl —— 又是一层外部依赖；② **我在 Windows 上没法验证它**，
> 那这个项目"没实测就不算做完"的规矩就破了。
>
> **最终做法：纯 JS 自己编码 X.509**（`src/x509.js` + `src/session-cert.js`）。
> Node 的 `crypto.sign` 给出的 ECDSA 签名**本身就是 DER SEQUENCE**，可以直接放进证书，
> 所以"自签 CA + 一张服务器证书"只是几百行直白的编码，不需要解析器、不依赖任何工具。
>
> **验证方式是这一项最关键的部分**：不看 API 返回什么，而是
> **起一个 HTTPS 服务器、拿生成的 CA 作信任根去连**（`src/session-cert-check.mjs`）：
>
> ```
> ✓ 以 CA 为信任根能连上        HTTP 200
> ✓ 错误的信任根会被拒绝         UNABLE_TO_VERIFY_LEAF_SIGNATURE
> ✓ 不提供信任根会被拒绝         UNABLE_TO_VERIFY_LEAF_SIGNATURE
> ✓ 主机名不匹配会被拒绝         ERR_TLS_CERT_ALTNAME_INVALID
> ```
>
> 后三条是**反向检查** —— 没有它们，第一条可能只是"校验根本没生效"的假阳性。
>
> #### 排查中踩的坑（都值得记）
>
> | 坑 | 症状 | 真相 |
> |---|---|---|
> | **`X509Certificate.checkIssued()` 的语义** | 对"被 CA 签发"的证书恒返回 false | 它不是"验签名链"那个 API。我据此以为 X.509 编码错了，改了两处**本来没错的地方** |
> | **`ca.verify(srv.publicKey)` 也是 false** | 同上 | 而 `crypto.verify(tbs, sig, caPublicKey)` 是 **true** —— 签名一直是对的。最后靠真实 TLS 握手才定案 |
> | **AKI 的 IMPLICIT 编码** | 多了一层 OCTET STRING | 这个**确实是错的**（tag 后应直接跟裸摘要），顺手修对了 |

> | **Key Usage 解码器把 `unused` 字节当成内容字节** | 自检报"CA 的 Key Usage 缺少 keyCertSign（实际: 空）"，把一张**完全正确**的证书判成不合格 | `raw[i+4]` 应为 `raw[i+5]`。BIT STRING 是 `03 <len> <unused> <内容…>`。**根源是解码器被写了两份**（`trust.js` 一份、`session-cert.js` 一份），于是两份以不同姿势出错。现在合并进 `src/x509.js`，编码与解码同处一地 |

### ✅ 已完成：PWA 可安装 + Web Share API（第 6 项，2026-10）

**两块内容：可安装（PWA）+ 系统分享面板（Web Share API）。**

#### 可安装：manifest 与图标全部内联为 data URL

常规 PWA 要三个额外文件（`manifest.webmanifest` + 两个 PNG 图标）。**这个项目做不到** ——
接收端页面会被两处发出：发送端从**局域网自签 HTTPS** 直接发，relay 从 **HTTPS** 发。
两处的路径、协议、可达文件都不一样；多出三个文件意味着 relay 的部署步骤又多三步，
而且任何一个路径写错就是"装不上、还不报错"。

所以整份 manifest 作为 **data URL** 放在 `<link rel="manifest">` 里，图标用 **SVG data URL**。
**一个额外文件都不需要**，与页面"单文件、零外部请求"的约束一致（合计约 5 KB）。

应用名跟着界面语言走（中文「闪传」/ 英文「Flicker」）—— 静态 manifest 做不到这点，
所以内联的是一段**运行时拼 manifest 的脚本**，并在切语言时重新生成。

#### 分享：只在"内容还在内存里"时提供

Web Share API 要 `File` 对象，也就是要拿到**全部字节**。而这个程序的核心承诺之一是
"大文件不爆内存"：走流式写盘那条路径时（Chromium + 用户选了目录），字节写完就放手了。

要为分享把整份文件再读回来吗？不行 —— 40 GB 的文件要占 40 GB 内存，而且和
"边收边写盘"的设计直接冲突。所以规则是：**内容在内存里就提供分享，不在就不提供，并说明原因**。

手机上恰好总是走内存路径（Safari/Firefox 没有流式写盘），所以"分享到相册/微信"
这个最需要它的场景，可用性反而最高。桌面 Chromium 上文件已经落盘了 ——
那时候用户要的是文件本身，不是分享面板。

#### 两个容易写错的地方（都有用例守着）

1. **不能只判断 `typeof navigator.share === 'function'`**。桌面 Chrome 有 `share()`
   但**不支持 files**，而且各平台对类型/大小还有限制。必须先问
   `navigator.canShare({ files: [file] })` —— 只判断 API 存在的话，按钮点了没反应。
2. **用户点系统面板的"取消"会抛 `AbortError`**。那是正常操作，不该弹错误框 ——
   否则用户以为自己操作错了。

#### ⚠️ 未在真机验证

**这一项没有在真实手机上跑过。** 逻辑与生成物都有测试守着
（manifest 字段完整性、图标自包含、maskable 安全区、语言跟随、分享的能力判断），
但"装到主屏幕上长什么样""分享面板里能不能选到微信"这类事情**只能真机看**。
按项目的惯例，这里如实标注：**未实测**。

另外 `路线图.md` 下面那条「已知障碍」仍然成立：从 **relay（HTTPS）** 加载的页面
不允许请求 `http://192.168.x.x`（混合内容），所以"不同网络时手机也能收"仍需
让用户点一次"继续访问"。

### ✅ 已完成：限速 `--rate`（第 9 项，2026-10）

**做之前它是个"文档里有、程序里没有"的功能** —— 使用手册第 6.2 节早就列着
`--rate`，但 CLI 会把它当未知参数**静默忽略**。用户以为限了 5 MB/s、
实际占满上行，而这一点只有等同事抱怨网络卡才会被发现。
（同一张表里的 `--one-file` 更是**全库无实现**，已一并从手册删除。）

实现：令牌桶（`src/rate.js`），两种模式共用。接入点分别是
`TransferServer._sendChunk`（局域网，加密前等待）和
`RelaySender.run`（中继，按这一批的**明文字节**取额度）。

**为什么是令牌桶而不是"每块 sleep 固定时间"**：固定 sleep 会把速率锁死在
`块大小 ÷ sleep`，块大小一变就失准，而且不允许突发。令牌桶按**字节**记账，
块大小怎么变都对。

**实现里踩了两个方向相反的坑**，都值得记住：

1. **限速失效**：把"要补多少"写成 `Math.min(n, capacity) - tokens`。
   桶满时它恒为 0（capacity − capacity）→ `waitMs = 0` → **永远不等**。
   实测 384 KiB 在 128 KiB/s 下只花了 4ms。
2. **超发**：修完坑一之后改成"请求比桶大就夹到桶容量再放行"。
   看着解决了，其实**少扣了令牌** —— 要 384 KB 只扣 128 KB，
   实测第二次请求只等 1038ms 就把 384 KB 放了过去（应等 3000ms）。

**正确做法**：桶必须装得下被请求的量 —— 桶比请求小的时候把它**长大**。
任何"夹一下再放行"都是在超发。（`test/rate.test.js` 现在两条都有用例钉住；
`_lab/check-rate.mjs` 可以直接看数字，稳态偏差 1–4%。）

顺带修掉一个**构建工具的误报**：打包器的"顶层 await"检查是逐行正则
`/^\s*await\s/m`，它分不清"顶层 await"和"函数体里缩进较浅的 await"。
`rate.js` 里一行 8 空格缩进的 `await`（class 方法 → try → if → while）
被误判，整个构建失败，而报错只说"含顶层 await"，不说是哪一行哪个模块。
这类判断交给 `node --check`（真实语法检查）才对 —— 它既不误报也不漏报。
回归用例见 `test/bundler.test.js` 的「坑 5c」。

### ✅ 已完成：大文件内存（第 9 项后半 + 第 12 项，2026-10）—— 而且**原来的判断是错的**

第 12 项写的是"单文件 89 MB，现在是**整体读进内存**后分块发的"。
实测下来**这句话不成立**：发送端本来就是流式的。写这句话时没有量过。

用 `_lab/bench-memory.mjs` 量了两种传输方式、四个数量级（峰值物理内存，Windows
`PeakWorkingSet64` 高水位；接收端只把明文喂给哈希、不保存，测的确实是发送端）：

| 文件 | 局域网直连 | 经中继（跨网络那条路） |
|---|---|---|
| 64 MiB | 84.7 MiB | 211.3 MiB |
| 512 MiB | 136.2 MiB | 228.0 MiB |
| **2048 MiB** | **139.9 MiB（占文件的 6.8%）** | **230.5 MiB（占文件的 11.3%）** |

判据不是"看着不大"，而是**斜率**：文件每多 1 MiB，峰值只涨
**9.9 KiB**（局域网 28.5 KiB）。整体读进内存的话这个斜率必然是 1 MiB/MiB、
且峰值占比会 >100%。更能说明问题的是**增量在收敛**：

```
局域网：64→512 MiB   每 MiB 文件 +117.7 KiB
        512→2048 MiB 每 MiB 文件   +2.4 KiB   ← 文件大 4 倍，增量反而小了 50 倍
中继：  64→512 MiB   每 MiB 文件  +38.1 KiB
        512→2048 MiB 每 MiB 文件   +1.7 KiB
```

**"有界"和"线性"的区别就在这里**：线性实现的每 MiB 增量是常数，
而这里它在下降 —— 说明工作集有上界（一个 1 MiB 读取缓冲 + V8 堆水位），
传 20 GiB 和传 2 GiB 的峰值应当在同一量级。

中继模式比局域网多约 90 MiB，那部分是**设计上就要的**：在途窗口 8 块
（8 MiB 明文 + 8 MiB 密文）、批量 POST 的请求体、以及多一层 HTTP 客户端。
它是常量，不随文件增长。

结论：**第 9 项与第 12 项都不需要改代码**，需要的是把数字量出来并守住。
完整过程、判据与脚本自身踩的坑见 [`_lab/实测报告-大文件内存.md`](../_lab/实测报告-大文件内存.md)。
所以新增了 `test/large-file.test.js`（7 个用例，0.6 秒）把这条性质钉住：

- 动态判据：哈希 96 MiB 文件时本进程 RSS 增量必须 < 48 MiB
- **正向对照**：同一个判据对 `readFile(96 MiB)` 必须报警（> 48 MiB）——
  没有这一条，"RSS 没涨"只证明测不出来，不证明实现是流式的
- 静态判据：`src/server.js` 与 `src/relay/client.js` 里**不许出现 `readFile(`**
- 缓冲只分配一次、且在循环之外；`hashFile` 与 `hashBuffer` 结果必须逐块一致

`_lab/bench-memory.mjs` 不进 CI（要几分钟、几 GB 磁盘），它负责给结论与数字；

```powershell

### ✅ 已完成（并修掉一个真 bug）：中继房间的"开局三种情况"（2026-10）

**来源**：核查 `PROTOCOL.md` §3.3.1 那条「待验证：恶意方可以 `POST from:"i"` 抢占房间名，
但房间名 256 bit 不可猜测，所以实际风险为零 —— 想抢占就必须先知道密码」。

**这句话的推理是错的**：房间名确实不可*猜测*，但它**就在链接里**（64 hex）。
拿到链接、没拿到密码的人不需要猜 —— 而"链接和密码分开发"正是本产品的推荐用法。

实测（`_lab/probe-relay-preempt.mjs`，真实的 `RelayClient` + 本地中继）：

| 情形 | 房间状态 | 旧行为 | 现在 |
|---|---|---|---|
| 攻击者建房间并占住 `seq 0` | `nextSeq=1`（全是垃圾） | 发送端**静默跳过清单** → 接收端解密失败 | 明确报 `ROOM_TAKEN` + 告诉用户重新启动 |
| **创建响应在回程丢了**（无攻击者） | `nextSeq=0`（空房间） | 发送端**静默跳过清单** → 接收端等 2 分钟超时 | 补投清单，传输照常 |

**第二行才是重点，而且它是我们自己的 bug**：旧实现在 `open()` 里只看
`created.created`，为假就认为"房间已就绪"而跳过投递清单。可是"房间已存在"有**两种**
完全相反的含义 —— ①自己刚建的（响应在回程丢了，房间是空的）②别人抢先占了（房间里有东西）。
触发条件很平常：初始 `POST` 的响应丢了一次。而用户此时**已经把链接发出去了**，
收到的是一个他完全无法理解的"等不到了"。

**修法**：判据改成"房间里有没有东西"（`src/relay/client.js` 的 `open()`）：

```
nextSeq === 0  → 情况 ① 自己的响应丢了 → 补投清单
nextSeq >  0  → 情况 ② 被别人占了     → 抛 ROOM_TAKEN（不重试，附可执行建议）
```

5 个用例（`test/relay-open.test.js`）用**真实的本地中继**逐条钉住，包括
"被抢占时我们一个字节都没写进别人的房间"。

**残留的、已被接受的限制**：拿到链接的人仍然能让这次会话开不起来（拒绝服务）。
不打算再堵 —— 它要求攻击者先拿到链接，而链接本来就是凭据；真正拿到**密码**的人
根本不需要 DoS（他能直接解密全部内容）。改进的是"失败得明确且可指导"。

### ✅ 已完成：路径安全只剩一份实现（2026-10，来自 PROTOCOL.md 的「待验证」）

**起因**：`PROTOCOL.md` §6.2 末尾挂着一条「**待验证**：macOS 上 HFS+/APFS 的
Unicode 规范化（NFD/NFC）可能导致同名文件冲突」。顺着它查下去，发现的问题比这一条大。

#### 真正的问题是"两份实现，规则还不一样"

| 位置 | 规则 |
|---|---|
| `src/manifest.js` | 12 条基本齐 |
| `web/receiver.html` | `rel.replace(/[<>:"|?*\x00-\x1f]/g, '_')` —— **只有一行** |

而**真正决定文件落到用户磁盘上叫什么的是浏览器那一份**。
于是同一份清单在 Node 测试里全绿，在浏览器里会丢文件：

| 情形 | 谁会遇到 | 后果 |
|---|---|---|
| 清单里同时有 `a:b.txt` 与 `a_b.txt` | Linux/macOS 发往 Windows | 改写后同名 → **后写的静默覆盖先写的** |
| `café`(NFC) 与 `café`(NFD) | macOS 接收端 | 那边是**同一个文件** → 同样静默覆盖 |
| `A.txt` 与 `a.txt` | Windows / macOS | 同上 |
| `CON.txt` / `NUL` | Linux 发往 Windows | 创建失败，报错离"文件名"十万八千里 |
| `name.`（结尾是点） | Linux 发往 Windows | Windows 静默丢掉那个点 → 两个文件变一个 |

**共同点是"没有提示"**：界面写着"传输完成"，磁盘上少一个文件。
这比报错严重得多 —— 报错用户还能重来，静默丢文件是用户根本不知道。

#### 做法

1. 规则收进 `src/path-safety.js` —— **唯一一份实现**，纯 JS（不许 import、不许 Buffer），
   所以能原样内联进页面。
2. `gen/inline-path-rules.mjs` 把它内联进 `web/receiver.html`，`--check` 守住同步
   （与 i18n、PWA 同样的做法，已进 `npm run check` 与 CI）。
3. **R12 的比较键 = NFC 规范化 + 大小写折叠**，且比较键只用于判断，
   不改写要写盘的名字。发送端去重用的是**同一个键**，否则发送端认为不冲突、
   接收端却只写出一个。
4. 接收端在**开传之前**把冲突查出来并中止（`E_MANIFEST_DUPLICATE_PATH`），
   页面用协议的错误码，并且**不给"重试"按钮** —— 清单是固定的，重试必然同样失败，
   给一个按了没用的按钮比不给更糟。
5. 顺手对齐了 R7：旧实现拒绝 1024 **字符**，协议写的是单段 255 **字节** / 整体 4096 **字节**。
   实现与协议不一致时以协议为准，否则照着文档写客户端的人会踩空。

#### 测试怎么保证"两边真的一样"

`test/path-safety.test.js`（23 个用例）里最关键的两条不是"防黑客"，而是防**漂移**：

- 把页面里内联的那段脚本放进一个**没有 `Buffer`、没有 `process` 的沙箱**里
  **真的执行**一遍，再与 Node 那份在**同一张输入表**（34 个输入 ×
  windows/posix × strict/宽松 四种组合）上逐条比行为。
  只断言"两边都有这个函数"是不够的 —— 从前两边也都有各自的实现。
- 正向对照：`readFile` 式的写法在这里跑不起来（沙箱里没有 Buffer），
  所以这条判据**能失败**。

> 为什么不用正则查 `Buffer`：本文件的注释里就写着"不许用 Buffer"，
> 正则会被自己的注释误伤；而在真缺 Buffer 的沙箱里跑，用到了就必然抛错。

#### 顺带修掉的一个自身缺陷

`safeRelPath` 的**降级分支**（净化失败时的兜底）原本是
`raw.replace(/\\/g,'/').replace(/^\/+/,'')`，会把 `../../evil.txt` **原样返回** ——
也就是说"安全函数"在兜底时吐出了一个穿越路径。**降级不等于放弃检查**：
兜底这段照样要过滤 `..`、`.`、空段。这条是测试抓出来的。

#### 同一类毛病：接收端页面也曾有两份

同一件事在**页面**上又出现了一次，只是形式不同：接收端页面被两处用到 ——
局域网直连时 `src/server.js` 直接读 `web/receiver.html`，跨网络时中继 Worker
读构建产物 `relay/page.generated.js`。产物是 `gen/gen-relay-page.mjs` 生成的，
它里面本来就写着**源文件指纹**，但**没有任何东西去核对**这个指纹。

于是就有了一次真实的漂移：改完页面只跑了 i18n 内联，忘了重跑生成脚本 ——
局域网是新版、**跨网络发出去的还是旧页面**。这种差异不会报错、不会失败，
要等到用中继的人反馈才会暴露。

现在两条路都堵上了：

- `node gen/gen-relay-page.mjs --check`：指纹对不上就报错，并直接告诉你跑哪条命令
  （已进 `npm run check` 与 CI）
- `test/receiver-page.test.js` 里有一条用例把产物和源文件**逐字符**比对 ——
  静态检查漏在 CI 之外时，`npm test` 也会拦住

> 判据本身也验过：往 `web/receiver.html` 末尾加一行注释，这条用例立刻变红；
> 还原后立刻变绿（还原前后文件哈希一致）。

## 五、IPv6 直连（用户提出）

### 现实检查（实测，2026-10 复查）

```
本机地址：只有 192.168.1.5（内网）+ fe80:: 链路本地
全局 IPv6：**一个都没有**
IPv6 出网：ENETUNREACH（连 DNS 的 AAAA 查询都返回空）

```

复查用的脚本：`node _lab/probe-network.mjs`（只读、有界，随时可以再跑一遍）。
**2026-10 又复查了一次**（专门查 IPv6 的脚本 `node _lab/probe-ipv6.mjs`）：本机仍然只有
`fe80::` 链路本地 + `::1` 回环，**没有全局 IPv6**；用 IPv6 出网（`api6.ipify.org` / `v6.ident.me`）
两个都是 `ENOTFOUND`。结论不变，**标注也继续保留"未验证"**。

**所以 IPv6 直连现在仍然做不了** —— 不是代码问题，是这条线路上根本没有 v6。
和上次实测（2026-10 初）结论一致：**得先让运营商开通**（通常免费，部分地区不给）。

判据分三层，缺一不可 —— 这也是将来开通后要照着验的顺序：

| 层 | 判据 | 现在 |
|---|---|---|
| 有地址 | `os.networkInterfaces()` 里有非 fe80::/fc00:: 的 v6 | ❌ 没有 |
| 能出网 | TCP 连得上 v6 目标（有地址**不等于**通，这是最常见的坑） | ❌ ENETUNREACH |
| 对端也有 | 目标域名有 AAAA 记录 | ❌ 查不到 |

### ✅ 代码已实现（2026-10）；**真实 IPv6 网络仍未验证**

原先这里写的是"真要做的话，实现要点"。2026-10 把**能在本机验证的那一段全做掉并验过了**：

| 实现要点 | 状态 |
|---|---|
| 启动时探测本机是否有可用 IPv6（排除 `fe80::` 链路本地、`::1`、IPv4-mapped） | ✅ `trust.localIPv6()` + `classifyIPv6()`，分类逐条钉住（`test/ipv6.test.js`） |
| 把 `[IPv6]:port` 作为一种可达地址候选、并显示给用户 | ✅ `trust.urlHost()` 加方括号；CLI 在**真的**有 IPv6 时多打一行候选链接 |
| 自签证书的 SAN 包含 IPv6 | ✅ 已有（`src/x509.js` 编成 16 字节）+ 这次接进启动流程 |
| 有 IPv6 时绑 `::`（双栈，一个端口同时收 v4/v6） | ✅ 绑不上就回落 `0.0.0.0`，**并把 IPv6 从链接里剔除**（绝不广告没在监听的地址） |
| 拼 URL 的代码只有一份（发送端/接收模式共用） | ✅ 抽成 `src/urls.js` —— 方括号漏一处，那条路的链接就是打不开的 |

**已经端到端验到的**（用回环 `::1`，不需要运营商开通）：证书 SAN 里编 IPv6 → 绑定 `::1` →
用 `https://[::1]:port/` 真的完成 TLS 握手；**反向对照**：证书里不含 `::1` 时同样的握手必须被拒
（否则"能连上"那条判据就是假的）。双栈绑定下 v4/v6 回环都能连进来。

**仍然做不到的**（不是代码问题，见下面的三层判据）：**公网 IPv6 直连**。
本机一个全局 IPv6 都没有，所以"两端都有公网 IPv6、不经中继直连"这条路
**没有在真实网络上跑过一次** —— 这条仍标"未验证"，开通后照下面的顺序验。

```
1. 启动时探测本机是否有全局 IPv6（排除 fe80:: 链路本地）      ← 已实现
2. 有 → 把 [IPv6]:port 作为一种"可达地址"候选                 ← 已实现
3. 接收端优先尝试 IPv6 直连，失败再回落到中继                  ← 未实现（属于会合模式，见 §八 C）
4. 需要处理的问题：
   · 地址要放进 URL 的方括号里（https://[2408:...]:8443/）      ← 已实现
   · 自签证书的 SAN 要包含 IPv6 地址                            ← 已实现
   · 部分网络有 IPv6 但没有 IPv6 出网路由（"有地址不一定通"）     ← 只能真机验
```

**收益**：跨网络时不必经中继，速度更快、延迟更低、也更私密。
**但前提是两端都有可用的公网 IPv6。**

## 五·补、速度：实测数据与一个真瓶颈（重要）

### ⚠️ 2026-10 复查：**浏览器里的中继模式从来没成功过** —— 四个缺陷叠在一起

这一节比下面所有的调优都重要，所以放在最前面。

**怎么发现的**：之前所有中继验证用的都是 **Node 端接收端**
（`test/relay-e2e.test.js`、`_lab/verify-relay.mjs`），而那两处都是自己按协议拼的。
这次改用**真实浏览器**（headless Edge，通过 CDP 驱动）跑中继托管的那份真实页面，
一次就撞出四个缺陷 —— 而它们在 Node 端验证里**全都不会出现**：

| # | 缺陷 | 在 Node 端验证里为什么不出现 | 真实后果 |
|---|---|---|---|
| 1 | 消息的**类型字节**没剥掉：中继存的是 `[类型][负载]`，页面直接在 `raw` 上切片（盐/IV/tag/密文整体差一个字节） | Node 端用了 `unpackMessage()`，天然剥掉了 | 清单解密失败，界面只报一句没有定位信息的"未知错误"。**整个中继接收路径从一开始就跑不通** |
| 2 | **从不发 ack**（只有一句写着"接收端每取一块都会 ack"的注释） | Node 端每块都 ack | 队列永不回收；发送端在途占满窗口后停住；完成判据 `ackedBase >= total` 永远不成立 |
| 3 | ack 的**序号差 1**：取块用 `1 + seq`（清单占 seq 0），ack 却用 `seq` | 同上，Node 端按消息序号循环 | 最后一条确认永远差一位 → 文件其实收完了，发送端却一直不结束，最后报"等不到确认" |
| 4 | `firstChunk` 只在**带赠品分支**里赋值（`prepare.js`），且页面依赖它算块号 | Node 端自己按 `chunks` 累加 | `--no-gift` 或**赠品生成失败**（那段只有一句警告）时 `seq` 变成 `NaN`，一个块都取不到 |

第 4 条尤其值得记：它把"块的全局序号"这个协议要素变成了某个分支的**副作用**，
而默认带赠品，所以这条路径一直没被走到。

#### 修法

1. 页面的中继取块：先校验并剥掉类型字节（`msg[0]` 必须是 `0x01`/`0x02`，再 `subarray(1)`）。
2. 页面补上 ack：**校验并写盘之后**才 ack（中继收到 ack 就删消息，提前 ack 会让
   中途失败的那块永远取不回来）；**不在热路径上等待** —— 合并成后台发送，
   收尾重试几次把最后一条送出去。
3. ack 用**消息序号** `1 + chunkSeq`，与取块同一个口径。
4. `prepare.js` 在**加密之前无条件**算好 `index`/`firstChunk`；
   页面**自己也累加一遍**（不依赖对端字段），两边都硬。

#### 验证方式也换掉了

新增 `_lab/e2e-relay-browser.mjs`：真实 CLI + 真实中继 + **中继托管的真实接收页** +
**真实 Edge**（headless，不弹窗；通过 CDP 用 Node 内置的 WebSocket 驱动，零依赖）。
判据是硬的且**只有真实浏览器才能满足**：

```
✅ 发送端退出码 0          ← 它只在「全部消息都被接收端确认」之后才这样收尾
✅ 接收页进入「完成」屏
✅ 下回来的文件逐字节一致（SHA-256 相同）
✅ 中继侧没有出现明文（文件名与密码都没出现）
```

实测 4 MiB 与 16 MiB 都通过（16 MiB：**14 MB/s**，逐字节一致）。
这个脚本同时是这一组缺陷的回归测试 —— 修好之前它必然失败。

> **教训（已经吃过两次了）**：**验证脚本与真实客户端行为不一致，等于验证了另一条链路。**
> 中继这条路上，Node 端扮演的接收端与浏览器页面差了三件事（剥类型字节、发 ack、算块号），
> 于是四个缺陷全部漏过。凡是要验"真实链路"，扮演的那一端就必须和真实客户端做**同样的事**。
> `_lab/verify-relay.mjs` 的注释里已经把这条写在最前面。

### 附：ack 缺失单独立案（`test/relay-ack.test.js`，7 个用例）

在浏览器验证之前，先用 Node 端复现过"不 ack 会怎样"
（`_lab/repro-no-ack.mjs`，12 块文件、窗口 8、空闲超时 6 s）：

| 接收端 | 收到 | 耗时 | 发送端返回 | 中继队列 |
|---|---|---|---|---|
| 会 ack | 13/13 | 0.1 s | `ok:true complete` | 0 条 |
| **不 ack（页面从前的行为）** | 8/13 | 220 s | ~~`ok:true complete`~~ → 现在 `ok:false incomplete` | 8 条 |

其中"发送端误报成功"是独立的一个缺陷：循环体里 `break` 之后，函数末尾**无条件**
`return {ok:true, reason:'complete'}` —— 于是"没传完"被报成"传输完成"（实测 148 ms
就返回成功，而 `ackedBase` 还是 0）。**失败被说成成功是本项目最不能接受的一类错误**，
现在改成先判 `posted >= total && ackedBase >= total`，否则返回 `ok:false` 并带上
`posted/ackedBase/total`，`run-relay.js` 也会把原因打给用户。

### ✅ 同时修掉：浏览器里那份纯 JS 的 SHA-256 慢 2.7 倍（局域网的真天花板）


被 `probe-network` 顺手带出来的：本机网卡是 **2.5 GbE（≈295 MB/s）**，
而 loopback 端到端只测到 187 MiB/s —— loopback 没有链路限制，所以那是**实现上限**。

顺着往下查，真正的天花板在接收端：浏览器里 **WebCrypto 的 `digest` 不能增量喂**，
所以"边收边算整文件摘要"只能用页面自带的纯 JS 实现。实测它只有 **92 MiB/s** ——
连 1 GbE 的 118 MB/s 都跟不上，加并发、换网卡都没用。

原因是 `_block()` 里最朴素的一行 `const w = new Uint32Array(64)`：
**每 64 字节新分配一个 256 字节数组**。1 MiB 数据 16384 次，2 GiB 文件 3355 万次。

| 写法 | 吞吐 | 相对 |
|---|---|---|
| 每块新建 `w`（原来） | 92 MiB/s | 1.00× |
| **只改成复用 `this.w`** | **208 MiB/s** | **2.26×** |
| 复用 + 局部变量（现在） | **252 MiB/s** | **2.73×** |
| 再展开消息扩展 | 244 MiB/s | （反而更慢，没采用） |
| `node:crypto` 原生（对照） | 2370 MiB/s | 25.8× |

复现脚本 `_lab/bench-sha256-variants.mjs`（含逐位一致性校验：8 个边界长度 + 3 MiB 大缓冲）。
数值与结论写进了 `web/receiver.html` 里那个类的注释 —— 免得有人"顺手清理"回去。

**修完之后的定位**：1 GbE 上接收端不再是瓶颈（链路 118 MB/s < 哈希 252 MiB/s）；
2.5 GbE 上仍有约 175 MiB/s 的实现上限（loopback 实测取块+解密+哈希），
那属于"要不要做接收端并发预取"的取舍，见下面「还没做的」。

### 实测（本机，2026-10 初）

| 目标 | 最小往返延迟 | 稳态吞吐 |
|---|---|---|
| Cloudflare（中继所在） | **195 ms**（中位 204） | 25 MB 载荷下 **29.5 MB/s**（≈240 Mbps） |
| 腾讯云（国内对照） | **83 ms**（中位 223） | — |
| GitHub（美国） | — | 14 KB/s（小文件，仅供参考） |

### ✅ 已修（2026-10）：窗口 1 → 8 + 批量投递，实测约 5×

原来的发送端是**停等**的：投一条、等确认、再投下一条。速度被死锁在
`块大小 ÷ 往返延迟`。链路本身能跑 29.5 MB/s，停等实现只跑到 5 MB/s ——
**瓶颈在实现，不在网络。**

| 在途窗口 | 实测吞吐（195 ms 合成延迟，32 MiB） | 相对停等 |
|---|---|---|
| 1（停等） | 4.72 MB/s（平均 206 ms/条） | 1.0× |
| **8（现在默认）** | **约 23.9 MB/s**（3 次中位 17.9，单次高至 23.9） | **≈ 3.8–5×** |

**代价**：中继上同时存在最多 8 MiB 在途密文（原来是 1 MiB）。
`--window N` 可以调；`--window 1` 就是原来的停等行为（低带宽省流时有用）。

### 🔬 吞吐已经撞到带宽墙（2026-10 实测）

窗口扫描（每档 3 次取中位，`_lab/bench-window-sweep.mjs`）：

| 窗口 | 中位吞吐 | 理论上限 | 达到 |
|---|---|---|---|
| 4 | 13.8 MB/s | 20.5 | 67% |
| 8 | 17.9 MB/s | 41.0 | 44% |
| 16 | 23.4 MB/s | 82.1 | 29% |
| 32 | 27.7 MB/s | 164.1 | 17% |

**关键读数不是"达到百分比"，而是"收益在饱和"**：16 → 32 只涨 18%，
外推渐近线约 **28–30 MB/s** —— 正好等于实测链路稳态（29.5 MB/s）。
所以**加窗口已经没有意义了，瓶颈变成了带宽本身**。

> ⚠️ 这套人造延迟基准的**单次波动可达 ±65%**（同一配置先后测到 35.7 与 23.4）。
> 用它做"哪个窗口更好"的粗判可以，做**细粒度实现取舍不行**。
> 下面第 3 条就是被它误导的一次教训。

#### 实现上踩过的三个坑（都值得记住）

1. **"允许更多在途"和"真的并发发出"是两件事。**
   最先只是把窗口常数改大，但每条仍是 `await` 完再发下一条 ——
   窗口 1 到 32 实测都还是 4.8 MB/s，平均 203 ms/条，一点没变。

2. **中继要求严格按序投递，所以并发 POST 必然撞车。**
   改成"同时发 N 条"之后，到达顺序不保证，于是撞 409 `BAD_SEQ`；
   更糟的是服务端给所有撞车请求报的是**同一个**期望序号，
   它们重试时又撞在一起（实测的连锁失败）。
   **干净解法是"一批一次 POST"**：序号由**服务端**按到达顺序分配
   （`POST /r/:room/batch`），既不撞车又只花一个往返。

3. **窗口是"块数"上限，所以"空位只剩 1 块"时那一个往返就白花了。**
   `putBatch` 响应里的 `ackedBase` 是**上一轮**的读数，于是下一次进循环
   算出的空位恰好很小，投一批只投 1 块 —— 实测每批块数是 `[7,1,7,1,…]`，
   平均 4 块，只有满窗的一半。**修法**：空位不足半个窗口时宁可不投、
   先问一次状态，拿回新 ack 再投满窗（另加"连续空转 3 轮就强制投"的
   反停滞保护）。修完每批变成 `[7,8,8,8,1]`，平均 6.4 块。

#### ❌ 试过但**没兑现**的优化（如实记录）

为了"省掉每个窗口多花的那一个往返"，试过让状态读取与投递**并发重叠**
（先发探测、再投递、最后 await 两者取较新的 ack）。**实测没有收益**：
与顺序写法在窗口 4/8/16/32 上分别是 13.8/17.9/23.4/27.7 对
15.1/18.0/24.8/28.4 MB/s —— 顺序写法反而略好。该改动已撤销，
只保留有证据支持的部分（最小批量阈值 + 反停滞保护）。
**教训**：在波动 ±65% 的基准上，小于 20% 的差异不能当结论。

   **干净解法是"一批一次 POST"**：序号由**服务端**按到达顺序分配
   （`POST /r/:room/batch`），既不撞车又只花一个往返。

顺带抓出一个真实竞态：`putBatch` 在 `await` 读分块期间会让出控制权，
此刻若用户点"取消"，DELETE 会先于那条 batch POST 到达服务端 ——
房间被删、随后那条 POST 拿到 404，一次**正常取消**被报成中继错误。
修法：`destroy()` 先等在飞的那一批结束再删房间，投递循环每一轮
重新问一次中止判据。这个 bug 是端到端测试用**精确的顺序断言**抓出来的，
靠读代码看不出来。

### 关于"传到国外"

路径是：发送端 → Cloudflare 边缘 → 中继 → 接收端。
所以延迟是**两段之和**，国外传输大约：

```
中国 → 境外       每段 150–250 ms
两端合计往返      400–600 ms
→ 停等实现下      1.7–2.5 MB/s（1 GB 约 7–10 分钟）
→ 现在的窗口实现  不再受延迟限制，改为受**带宽**限制
```

**注意别再按"窗口 × 块 ÷ 延迟"去外推国外的速度了** ——
本机实测已经证明吞吐在 28–30 MB/s 处饱和（见上一节），
而那正是**本机到 Cloudflare 的链路稳态**。跨国的瓶颈是对端的
国际出口带宽，不是这个工具，也不是延迟。

所以诚实的说法是：**能跑多快取决于你和中继之间的链路有多快**，
程序的实现已经不是瓶颈（同一链路从 4.7 提到约 24 MB/s，接近饱和点）。

> ⚠️ **上面这段结论要加一个前提**：那 24 MB/s 是**接收端用 16 条并发取块**测出来的
> （`bench-window-sweep.mjs` 的 drain 默认并发 16）。而浏览器接收端是**逐块串行**的，
> 且（在修好之前）**不 ack** —— 见本节开头。所以那个数字描述的是"链路能力"，
> 不是"用户实际拿到的手感"。修好 ack 之后的真实数字需要在真机上重测。

### ✅ 已量清楚（2026-10）：串行取块就是跨网络的真正瓶颈，而且值得改

原来的判断（"收益只对 2.5 GbE 有意义，不值得动"）**是错的** —— 错在基准只给发送端方向加了延迟
（见本节末尾那条被撤销的假设）。用**真实接收页 + 真 Edge + 双向延迟中继**重测之后
（`_lab/bench-recv-rtt.mjs`，64 块 × 1 MiB，链路按本机实测的 29.5 MB/s 封顶），结论反过来了。

**① 真实页面在跨网络链路上被"一块一个往返"锁死**（改之前）

| RTT | 真实页面（改之前，逐块串行） | 理论 = 块大小 ÷ RTT |
|---|---|---|
| 0 ms | 20.4 MB/s | 不受延迟限制 |
| 50 ms | 8.9 MB/s | 20.0 MB/s |
| **195 ms** | **4.0 MB/s** | 5.1 MB/s |

相邻两次取块的间隔中位 **261 ms**（195 ms 往返 + 约 66 ms 解密/哈希/写盘/界面），
其中每块真正花在计算上的只有约 20 ms —— **其余全在等往返**。

**② 只要不再串行，同一条链路能跑满**（纯取块，不含解密/哈希）

| RTT | K=1 | K=2 | K=4 | K=6 | K=8 |
|---|---|---|---|---|---|
| 0 ms | 21.2 | 29.4 | 29.4 | 29.4 | 29.4 |
| 50 ms | 10.8 | 21.8 | 28.8 | 28.8 | 28.8 |
| **195 ms** | 4.4 | 8.7 | 17.0 | **24.5** | 24.9 |

（单位 MB/s。K=1 那列与"块大小 ÷（RTT + 块传输时间）"完全吻合：195 ms 时实测 4.4、理论 4.34。）

**③ 一条硬约束：浏览器对同一个源最多 6 条并发连接**

中继侧实测"同时挂着的取块请求"峰值：K=6 → 6，K=8 **也只有 6**。
所以 1 MiB 的块在 195 ms 上最多 6 MiB 在途 ≈ 30.8 MB/s 的理论上限，实测 24.5–24.9（约 83%）。
**想跑满更快的链路，块大小必须跟着涨**：2 MiB × 6 = 12 MiB 在途，链路才会重新成为瓶颈。

**④ ✅ 已经做了（2026-10）：接收端有界预取，实测 3.5–4.3×**

做法就是上面说的那样：`web/receiver.html` 里加了一个 `createPrefetcher`
（只并行"取回来"这一半；解密、逐块校验、写盘、ack 仍然严格按序在原地做 ——
顺序写盘与"写盘后才 ack"两条语义一个字没改）。默认深度 6（用满浏览器的 6 条连接），
缓冲上限 = 深度 × 块大小 = **6 MiB**，可用链接里的 `&pf=N` 覆盖（A/B 用）。

同一套基准、同一条链路（RTT 195 ms，链路 29.5 MB/s 封顶），真实页面的端到端读数：

| 配置 | 端到端 | 取块阶段 | 相邻取块间隔中位 |
|---|---|---|---|
| 改之前（串行） | 4.0 MB/s | 4.2 MB/s | 261 ms |
| 深度 4 | 14.0 MB/s | 15.2 MB/s | 61 ms |
| **深度 6（默认）** | **13.9–17.0 MB/s** | 16.5–19.3 MB/s | 44–48 ms |

局域网那一档也顺手量了：RTT 0 时 20.4 → 23.2 MB/s（取块阶段 28.4 MB/s，已经贴着 29.5 的链路封顶）。

> ⚠️ **诚实标注噪声**：端到端在 195 ms 上有 ±20% 的波动（深度 4 一次 14.0、
> 深度 6 两次 17.0 与 13.9）—— 按本项目的规矩，**这一档差异还不足以当结论**。
> "默认取 6"的依据是噪声小得多的纯取块那组（K=4 17.0 vs K=6 24.5），
> 以及 6 正好等于浏览器的连接预算。要把 4 与 6 分出高下，得各跑多次取中位。

**⑤ 代价与做法**（实现时守住的四条，都有对应测试）：有界乱序缓冲 + 按序写盘 + 取消清理，
内存上限按**挂起表大小**封顶（不是按"在飞请求数"—— 那样已取回未消费的块会无限堆积）；
`stop()` 必须把正在等的 `take()` 叫醒并释放缓冲。测试见 `test/receiver-prefetch.test.js`（11 条）。

### 📏 已量清楚（2026-10）：块大小值多少？—— **2 MiB 是甜点，4 MiB 没有收益**

判据是两条不等式：`连接数 × 块 ≥ 带宽 × 往返`（跑满链路），`深度 × 块 ≤ 内存预算`。
浏览器给同一个源 6 条连接，所以第一式就是 `6 × 块 ≥ BDP`。

**同一套基准（真实页面 + 真 Edge + 双向延迟中继），256 MiB，链路 29.5 MB/s 封顶：**

| 块大小 | RTT 0（局域网） | RTT 195 ms（跨网络） | 相邻取块间隔（195 ms） |
|---|---|---|---|
| 1 MiB | 25.2 MB/s | 18.9 MB/s | 45 ms |
| **2 MiB** | **27.5 MB/s** | **26.3 MB/s** | 74 ms |
| 4 MiB | 26.5 MB/s | 25.8 MB/s | 140 ms |

跨网络那一列：1 MiB 需要 5.75 MiB 在途、而 `6 × 1 = 6 MiB` **刚刚够**（所以只到 18.9）；
2 MiB 给出 12 MiB 在途（两倍余量）→ **26.3 MB/s，达到链路封顶的 89%**；4 MiB 的 24 MiB 在途**没有任何额外收益**，
只多花内存。局域网因为 BDP ≈ 0，块大小几乎不影响（25.2 / 27.5 / 26.5 是噪声级别）。

**慢链路是反例（5 MB/s、RTT 195 ms、64 MiB）：**

| 块大小 | 吞吐 | 相邻取块间隔中位 |
|---|---|---|
| 1 MiB | 4.6 MB/s | 212 ms |
| 4 MiB | 4.6 MB/s | **837 ms** |

**吞吐一模一样**（都是链路瓶颈），但大块把"进度/重传/首字节"的粒度拉粗了 4 倍：
界面 0.84 秒才动一次、丢一块要多重传 4 倍数据、第一块要等 `块 ÷ 带宽` 才落盘。
**所以"越大越好"是错的：超过 BDP 之后，多出来的块大小只买到一个更粗的粒度。**

**结论（本机、这类链路）：2 MiB 是甜点；但默认值暂时不能改** —— 因为下面这条硬墙。

**⚠️ 改成 2 MiB 会撞上中继的硬上限（这才是真正挡住它的东西）**

一条消息就是一块，而中继的 `MAX_MESSAGE_BYTES = 1 MiB + 17`。
这个常量**写在用户自己部署的 Cloudflare Worker 里**：客户端改成默认发 2 MiB，
**所有已部署的老中继都会 413 拒收**（`TOO_LARGE`），而用户不会知道要去重新部署。
所以块大小不是纯本地参数 —— 要动它，得先给中继加一条"我能收多大"的**能力协商**
（协议 §0.1 的"只增不改"允许新增可选字段），发送端取 `min(想要的, 对方声明的)`；
老中继不声明 → 回落到 1 MiB，谁都不会坏。

**顺带抓出两个真 bug（都是"块大小 ≠ 协议默认值"时才会触发）**

| 位置 | 症状 | 根因 |
|---|---|---|
| `src/server.js`（局域网发送端） | 块大于默认值时**静默截断**：读盘只读满 1 MiB，剩下的当成零字节发出去 —— 文件到接收端就是坏的，而没有任何一处报错 | 常驻读缓冲写死 `Buffer.allocUnsafe(PARAMS.chunkBytes)`，却按 `file.chunkBytes` 去读 |
| `src/relay/client.js`（中继发送端） | 报"文件在传输过程中被改动（第 N 块）"—— 错误指向用户的文件，其实缓冲区小了一倍 | 同一个坑的第二处，只是这次有 `bytesRead !== plainLen` 把它拦下来了 |

两处现在都按**清单里实际用到的最大块**分配。这类"默认值之外的分支从没被走过"的问题，
正是"**没实测就不算做完**"要防的东西 —— 量块大小顺手就把它们逼出来了。

> 测量用的开关是环境变量 `FLICKER_CHUNK_BYTES`（`bin/flicker.js`），**刻意不做成 `--chunk` 参数**：
> 在能力协商落地之前，让用户随手把块调大只会给他们一个"对方中继 413"的哑巴错误。

### ✅ 已做（2026-10）：能力协商 —— 让 2 MiB 的块能安全启用

上面量出"2 MiB 是甜点"，但它的前提是**中继收得下**：一条消息就是一块，
而中继的单条上限写在**用户自己部署的 Worker 里**。直接改默认值 = 老中继全部 413。
所以做的是协商，而不是改常量：

| 角色 | 做什么 |
|---|---|
| 中继 | `GET /health` 与创建房间的响应里**声明** `maxMessageBytes`；本项目部署默认 `2 MiB + 17`，协议保证的最小值仍是 `1 MiB + 17` |
| 发送端 | 先问能力，再取 `min(想要的, 对方声明的 − 17)`，夹在 `[64 KiB, 8 MiB]`；**读不到就按 1 MiB**（老中继、非 JSON、探测失败三种情况都回落） |
| 接收端 | 不参与 —— 块大小在清单的 `files[].chunkBytes` 里（IV 只由块号派生、AAD 只绑文件下标/块号/总块数/明文长度，都与块大小无关） |
| 用户 | `--chunk=auto`（默认）/ `512k` / `2m` / `4m`；超过中继上限会被**压低并说明**，而不是发出去被拒 |

实测（256 MiB、往返 195 ms、链路 29.5 MB/s 封顶，**走的是产品自己的默认路径**）：

| 配置 | 端到端 |
|---|---|
| 最早的串行接收端 | 4.0 MB/s |
| 预取 6（1 MiB 块） | 18.9 MB/s |
| **预取 6 + 自动块大小（协商到 2 MiB）** | **25.5 MB/s（链路的 86%）** |
| 手动 4 MiB | 25.8 MB/s（没有收益） |

测试：`test/chunk-size.test.js`（9 条，策略与回落）、`test/relay-e2e.test.js` 里那条
"新中继用 2 MiB 跑通 / 老中继回落到 1 MiB 也跑通"（真的传一遍并逐字节比对）。

### 🔬 已量（2026-10）：链路到 2.5 Gbps 时会卡在哪

把基准的链路上限调到 **295 MB/s（≈2.5 Gbps）** 重跑（256 MiB、往返 0）：

| 测什么 | 结果 | 说明 |
|---|---|---|
| **纯取块**（不解密、不校验） | **280.8 MB/s（≈2.25 Gbps，链路的 95%）** | 传输层没问题：6 条连接 × 2 MiB 的块就够了 |
| **真实页面端到端** | **105.1 MB/s（≈0.85 Gbps）** | **瓶颈变成接收端主线程的每块计算** |

拆开看：真页面上每块要做"WebCrypto 解密 + 每块 `crypto.subtle.digest`（原生）+ **纯 JS 的整文件增量哈希** + 写盘/界面"，
而其中纯 JS 那一份实测上限是 **252 MiB/s**，且全在**主线程**上、与其它步骤串行。
所以 2.5 Gbps 上"网卡够快、中继够快、发送端够快"，先到顶的是浏览器里那一条线程。

> ⚠️ 这两个数字还说不上是"接收端的天花板"：105 MB/s 那组里，路径上还有本基准自己的
> Node 中继（每条 2 MiB 消息要几次内存拷贝）。**要量准就得把中继从路径上拿掉** ——
> 那一组**已经补做了**，见下面「✅ 已量（2026-10）：局域网直连、真页面、中继不在路径上」。
> 这里如实写下"量的是什么、还缺什么"，免得以后把 105 MB/s 当成产品的上限。

**真要继续往上走，杠杆的顺序是：**

1. **把整文件增量哈希挪到 Web Worker**（现在它在主线程上，252 MiB/s，且挡着一切）；
2. 每块少碰 DOM（进度更新合并成每 N 块一次）；
3. 高延迟链路上块大小按 BDP 自适应（`6 × 块 ≥ 带宽 × 往返`：2.5 Gbps × 195 ms ≈ 57.5 MiB，
   即需要 ~10 MiB 的块才喂得满，而块越大内存与粒度代价越大）；
4. 真要 2.5 Gbps 跨网络，6 条连接这条浏览器硬上限本身也会成为约束。

### ✅ 已量（2026-10）：局域网直连、**真页面**、中继不在路径上

上面那两个数字还带着一个疑点："105 MB/s 里有多少是基准自己的中继？" 所以补做了这一组
（`_lab/bench-lan-page.mjs`）：真 CLI 发送端 + 真 Edge + **真页面直连发送端的 HTTPS**，
中继完全不参与。256 MiB，headless：

| 配置 | 端到端 | 取块阶段 |
|---|---|---|
| 块 1 MiB，预取 6 | 117.4 MB/s | 130.3 |
| 块 2 MiB，预取 6（默认） | 128.6 MB/s | 135.4 |
| 块 4 MiB，预取 6 | 132.5 MB/s | 147.9 |
| 块 2 MiB，**预取 1（串行）** | 127.6 MB/s | 137.8 |
| 块 2 MiB，**走真实网卡（2.5 GbE）** | 123.0 MB/s | 140.3 |

> 写盘在这里用**替身**（headless 里驱动不了原生保存对话框）：给 `showSaveFilePicker`
> 装一个**计数用的假句柄**，页面仍然走它自己的流式写盘分支，只是字节被数一下丢掉。
> 因此这一组不校验落盘内容 —— 内容正确性由页面自己的逐块哈希/整体哈希保证
> （任何一块不对都会停在错误屏，脚本会如实报出来）。脚本输出里也写明了这一点。

**读数说明了三件事：**

1. **瓶颈不是网卡、不是发送端，而是页面主线程的每块计算。**
   走真实网卡（2.5 GbE，理论 295 MB/s）只比回环慢 4%；而发送端本身在 loopback 上
   能跑 250+ MiB/s（`bench-lan-parallel.mjs`：仅取块 253.5、取块+解密+哈希 174.7）。
2. **预取在局域网里没有差别**（127.6 vs 128.6）—— 回环往返≈0，流水线没有可隐藏的延迟，
   于是全部时间都花在消费循环的 CPU 上。这与"预取是为跨网络做的"完全一致。
3. **块大小影响很小**（117 → 128 → 132）—— 也说明限制在**每字节**的 CPU，
   而不是每块的固定开销。

**所以这台机器上接收端的真实天花板是 ~130 MB/s ≈ 1.04 Gbps**，
而它由"主线程上那条串行消费循环"决定；其中纯 JS 的整文件增量 SHA-256（实测 252 MiB/s）
大约占一半。浏览器自己的取块能力远不止于此（中继那条路的纯取块实测 280.8 MB/s）。

> **修正上面那节的措辞**：2.5 Gbps 那组里"真页面 105 MB/s"与这里的 128.6 相差约 20%，
> 也就是说**中继只占小头，主线程 CPU 才是大头**。当时的谨慎是对的，现在的数字也把
> 两者的份额分开了 —— 这一节的目的正是"把基准自身的开销从结论里摘出去"。

### ✅ 已做（2026-10）：把主线程那笔 CPU 搬走 —— 局域网 123 → 208.7 MB/s

上面那组读数把天花板指得很清楚：**瓶颈是接收端主线程上的每块计算**。
于是做了两件事（都在 `web/receiver.html`）：

| 改动 | 为什么 |
|---|---|
| **整文件增量摘要挪进 Web Worker** | 它是主线程上最大的一笔 CPU：纯 JS 的 SHA-256，实测 252 MiB/s（2 MiB 的块约 8 ms），而它与取块、写盘完全无关。逐块校验本来就走 `crypto.subtle.digest`（原生、不在主线程），所以只有这一项需要搬 |
| **进度刷新节流到 100ms 一次** | 从前每收一块写 5 个 DOM（两个宽度 + 三段文字）。2 MiB 块、300 MB/s 时那是每秒 150 次样式/布局；改成最多 10 次/秒，收尾强制刷一次保证显示到 100% |

**结果**（256 MiB、真页面、中继不在路径上；同一条 2.5 GbE）：

| 配置 | 端到端 | 取块阶段 |
|---|---|---|
| 改之前（主线程哈希 + 每块刷 UI） | 123.0 MB/s | 140.3 |
| **改之后** | **205.4～208.7 MB/s** | **293.2～300.2** |

取块阶段 293 MB/s ≈ **2.35 Gbps**，已经贴着 2.5 GbE 的线速（295 MB/s）——
也就是说**传输层这一半基本跑满了**，剩下的差距（293 → 209）是主线程上仍然要做的
解密、逐块校验与写盘。跨网络那条路同样受益：195 ms 往返、自动块大小下 25.5 → **26.4 MB/s**。

**几个必须一起记住的实现细节**（都有测试盯着）：

- **Worker 的源码是从页面自己的实现拼出来的**（`K256` 由运行时数组还原、类体取
  `Sha256.toString()`）—— 手抄第二份实现迟早会漂移，症状是"文件明明完好却报校验失败"。
  `test/receiver-hash-worker.test.js` 会把这段源码真的跑起来，与 `node:crypto` 逐位比对。
- **零拷贝转移只允许发生在流式写盘那条路**：Blob 回退路径会把每一块的**视图**留到最后拼 Blob，
  这时把底层缓冲转移给 Worker 就会把数据"挪走"，结果是**校验通过、文件是坏的**。
  所以 `update(pt, { transferable: streamingSink })` 的开关由 sink 决定。
- **拿不到 Worker 就退回主线程**（CSP、老浏览器、创建失败）——功能不能因为一个优化而消失。
  为此给局域网那条路的 CSP 加了 `worker-src blob:`（仍然只允许本页自己的 blob）。
- **Worker 整页共用一个**：每个文件新建一个既浪费，又会多出一堆 `blob:` 对象 ——
  实测连演练脚本的探针都被它们骗过一次（把 8 个 Worker 脚本当成了"多收到的 8 个文件"）。

**还剩什么**：主线程上仍有解密（WebCrypto）、逐块 `subtle.digest`（原生）与写盘调用；
再往上走得把这几步也并行化（多条消费流水线），复杂度和风险都高一个量级 ——
按现在的数据（局域网已贴线速、跨网络已贴链路），**收益不值这个风险**。

**⑥ 这个基准自己踩的三个坑**（都记下来，免得下次重犯）
1. **ack 被放进了热路径**：并发取块器里 `await` 一次 ack 就是多一个往返，于是"并发 8"看起来
   和"并发 1"一样快 —— **页面当初就是这么错的**，我在基准里又错了一次。
2. **发送端会超时销毁房间**：它等不到 ack 就把房间删了，长测量中途开始报 `NO_ROOM`；
   改成直接从 Node 灌满房间、绕开发送端之后才量得准。
3. **漏清定时器**：prefill 模式没有发送端，收尾代码去读 `sender.cli` 抛错、跳过了 `clearInterval`，
   于是脚本跑完全部用例却不退出 —— 实测卡了近一小时，什么结果都没打印出来。

> ⚠️ **本节末尾那条"被否掉的假设"应当撤销。** 当时用 `bench-recv-concurrency.mjs` 测出
> "串行反而最快（29.3 MB/s）"，是因为那个基准**只给发送端方向加了延迟**、
> 接收端的 GET 是零延迟返回的 —— 它根本测不到"每块一个往返"。
> 换成双向延迟之后，**原来的担心是对的**：串行 = 每块一个往返，跨网络就是被它锁死的。

## 六、明确**不做**的（避免以后被问）

| 不做 | 原因 |
|---|---|
| 传完自动删除源文件 | 误操作无法挽回，不该由传输工具做 |
| 云端存储 / 离线传输 | 那就不叫"一次性"了 |
| 多对多群发 | 会破坏"两台电脑、一个密码"的简单模型 |
| 记住密码 | 违背一次性原则，任何持久化都会削弱核心承诺 |
| 遥测 / 使用统计 | 这个项目不该有 |
| 插件往页面里插任意 DOM（"插槽 UI"） | 要动页面结构，**风险比收益大**；页面插件只保留 `page/actions` 一个按钮位（2026-10 决定，原列在 `插件.md` §11） |
| **跨会话断点续传**（关掉页面过一会儿接着传） | **要同时放宽三条已经写进文档的承诺**：① 不使用 Cookie / localStorage / IndexedDB —— 而"记住写到第几块"只能存进 IndexedDB（`行为与运行.md` §七）；② 一次性链接首次访问即失效 —— 而重开页面就得让同一个令牌再生效一次；③ 密钥随本页释放 —— 而接着解密必须留着会话密钥（或让用户重输密码）。再加上它**只在 Chromium 上有可能**（Firefox / Safari 的数据只在内存里），还要和**中继房间的 15 分钟 TTL** 赛跑。**2026-10 用户决定：不做**，理由记在 §二（见上） |

## 七、和同类工具的关系（竞品调研记录）

### 起因：一个需要纠正的判断

2026-10 有过一句判断："应该没有什么文件传输工具像我们这样吧，竞争对手应该会很少。"

**这个判断是错的**，而且错得值得记下来 —— 因为它会直接带偏开源后的宣传口径。
真去查一遍就会发现同类产品有几十个，其中好几个已经做了很多年、用户量比我们大得多。
如果 README 里写"没有同类工具"，内行一眼就看穿，反而把可信度赔进去。

### 调研记录（2026-10，来源见各条链接）

| 类别 | 代表 | 它的位置 | 与我们最关键的差别 |
|---|---|---|---|
| 浏览器 P2P，两端零安装 | [PairDrop](https://github.com/schlagmichdoch/PairDrop)（Snapdrop 后继）、[FilePizza](https://github.com/kern/filepizza) | 和我们的**接收端**最像，[浏览器打开就能用、什么都不用装](https://www.makeuseof.com/using-pairdrop-in-browser-windows/) | 走 WebRTC DataChannel，收进内存再拼 Blob。PairDrop 的 issue 里就有[给 iPhone 传 200 MB 的限制](https://github.com/schlagmichdoch/PairDrop/issues/294) —— 这正是"几十 GB"分道扬镳的地方 |
| 命令行 + 中继 | [croc](https://github.com/schollz/croc)、[magic-wormhole](https://github.com/magic-wormhole/magic-wormhole) | 成熟、跨平台、有续传，用户比我们多 | magic-wormhole 用的是 **SPAKE2（真正的 PAKE）**，我们不是。见下面"要诚实承认的差距" |
| 局域网互传（含手机） | [LocalSend](https://github.com/localsend/localsend) | 手机↔电脑是它的主场景 | [两端都要装 App](https://wiki.archlinux.org/title/LocalSend)；我们要求接收端零安装，代价是手机当不了发送端 |
| 加密后过服务器再下载 | [Wormhole.app](https://wormhole.app/)、[Send](https://github.com/timvisee/send)、网盘 | 用户体验最省事：发送方上传完就能关页面 | 是**存储转发**：Wormhole.app 是[10 GB 上限、链接 24 小时失效](https://www.blogdumoderateur.com/tools/wormhole/)，数据要先落到它的服务器（加密的）。我们要求两边同时在线，但中继只在内存里转发 |
| 新一代 P2P 桌面端 | [dropwire](https://github.com/muhamadjawdatsalemalakoum/dropwire)（基于 iroh）等 | 端到端加密 + 可续传，工程上比我们先进 | 两端都要装桌面程序；我们的接收端是浏览器 |

> 数量级参考：一个法国测评站光"文件传输"这一类就列了
> [19 个替代品](https://www.blogdumoderateur.com/tools/productivite/transfert-fichiers/)；
> HN 上"最好的 FOSS 文件分享工具"是[常年在讨论的话题](https://news.ycombinator.com/item?id=38876954)。

### 我们真正的差异：四条同时要才成立

| 差异 | 为什么对手做不到（或不愿意做） |
|---|---|
| 接收端零安装 **且** 边收边写盘 | WebRTC 那条路要先把数据收进内存；流式写盘要 Chromium 的 File System Access API，而且得整条链路（HTTP + 分块 + 增量哈希）都为它设计 |
| 两边只共享一个**密码** | 没有账号、房间号、"先上传再下载"。房间名本身就是密码派生出来的，没密码连房间都找不到 |
| 一次性 + **中继不落盘** | 中继内存队列 15 分钟 TTL。商业产品靠"存下来"提供"对方离线也能取"，那不是我们要的模型 |
| 零运行时依赖 + 单文件 + **中继可自部署** | "自己托管、不需要相信任何公司"是商业模式的禁区，也是我们唯一无法被复制的部分 |

**判定标准写在这里**：这四条是"和同类放在一起还值得存在"的理由。
以后加功能时，如果某个改动会削弱其中任何一条（比如为了体验引入云端存储、
为了让房间更好记而放弃密码派生房间名），那它就该被拒绝 —— 见第六章"明确不做"。

### 要诚实承认的差距（比"我们最好"重要）

| 差距 | 现状 | 对应 |
|---|---|---|
| 手机不能当发送端 | LocalSend / PairDrop 的主场景我们做不了 | 第 7 项 |
| 只实测过 Windows | 开源后第一批 issue 一定来自 macOS / Linux | 第 8 项 |
| 没有代码签名 | SmartScreen 会拦，而多数同类是签名的安装包 | 第 11 项 |
| **不是 PAKE** | 共享密码 + PBKDF2 60 万轮 + HKDF。密码弱 → 离线爆破可行；默认生成的 4 词口令熵够，用户自设的弱密码就是弱点（`使用手册.md` §10.5 已写明"不防弱密码"） | 记为**已知弱点**，见 `SECURITY.md` |
| 没有第三方审计 | "端到端加密"目前只是我们自己说的 | 开源本身就是为此；但审计仍是空的 |
| 块粒度续传做不到 | `createWritable()` 顺序写且每次截断，浏览器 API 层面没有"从第 N 字节接着写" | 第 5 项 |

### 因此开源时的口径（已落到 README）

1. **不写"没有同类工具"**，写清楚"这不是唯一选择，我们是某个交叉点上的选择"，
   并把同类工具**按名字列出来**（`README.md` / `../README.md` 各有"和同类工具比，它站在哪儿"一节）。
2. **配一张"什么时候你该去用别的工具"的表** —— 手机当发送端、对方离线、要匿名、
   要经审计的密码学、要跨会话续传、连 90 MB 都不想下：这六种情况明确指向别的工具。
   主动劝退不适用的用户，比事后解释"其实我们不适合你"便宜得多。
3. 差距写进 `SECURITY.md` 的已知弱点，而不是只写在路线图里 —— 评估安全的人只看那一份。

## 九、写演练脚本时抓出来的两个协议问题（2026-10）

写 `_lab/rehearsal-lan.mjs` 的过程中，第一次用**真浏览器**跑局域网全流程，
抓到两个此前所有测试都照不到的问题。

### ① 真 bug：页面的握手 MAC 漏了域分隔前缀 → 局域网模式根本连不上

**症状**：真浏览器打开局域网链接、输入正确密码，页面永远显示"密码不一致"。
探针显示 `POST /api/auth/finish → 401`。

**原因**：页面的 `localTransport()` 直接签了挑战本身
（`sign('HMAC', keys.auth, challenge)`），而发送端按套件算的是
`HMAC(K_auth, "flicker/1/recv\n" ‖ challenge)`。两边永远对不上。

**为什么测试没发现**：`test/e2e.test.js` 用的是 Node 侧那份**按协议写**的接收端，
而页面这套握手是**另写了一遍**的 —— 又是"两份实现"。
390 多个用例全绿，因为**没有一个用例执行过页面里那段握手代码**。

**修复与判据**：
- 页面加 `macInput(role, challenge)`，`recv`/`send` 两个方向都用它
- `test/receiver-page.test.js` 新增两条：把页面那个函数**抠出来真跑**，
  与套件的 `receiverMac`/`senderMac` 比**真实 MAC 值**；再把前缀的字面值钉死
- 反向验过：把调用点改回"直接签 challenge"，用例立刻变红
  （顺带把"改了页面忘了重生成中继页面"那条判据也一起点红了 —— 两条守卫生效）

> **教训**：这是"测试全绿但功能是坏的"的又一例。判据必须落在
> **真实客户端执行的那段代码**上；只测"另一份按协议写的实现"等于没测。

### ② 文档与实现不一致：`PROTOCOL.md` §4.5 的 MAC 构造从未实现

核对时发现三套东西各说各话：

| 来源 | MAC 输入 |
|---|---|
| `PROTOCOL.md` §4.5 / 附录 B | `"flk1-recv"` ‖ `"FLICKER/1"` ‖ `"recv"` ‖ nonce（`mac_i` 还要拼 `SID`） |
| `src/suite/flicker1.js`（**实际线上格式**） | `"flicker/1/recv\n"` ‖ nonce |
| `web/receiver.html`（修复前） | nonce（什么都没有） |

文档那套**更强**（显式绑定协商出的 `suite_id`，`mac_i` 里还有对 `SID` 的承诺），
但**从来没实现过**：当前 `SID` 是认证后随机生成的，要实现文档那套就得把 `SID` 改成可推导，
是一次两端 + 页面的线上协议变更。

**这一次没有"以协议为准"直接改**，理由是：

1. 它是一次**线上格式变更**，不是修 bug —— 现有两端 + 页面都按实现那套工作
2. 文档那套的额外强度（`suite_id` 绑定）在实现里**部分存在**：前缀 `flicker/1/` 就暗含了套件名
3. 真正的决策点只有一个：**要不要为了 `SID` 承诺和显式套件绑定，改一次协议**

**已做的处理**（在决定之前不能让文档误导人）：
- `PROTOCOL.md` §4.5 加了一段醒目的"与当前实现的差异"，明确告诉第三方实现者
  **按代码块那种构造**互通，并列出两处差异各自意味着什么
- 决策本身留在这里，不悄悄改任何一边

**建议**：发布前**先不动**（现状可用、自洽、有测试），把它作为 `FLICKER/2` 的候选内容 ——
那时可以连"换成真正的 PAKE"一起考虑（见 `SECURITY.md` §5.6），
反正都要动握手，一次动清楚比分两次动安全。

## 十、用户实测反馈的三件事（2026-10，均已处理）

用户拿去做了一次真实测试（局域网传文件），报了三条。**三条都是真的**，
而且第一条是最严重的一类 —— "点了没反应"。

### ① 「发送端的销毁没有用，点击没有反应」—— 两个 bug 叠在一起

**bug A：按钮只改文字，不销毁。**
`gui.js` 的 `destroyNow()` 用了 `if (!S.run && …)` 才设 `phase='destroyed'`。
而传输一旦启动 `S.run` 就存在 —— 于是**恰好在这个按钮最该起作用的时候什么都不做**。
就算条件成立，也只是把阶段文字改成"已销毁"，会话、服务、密钥、证书一个都没动。

修法：`onReady` 回调里本来就把 `session` 交给我们了，只是**从前被丢掉了**。
现在留住句柄，销毁时直接 `session.destroy()`；`runSend` 的 `waitForCompletion`
每 200ms 检查一次 `session.destroyed`，于是它会立刻走完整的销毁链并把清单交回来。

**bug B（更深）：`/api/start` 要等到传输结束才响应。**
`startTransfer()` 里 `await S.run`，而 HTTP 处理器是 `await startTransfer(...)` 之后才回响应 ——
一个请求就这么挂着，直到传输结束（大文件就是几分钟）。
页面靠轮询 `/api/state` 才看起来正常，所以一直没暴露。
这也是排查时最费时间的一点：**测试脚本卡在 `api('start')` 上 8 秒拿不到响应**，
一开始还以为是销毁没生效。

修法：把收尾逻辑放进 `S.run.then(...)`，`startTransfer` 立刻返回。

**判据**（`test/gui.test.js`）：走页面按钮调用的那个接口，断言
阶段真的变成 `destroyed`、提示是"已按你的要求销毁"、销毁清单里有清零/关服务/链接失效、
**并且那个链接真的连不上了**（这条才是"销毁"的实质判据），最后还能 reset 再传一次。

### ② 「接收端有不安全的提醒」—— 行为是对的，但**发送端一句话都没说**

证书只装在**发起方**这台机器上，接收方那台第一次打开必然看到"不安全"警告。
这是设计取舍（在对方电脑上装陌生根证书比点一次"继续前往"危险得多），**不是 bug**。

问题出在提示语：终端那句"对方首次打开会看到一次安全提示"挂在 `if (!trusted)` 下面，
而 `trusted` 说的是**本机装没装证书** —— 发送端装好了（trusted=true），
于是这句提示**不打印**，发送方以为一切正常，接收方对着红警告不知道点哪里。

修法：无条件打印，并给出确切的按钮文字（「高级 → 继续前往」）；
GUI 的等待屏提示同样补上；`使用手册.md` §10.3 原来写着"让对方打开链接时不出现红色警告"
（只在发起方本机上成立），改成一张"哪台电脑会看到什么"的表，并说明为什么刻意不做成"对方也不用点"。
新增 §8.4.1（看到不安全怎么办）与 §8.4.2（"是否允许修改文件"是什么意思）。

演练脚本里加了判据：发送端的输出**必须**包含"不安全"与"继续前往"两条 —— 少一条就算失败。

### ③ 「送过去不是一个 exe，是 flicker-0.1.0-source.fkz」—— 行为对，界面在骗人

用户当时跑的是源码版（`node bin/flicker.js --gui`），源码形态只能送源码包 `.fkz`，
对方需要先装 Node —— 这是**正确行为**。但界面上那行说明一直是
"对方收到后也能把文件发给别人，不用再去下载"，**两种形态共用一句话**：
在源码模式下这句话是假的（对方拿到 `.fkz` 根本双击不了）。

修法：`giftNoteForUser()` 按运行时事实（`detectSelf()`）给两种不同的说明，
单文件版说"送的是这个程序本身，双击即可运行"，源码版明说"要先装 Node.js 24+，
想要对方双击就能用请改用单文件版"。测试断言这句话必须如实。

> **这三条合起来说明一件事**：前面那一大堆测试和演练脚本覆盖的是**协议与数据面**，
> 而用户第一次真正用界面，撞到的是**界面状态机**和**提示语**。
> 两条 `/api/start` 与 `destroyNow` 的 bug 都是"看起来在工作"的那种 ——
> 页面靠轮询掩盖了请求被挂住，按钮靠存在感掩盖了它什么都没做。

### ④ 复查时自己发现的第四条：拒绝写入权限会被静默吞掉

用户问"原生保存对话框是什么意思"，我顺着去读那段代码，发现一个**没人报、但更危险**的问题：

```js
// 从前的写法
} catch (e) {
  if (e && e.name === 'AbortError') { return cancelled = true, finished(true); }
  dirHandle = null;    // 用户拒绝或环境不支持 → 退化到逐个文件询问
}
```

三种**完全不同**的失败被合并成了一句"退化"：

| 实际情况 | 从前 | 现在 |
|---|---|---|
| 用户点「取消」（AbortError） | 干净中止 ✓ | 不变 |
| 用户点「拒绝」（NotAllowedError） | **静默退到内存模式** | 见下 |
| 环境不支持 | 回退 ✓ | 不变 |

"拒绝"那条为什么危险：浏览器**本身支持**流式写盘，所以那句
"你的浏览器不支持边收边写盘"的警告**不会**触发；可权限没给，页面实际上会
**把全部内容收进内存再拼装**。小文件撑得住，几十 GB 会在**传到一半**时把浏览器撑爆 ——
而那时候用户已经等了很久，且完全不知道自己做错了什么（他只是点错了一个按钮）。

**修法**（分两种，都基于同一个阈值常量 `MEMORY_MODE_LIMIT`）：

- **小文件**（< 约 900 MB）：继续，但把 `#go-note` 换成警告样式，
  明确写出"你刚才没有允许写入文件，所以接下来会先收进内存再保存"
- **大文件**：**直接停下来**并报 `NO_WRITE_PERMISSION`，文案告诉用户
  "点重试，在文件夹窗口里选允许" —— **现在停下比传到一半崩掉划算**

**判据**：
- `test/receiver-page.test.js`：三种失败必须分开识别；大文件分支必须抛
  `NO_WRITE_PERMISSION`；小文件分支必须给警告；两条路共用同一个常量；
  错误码要登记进 `KNOWN`（否则界面退化成"未知错误"，看不到那句关键指引）；
  并且**不许标 fatal**（点一次"允许"就能成功，要给重试按钮）。
  已反向验过：把这段改回旧写法，用例立刻变红。
- `_lab/rehearsal-lan.mjs` 新增演练三（默认就跑）：在真浏览器里让文件夹窗口
  抛 `NotAllowedError`，断言页面**确实给出了警告**，而且**文件仍然传完且逐字节一致**。

> 顺带把 `test/protocol-facts.test.js` 里那条"大文件要警告"的判据改了：
> 它原来钉的是字面量 `900 * 1024 * 1024`，于是我把它抽成常量的那次改动**把测试弄红了**。
> 判据该盯行为（拿常量去比 + 常量值在合理区间），不该盯字面值 ——
> 否则"把魔法数字抽成常量"这种改进会被测试逼回去。

## 十一、最严重的一条：单文件产物**根本不单文件**（2026-10 用户实测发现）

### 症状

用户把 `dist/flicker-0.1.0-windows-x64.exe` 复制到桌面双击：

> "CMD 弹出来一下立刻消失"（管理员身份运行也一样）

在项目目录里跑同一个 exe 却**一切正常** —— 包括我自己的冒烟脚本、整套 415 个用例。

### 根因

**产物里只有 5 个模块，其余模块靠运行时去磁盘上找。**

```
打包前 5 个模块：assets.js · suite/flicker1.js · destroy.js · rate.js · bin/flicker.js
```

其余模块（`gui.js`、`run.js`、`server.js`、`prepare.js`、`trust.js`、`relay/*` …）
都是通过 **相对路径的动态 `import()`** 加载的，而打包器只跟**静态** import 走模块图 ——
那些 `import('../src/gui.js')` 被原样留在了产物里。

单文件产物运行时磁盘上没有 `src/`，于是它按 exe 所在目录去解析：

| 在哪运行 | `import('../src/gui.js')` 解析成 | 结果 |
|---|---|---|
| 源码目录（`dist/`） | `D:\闪传\src\gui.js` | **恰好存在** → 一切正常，测试全绿 |
| 桌面 | `C:\Users\…\src\gui.js` | `Cannot find module` → 控制台一闪而过 |

**一切验证都在源码树里做的**，所以这个问题可以无限期地藏着。

### 修法（一层套一层，每一层都被构建期自检逼出来）

| 层 | 问题 | 修法 |
|---|---|---|
| 1 | 5 处相对路径动态 import（`flicker.js`、`gui.js`） | 全改成**静态 import** |
| 2 | 打包器见到重名就拒绝：`OID_SERVER_AUTH` / `selfCheck` / `support` / `toPem` / `probe` **各有两份实现** | 各自收拢成一份：OID 常量进 `x509.js`；trust 那个"不合格就抛"的包装改名 `selfCheckOrThrow`（契约不同，本来就不该同名）；`session-cert.js` 里那个 `support()` 是死代码，删掉；`toPem` 只留 `x509.js` 一份；`session-cert-check.mjs` 里的私有 `probe` 改名 `tlsProbe` |
| 3 | `session-cert-check.mjs` 的 CLI 段有**顶层 await** | 包进 `runHandshakeSelfCheck()`（CommonJS 产物不允许） |
| 4 | `import * as D from './x509.js'` 拼接后 `D` 不存在 | 打包器生成命名空间对象 `const D = { toPem, SEQUENCE, … }` |
| 5 | 内置模块只硬编码了一小串兜底 require | **从源码推导绑定**：命名导入 → `{ a, b }`、默认导入 → `const path = …`、带 as → `{ 原名: 本地名 }` |
| 6 | 相对导入的 `as` 别名（`version as pkgVersion`）断链 | 补 `const pkgVersion = version`（入口也要，这条是测试抓出来的） |
| 7 | `createServer` 分别来自 `node:http` 与 `node:https` | 源码里改名区分（`createHttpServer`），打包器遇到同名不同源直接拒绝构建 |

最后产物从 **5 个模块 变成一个都不少（23 个模块、314 KB）**。

### 判据（三道，都验过能失败）

1. **打包器拒绝相对路径的动态 import**（`gen/bundler.mjs`）—— 见到就构建失败，
   并说明"运行时磁盘上没有源码"。已反向验证：造一个动态 import，构建立刻失败。
   还顺手处理了"注释里提到动态 import 被自己文档误伤"这个坑。
2. **冒烟必须在源码树之外跑**（`gen/smoke-sea.mjs`）—— 从前所有检查都在 `dist/` 里直接跑，
   而 `dist/` 就在源码树里。现在**每个产物先复制到临时目录**，再验
   `--version` / `--help` / `send --dry-run` / `--assets` /
   **图形界面能不能起来（12 秒未退出）**。最后一条正是用户双击那条路的判据。
3. **打包器测试**新增 6 条（`test/bundler.test.js`）：动态 import 必须失败、
   注释不该误判、`as` 别名要补绑定、命名空间要生成对象、同名不同内置模块要失败、
   内置绑定要真的生成。其中一条"允许并跳过 node: 内置模块"里写着
   *"内置模块是全局可用的"* —— **那个信念本身就是这个 bug 的一半**，已改写成新契约。

> **教训**：这次不是"某个分支没测到"，而是**整个验证环境都在源码树里**。
> 凡是"产物/部署形态"的东西，验证必须在**它真正被使用的那种环境**里做 ——
> 对单文件产物来说，就是"复制到别的目录再跑"。这一条现在写进了冒烟脚本。

**修完的结果（用户实测确认）**：把 `dist\flicker-0.1.0-windows-x64.exe` 复制到桌面双击，
图形界面正常起来 —— 用户原话"现在好了"。加上之前确认的"原生保存对话框正常"，
发布判据②里那两截只有人能验的部分也就闭合了。

## 十二、文档分两套（中文 / 英文）+ 赠品带源码与文档（2026-10，用户提出）

用户的原话：

> "发送闪传应该一起发送 EXE 和源码还有文档。中文的 README 改名读我，英文的 README
> 把后面的 EN 删掉，两个 README 放在根目录，文档分成两个文件夹一个中文文档一个英文文档，
> 用各自的语言写文件夹的名字。文档做两份一份中文一份英文。"

### 结构（现在是这个样子）

```
读我.md            中文 README（根目录）
README.md          英文 README（根目录，原来的 README.en.md）
中文文档/           10 份中文文档：使用手册 · 行为与运行 · 设计文档 · 架构决策 ·
                   PROTOCOL · 中继部署 · 路线图 · 构建单文件 · UI设计 · SECURITY
docs/              同样 10 份，**文件名一一对应**，内容为英文
```

`SECURITY.md` 放进 `docs/` 仍然有效：GitHub 的"安全策略"会找根目录、`.github/`
和 **`docs/`** 三处 —— 所以安全策略页照旧能用。

### 为什么要有"配对检查"（`gen/check-doc-pairs.mjs`）

两份文档天生会漂移：**没有任何一个人会同时读两份** —— 中文读者看中文、英文读者看英文，
中文改了一句、英文忘了跟，谁都不会发现。这跟本项目反复吃亏的"两份实现"是同一类问题，
所以用同样的办法：把它变成机器判据。检查两件事：

1. **文件名一一对应**（缺哪一边就报哪一边）
2. **结构一致**：`#`/`##`/`###` 标题数、代码围栏数、表格行数 —— 译文可以改措辞，
   但不该删章节、丢代码块、漏表格行

> ⚠️ **刻意不比较正文行数**：译文长短本来就会差，卡行数只会逼人凑字数。
> 结构一致 + 链接有效（`check-doc-links.mjs`），才是"两份内容对得上"的合理近似。
> 实测：10 对文档的结构**全部一致**（翻译时逐份核对的结果，不是碰巧）。

这条检查进了 `npm run check`、CI，以及 `test/docs-pairing.test.js`
（`npm test` 也会拦 —— "加了一份中文文档忘了英文"恰恰是开发中最容易发生的事）。

### 赠品：EXE + 源码 + 文档（`src/gift.js`）

从前只送**一个**：单文件形态送 exe、源码形态送 `.fkz` 源码包。现在单文件形态送**两个**：

```
🎁 附带赠送程序：flicker-0.1.0-windows-x64.exe (94 MB)
🎁 附带赠送源码与文档：flicker-0.1.0-source.fkz (1.1 MB)
```

**关键实现点**：单文件产物运行时磁盘上**没有 src/ 也没有文档**，现场打不出源码包。
所以构建时（`gen/build-sea.mjs`）就把源码 + 中英文文档打成 `source-pack.fkz`
**嵌进产物**（36 个文件、20 份文档、约 1.1 MB，产物因此从 89.9 MB 长到 91.0 MB）。
运行时从内嵌资产里取出来送给对方 —— 于是**产物复制到哪儿都完整**，不依赖源码树。
这与第十一章那条教训是同一条。

- 打包逻辑只有一份（`buildSourcePack()`），构建期与源码形态共用，避免两边打出不同的包
- 文档一份都没打进包 → **明确报错**，而不是悄悄送出一个"没有文档的源码包"
- 老产物里没有这份资产 → 只送程序本身，并**明确告诉用户**这次没有源码包
  （静默少送一样东西，比报错更糟）
- 源码形态仍然只能送源码包（自己就是靠磁盘上的源码跑起来的，变不出 exe）——
  界面上那句话按运行时事实分两种写法，不共用（见 `gui.js` 的 `giftNoteForUser()`）
