## 一、站点模型：从"发送端/接收端"到"对等站点"

### 1.1 原始需求里的隐含假设

最初的需求写的是"发起传输的电脑有这个程序"，也就是 **发送端装机、接收端裸奔**。
这在"我传给别人"时成立，但一旦出现下面任一情况就崩塌：

- 对方收完了，也想给我发一个文件 → 他没有程序
- 两台电脑都是我的，我想双向同步 → 得决定哪台装
- 手机上想发文件给电脑 → 手机装不了 Node

### 1.2 决策：一个可执行文件，两种角色，运行时决定

```
                     ┌─────────────────────────┐
                     │      闪传 Station        │
                     │                         │
     命令行 / GUI ──▶│  ┌───────┐  ┌────────┐  │
                     │  │ 发送方 │  │ 接收方 │  │
                     │  └───┬───┘  └───┬────┘  │
                     │      └────┬─────┘       │
                     │      ┌────▼─────┐       │
                     │      │  会话内核 │       │  ← 密码学 / 分块 / 清单 / 销毁
                     │      └────┬─────┘       │     全部与角色无关
                     │      ┌────▼─────┐       │
                     │      │  通道层   │       │  ← 局域网 / relay / 直连
                     │      └──────────┘       │
                     └─────────────────────────┘
```

**关键性质：会话内核与角色完全无关。** 谁是发起方只是一个标志位，握手、加密、分块、销毁的代码
两边共用同一份。这不是为了省代码，而是因为**密码学协议本来就是对称的**（挑战—应答天然双向）。

由此得到三种用法，**一份程序全覆盖**：

| 用法 | 怎么做 | 谁需要装程序 |
|---|---|---|
| 我 → 别人 | 我运行 `send`，对方开浏览器 | 只有我 |
| 别人 → 我 | **对方也装了程序**，他 `send`，我等着接 | 双方（但可以靠"自赠程序"变成这样） |
| 我 ⇄ 我 | 两台机器都跑 `flicker`，谁先发起都行 | 双方 |
| 手机 → 电脑 | 手机浏览器上传（受限，见 §5.4），或用 P4 的移动外壳 | 电脑 |

> ✅ **2026-10 两半都实现了，走的是同一条实现**：
> · **命令行（`flicker recv <链接>`）由程序自己接收**：Node 下载、逐块校验、整文件哈希、
>   按 `src/path-safety.js` 的规则落盘，收完再通知对方销毁。
>   从前它只是 `openBrowser(link)`，把链接丢给浏览器 —— 于是"双方都装了程序"没有任何区别。
> · **图形界面（站点页「或者，从对方的链接接收」）也已就位**：贴链接 + 一次性密码 →
>   点「连上去看证书指纹」→ 核对那 8 位 → 开始。界面**不做**跨源请求：它只对
>   `127.0.0.1` 上的本机服务发 `/api/pull/*`，取文件仍然由**同一个** `src/pull.js` 在 Node 里做。
>   于是 §1.3 里那两条阻塞（CORS、自签证书）根本不用碰协议就能绕开。判据：
>   `test/pull-gui.test.js`（真发送端 + 真界面，含"没核对就不许开始"与"停止是真中断"的反向验证）。
>
> 另外，这条路**只吃直连链接**（`https://<地址>:<端口>/?k=…`）。中继链接
> （`/room/<房间>#<盐>`）的接收端在页面里，程序这边没有实现 —— 那条路请用浏览器打开。

### 1.3 界面上的体现：站点页

图形界面不是"发送界面"，而是**站点页（Station）**，一进来就能看到两组动作：

> ✅ **2026-10 补齐**：下面这张早期草图里的"输入密码 → 开始接收"就是今天的
> 「**或者，从对方的链接接收**」一块（贴链接 + 密码 → 核对证书指纹 → 开始）。
> 今天的接收入口有两种，别混：**别人发给我（手机扫码）** 与 **从对方的链接接收（对方也装了程序）**。
>
> 为什么不能"页面直接 fetch 对方的接口"（两条真实阻塞，都没变）：
>
> 1. **跨源**：站点页在 `http://127.0.0.1:<端口>`，对方的接口在 `https://192.168.x.x:<端口>`，
>    而 `src/server.js` **一个 CORS 响应头都不发** —— 浏览器的 `fetch` 直接就被拦下。
> 2. **证书**：对方用的是**自签证书**，CA 只装在**他**那台机器上。你这台机器的浏览器
>    没有把它放进信任库，`fetch` 会以证书错误失败；而"XHR 里点继续前往"这种事浏览器不给。
>
> 解决办法是**换执行者，而不是改协议**：页面只跟本机 `127.0.0.1` 服务说话（`/api/pull/probe|start|stop|open`），
> 真正取文件的是 Node 里的 `src/pull.js` —— 与 `flicker recv <链接>` 是**同一份**实现（单一来源）。
> 证书那一关从"改信任库"变成"**人核对 8 位指纹**"：界面把探测到的指纹显示出来，
> 用户点「指纹一致」或自己把对方屏幕上的指纹打进来；「不核对，直接开始」等价 `--insecure`，日志里会留一行。
> 判据 `test/pull-gui.test.js`（9 条，含反向验证）。

```
┌──────────────────────────────────────────────┐
│  闪传 Flicker                    ● 空闲中     │
├──────────────────────────────────────────────┤
│                                              │
│   ┌── 我要发文件 ────────────────────────┐   │
│   │  把文件拖到这里，或 [ 选择文件 ]     │   │
│   └──────────────────────────────────────┘   │
│                                              │
│   或者，让别人发给我                         │
│   ┌── 手机 → 这台电脑 ──────────────────┐   │
│   │  手机扫码，把照片/视频推过来         │   │
│   │  [ 接收文件 ]                        │   │
│   └──────────────────────────────────────┘   │
│                                              │
│   或者，从对方的链接接收                     │
│   ┌── 对方也装了闪传 ────────────────────┐   │
│   │  贴对方的链接 + 一次性密码           │   │
│   │  [ 从链接接收 ]                      │   │
│   └──────────────────────────────────────┘   │
│                                              │
└──────────────────────────────────────────────┘
```

**为什么接收区要常驻在第一屏**：因为我作为"装机方"，随时可能有人要发东西给我。
接收不是发送流程的附属品，它是一等公民。

## 二、图形界面：决策与理由

### 2.1 三个候选方案

| 方案 | 做法 | 优点 | 致命缺点 |
|---|---|---|---|
| **A. 原生窗口（Electron/Tauri）** | 打包 Chromium / 用 Rust 外壳 | 真·桌面应用 | 体积 80–150 MB；引入大量第三方依赖；与"零依赖"原则冲突；跨平台打包维护成本高 |
| **B. WebView2 外壳** | 用 `msedgewebview2.exe --app=` 拉窗口 | 小、免安装运行时（Win10+ 自带） | **仅 Windows**；macOS/Linux 无对应物；依赖系统运行时版本 |
| **C. 本地 Web 界面 + 浏览器** | Node 起一个只监听 `127.0.0.1` 的服务，用浏览器打开 | 跨平台一致；同一套 UI 同时服务接收端和发送端；可以"安装为应用"；零新依赖 | 不是"原生"应用；需要选对浏览器 |

### 2.2 决策：以 **C** 为主，**B** 作为 Windows 上的可选增强

**理由：**

1. **接收端本来就是网页。** 如果发送端也用网页，那么**整个产品只有一套 UI 代码** ——
   发送界面和接收界面可以共享全部设计令牌、组件、进度显示逻辑。这是巨大的简化。
2. **发送端界面天然可以访问本地文件。** 因为它跑在 `127.0.0.1`，浏览器允许它使用
   `showSaveFilePicker()` / `showOpenFilePicker()`，也就是说**发送方自己接收别人的文件时，
   同样能享受流式写盘**，不受内存限制。（这一点很重要：站点模型下发送方也是接收方。）
3. **可以"安装"成桌面应用而不需要安装程序。** Edge/Chrome 支持「安装此站点为应用」，
   生成开始菜单图标、独立窗口、无地址栏。用户感知上就是一个桌面软件，
   而我们的代码一行都没多写。
4. **Windows 上的增强**：检测到 WebView2 时，可用 `msedgewebview2.exe --app=<url>` 直接弹一个无边框窗口，
   完全不像浏览器。这是可选路径，不是必需路径。

### 2.3 一个必须处理的现实问题：**默认浏览器可能是 Firefox**

实测本机环境：

```
默认浏览器      Firefox（注册表 UserChoice = FirefoxURL-...）
已装 Edge       155.0.4283.45   ← Program Files (x86)
WebView2 运行时 154.0.4258.62   ← 已安装
```

而 **Firefox 不支持 File System Access API**（`showSaveFilePicker`），也没有 `--app` 模式。
这意味着：

- 如果无脑用系统默认浏览器打开 GUI，用户会掉进"大文件传不了"的坑，而且**不告诉他就不会知道**
- 如果强制要求 Edge/Chrome，Mac 用户（Safari 也不支持）会很难受

**决策：浏览器探测 + 显式降级 + 诚实告知。**

```
启动 GUI 时的探测顺序：
  1. 查找 Edge / Chrome / Brave 等 Chromium 系浏览器（注册表 + 常见安装路径）
  2. 找到 → 用它打开，并附带 --app=<url> 得到独立窗口
  3. 没找到 → 用系统默认浏览器打开，同时在页面上显示醒目提示：
        ⚠️ 当前浏览器不支持大文件流式写盘
           接收超过约 1 GB 的文件可能失败
           建议改用 Edge 或 Chrome
  4. 页面内始终显示当前浏览器能力检测结果（不猜，实测 API 是否存在）
```

**原则：能力检测永远优先于 UA 判断。** 直接 `typeof window.showSaveFilePicker === 'function'`，
比猜浏览器名字可靠得多。

### 2.4 GUI 与命令行的关系

**不是两套程序，是同一个内核的两个前端。**

```
                     ┌──────────────┐
        --gui  ─────▶│  GUI 前端     │──┐
                     │  (浏览器页面) │  │
                     └──────────────┘  │      ┌──────────────┐
                                       ├─────▶│   会话内核    │
                     ┌──────────────┐  │      │ + 事件总线    │
        默认   ─────▶│  TTY 前端     │──┘      └──────────────┘
                     │  (终端渲染)   │
                     └──────────────┘
```

- 内核通过一条**事件流**（进度、状态、错误、对方连接、密码核对结果）对外播报
- TTY 前端把事件渲染成框线和进度条；GUI 前端把同样的事件渲染成网页
- 两个前端**可以在同一个进程里同时存在**：既在终端刷进度，又开着网页窗口

这条设计让 GUI 不需要重新实现任何业务逻辑，也让 CLI 在无图形界面的服务器上照常可用。

## 三、自赠程序：让程序自己流传出去

### 3.1 需求

> "程序能够从传输文件的那一端被传输到被传输的那一端，这样可以让其他人也使用这个程序，这个不是强制的。"

这是原始需求里**最有远见的一条**：它解决的其实不是技术问题，而是**传播问题**。
一次性传输工具的使用场景天生是"点对点"的，如果每次都要教对方去 GitHub 下载，
这个工具就永远只在会用的人之间流动。

### 3.2 决策：作为一次可选的额外清单项

在界面上表现为一个默认开启的复选框：

```
┌─ 传输选项 ──────────────────────────────┐
│  ☑ 顺便把「闪传」也送给对方              │
│     对方收到后也能把文件发给别人          │
│     约 18 MB（不影响本次传输的内容）      │
└─────────────────────────────────────────┘
```

在协议里，它就是**清单里的一个普通文件条目**（见 `PROTOCOL.md` 的自赠章节），
带一个特殊标记，接收端识别后展示一个额外的说明卡片。

**为什么默认开启**：18 MB 相对于现代传输量微不足道，而它把接收方从"只能收"变成"也能发"。
但**必须可以关掉** —— 企业内部环境可能有规定，或者对方就是不想要。

### 3.3 关键设计：送什么，取决于程序自己是什么形态

程序必须能分辨"我是怎么被分发的"：

| 我是哪种形态 | 我该送什么 | 对方怎么用 |
|---|---|---|
| **单文件可执行程序**（`flicker.exe`） | 直接把**自己**送过去 | 双击就能跑，什么都不用装 ⭐ 最优 |
| **从源码目录运行**（`node flicker.js`） | 打包**运行所需的源码 + `启动.cmd`** | 需要先装 Node.js，启动脚本会检测并引导 |
| **全局安装**（`npm i -g`） | 同上的源码包 | 同上 |

实现上就是：探测 `process.execPath` 与 `process.argv[1]` 的关系，
判断自己是被 SEA 打包的单文件还是普通脚本，决定赠品形态。

### 3.4 单文件可执行程序 —— 这是自赠功能的真正价值所在

Node.js 24 内置 **SEA（Single Executable Applications）**，可以把 Node 运行时和代码
打成**一个可执行文件**，不需要对方装 Node。

```
构建产物（GitHub Release 附带）：
  flicker-windows-x64.exe     约 80 MB
  flicker-macos-arm64          约 75 MB
  flicker-macos-x64            约 78 MB
  flicker-linux-x64            约 80 MB
```

**结论：P3 阶段必须把 SEA 打包做出来。** —— ✅ **已实现**，见 `构建单文件.md`。
实测产物 `flicker-0.1.0-windows-x64.exe` 约 94 MB，
自赠程序会识别出自己是单文件形态并**赠送程序自身**（而不是源码包）。 否则"自赠程序"这个功能是半成品 ——
送过去的源码包对方还得去 Node 官网下载安装，绝大多数非技术用户在这一步就放弃了。

这也顺带解决了"发送端必须装 Node"的限制：用单文件版，发送端也零安装。

### 3.5 链式传播：设计上的一个自然结果

```
我 ──送文件+程序──▶ 同事 ──送文件+程序──▶ 他的朋友 ──▶ ...
```

程序每被送出去一次，接收方就多一个完整的站点。
**这是这个项目唯一的推广机制**，也是它和网盘类工具体验上最大的区别：
网盘是中心化的，越用越依赖那个中心；闪传是**越用越不需要闪传本身**（因为大家都装了）。

> 附带的好处：自赠的包里应该带上一个精简版的 `使用手册.md` 和本仓库地址。
> 对方拿到程序后，第一眼就知道这东西怎么用、从哪来的。这也是开源项目的自然曝光路径。

## 四、HTTPS 与证书信任：一个必须解决的体验问题

### 4.1 为什么绕不开 HTTPS

接收端的网页要用 `crypto.subtle`（WebCrypto）。而浏览器规定：
**`crypto.subtle` 只在安全上下文（secure context）中可用。**

- `http://127.0.0.1` ✅ 被当作安全上下文
- `http://192.168.1.5` ❌ **不是**安全上下文 → `crypto.subtle` 为 `undefined` → 加密功能直接不可用
- `https://192.168.1.5` ✅ 安全上下文

而局域网模式恰恰是**主力场景**，接收端必须访问 `https://192.168.1.5:端口`。
**所以我们无论如何都要有一个 HTTPS 服务，而且它的证书必须被浏览器信任。**

### 4.2 三条路的对比

| 做法 | 用户体验 | 评价 |
|---|---|---|
| 自签证书，不管信任 | 每个浏览器都弹"您的连接不是私密连接" | ❌ 对方会以为中毒了，产品直接死掉 |
| 引导用户手动点"继续访问" | 要教对方点"高级 → 继续前往" | ⚠️ 可行但很糟，且部分浏览器不给"继续"按钮 |
| **把证书装进当前用户的信任库** | **完全没有提示，和正常网站一样** | ✅ **已实测成立**（见 §4.3） |

### 4.3 决策：会话级证书 + 自动安装 + 自动卸载（**已实测验证**）

> **本节结论来自本机实测，不是推断。** 测试方法：用 CDP（Chrome DevTools Protocol）
> 直接读取浏览器对证书链的验证结论，而不是靠肉眼看页面。
> 测试脚本：`_lab/lab-cert.mjs`（可重复运行）。

#### 4.3.1 实测结果

| 变体 | CA 带 `CA=TRUE` 标志 | 装入 Root 库 | 浏览器结果 |
|---|---|---|---|
| 变体 1 | ❌ 无（`Subject Type=End Entity`） | ✅ 已装 | ❌ `net::ERR_CERT_INVALID` |
| 变体 2 | ❌ 无 | ✅ 已装 | ❌ `net::ERR_CERT_INVALID` |
| **实验组 A** | ✅ **有**（`Subject Type=CA`） | ✅ 已装 | ✅ **页面正常渲染、fetch 200、CDP 见到 SSL 详情、零失败事件** |
| 对照组 B | ✅ 有 | ❌ 未装 | ❌ `net::ERR_CERT_AUTHORITY_INVALID` |
| 对照组 C | ✅ 有 | ✅ 已装 | ✅ 正常（`--ignore-certificate-errors`，证明服务端本身无问题） |

环境：Windows 10 19044 · Edge 155.0.4283.45 · Node v24.21.0 · 非管理员身份

**四条结论：**

1. **✅ 方案成立。** 会话 CA（带 `CA=TRUE`）+ 服务器证书，只把 CA 装进
   `Cert:\CurrentUser\Root`，浏览器**完全接受，零警告**。headless 模式**确实读取 Windows 信任库**。
2. **⚠️ 真正的地雷是证书生成，不是信任库。** 两次失败的唯一原因是我最初用
   `New-SelfSignedCertificate -TextExtension '2.5.29.19={text}critical:ca2'`
   生成的 CA **缺少 CA 基本约束**（`Subject Type` 显示 `End Entity`），
   导致整条链无效，浏览器报 `ERR_CERT_INVALID`（"证书本身是坏的"）。
   正确写法是 `'{critical}{text}ca=1'` —— 注意 `ca2` 是错的，`ca=1` 才对。
3. **对照组 B 是决定性证据。** 同一个证书，不装 Root 库时报的是
   `ERR_CERT_AUTHORITY_INVALID`（"签发者不受信任"），而不是 `ERR_CERT_INVALID`。
   **错误码从"证书坏了"变成"签发者不认识"，本身就证明了装信任库确实生效。**
   没有这个对照，很容易把"证书生成错了"误判成"信任库不生效"。
4. **卸载只能靠 `certutil -delstore`。** `Remove-Item Cert:\CurrentUser\Root\<指纹>`
   会失败并报 `The operation is on user root store and UI is not allowed.`
   —— 这不是习惯问题，是别的办法根本不工作。

#### 4.3.2 由此确定的三条实现约束

**约束 1：证书生成必须显式且正确地设置基本约束。**
从这条实测推出一个重要的实现决策 —— **不自己手搓 X.509，也不裸调 `New-SelfSignedCertificate`**，
而是把证书生成集中到一个可测试的模块，并**在生成后立即自检**：

```
生成证书后，在启动服务之前必须校验：
  ✓ CA 的 basicConstraints 必须含 CA=TRUE，且 critical
  ✓ CA 必须含 keyUsage = keyCertSign
  ✓ 服务器证书必须有 SAN，且 SAN 里必须包含接收端将要访问的那个 IP
  ✓ 服务器证书必须有 EKU serverAuth
  ✓ 用 Node 的 X509Certificate.verify() 验证链是否成立
  ✓ 服务器证书不能同时被当作 CA 使用
自检失败 → 明确报错并降级到"手动信任引导"，绝不让用户面对一个看不懂的浏览器错误
```

这条自检能挡住的正是本次踩到的坑 —— 而且成本极低。

**约束 2：必须扫描并清理上次残留的证书。**
因为卸载只能靠 `certutil`，一旦装入后被强杀（任务管理器结束进程、断电、蓝屏），
证书就会永久残留。所以**每次启动时先扫描 Root 库里 subject 含 `Flicker Session` 的证书，
发现残留就清理掉**。这让"一次性"在异常路径下也能自愈。

**约束 3：启动顺序必须是"先装证书，再监听端口"。**
否则浏览器可能在证书就绪前就发起了连接，收到一个不受信任的响应并缓存了验证结果
（Chrome 已知会缓存证书错误），之后再装证书也不生效 —— 用户会看到一次莫名其妙的警告。

**约束 3b：就绪探测通过后才允许打开浏览器窗口。**（**实测复现的真实缺陷**）
`--app=<url>` 模式的浏览器窗口**一启动就会导航**那个地址。
如果此时 HTTPS 还没监听，用户会看到一个 **"嗯… 无法访问此页面"（`ERR_CONNECTION_REFUSED`）**，
而且它会**一直停在那里、不会自己重试**，必须手动按 F5。
实测因果链：浏览器先开 + 服务后起 → 错误页；按 F5 → 正常；服务就绪后再开 → 正常。
**所以绝不能存在"窗口已存在但服务还没准备好"的窗口期。**
复现脚本：`_lab/lab-race.mjs`。

#### 4.3.3 关键参数

```
启动时：
  1. 生成会话专用根 CA（CA=TRUE, keyCertSign）+ 服务器证书
     —— 服务器证书的 SAN 必须包含接收端实际访问的 IP，一张证书覆盖本机全部局域网地址
  2. 自检证书链（见约束 1），失败则降级
  3. 扫描并清理上次残留（见约束 2）
  4. certutil -user -addstore -f Root <ca.cer>   ← 不需要管理员权限（已实测）
  5. 启动 HTTPS 监听
  6. 【就绪探测】主动请求一次自己的地址，直到真的返回 200（见约束 3b）
  7. 打开浏览器窗口（仅 GUI 模式）              ← 必须在第 6 步之后
  8. 终端打印 CA 指纹，供高级用户手工核验

销毁时：
  9. certutil -user -delstore Root <指纹>        ← 唯一可行的卸载方式
 10. 从 Cert:\CurrentUser\My 删除服务器证书私钥
 11. 删除内存中的私钥材料
```

**为什么这件事对这个项目格外重要：** 它把"用完即销毁"从**文件层面**延伸到了**系统信任层面**。
程序退出后，它在你电脑上留下的所有痕迹（密钥、证书、信任项、服务、临时文件）全部消失。

**必须提供 `--no-cert-install` 开关**：会有用户不接受任何程序动自己的证书库。
此时降级为"自签证书 + 页面引导手动信任"，并把差异讲清楚。
**这个开关也顺便成了保底方案** —— 即使证书方案在某个用户的机器上因为策略限制而失败，
程序仍然可用，只是多一次点击。

> **仍未验证的事**（诚实标注）：
> ① ~~真实交互式浏览器窗口~~ —— ✅ **已验证通过**。补测了两种真实窗口形态：
>    **可见窗口**（127.0.0.1）和 **app 无地址栏窗口**（127.0.0.1 与真实局域网 IP `192.168.1.5` 各一次），
>    全部零警告通过。同时用一组"应当失败"的对照（app 模式 + 不装 CA）确认测试脚本
>    **能正确识别安全警告页**，排除检测器过宽导致的假阳性。
>    至此 Windows + Edge 的所有模式（headless / 可见窗口 / app 窗口）与两种地址形态均已验证。
> ② **macOS / Linux 未验证。** 这一条的结论在 2026-10 变得更明确了：
>    证书**生成**已经改成纯 JS（`src/x509.js` + `src/session-cert.js`），
>    全平台同一份代码，且用真实 TLS 握手验证 —— 也就是说**"生成"不再是平台短板**。
>    剩下的是"装进系统信任库"，而两个平台各有硬原因，不是工程量问题：
>    · **macOS**：`security add-trusted-cert` 系统自带、无需第三方工具，但 `man security` 写得很清楚 ——
>      *"When modifying per-user Trust Settings, user authentication is required via an
>      authentication dialog"*，改 admin 域则必须 root。**没有静默生效的选项**，
>      这与"启动即用"的定位冲突。
>    · **Linux**：**不存在零依赖路径**。浏览器不读系统 CA 目录 —— Chromium 读 NSS Shared DB
>      （M146 起 `~/.local/share/pki/nssdb`，之前 `~/.pki/nssdb`），写入需要 `certutil`
>      （来自 `libnss3-tools` / `nss-tools`，**默认不装**），Firefox 另有自己的 profile 库。
>      依据：[Chromium 官方 `docs/linux/cert_management.md`](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/docs/linux/cert_management.md)。
>    · 因此程序改为**打印手动安装的确切命令**（`trust.manualTrustHint()`）而不代跑，
>      两个平台继续默认 `--no-cert-install`。**跨平台证书信任必须逐平台实测，
>      不能沿用 Windows 的结论。**

## 五、打包与分发

### 5.1 三种分发形态

| 形态 | 目标用户 | 体积 | 依赖 |
|---|---|---|---|
| **单文件 exe / 可执行程序** | ⭐ 所有人（推荐） | 75–80 MB | **无** |
| **源码 + 启动脚本** | 开发者、想看代码的人 | 约 200 KB | Node.js 24+ |
| **npm 全局安装** | 开发者 | 约 200 KB | Node.js 24+ |

### 5.2 启动脚本（源码形态下的体验补救）

```
启动.cmd          ← 双击这个（Windows）
启动.command      ← 双击这个（macOS）
启动.sh           ← ./启动.sh（Linux）
```

脚本做三件事：
1. 检测 `node` 是否存在、版本是否 ≥ 24
2. 不存在 → 打印清晰的中文指引（含官网地址）+ 自动打开下载页，然后退出
3. 存在 → 启动图形界面

**为什么必须有这个脚本**：源码形态下如果让对方"打开命令行，cd 到目录，输入 node flicker.js"，
95% 的人会卡住。双击一个文件是人类的基本预期。

### 5.3 版本与命名

```
flicker-0.1.0-windows-x64.exe
flicker-0.1.0-macos-arm64
flicker-0.1.0-macos-x64
flicker-0.1.0-linux-x64
```

自赠程序时，文件名里带上版本号，接收方一眼能看出新旧 —— 这决定了链式传播时大家会不会用上最新版。

### 5.4 手机端的边界（诚实说明）

| 方向 | 可行性 | 说明 |
|---|---|---|
| 电脑 → 手机 | ✅ **完全可行** | 手机浏览器打开链接、输密码、接收；用 Web Share API 存进相册/文件 App。**这就是你要的"电脑文件传输到手机"** |
| 手机 → 电脑 | ⚠️ **受限** | 浏览器**无法读取任意路径的文件**（平台限制）。只能让用户在文件选择器里手动选，不能"选个文件夹自动发送" |
| 手机 → 手机 | ⚠️ **受限** | 同上，且手机不能当 HTTPS 服务端 |
| 手机装闪传本体 | ❌ 不做 | 要装 App 就违背了"接收端零安装"的核心前提 |

**结论：手机端的正确定位是"优秀的接收端 + 受限的发送端"。**
"电脑 → 手机"这条主路径可以做得和桌面一样好，这就是需求的满足点。
手机上要当发送端，属于 P4（移动外壳包装），不是当前范围。

## 七、更新后的实现阶段

| 阶段 | 内容 | 新增/变化 |
|---|---|---|
| **P0** | 密码学与分块内核 + 局域网 HTTPS 传输 + 销毁流程 | 不变 |
| **P1** | 接收端双写盘路径 + 断点续传 + 完整性校验 | 不变 |
| **P2** | **GUI 前端**（站点页）+ 浏览器探测 + 证书信任 | ⬅ 新增，提前到 P2 |
| **P3** | relay Worker + 跨网络 | 后移 |
| **P4** | 自赠程序 + SEA 单文件打包 + 启动脚本 | ⬅ 新增 |
| **P5** | 公网 IPv6 / 端口转发探测、PWA、Web Share API、i18n | 扩展 |

**调整理由**：GUI 是"这个程序能不能被别人用起来"的门槛，比跨网络更影响实际使用。
在你自己的机器上，局域网已经够用；但 GUI 决定了你**愿不愿意把它推荐给别人**。
自赠程序则决定了它**能不能自己传播**。两者都比 relay 优先级高。
