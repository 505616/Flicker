## 〇、先给项目起个名字

开源项目的名字是要用很久的东西，建议现在就定。

| 候选 | 含义 | 评价 |
|---|---|---|
| **Flicker / 闪传** | 火光一闪即逝 —— 正是"用完即销毁" | ⭐ **推荐**。短、好读、好搜、npm 上可用，英文名和中文名都贴题 |
| Meteor / 流星 | 转瞬即逝 | 备选，但 npm 上已被占用很多 |

| OneShot | 一次性的 | 太通用，SEO 会被淹没 |

**建议**：仓库名 `flicker-transfer`，npm 包名 `flicker-transfer`，短命令 `flicker`，中文名"闪传"。
（`ui-prototype.html` 里已经用了这个名字，你可以直接看效果决定。）

## 一、UI 的核心矛盾

这个项目有两个界面，但**它们的重要性完全不对等**：

| | 发送端 | 接收端 |
|---|---|---|
| 用户 | **你**（装了程序，会用命令行） | **对方**（什么都没装，可能不懂技术） |
| 形态 | 命令行终端 | 浏览器单页 |
| 出现频率 | 每次传输都在看 | 一辈子可能只看这一次 |
| 设计目标 | **信息密度 + 可控感** | **零学习成本 + 建立信任** |

**结论：接收端才是产品的脸。** 发送端做得好是"顺手"，接收端做得好才是"敢让别人用"。
所以下面的设计里，接收端占的比重大于发送端，这是刻意的。

还有一条贯穿全局的约束：**接收端必须是单文件、零外部依赖、零 CDN**。
不能引任何字体、图标库、CSS 框架 —— 因为：
1. 局域网模式下接收端可能**完全没有外网**，任何 CDN 依赖都会直接导致白屏
2. 这是安全工具，从第三方加载 JS 是自毁信任

→ 所以 UI 只能靠**手写 CSS + 少量内联 SVG + Unicode 符号**来实现。

## 二、接收端设计（浏览器）

### 2.1 状态机：六屏，一屏一动作

```
  ① 密码输入 ──> ② 连接中 ──> ③ 传输中 ──> ④ 完成
       │                          │            │
       └──────── ⑤ 出错 <────────┘            └──> ⑥ 取消/销毁
```

设计铁律：**任何一屏都只有一个主按钮。** 对方可能很紧张（"我是不是点错了""会不会中毒"），
选择题越少越好。

### 2.2 每屏的设计要点

**① 密码输入**
- 第一眼就要回答三个问题：**谁发给我的**、**有多大**、**我要做什么**
- ⚠️ **文件清单在输入密码之前是拿不到的，这里已按实现更正（2026-10）。**
  本节原先写的是"文件清单必须在输入密码**之前**就显示（不含内容，只有名字和大小）"。
  但**整个清单（含文件数量与总大小）都是加密的**，密钥由密码派生 ——
  服务端在认证之前根本没有可以拿给页面看的东西。
- 所以这一屏改为**明说"看不到"**，而不是含糊过去：`文件清单已加密` +
  `输入正确密码后才能看到`。用户会疑惑"为什么什么都没有"，主动回答掉它。
- 为什么不把数量/总大小做成明文（让这一屏更好看）：那样**拿到链接的任何人都能知道
  "这是几个文件、多大"**。而链接是会被转发的。`使用手册.md` §10.4 对用户的承诺是
  "连文件名和文件数量都看不到"，这条承诺比"提前看到一个数字"更值钱。
  详见 `PROTOCOL.md` §4.5。
- 密码框：`type=password` + 眼睛切换；等宽字体 + 字间距（密码里有连字符和空格，等宽字体更容易核对）
- 页面底部一行小字：**"密码不会离开你的电脑 —— 它只用来核对双方是否一致"**
  - 这行字很关键，用户在输密码时一定会有"这个密码会被发到哪去"的疑虑，主动回答掉
- 强度条：`4 段`，用颜色告诉你生成的默认密码是好密码

**② 连接中**（合并进 ③ 的初始态，不单独占一屏，避免闪烁）

**③ 传输中**
- 三层进度是刻意的设计：**总进度条 → 当前文件 → 实时速度**
  - 只有总进度条：传大文件时进度条几乎不动，用户会以为卡死
  - 加上当前文件 + 速度 + 剩余时间：**"在动"的感觉**就出来了
- 速度用等宽字体 + 强调色 —— 数字跳动时不会左右抖动
- 明文标注"**边收边写入磁盘，不占用内存**" —— 这是技术卖点，也是大文件不崩的保证
- 两个按钮：`暂停` / `取消并销毁`
  - **"取消并销毁"要写全**，不要只写"取消"。用户要确切知道这个按钮意味着什么

**④ 完成**
- 成功动效克制（一次勾号 + 柔和光环，不要撒花）
- **每个文件单独显示校验结果**：`✓ 校验通过 · SHA-256 一致`
  - 这一行是"传输可信"的最终证据，不能省
- **销毁清单**（本设计里最重要的一块）：
  ```
  会话销毁清单
  ✓ 密码与会话密钥已清零
  ✓ 发送端服务已关闭
  ✓ 一次性链接已失效
  ✓ 本页刷新后将无法再次访问
  ```
  - 别的程序把"用完即销毁"当营销词，你要把它**做成可见的清单**
  - 这是整个产品最独特的信任资产，也是开源后最容易被人截图传播的一块 UI
- 主按钮 `打开文件夹` 用 `showSaveFilePicker` 拿到的 handle 不行 —— 浏览器**不允许网页打开本地文件管理器**。
  - 实现时改为 `打开所在位置` 的降级方案：显示完整保存路径 + 一键复制，并提示"文件已在你的下载目录"
  - 这一点必须在实现时验证，别在 UI 上承诺做不到的事

**⑤ 出错**
- **安全类错误必须明确说"什么也没发生"**：`没有传输任何数据，也没有文件被写入磁盘`
  - 这句话能把用户的恐慌降低一个数量级
- 失败计数要可见：`已连续失败 2 次，再失败 3 次后本次会话将自动销毁`
- 只给一个动作：`重试`。不要给"返回""取消""帮助"三个按钮

**⑥ 取消/销毁**：一句话说清已销毁什么、什么没保存，然后关闭页面即可。

### 2.3 版面：卡片宽度要跟着屏幕走，而且要**垂直居中**

原先是 `.wrap{max-width:520px}` + `body{justify-content:center}`。在 1920 屏上：

- 两边各空出约 700px（写死窄宽度）
- `justify-content` **只管水平** —— 于是所有多余的**竖向**空间全堆在卡片下面，
  整页看起来像"内容飘在左上角"，比留白本身更显空

改法（`web/receiver.html`）：

```css
body{display:flex;justify-content:center;align-items:center;padding:28px 16px}  /* 加 align-items */
.wrap{width:100%;max-width:520px}
@media (min-width:1200px){ .wrap{max-width:640px} }
@media (min-width:1600px){ .wrap{max-width:720px} }
```

接收端只加到 720px：它是**一件事**的界面（输密码→等→收完），
再宽就是卡片内部空，反而不好看。发送端内容更多（清单、密码、选项、进度），
所以放到 860–1000px 并排成两栏，见 §3.5。

> ⚠️ 这一条是**用截图看出来**的，不是推理出来的：`_lab/screenshot.mjs`
> 用 headless Edge 拍一张 1920×1080 就能看见。改版面时请顺手拍一张再下结论。
>
> 交互改动（点一下会不会生效）光看截图不够：`_lab/verify-remove-ui.mjs`
> 会开一个 headless Edge **真的点**清单里的 ✕ 和语言按钮，再回头核对后端状态 ——
> 这类"长在 DOM 上"的功能，只有真点一次才算验证过。

### 2.3 视觉设计令牌

```css
/* 深色为主（文件传输常在晚上、常对着大屏），浅色自动跟随系统 */
--bg: #0b0e14         /* 页面底 */
--bg-elev: #121722    /* 卡片 */
--border: #232c3d
--text: #e6ebf5
--text-dim: #8c9ab4   /* 次要文字 */
--accent: #4d9fff     /* 主色：蓝（可信、冷静） */
--ok: #2fbf71         /* 成功/校验通过 */
--warn: #f0a83c       /* 警告/提示 */
--danger: #ff5f57     /* 危险/销毁 */
--mono: ui-monospace, "Cascadia Mono", Consolas  /* 数字、密码、路径、哈希 */
--sans: -apple-system, "Segoe UI", "Microsoft YaHei", "PingFang SC"  /* 正文 */
```

三条字体规则（安全工具的气质就靠这个）：
1. **所有数字、密码、路径、哈希 → 等宽字体**（不抖动、易核对）
2. 正文用系统字体，**绝不加载网络字体**（局域网可用性 + 不做外部请求）
3. 中英文混排时给中文留 `letter-spacing: 0`，不要用斜体（中文斜体是伪造的，很难看）

## 三、发送端设计（终端）

### 3.1 终端 UI 的边界

命令行 UI 有个天然限制：**不能用任何 TUI 库**（那是第三方依赖）。所以只用：
- ANSI 转义码（颜色、光标移动、清行）
- Unicode 框线字符（`┌ ─ ┐ │ └ ┘`）
- 块字符做进度条（`█ ░`）

这些在 Windows Terminal / PowerShell 7 / macOS / Linux 上表现都很好。
老式 `cmd.exe` 需要检测并降级到纯 ASCII（`+ - |` 和 `# .`）。

### 3.2 终端的五个阶段

```
① 启动+清单    看到要传什么、多大
② 计算校验     进度条（大文件时需要，否则用户以为卡死）
③ 密码        生成强密码 + 二次确认
④ 分享        链接 + 二维码 + 超时倒计时
⑤ 传输        实时进度 + 速度 + "Ctrl+C 立即销毁"
```

### 3.3 终端里的三个关键决定

**1. 二次确认只针对"自己设的密码"，不针对自动生成的**

对方在另一台电脑上要一字不差地手打密码。如果发送端打错了，对方永远进不来，而且**看不出原因** —— 所以设密码这个动作需要二次确认。

**但确认的范围必须精确**，这一点是实测之后才想清楚的：

| 用户的操作 | 是否二次确认 | 为什么 |
|---|---|---|
| **直接回车**（接受自动生成的密码） | ❌ **不确认** | 生成的密码有 26 个字符。逼用户手抄一遍来"确认接受默认值"既荒谬又极易出错，而它本来是零风险操作 —— 不接受就重新生成即可 |
| **自己输入密码** | ✅ **必须确认** | 打错了对方永远进不来，且双方都看不出原因。这是真正需要防的错 |

> 这条规则是 `test/password.test.js` 逼出来的：最初写的是"一律二次确认"，
> 测试跑出来才发现那个设计在逼用户手抄随机词。**测试暴露的不只是代码 bug，还有设计缺陷。**

**2. 默认生成强密码，而不是让用户自己想**
`correct-horse-battery-staple` 这种 4 词密码：
- 约 52 bit 熵 —— 对几分钟生命周期的会话足够了（且限速 + 5 次自动销毁）
- **对人是可读、可念、可手打的** —— 用户可以电话念给对方，或微信发过去
- 提醒：默认密码可以直接回车接受，想自己设定就打字

> 不要用 `aB3#xK9!` 这种随机串。它的熵差不多，但**没法念、没法手打**，会逼用户复制粘贴，
> 而复制粘贴的渠道往往就是被监听的渠道。

**3. 二维码是刚需，但必须有备选**
终端里画二维码（半块字符 `▀▄█` 拼两个像素）能让对方**扫一下就打开**，省掉手打长 URL。
- 需要约 250 行纯 JS 实现 QR 编码（零依赖，不用 npm 包）
- **但部分 Windows 控制台的字体/编码会让它错乱** → 必须给两个备选：
  - `--card=share.png`：导出一张分享卡图片（见原型第 7 屏），可以直接微信发送
  - `--no-qr`：纯文本模式，只输出链接 + 密码，适合远程 SSH 会话

### 3.4 图形界面（站点页）：铺满窗口 + 点着选文件

终端之外，发送端还有一个本地网页界面（`web/station.html`，只监听回环）。

**版面：铺满窗口的"应用外壳"**（2026-10 改）

```css
body{padding:0}                        /* 不再是居中的浮动卡片 */
.station{min-height:100vh;display:flex;flex-direction:column}   /* 外壳铺满 */
.sec{flex:1;max-width:1180px;margin:0 auto}                     /* 内容限宽居中 */
.foot{border-top:1px solid …;flex:none}                         /* 页脚留在视口内 */
```

为什么要改：从前是 `max-width:620px` 的卡片居中，在 1600/1920 的屏上四周全是空的 ——
卡片像"浮在左上角的一块"。现在外壳贴边铺满（背景、边框、圆角都去掉），
只有**文字行宽**限到 1180px，避免超宽屏上一行拉到两千像素。

- 选择屏的内容**垂直居中**，拖放区给足高度（拖放目标本来就该大）
- 计划屏的文件列表 `flex:1`，列表长了自己滚动，按钮始终够得着
- ⚠️ 页脚那行"本页面只监听本机回环地址"必须留在 `.station` **内部** ——
  外壳是 `min-height:100vh`，放到外面会被挤到视口下方，不滚动就看不见，
  而它是一句安全承诺

**选择文件 / 选择文件夹：不许让用户手打路径**（2026-10 改）

这是本次改动的重点。原来的三个按钮（选择文件 / 选择文件夹 / 输入路径）**都是**
把输入框露出来让用户自己敲路径 —— 那不是"选择"，那是甩锅。

为什么不能像普通网页那样用 `<input type=file>`：**浏览器不会把本地文件的绝对路径
交给网页**（沙箱的基本约束；`input[type=file]`、拖拽、File System Access API 都不给，
`File.path` 是 Electron 才有的东西）。而发送端是 Node **直接读原文件**
（不复制、不占内存 —— 几十 GB 才可行），它要的恰恰是路径。

所以：**由本地服务列目录**（`GET /api/browse?path=…`），页面渲染成一个浏览窗口。

```
选择文件 / 选择文件夹 → 弹窗（盘符 → 目录 → 文件）
  · 文件夹在前、文件在后，各自按名字排（跟资源管理器一致）
  · **两个按钮的行为真的不同**（见下表）—— 一开始做成几乎一样，等于白放两个按钮
  · **多选**：点右边的方框选中/取消，**Shift 连选一段**
  · **选择跨目录累积**：在 A 目录选两个、进 B 目录再选一个，凑齐了再确认
  · 双击某一项 = 直接发这一个（只加一个时的快路径）
  · 不跟随符号链接（与 scan() 的口径一致）
  · 读不了时给人话（"权限不够 / 盘符不在线"），不抛裸 EPERM
```

**两种模式的分工**（点同一个位置，行为不同）：

| 点在哪儿 | 选择文件模式 | 选择文件夹模式 |
|---|---|---|
| 文件的名字 | 选中 | —（不列文件） |
| 文件夹的**名字** | 进去 | **选中**（"我就要发这个"） |
| 文件夹左边的 **▸** | 进去 | 进去 |
| 右边的方框 | 选中/取消 | 选中/取消 |
| 双击 | 直接发这一个 | 直接发这一个 |

选文件夹模式下 `/api/browse?only=dir` **只列文件夹** —— 列文件既选不了又占地方。

> ⚠️ **「上一级」必须用服务端给的 `parent`，不能在本地拼字符串。**
>    这里踩过一个很典型的坑：本地拼 `D:\闪传` 的上级得到 `D:`（丢了反斜杠），
>    而 Windows 上 `path.resolve('D:')` 是"**D 盘的当前目录**"= 进程的 CWD
>    = `D:\闪传` —— 于是"上一级"原地打转，怎么点都退不出去。
>    服务端的列表响应里本来就有权威的 `parent`。同时服务端现在**拒绝相对路径**
>    （`需要绝对路径`），免得那个 `path.resolve` 的隐式行为再从别处钻进来。

> ⚠️ **Shift 连选必须最先处理、并且 `return`。**
>    从前的写法是"有锚点才连选"，没有锚点时这一支被跳过，落到"点名字进目录"
>    那一路 —— 用户想从头连到尾，结果点进了文件夹里。现在没有锚点就以当前项为锚，
>    而且这一支永不进目录。

> ⚠️ **选择必须存在列表数据之外**（`browseSel` 是一个 Map，只在**打开窗口**时清空）。
>    放进列表数据里的话，翻一次目录就被重建冲掉 —— 而那正是多选最需要的能力：
>    "从几个文件夹里各挑几个"。

安全性只有一条前提，而且它已经成立：**这个服务只监听 127.0.0.1**
（`test/gui.test.js` 有"只监听回环地址"的用例盯着）。能访问它的进程本来就能直接
读同一台机器的文件系统，所以没有额外风险。拖拽也走同一条路：浏览器同样不给路径，
拖进来之后直接打开浏览窗口，而不是让用户手抄。

**文件清单按"添加项"分组**（2026-10 改）

加一个文件夹 → 列表里是**一行文件夹**（名字 + N 个文件 + 总大小 + 完整路径），
点一下展开看里面有什么；明细里的路径会去掉文件夹前缀，免得每行都重复一遍。

```
📁 web                        4 个文件 · 245 KB
   D:\闪传\web
   └ i18n-runtime.js   10 KB
     receiver.html    135 KB
     …
```

- 后端按 `srcIndex`（来自 `inputs` 里的第几项）分组，不靠 `rel` 的第一段去猜 ——
  两张卡里各有一个 `照片` 时会被去重改名，猜就会串组
- 明细**按需拉**（`/api/group?p=<路径>`）：`/api/state` 每 400ms 轮询一次，
  几万个文件的明细不能每轮都往页面灌
- ⚠️ **定位一律用路径，不能用序号**（`?p=`，不是从前的 `?i=N`）。
  删掉中间一项之后，它后面所有项的序号都会前移；而页面里"哪一项展开着"是按路径记的，
  两边口径不一致就会展开到错的那一项。分组 DOM 的指纹同理，用 `path:fileCount`
- ⚠️ 分组 DOM 只在**结构变了**的时候重建：无脑重建会把用户的展开状态冲掉，
  表现是"点开一秒后自己又收起来"

**单独去掉一项**（2026-10 新增）：每一行分组右边有一个 `✕`（常显但低调，
悬停变红），点它只把那**一项**从清单里移掉。

用户的原话是"如果选错了文件或者文件夹只能全部清除，应该加入单独清除的选项" ——
当时只有「全部清空」，选错一个文件夹就得从头再选一遍（对几十 GB 的清单尤其难受）。

- 后端 `POST /api/remove {path}` → `removePath()`，按**当初加进去的那个路径**匹配
- 加一项、删一项走的是**同一个** `applyPaths()`：两条路径必须得到同一个状态形状，
  否则删完之后分组编号、总字节数、phase 会和加进去时不一致
- 删到空 → `phase` 回到 `idle`（界面退回"我要发文件"那一屏），
  而不是停在一个空清单上等人点「开始传输」
- 移除一个本来就不在清单里的路径 → 404 并说人话（"这一项已经不在清单里了"），
  **状态不变**；没给 `path` → 400
- ⚠️ `✕` 必须**常显**（`.7` 透明度），不能做成"悬停才出现" ——
  那样没人知道有这个功能。用户当初就是因为找不到单独清除、只能用「全部清空」
  才提的这一条

**语言切换按钮要显眼**（2026-10 改）：原来是一个灰字、透明底、细边框的小胶囊，
混在页头里几乎看不见 —— 而**需要它的人恰恰是看不懂当前界面的人**，
按钮藏起来等于没有。现在两个页面统一成：`🌐` + 目标语言名 + `▾`，
主色文字、主色淡底、主色描边，悬停时整块填成主色。

- 图标走 `::before`/`::after`，**不能写进 HTML**：按钮文字是运行时
  `set textContent` 填的（要显示"另一种语言"的名字），放进去会被冲掉
- 按钮文字显示的是**另一种语言**的名字，切完要跟着换 ——
  否则切到英文后按钮上还写着"English"，等于点不动自己

**限速选项**（2026-10 新增）：`传输选项` 里除了「顺便把赠品送给对方」，还有「限速」。
- 预设：`不限速 / 1 / 2 / 5 / 10 MB/s`，外加「自定义…」展开一个文本框
- 写法与命令行 `--rate` **完全一致**（同一个 `parseRate`）：`512K` / `5M` / `2G`，
  纯数字按字节/秒算；空 = 不限速
- ⚠️ **看不懂的写法必须报错，不能当成不限速**。这一项的用途就是"别占满上行带宽"，
  悄悄放行会让用户以为限住了、实际把带宽吃满 —— 而这种误解只有等别人抱怨网络卡
  才会被发现（`src/rate.js` 的注释里记着这条）。界面上表现为：输入框标红 + 弹出
  正确写法，**后端状态保持原样**
- 输入时防抖 500ms 再提交：`5` 是合法的 5 字节/秒，每敲一个字符就提交会真的生效

**密码框必须被填上**（同一次截图发现的）：后端启动时就生成好了密码并通过
`/api/state` 下发，而页面从前只在点「换一个」时才填 —— 用户看到空框、点「开始传输」，
得到的是"密码不能为空"。现在轮询时会填上，但**只在用户没自己动过的时候**填，
免得把人家手输的密码冲掉。

### 3.5 终端里的销毁承诺

传输中必须常驻显示一行：

```
  按 Ctrl+C 立即中止并销毁全部密钥
```

并在 `Ctrl+C` 时真的执行销毁流程，然后打印：

```
✓ 已销毁：会话密钥 · 密码验证值 · 临时缓冲
✓ 发送端服务已关闭
```

**把销毁过程打印出来**，和接收端那份销毁清单呼应 —— 这是这个项目的气质所在。

### 4.2 算法敏捷性 —— 这是"以后加更多加密方法"的正确做法

**千万不要把加密算法写死在流程里。** 从现在开始就按这个结构做：

```
握手第一步：双方交换"我支持哪些加密套件"
            ↓
            协商出双方都支持的最强套件，写入会话
            ↓
            之后所有密钥派生、加密、校验都走"套件接口"

套件 = { id, 密码派生函数, KDF, AEAD, 哈希, 分块大小 }
```

于是未来加算法只是**新增一个套件对象**，不动任何流程代码：

| 想加的 | 怎么做 | 注意 |
|---|---|---|
| **Argon2id** 替代 PBKDF2 | 加套件 `FLICKER/2` | WebCrypto 没有 Argon2，需要 WASM 或纯 JS 实现 —— 体积换安全性，做成可选 |
| **ChaCha20-Poly1305** | 加套件 | 在没 AES 硬件加速的设备上更快；浏览器 `crypto.subtle` **不支持**，需要 WASM |
| **X25519 + 短认证串** | 增强版握手 | 现在靠密码认证。加上密钥交换 + 6 位数字核对码，可以防"relay 篡改握手" |
| **后量子**（ML-KEM） | 远期 | 等浏览器和 Node 都原生支持再说，先用套件接口留好位置 |

**版本协商必须双向兼容**：新版程序遇到老版对方，要能自动降级到 `FLICKER/1`，而不是直接报错。
这条从第一天就要写进协议，否则以后加算法就会造成"我不升级就用不了"的割裂。

### 4.3 代码结构建议（为开源和演进做准备）

```
flicker/
├─ bin/flicker.js            # CLI 入口（保持极薄）
├─ src/
│  ├─ suite/                 # ★ 加密套件目录，未来加算法的唯一入口
│  │  ├─ index.js            #   注册表 + 协商
│  │  └─ flicker1.js         #   FLICKER/1 = PBKDF2 + HKDF + AES-256-GCM
│  ├─ transport/             # 通道实现（LAN / relay / 未来更多）
│  │  ├─ lan.js
│  │  └─ relay.js
│  ├─ protocol/              # 握手、分块、清单（与套件解耦）
│  ├─ ui/
│  │  ├─ tty.js              # 终端渲染（ASCII 降级在此处理）
│  │  └─ qr.js               # 零依赖二维码
│  └─ destroy.js             # 销毁流程（单独成模块，便于测试和审计）
├─ web/receiver.html         # 接收端单页（构建时把共享代码注入）
├─ relay/worker.js           # Cloudflare Worker
├─ test/                     # node --test
├─ PROTOCOL.md               # ★ 协议规范
├─ SECURITY.md               # 威胁模型
└─ 设计文档.md
```

**关键点**：`suite/` 和 `destroy.js` 单独成目录，是因为这两个是这个项目**唯二真正难的部分**，
也是最需要被审计、被测试、被独立阅读的部分。把它们混在别处，开源后会很难被人 review。

### 4.4 手机端：现在就要做的准备（成本极低，收益极大）

你提到"以后允许电脑文件传输到手机"。有三件事**现在做几乎不额外花时间，但以后省很多事**：

**1. 把接收端做成 PWA**（加一个 `manifest.json` + 一个极简 `sw.js`，约 40 行）
- 手机浏览器可以「添加到主屏幕」，看起来像个 App —— 但仍然**不需要应用商店、不需要安装**
- 完全契合你"接收端不装程序"的核心需求
- 注意：PWA 需要 HTTPS（局域网自签证书下会受限，跨网络走 relay 时天然满足）

**2. 手机端用 Web Share API 落地文件**
- 桌面上是"下载到文件夹"，手机上应该是"**调起系统分享面板**" → 可以存相册、存文件 App、直接发微信
- `navigator.share({ files: [...] })` 一行代码，iOS 15+/Android Chrome 都支持
- 这是"电脑→手机"体验的关键一步，不做的话手机上只能存到下载目录，用户找不到文件

**3. UI 从第一天就按响应式布局写**
- 手机不是"缩小版的桌面"，是独立场景（见原型第 4 屏）
- 竖屏一列到底、按钮全宽、进度数字加大、路径信息收起来
- 现在写 CSS 时用媒体查询兜住，比以后重构便宜十倍

> **手机作为发送端**是真正的难题：浏览器无法读取任意路径的文件，这是平台限制，不是设计问题。
> 可行路线只有两条：① 手机 → 电脑方向（手机上传，电脑接收）；② 把程序包进移动外壳
> （Capacitor/Tauri Mobile），那时才能在手机上跑发送端。这属于 P4 阶段，现在不用管。

### 4.5 其他零散但重要的建议

| 建议 | 理由 |
|---|---|
| **Windows 防火墙一键放行脚本** | 首次监听必然弹窗，很多人会点错。附一个 `放行防火墙.ps1`（需管理员），文档里写清楚 |
| **速率限制 + 失败计数** | 密码只有几分钟有效期，但必须有：5 次失败自动销毁、握手阶段强制延迟 |
| **`--dry-run` 干跑模式** | 打印将要发送的清单和大小，不启动服务。调试和确认用 |
| **传输速度上限 `--rate=N`** | 局域网跑满千兆会拖慢别人，大文件传输时用户会想要限速 |
| **断点续传的 UI 反馈** | 断线重连后要明确显示"从 xx% 继续"，否则用户以为重头开始了 |
| **日志脱敏** | 任何日志里**绝不能出现密码、密钥、文件内容**；文件名是否记录要做成开关（默认不记录）|
| **不要做"记住密码"** | 违背一次性原则。任何持久化都会削弱产品的核心承诺 |
| **GitHub Release 附预编译产物** | 用 `node --experimental-sea-config` 打包 Windows/macOS/Linux 单文件，Mac 用户没装 Node 也能用发送端 |
