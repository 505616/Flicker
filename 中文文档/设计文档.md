# 一次性文件传输程序 —— 设计与实现方案

> 需求来源：[`原始需求以及作者的话.md`](原始需求以及作者的话.md)（作者一开始写的原始需求）
> 目标：把文件从本机传到另一台电脑，**接收端不装任何程序**，两台电脑**输入同一个密码**才能传，**所有东西用完即销毁**。

---

## 一、需求拆解（把口语需求翻译成技术约束）

| 原始需求 | 技术约束 | 影响的设计决策 |
|---|---|---|
| "不需要目标电脑下载程序" | 接收端唯一的运行环境是**浏览器** | 接收端是纯网页（HTML+JS）；发送端必须能向接收端提供这个网页 |
| "选择要发送的文件" | 发送端需要一个文件选择入口 | 命令行传入路径 / 拖拽进网页（网页只回传路径，见 5.3） |
| "设置密码" | 密码在发送端设定 | 发送端终端输入，二次确认后"上膛" |
| "必须两台电脑输入同样的密码才能传输" | **双向认证**，不是单边校验 | 挑战—应答握手，密码本身永不上网线（见第四章） |
| "两台电脑肯定要先链接到一起" | 需要一条传输通道 | ①同局域网直连 ②WebRTC 打洞 ③端口转发（见第三章） |
| "所有传输用到的东西都是一次性的用完就销毁" | 无落盘、无残留、会话即焚 | 密钥只在内存、流式加密不落临时文件、结束即擦除+关服（见第六章） |

## 二、环境事实（已在本机核实）

```
Node.js  v24.21.0        ← 已安装，是本方案的发送端运行时
Python   3.14.7
本机 IPv4 192.168.1.5  ← 局域网地址（以太网）
OS       Windows 10 (10.0.19044), AMD64
```

Node 24 的关键能力（已用 `node -e` 实测，不是查文档猜的）：

| 能力 | 实测结果 | 对方案的用处 |
|---|---|---|
| `WebSocket` 全局 | ✅ 内置 | 与 relay 通信，**零 npm 依赖** |
| `crypto.subtle` | ✅ 内置 | 与浏览器端共用同一套 WebCrypto 代码 |
| `fetch` | ✅ 内置 | HTTP 长轮询备用通道 |
| `RTCPeerConnection` | ❌ **undefined** | ⚠️ **发送端无法自己跑 WebRTC** |

**这条 ❌ 直接改变了架构。** 常见做法是让两端浏览器用 WebRTC 互传，但发送端要跑 WebRTC 就得装 `node-datachannel`（带原生的 libdatachannel 二进制）或 `wrtc`——既违背零依赖，也让"一个程序拷过去就能用"变复杂。

**所以本方案让发送端做数据面，浏览器做控制面与落盘端。** 见 5.1。

## 二·补、本机实测网络结论（重要）

对发送端所在的这条宽带做了实测，结果直接排除了两条路径：

```
出口公网 IP        （已隐去：实测时是作者家的宽带出口，具体值对结论没有影响）
本机地址           192.168.1.5
默认网关           192.168.1.1        ← 你自己的路由器

路径追踪（tracert 到 114.114.114.114）：
  第 1 跳   192.168.1.1      <1 ms    ← 你的路由器
  第 2 跳   192.168.1.1       <1 ms    ← 还有一级路由器
  第 3 跳   100.64.x.x         6 ms    ← 运营商设备，100.64.0.0/10 是运营商级 NAT 专用段
  第 4 跳   超时

全局 IPv6          无（Test-NetConnection 240c::6666 → 不可达）
路由器 UPnP        SSDP 探测无响应（不可用）
```

**三条结论，都是硬事实：**

1. **公网 IPv4 在运营商的大 NAT 后面（CGNAT）** —— 你分到的那个公网地址是很多用户共用的地址。你在自己路由器上做端口转发**没有意义**，因为请求根本到不了你家路由器（中间还夹着 `192.168.1.1` 和运营商那一层）。
2. **没有公网 IPv6** —— 第 3 层（端口转发/直连）彻底不可行。
3. **双重 NAT + UPnP 不可用** —— 连"自动开端口"这条退路也断了。

### 因此对本机而言，跨互联网**只剩一条路：relay（会合点）**。

这不是设计偏好，是网络环境逼出来的唯一解。第四章会详细解释 relay 是什么、为什么必须有它。

## 三、连接：三层降级策略

两台电脑要能连上，必须满足以下**至少一条**。程序自动探测并给出可用的那一条。

### 第 1 层：同一局域网（推荐，最可靠、最快）
发送端在 `0.0.0.0:随机端口` 起一个 HTTPS 服务，接收端浏览器打开 `https://192.168.1.5:<port>/?k=<一次性令牌>`。
- 速度 = 局域网带宽（通常 100MB/s+，秒传几个 GB）
- 不需要公网、不需要 relay、不需要 WebRTC
- ⚠️ Windows 首次会弹防火墙授权框，点"允许"即可（可附 `netsh` 一键放行脚本）

### 第 2 层：不同网络 —— 中继转发（**已实现，且与原设想不同**）

> **⚠️ 本节是当初的设计设想，实现时被推翻了。保留是为了记录判断过程。**
>
> 原设想：relay 只做会合，接收端拿到发送端地址后**直连**发送端，数据永不经过 relay。
> 前提是发送端有一个接收端够得着的地址（公网 IPv6 / 同网段 / 端口转发）。
>
> **实测把这三条全否掉了**：用户出口是 CGNAT（公网 IP 与他人共用），且没有全局 IPv6。
> 于是"牵线之后直连"根本没有线可牵。
>
> **最终实现：中继转发全部数据**（`src/relay/`）。
> 代价如实记录：中继承担全部带宽，且能看到"有人在传、有多大"。
> 换来的是**一定可用** —— 不依赖任何打洞成功率。
> 加密承诺不变：中继经手的全是密文，密钥只在两端。
>
> 决策过程见 `架构决策.md`，协议见 `中继部署.md` 与 `PROTOCOL.md`。
> 想彻底避开中继，就用局域网模式或自建中继。

<details>
<summary>以下是当初的设想（已不适用，点开仅为存档）</summary>

两端都连上 **relay（会合点）**，交换 SDP，然后用 WebRTC DataChannel 建立浏览器 ↔ **发送端** 的点对点通道。

但如第二章所述，发送端没有 WebRTC。**因此数据面改为：浏览器 ↔ 发送端 的加密分块 HTTP 流**，relay 只负责"把接收端引导到发送端"：

```
接收端浏览器 ──打开 relay 页面（密码哈希派生房间号）
                    │  relay 通知发送端"N 号房间有人来了"
发送端(Node) ───────┘  发送端把"如何直连我"的邀请帖进房间
接收端读到邀请 ──> 浏览器 fetch 直连发送端 ──> 分块加密下载
```

这个邀请帖里放什么？按可达性优先级排列：
1. 发送端在**公网 IPv6** 上的地址（IPv6 无 NAT，直接可达，最干净）
2. 发送端在**局域网**的地址（双方其实同网段时命中，此时 relay 只当了一次"牵线人"）
3. 发送端公网 `IP:port`（用户在路由器上做了端口转发时）

如果三条都不可达，浏览器 fetch 会失败——程序会明确告诉用户选第 1 层或第 3 层，**不会假装成功**。

> 为什么不用 TURN 中继兜底？因为公开 TURN 服务需要账号/凭据，属于"依赖第三方服务"，且长期可靠性无法保证。宁可给出清晰的失败提示 + 可操作的替代路径。

</details>

### 第 3 层：端口转发 / 公网 IPv6 直连（**本机已实测排除**）
发送端打印公网 IP + 端口，用户在路由器把该端口转发到本机，接收端直接开链接。
- 前提：家里有**独占的公网 IPv4**（能自己做端口转发），或双方都有**公网 IPv6**
- **本机实测不满足**：CGNAT（公网 IP 与他人共用）+ 无 IPv6 → 此层不可用
- 若换了宽带（有公网 IP）或打电话让运营商开公网 IPv4/IPv6，此层自动恢复可用
- 这一层在代码里保留实现，因为它对"别人家的宽带"是有效的兜底

### 关键设计点：relay 做数据面（**与原设想相反**）

> 原设想的三个"好处"建立在"relay 不碰数据"之上，实现后不成立，逐条对照：

| 原以为的好处 | 实际情况 |
|---|---|
| 免费额度绰绰有余 | ❌ **不成立**：数据全走中继。免费额度够日常用量，但大文件要自己算账 |
| relay 无法拿到文件内容 | ✅ **仍然成立**，但靠的是**加密**而不是"不经过"：中继拿到的是密文 |
| 传完房间立刻销毁 | ✅ **仍然成立**：传输完成即 DELETE，另有 15 分钟 TTL 兜底 |

**结论**：安全承诺没有变（甚至说得更清楚了），变的是**带宽成本由中继承担**。
所以"自建中继"从"可选"变成了"在意成本和元数据的人应该做的事"。

## 三·补、relay 到底是什么（详解）

> **⚠️ 本节的示意图描述的是"牵线后直连"的旧设计。实际实现是"中继转发数据"。**
> 第 ④ 步"双方直接对连、relay 退出"**没有发生** ——
> 在 CGNAT + 无 IPv6 的现实条件下，牵线之后依然连不上，
> 所以数据继续走中继（只是全程是密文）。**读本节时请把第 ④ 步替换成
> "数据经中继转发，中继看到的是密文"**。前面几节讲的"为什么需要中继、
> 为什么只能自建"仍然完全成立。

### 1. 为什么非有它不可

你家路由器给了你一个**内网地址** `192.168.1.5`。这个地址在全世界的互联网上是**不存在**的 —— 它是你家局域网内部的门牌号，出了路由器就没人认识。

所以接收端那台电脑，**没有任何办法主动连到你家路由器后面的这台机器**。它连地址都不知道，就算知道也路由不到。

那怎么办？**两边都主动往外连。**

```
   你家（192.168.1.5）                云端                       对方家
         │                               │                           │
         │ ① 主动连出去（对外连接不会被拦） │                           │
         ├──────────────────────────────>│<──────────────────────────┤
         │                               │  ① 主动连出去              │
         │                               │                           │
         │ ② "我是 A，我的密码哈希是 X"   │  ② "我是 B，密码哈希也是 X" │
         ├──────────────────────────────>│<──────────────────────────┤
         │                               │                           │
         │ ③ relay 把 B 的地址告诉 A     │  ③ relay 把 A 的地址告诉 B  │
         │<──────────────────────────────┤──────────────────────────>│
         │                               │                           │
         │ ④ 双方现在都知道对方地址了，直接对连（relay 退出）           │
         └──────────────────────────────────────────────────────────>│
```

**这就是 relay：一个"双方都够得着"的中间人，负责牵线，牵完就走。**

### 2. 为什么非得自己部署

因为"云端那个点"必须**一直在线**、**双方都能访问**、且**长期稳定**。

- 用别人的公共服务？它可能明天就关站，也可能记录你的房间号。不可控。
- 用自己的电脑当 relay？你家电脑自己就在 NAT 后面，别人同样够不到它 —— 死循环。
- **所以只能是一个免费云服务上的自己的小程序。** 这就是"部署一次"的真实含义：把自己的 120 行代码，放到一个 24 小时在线的免费机器上。

### 3. 具体部署动作（到时候的真实操作）

```powershell
# 1. 注册一个 Cloudflare 账号（免费，不需要信用卡）
# 2. 安装一次 wrangler（Cloudflare 的官方命令行工具）
npm install -g wrangler
wrangler login          # 浏览器里点一下授权

# 3. 部署（这一行之后，你的 relay 就有永久地址了）
cd relay
wrangler deploy
# 输出：https://one-shot-relay.你的用户名.workers.dev   ← 记下这个地址

# 4. 以后每次传输，加上参数即可
node 传输.js send "D:\视频\a.mp4" --relay=https://one-shot-relay.你的用户名.workers.dev
```

**"一次"的意思**：这个部署是永久的，之后每次传输都直接用它，**不再需要重复任何步骤**。免费额度是 10 万请求/天，而一次传输只消耗个位数请求。

### 4. relay 里跑的东西到底多小

```
职责（就三件事）：
  ① 托管接收端那个单页（发送端不方便给的时候）
  ② 在同一个房间号的两端之间转发几条会合消息
  ③ 房间自动过期删除（TTL 兜底）+ 支持主动 DELETE（用完即焚）

不做的：
  ✗ 不碰文件数据
  ✗ 不保存任何东西到磁盘
  ✗ 不需要数据库、不需要登录、不需要域名
```

**它不是文件服务器，是个传话的。** 一次传输的全部流量就是几条会合消息，可能几 KB。

### 5. 为什么不用现成的方案（都考虑过并排除了）

| 方案 | 为什么不用 |
|---|---|
| Google Drive / 微信 / 网盘 | 文件要落到第三方服务器，违背"用完即销毁" |
| 公开 TURN / WebRTC 中继服务 | 需要账号凭据，长期可靠性不可控 |
| 公开 MQTT broker 当会合点 | 意外断线、无 TTL 保证，且把房间号暴露给陌生人的基础设施 |
| ngrok / cloudflared 之类隧道 | 属于"安装第三方程序"，且免费版有各种限制 |
| Tailscale | 接收端得装 —— **直接违背你的第 1 条需求**（这条是硬否决） |
| 直接传公网 IP 让对方连 | 本机实测是 CGNAT，根本连不上（见第二章·补） |

### 6. 对你家网络的最终结论

| 场景 | 能不能用 | 走哪条路 |
|---|---|---|
| 两台电脑在**同一个 WiFi / 同一个路由器**下 | ✅ 完美 | 第 1 层局域网直连，速度最快，**什么都不用部署** |
| 两台电脑在**不同网络**（一个在家一个在公司/外地） | ✅ 但需要 | 第 2 层：必须先有那个免费 relay |
| 只靠端口转发不用 relay | ❌ 不可能 | CGNAT + 无 IPv6，实测排除 |

**所以 relay 是"跨网络"的唯一门票，而"同网络"完全免费。** 如果你平时的场景就是在家里两台电脑之间传，P0 阶段做完就已经够用了，relay 可以以后再说。


### relay 的部署（一次性，约 3 分钟，免费）
提供一个约 120 行的 Cloudflare Worker（HTTP 长轮询房间，内存存储 + TTL 自动过期 + 用完即删），用 `wrangler deploy` 部署到自己的免费账号。
> Cloudflare Workers 免费版含 Durable Objects（仅 SQLite 后端），额度为 100,000 请求/天、13,000 GB·s/天（[定价文档](https://developers.cloudflare.com/durable-objects/platform/pricing/)）。本方案只用来会合，消耗可忽略。

也提供**纯静态托管版**（GitHub Pages / 任意静态空间）：只托管接收端网页，发送端在 `邀请帖` 里直接写入自己的公网地址，**完全不需要自建 relay**——适合第 1/3 层可达的场景。

## 四、密码：为什么"两台电脑输同一个密码"能被密码学强制

不能只是"页面上比一下字符串"，那样密码会明文过网线。采用**挑战—应答**，密码本身永不传输：

```
1. 发送端设定密码 P，随机盐 S（16 字节）
   计算  V = PBKDF2-SHA256(P, S, 600000)        ← 32 字节，绝不离开发送端内存
2. 发送端用 HKDF-SHA256(V) 派生三把互不相关的钥匙：
       K_room = HKDF(V, "room")     → 房间号 → 两台电脑只有密码相同才会进同一个房间
       K_auth = HKDF(V, "auth")     → 握手认证
       K_enc  = HKDF(V, "enc")      → 文件加密
3. 握手（接收端先证明自己知道密码）：
      接收端 → 发送端 : nonce（随机 32 字节）
      接收端 → 发送端 : MAC_r = HMAC(K_auth, "recv" ‖ nonce)
      发送端校验 MAC_r；通过后回 MAC_s = HMAC(K_auth, "send" ‖ nonce)
      接收端校验 MAC_s
4. 双向认证完成，双方共享 K_enc，开始传输
```

这套设计的性质：
- **密码从不上网线**，抓包拿不到密码，也拿不到可直接复用的凭据（nonce 一次性，抗重放）
- **密码一致是数学结论**，不是界面提示：密码不同 → 房间号不同（找不到对方）或 MAC 校验失败（立刻中止）
- **接收端也要被认证**：发送端同样校验接收端，防止房间里混进第三方
- **抗离线爆破**：PBKDF2 迭代 60 万次；房间 TTL 只有几分钟，且失败尝试有次数上限
- 弱密码是唯一残余风险 → 发送端支持生成强随机密码（默认给出建议值）

> Windows/macOS 上禁止浏览器 `fetch` 访问自签名 HTTPS —— 所以第 1 层用**运行时自签证书**并在页面上给出一次性的"继续访问"引导。证书同样是会话级的，用完销毁。（此点需在实现时用一个真实的 Chrome 做端到端验证。）

## 五、传输层设计

### 5.1 角色分工（因为发送端没有 WebRTC）
- **发送端（Node）**：读文件、分块加密、提供 HTTP 分块接口、控速、算校验、销毁
- **接收端（浏览器）**：解密、验签、写盘、显示进度
- **relay（可选）**：只做会合

### 5.2 分块加密（支持任意大小文件）
```
块大小       1 MiB
每块         密文 = AES-256-GCM(K_enc, IV = f(文件序号, 块序号), 明文, AAD = 文件序号‖块序号‖总块数)
标签         16 字节（GCM 认证标签）
```
- **AAD 绑定块坐标** → 乱序、重放、跨文件拼接、截断，全部在解密时被拒绝
- 每块独立认证 → 中途失败可**断点续传**（接收端报 `RESUME(文件序号, 块序号)`）
- 服务端也只在内存里持有密文，**绝不写临时文件**

### 5.3 接收端写盘（大文件的关键）
“几百 MB 到几十 GB”量级决定了**不能把整个文件堆在内存里**：

| 浏览器 | 写盘方式 | 能力 |
|---|---|---|
| Chrome / Edge（桌面） | `showSaveFilePicker()` + `createWritable()` | 边收边写盘，内存占用恒定，支持几十 GB |
| Firefox / Safari | 累积 Blob → 触发下载 | 受内存限制，约 1~2 GB 上限，程序会提前警告 |

> 已核实：File System Access API（`showSaveFilePicker`）**仅 Chromium 系支持**，Firefox 给出 negative 立场、Safari 明确 oppose（[Web features explorer](https://web-platform-dx.github.io/web-features-explorer/features/file-system-access/)）。所以必须实现双路径，并在接收端页面检测 API 可用性后自动选择。

### 5.4 完整性
- 发送端预扫文件时算出 SHA-256 与分块哈希（Merkle 树根），先发**加密的清单**（文件名、大小、根哈希）
- 接收端**边收边算 SHA-256**，收完比对；不一致立即中止并提示
- 清单本身加密 → 文件名不会泄露到网络

### 5.5 多文件与文件夹
清单里带相对路径，接收端按相对路径落盘（Chromium 下可选 `showDirectoryPicker()` 重建目录树）。
路径安全：拒绝 `..`、绝对路径、Windows 非法字符 —— 防止恶意清单越权写文件。

## 六、"用完就销毁"的具体落实

| 对象 | 销毁时机 | 销毁动作 |
|---|---|---|
| 密码验证值 V、K_auth、K_enc | 传输完成 / 用户按 Ctrl+C / 超时 / 出错 | 内存 `fill(0)` 覆写，释放引用 |
| 分块密文缓冲 | 每块发出后立即 | 缓冲区复用并清零 |
| 会话密钥、房间号 | 同上 | 清零 |
| 发送端服务 | 传输完成即触发 | 关闭监听、强制断开会话 socket、进程退出 |
| 临时文件 | **从不产生** | 没有临时文件可销毁（这是设计目标，不是巧合） |
| relay 房间 | 发送端主动 DELETE + 服务端 TTL 双保险 | 立即删除，过期自动清理 |
| 接收端网页 | 每次启动重新生成，带一次性令牌 `?k=` | 关闭即失效；令牌一次使用后作废 |
| 接收端已保存的文件 | **不销毁**（这是用户要的成果） | 会话与密钥销毁，文件留在用户选的位置 |

发送端**原始文件不动**：程序只读原文件，从不复制、不移动到临时目录，所以不存在"副本残留"问题。

## 九、已知限制（诚实清单）

1. **跨互联网必须有 relay，这是数学必然，不是偷懒。** 根本原因：接收端要运行一段程序（浏览器里的网页），而**这段程序的来源必须是一个接收端能访问到的公共地址**。没有公网地址的一方，永远无法成为"被访问"的那一方。唯一的替代是让接收端**装**一个程序 —— 那直接违背第 1 条需求（Tailscale、Syncthing 之类都因此出局）。因此："跨网络" = "必须有 relay"。
2. **发送端必须有 Node 24+**（接收端什么都不用装）。若要发送端也零安装，P3 打包成单文件 exe 即可。
3. **本机的跨网络路径已被实测收窄到只剩 relay**：公网 IPv4 在运营商 CGNAT 后面（经运营商设备中转，跳数见第二章·补）、无全局 IPv6、双重 NAT 且路由器 UPnP 不可用 —— 端口转发与 IPv6 直连都被排除（详见第二章·补）。
4. **同一局域网内完全不需要联网**：不需要 relay、不需要公网、不需要任何部署，速度只受限于你的交换机/路由器（通常 100MB/s 以上）。
5. **Firefox / Safari 接收大文件受内存限制**（它们不支持流式写盘 API），约 1~2 GB 上限；建议接收端用 Chrome / Edge。程序会在页面上自动检测并提前警告。
6. **自签证书**场景下浏览器会有一次安全提示（每会话一次）。这个点需要在 P0 阶段用真实 Chrome 做一次端到端实测确认。
7. 通过 HTTPS 提供的接收页只在**当前会话**存在，进程退出后链接立刻失效 —— 这正是"一次性"的体现，但也意味着**刷新旧链接会失效**。
