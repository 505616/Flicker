## 0. 文档定位与版本约定

### 0.1 代码可重写，协议要能延续

`FLICKER/1` 是本项目**唯一需要长期兼容**的东西。发送端可以重写成 Go、Rust 或打包成单文件 exe；接收端页面可以重新设计；relay 可以换一家云厂商。但只要线协议不变，新旧实现就必须能互通。

由此产生三条硬性工程纪律：

| 纪律 | 含义 |
|---|---|
| **协议版本独立于程序版本** | 程序版本 `v0.4.2` 与协议版本 `FLICKER/1` 无关。程序升级不必然升级协议 |
| **线格式只增不改** | 已发布字段的**名称、类型、字节序、语义**永不修改。需要变化时新增字段或新增套件 |
| **未知字段必须忽略** | 任何一端收到不认识的字段/消息类型，**忽略并继续**，不得报错中断（前向兼容的唯一手段） |

### 0.2 本文件中的记号约定

| 记号 | 含义 |
|---|---|
| `‖` | 字节串拼接（concatenation），无分隔符、无长度前缀 |
| `BE64(x)` | 把整数 `x` 编码为 **8 字节无符号大端**（big-endian） |
| `BE32(x)` | 同理，4 字节大端 |
| `BE16(x)` | 同理，2 字节大端 |
| `[0x00] * n` | n 个零字节 |
| `HMAC(K, m)` | HMAC-SHA-256，输出 32 字节 |
| `HKDF(K, label)` | HKDF-SHA-256，salt 为空，info = `label` 的 ASCII 字节，输出 32 字节 |
| `BASE64` | 标准 Base64（RFC 4648 §4，含 `=` 填充） |
| `HEX` | 小写十六进制，无前缀 |
| **待验证** | 该条为设计推断，**未经实测**，实现时必须验证 |

> **全局字节序**：协议中**所有**整数字段一律**大端**（网络字节序）。唯一例外是 `JSON` 载荷内部的数字（JSON 数字无语序概念）。

## 1. 总体分层

### 1.1 分层图

```
┌──────────────────────────────────────────────────────────────────────┐
│  L6  应用层  Application                                             │
│      manifest 语义、路径安全、目录树重建、program gift 识别            │
│      产物：落盘的文件 + 界面状态（TTY / GUI 两个前端共用同一事件流）    │
├──────────────────────────────────────────────────────────────────────┤
│  L5  数据面  Data plane                                              │
│      chunk 帧、IV/AAD 派生、断点续传（RESUME）、ACK、背压               │
│      产物：定长密文块序列                                              │
├──────────────────────────────────────────────────────────────────────┤
│  L4  会话层  Session                                                 │
│      密码派生 V、HKDF 派生子密钥、双向 MAC 握手、会话 ID、失败计数       │
│      产物：双向认证完成 + (K_enc, SID)                                │
├──────────────────────────────────────────────────────────────────────┤
│  L3  套件层  Cipher suite                                            │
│      FLICKER/1 = PBKDF2-SHA256 + HKDF-SHA256 + AES-256-GCM + SHA-256 │
│      产物：所有密码学原语的**可替换接口**                              │
├──────────────────────────────────────────────────────────────────────┤
│  L2  传输层  Transport                                               │
│      https-chunk（P0/P1/P2 唯一实现） / wss-stream / webrtc-dc（预留）  │
│      产物：可靠、有序的字节流或请求-响应                              │
├──────────────────────────────────────────────────────────────────────┤
│  L1  会合层  Rendezvous                                              │
│      房间、长轮询消息、TTL、销毁。**永不接触文件数据**                  │
│      产物：双方互相知道"对方在哪、支持什么套件"                        │
├──────────────────────────────────────────────────────────────────────┤
│  L0  载具层  Page delivery                                           │
│      接收端 HTML/JS 从何而来：发送端自托管 / relay 托管 / gift 载入     │
│      产物：接收端跑起一段能执行本协议的代码                            │
└──────────────────────────────────────────────────────────────────────┘
```

### 1.2 每一层的归属与依赖方向

| 层 | 谁实现 | 依赖下层 | 关键性质 |
|---|---|---|---|
| L0 载具 | 双方站点 / relay Worker | — | **接收端零安装的唯一入口**；三种来源必须产出**行为等价**的客户端 |
| L1 会合 | relay Worker（可选） | — | **可完全跳过**（局域网模式）；只转发不透明字节 |
| L2 传输 | 双方 | L1（仅用于取地址） | 可替换：HTTP 分块 / WebSocket 流 / WebRTC DataChannel |
| L3 套件 | 双方 | — | **唯一的算法入口**，新增算法只改这一层 |
| L4 会话 | 双方 | L2、L3 | 密码永不上线；双向认证 |
| L5 数据面 | 双方 | L2、L3 | 分块独立认证；可断点续传 |
| L6 应用 | 双方 | L5 | 路径安全是**安全边界**，不是 UI 细节 |

### 1.3 术语表

| 术语 | 定义 |
|---|---|
| **发起方 / Initiator** | 掌握文件、运行发送端程序的一方（Node 进程）。在站点模型下即主动执行 `send` 的那个站点 |
| **接收方 / Responder** | 打开链接、运行浏览器页面的一方；或站点模型下输入密码接收的那个站点 |
| **站点 / Station** | `架构决策.md` 定义的统一程序形态：**一个可执行文件，两种角色，运行时决定**。本协议中"发起方"与"接收方"是**会话角色**，任何站点都可扮演任一角色 |
| **角色无关 / Role-neutral** | 协议消息本身不假设谁先说话；角色靠显式字段表达。本规范中 L1 的 `HELLO`、L4 的 `AUTH_REQ` 均带 `role` 字段 |
| **会话 / Session** | 从密码确认到销毁的完整生命周期，由 `SID`（16 字节）标识 |
| **房间 / Room** | relay 上的一个消息信箱，由 `room_name` 标识，有 TTL |
| **V** | 密码验证值（password verifier），由套件的 PDF 产生，**永不上网线** |
| **SID** | 会话 ID，`SHA-256(nonce_r ‖ nonce_i)` 的前 16 字节 |
| **gift** | manifest 中标记为「程序」的条目，用于把接收端程序本身送给对方 |

## 2. 套件层：密码学套件协商

### 2.1 为什么套件层必须独立存在

需求明确要求"以后可以加入更多加密方法"。如果加密算法写死在握手和分块流程里，每加一种算法就要改一遍流程代码，必然引入回归缺陷。

**因此：流程代码只调用套件接口，永不直接出现 `AES-GCM`、`PBKDF2` 等字样。**

### 2.2 套件 ID 命名规则

```
suite_id := "FLICKER/" 1*DIGIT
```

| suite_id | 状态 | 内容摘要 |
|---|---|---|
| `FLICKER/1` | **本规范定义，必须实现** | PBKDF2-SHA256/600k → HKDF-SHA256 → AES-256-GCM, 1 MiB chunks, SHA-256 |
| `FLICKER/2` | 预留：Argon2id | 见 §2.6 |
| `FLICKER/3` | 预留：ChaCha20-Poly1305 | 见 §2.6 |
| `FLICKER/4` | 预留：X25519 + SAS | 见 §2.6 |

编号**只增不复用**。即使某个套件被弃用，其编号也永久保留，防止老实现误认。

### 2.3 套件接口（实现必须提供这 7 个成员）

任何套件对象必须完整暴露以下成员。**字段名是本规范的一部分**，实现内部命名可不同，但套件注册表的键名必须一致。

| 成员 | 类型 | 作用 |
|---|---|---|
| `id` | string | 套件标识，如 `"FLICKER/1"` |
| `pdf` | 函数 | **Password Derivation Function**：`(password: string, salt: bytes) → V: bytes` |
| `kdf` | 函数 | **Key Derivation Function**：`(V: bytes, label: string) → key: bytes` |
| `aead` | 对象 | **AEAD**：`{ seal(key, iv, plaintext, aad) → ciphertext‖tag, open(key, iv, ciphertext‖tag, aad) → plaintext }` |
| `hash` | 对象 | **哈希**：`{ digest(bytes) → bytes }`，用于清单校验与分块完整性 |
| `chunkSize` | 整数 | 明文分块字节数 |
| `tagSize` | 整数 | AEAD 认证标签字节数 |

另有三个由协议固定、**不属于套件**的量（所有套件共用，因为它们是线格式的一部分）：

| 量 | 值 | 原因 |
|---|---|---|
| `SALT_LEN` | 16 | 线格式字段长度 |
| `NONCE_LEN` | 32 | 线格式字段长度 |
| `IV_LEN` | 12 | GCM 要求；其他 AEAD 若不同则由套件覆盖（见 §2.4 注） |

> **注**：`IV_LEN` 允许套件覆盖。若某套件的 AEAD 使用 24 字节 nonce（如 XChaCha20），该套件须在自身定义中声明 `ivLen`，L5 的 IV 派生按套件声明执行。**这是 `FLICKER/1` 唯一允许套件改变的线格式细节**，其余线格式对所有套件统一。

### 2.4 `FLICKER/1` 完整参数

| 项 | 参数 | 值 |
|---|---|---|
| **PDF** | 算法 | `PBKDF2` |
| | 哈希 | `SHA-256` |
| | 迭代次数 | `600000` |
| | 盐长度 | `16` 字节（对每个会话随机生成） |
| | 输出长度 | `32` 字节 → 即 `V` |
| **KDF** | 算法 | `HKDF`（RFC 5869，extract-then-expand） |
| | 哈希 | `SHA-256` |
| | salt | **空**（空字节串，不是省略） |
| | IKM | `V`（32 字节） |
| | 输出长度 | `32` 字节 |
| | label `room` | `K_room = HKDF(V, "room")` |
| | label `auth` | `K_auth = HKDF(V, "auth")` |
| | label `enc` | `K_enc  = HKDF(V, "enc")` |
| **AEAD** | 算法 | `AES-256-GCM` |
| | 密钥 | `K_enc`（32 字节，即 AES-256） |
| | IV 长度 | `12` 字节 |
| | 标签长度 | `16` 字节 |
| | 分块明文长度 | `1048576` 字节（1 MiB） |
| **完整性** | 哈希 | `SHA-256` |
| | 用途 | 文件级校验（`files[].sha256`）、分块级逐块指纹（`files[].chunkHashes`） |
| **会话 ID** | `SID` | `SHA-256(nonce_r ‖ nonce_i)` 的前 `16` 字节 |

> **待验证**：`PBKDF2` 迭代 600000 在低端手机浏览器上的耗时。若超过 2 秒，需要在 UI 上给出明确等待提示，而不是降低迭代次数。（候选实测目标：Android 中端机 Chrome）

#### 2.4.1 `label` 的精确定义（防止实现分歧）

```
label "room"  := 字节序列 72 6F 6F 6D        （ASCII "room"，4 字节）
label "auth"  := 字节序列 61 75 74 68        （ASCII "auth"，4 字节）
label "enc"   := 字节序列 65 6E 63           （ASCII "enc"，3 字节）

K_room = HKDF-Expand(HKDF-Extract(salt = "", IKM = V), info = "room", L = 32)
```

**注意**：HKDF 的 `salt` 为**空**，而 `info` 为上述 label。不要把 label 放进 salt，不要把盐 `S` 放进 HKDF —— `S` 已经通过 PDF 影响 `V`，重复注入没有额外收益但会造成实现分歧。

#### 2.4.2 `room_name` 的定义

```
room_name := HEX(K_room)         // 64 个小写十六进制字符
```

`room_name` 是一个 **256 bit 的不可猜测字符串**。它直接作为 URL 路径段使用，relay **不解析其内容**，只当作不透明键（opaque key）。

**必须理解的性质**：`room_name` 是可被 relay 观察到的。但：
- 它由 `K_room` 派生，而 `K_room` 由 `V` 派生，而 `V` 由密码派生 —— **不知道密码就无法生成它**
- 它**不能**用于反推密码或任何子密钥（HKDF 是单向的，且三个 label 的输出互不相关）
- 它的唯一作用是让"密码相同的双方落在同一个信箱"

> 因此 relay 学到的是：「某个 64 位十六进制字符串对应的信箱里，今天有两条消息」。仅此而已。

### 2.5 协商流程

```
        发起方 A                                     接收方 B
           │                                            │
           │  ← 从链接/页面读出可用的 suite_id 列表        │
           │                                            │
     A 把自己的支持列表编码进链接的 fragment 或 L0 页面
           │                                            │
           │  ① A 在 HELLO 里携带 suites: [S_a1, S_a2…]  │
           │ ─────────────────────────────────────────> │
           │                                            │  ② B 与自身列表求交
           │                                            │     取 B 列表中最靠前的共同项
           │  ③ AUTH_REQ 携带 suite: <协商结果>           │
           │ <───────────────────────────────────────── │
           │                                            │
           │  ④ A 校验：该 suite 必须在 A 的列表内         │
           │     否则发 ERROR(E_SUITE_REJECTED) 并中止    │
```

**选强规则（必须严格实现，否则会出现双方选不同套件的静默失败）**：

- 每个实现的套件列表**按强度降序排列**（最新最强在前）
- **接收方（Responder）做决定**：遍历自身的列表，取第一个同时出现在发起方 `HELLO.suites` 中的套件
- **发起方只校验不选择**：若接收方选出的套件不在 `HELLO.suites` 中，发起方必须中止
- 结果写入会话的 `suite_id`，此后**所有** PDF/KDF/AEAD/hash/chunkSize 都取该套件

### 2.6 版本降级规则（关键）

> **新版本遇到旧版本必须自动降级，不得报错。**

| 情形 | 必须的行为 |
|---|---|
| 双方唯一共同套件是 `FLICKER/1` | 正常使用 `FLICKER/1`，**不得**因为"我支持更好的"而拒绝 |
| 发起方只有 `FLICKER/1`，接收方有 `FLICKER/1,2,3` | 选 `FLICKER/1` |
| 双方**没有任何**共同套件 | 发 `ERROR(E_NO_COMMON_SUITE)`，在 UI 上明确提示"双方程序版本差距过大，请任一方升级"，**不要**提示密码错误 |
| 收到不认识的**消息类型** | 忽略该消息并继续（§0.1） |
| 收到不认识的**字段** | 忽略该字段并继续 |
| 收到**更高**的 `protocol` 版本号 | 按已知字段尽力解析；若缺少必需字段则发 `ERROR(E_PROTOCOL_TOO_NEW)` |

**反降级攻击的取舍（2026-10 已实现，见 §4.5.1）**：上述规则允许中间人（relay）把 `HELLO.suites` 削成只剩 `FLICKER/1`，从而迫使双方使用较弱套件。

- 在 `FLICKER/1` 是唯一套件时，此攻击无意义（本来就只有它）
- 引入 `FLICKER/2` 之后，若要防降级，必须在**已认证的 MAC 中绑定 `suite_id`**：`MAC_r = HMAC(K_auth, suite_id ‖ role ‖ nonce)`（细节见 §4.5.1）。因此：
  - 中间人改 `HELLO.suites` → 双方选的 `suite_id` 不同 → **MAC 校验必然失败** → 攻击被检测到
  - 这就是为什么 `suite_id` 必须进 MAC，而不是"商量好就行"
- 与 0.1.0 的**兼容**靠"两种具名构造 + 回执"解决：新对端用绑定的构造；老对端（不回执）
  按旧字节继续并**明确告警**；而"我报了新版、对方却回执旧版"**直接中止** —— 见 §4.5.1

### 2.7 未来如何新增套件（只加对象，不改流程）

新增套件 = 新增一个满足 §2.3 接口的对象 + 在注册表登记 + 在列表里按强度排序。**L4/L5/L6 的代码一行不动**。

| 计划套件 | 需要改的 | 已知障碍 |
|---|---|---|
| **`FLICKER/2`：Argon2id** 替代 PBKDF2 | 只换 `pdf` 成员 | WebCrypto **不提供** Argon2，需 WASM 或纯 JS 实现。体积换安全性 → 作为可选套件，默认不启用（待验证：WASM 体积对接收端首屏的影响） |
| **`FLICKER/3`：ChaCha20-Poly1305** | 换 `aead` 成员 | WebCrypto **不支持** ChaCha20-Poly1305，同样需 WASM。在无 AES 硬件加速的设备上更快 |
| **`FLICKER/4`：X25519 + 短认证串（SAS）** | 换 `kdf` + 在握手里增加密钥交换消息 | 可防御"relay 篡改握手"。需要在 UI 上显示 6 位数字供双方核对。**这是唯一需要新增握手消息的演进**（新增不是修改，符合 §0.1） |
| **后量子（ML-KEM 等）** | 取决于最终形态 | 等 WebCrypto/Node 提供稳定原生实现后再评估；套件接口已留好位置 |

**注册表形态（实现约束）**：

```
SUITES = [ flicker1, flicker3, flicker2, flicker4 ]   // 顺序 = 强度降序
```

新套件插入正确位置即自动参与协商，无需改动任何流程分支。

## 3. 会合层（Rendezvous）

> ### ⚠️ 先说清楚这一章与已实现的中继有什么关系（否则会读错）
>
> 本文件有**两条跨网络的路**，它们的差别是"数据走不走中继"：
>
> | | §3 会合层（本章） | §3R 中继转发（[`中继部署.md`](中继部署.md)） |
> |---|---|---|
> | 中继的角色 | 只牵线，牵完**退出数据路径** | **转发全部数据**（密文） |
> | 数据路径 | 接收端直连发送端 | 两端各自连中继 |
> | 前提 | 发送端有接收端够得着的地址 | 无（只要能连上中继） |
> | 现状 | **协议保留；中继侧端点与客户端都未实现**（见下） | ✅ **实际使用的跨网络方案** |
>
> ⚠️ **本章是设计，不是可以照做的实现说明（2026-10 核对）。**
> 原文写的是"协议完整保留，代码也保留" —— 后半句不成立：
>
> - 代码里**没有任何东西提供本章的 `/room/{room_name}` 端点**（中继只实现了 §3R 的 `/r/:room/*`）
> - 客户端也没有接入会合模式；能跑的两条路是**局域网直连**（§3.6）与**中继转发**（§3R）
>
> 保留这一章的理由：它是一条**完整设计过**的路（中继只牵线、数据不经手），
> 一旦哪天发送端有了公网地址就能用上；而且它把"中继能看到什么"的上限讲清楚了。
> 但**照本章写客户端会连不上任何东西** —— 实现请以 §3R、§4、§5、§6 为准。
>
> **为什么实际用的是中继转发**：会合模式要求发送端有一个"对方够得着"的地址
> （公网 IPv6 / 同网段 / 端口转发）。本机实测三条全不满足（CGNAT + 无全局 IPv6），
> 于是"牵线之后直连"无线可牵。详见 `设计文档.md` 第二·补章与 `路线图.md`。
>
> 所以本章的"**文件数据从不经过 relay**"是**会合模式内部**的约束，成立且有测试盯着；
> 但它**不是整个程序对外承诺的全部** —— 在中继转发模式下，中继确实经手密文。
> 完整、准确的"中继能看到什么"见 [`中继部署.md`](中继部署.md) §三。

### 3.1 职责边界（必须严格遵守）

| relay **做** | relay **绝不做** |
|---|---|
| 按 `room_name` 存储并转发**不透明消息** | 不解析消息内容 |
| 长轮询（long-poll）返回新消息 | 不接触任何文件数据（**会合模式内：文件数据从不经过 relay**） |
| TTL 到期自动删除房间 | 不写磁盘、不需要数据库 |
| 支持主动删除（用完即焚） | 不需要登录、不需要账号 |

**"文件数据永不经过 relay"是本节（会合模式）的协议级约束**：L1 的消息类型集合被**封闭枚举**（§3.5），其中没有任何一种能承载文件内容。任何扩展都不得新增"传递文件块"的消息类型。

> 中继转发模式走的是**另一组端点**（`/r/:room/*`），它搬运的是密文分块，
> 与本章的 L1 会合消息类型集合**互不相干**（各自的解析器独立、字节格式不同）。
> 不要因为"§3.5 里没有文件块类型"就以为中继转发不存在 —— 它不在这一章里。

### 3.2 消息格式（线格式）

所有会合消息是 **UTF-8 编码的 JSON 对象**，`Content-Type: application/json`。

```json
{
  "v": 1,
  "type": "HELLO",
  "seq": 1,
  "from": "i",
  "ts": 1765500000000,
  "body": { }
}
```

| 字段 | 类型 | 必需 | 说明 |
|---|---|---|---|
| `v` | number | 是 | 会合层消息格式版本，`FLICKER/1` 固定为 `1` |
| `type` | string | 是 | 消息类型，见 §3.5 |
| `seq` | number | 是 | 发送方自增序号，从 `1` 开始。用于去重，不用于排序 |
| `from` | string | 是 | `"i"` = 发起方（Initiator），`"r"` = 接收方（Responder） |
| `ts` | number | 是 | 发送时刻的 Unix 毫秒时间戳（仅供参考，**不得用于安全判断**） |
| `body` | object | 是 | 类型相关的载荷，见 §3.5 |

**中继回执（receipt）格式** —— relay 返回给拉取方时**额外包裹**一层：

```json
{
  "cursor": 7,
  "msg": { "v": 1, "type": "HELLO", "seq": 1, "from": "i", "ts": 1765500000000, "body": { } }
}
```

| 字段 | 说明 |
|---|---|
| `cursor` | relay 分配的**单调递增**整数，从 `1` 开始，每个房间独立计数 |
| `msg` | 原始消息，**逐字节不改** |

**关键**：`cursor` 由 relay 分配，**不来自 `seq`**。这样即使发送方重发同一 `seq`，拉取方也能靠 `cursor` 区分"这是新到的还是重复的"，而用 `(from, seq)` 做去重。

### 3.3 HTTP 端点

Base URL 记为 `<relay>`（例如 `https://flicker.example.workers.dev`）。

| 方法 | 路径 | 作用 | 成功状态码 |
|---|---|---|---|
| `POST` | `/room/{room_name}` | 向房间投递一条消息（**发起方**的首次投递兼有创建语义，见 §3.3.1） | `202 Accepted` |
| `GET` | `/room/{room_name}?cursor=N` | 长轮询拉取 `cursor > N` 的消息 | `200 OK`（有消息）/ `204 No Content`（超时无消息） |
| `DELETE` | `/room/{room_name}` | 立即销毁房间 | `204 No Content` |
| `GET` | `/healthz` | 健康检查 | `200 OK` |

**没有独立的"创建房间"端点**：房间在**发起方的首次 `POST`** 时隐式创建。这个设计减少了一次往返，代价是创建规则依赖消息体的 `from` 字段（见 §3.3.1）。

**路径变量**：`{room_name}` = 64 个 `[0-9a-f]` 字符（§2.4.2）。relay **必须**校验该正则，不匹配则返回 `400`。

#### 3.3.1 `POST /room/{room_name}`

```
请求头:  Content-Type: application/json
请求体:  一条会合消息（§3.2），UTF-8
响应:    202 Accepted，体为 { "cursor": 12 }
```

| 错误 | 状态码 | 说明 |
|---|---|---|
| 房间从未创建 | `404` | 投递方应发 `ERROR(E_ROOM_GONE)` 并在 UI 告知"会话已超时，请重新发起" |
| 房间已过期或已销毁 | `404` | 同一个状态码，但含意不同（销毁是**终态**，见 §3.3.3）。投递方处理方式与上一行相同 |
| 接收方向不存在的房间投递 | `404` | **接收方永不创建房间**（否则陌生人可以用任意 `room_name` 灌数据）。只有发起方的首次投递具有创建语义，见下 |
| 体过大 | `413` | 超过 8 KiB 上限 |
| 房间消息数达上限 | `429` + `Retry-After` | 上限 100 条 |
| 格式非法 | `400` | JSON 解析失败或缺必需字段 |

**房间的创建时机（必须明确，否则会歧义）**：

```
发起方启动 →  首次 POST /room/{rn}  →  relay 发现房间不存在，则**创建**并投递
              （此后 DELETE 过的房间不再自动创建 —— §3.3.3 的"销毁是终态"优先）

接收方 POST /room/{rn}  →  若房间不存在，返回 404
              （接收方永不创建房间，防止陌生人用任意 room_name 灌数据）
```

> 判据是**投递方的角色**：`from: "i"` 的首次 `POST` 具有创建语义；`from: "r"` 的 `POST` 不创建。实现时按消息体的 `from` 字段区分。
>
> ✅ **已实测核查（2026-10），原推理有错，且顺带修掉一个自身缺陷。**
>
> 原文写的是：「房间名是 256 bit 不可猜测的，所以实际风险为零 —— 想抢占就必须先知道密码。」
> **这句话的推理不成立**：房间名确实不可*猜测*，但它**就在链接里**（64 hex）。
> 拿到链接、没拿到密码的人不需要猜 —— 而"链接和密码分开告诉对方"正是本产品的用法。
>
> 实测（`_lab/probe-relay-preempt.mjs`，用真实的 `RelayClient` + 本地中继）：
>
> | 情形 | 房间状态 | 旧行为 | 现在 |
> |---|---|---|---|
> | 攻击者建房间并占住 `seq 0` | `nextSeq=1`，全是垃圾 | 发送端**静默跳过清单** → 接收端解密失败 | 明确报 `ROOM_TAKEN`，并告诉用户重新启动 |
> | **创建响应在回程丢了**（无攻击者） | `nextSeq=0`，空房间 | 发送端**静默跳过清单** → 接收端等 2 分钟超时 | 补投清单，传输照常 |
>
> 第二行不是安全问题，是个**可靠性缺陷**：旧实现在 `open()` 里只判断
> `created.created`，为假就认为"房间已就绪"而跳过投递。可是"房间已存在"有**两种**
> 完全相反的含义 —— ①自己刚建的（响应丢了，房间是空的）②别人抢先占了（房间里有东西）。
> 触发条件很平常：初始 `POST` 的响应在回程丢了。而用户此时已经把链接发出去了。
>
> **现在的判据是"房间里有没有东西"**，见 `src/relay/client.js` 的 `open()`：
> `nextSeq === 0` → 情况 ①（补投清单）；`nextSeq > 0` → 情况 ②（报 `ROOM_TAKEN`，中止）。
> `ROOM_TAKEN` 不在可重试名单里 —— 重试一万次房间也还是别人的，只会让用户白等四轮退避。
>
> **残留的、已被接受的限制**：拿到链接的人仍然可以让这次会话开不起来（拒绝服务）。
> 不打算再堵，因为它要求攻击者先拿到链接，而链接本来就是凭据；
> 真正拿到**密码**的人根本不需要 DoS —— 他能直接解密全部内容。
> 现在的改进是"失败得明确且可指导"，而不是"不可能失败"。


#### 3.3.2 `GET /room/{room_name}?cursor=N`

**必须实现长轮询**，而不是立即返回空：

- relay 收到请求后，若 `cursor` 之后没有消息，**挂起最多 25000 ms**
- 期间有新消息 → 立即返回 `200` + 消息数组
- 25000 ms 内无消息 → 返回 `204 No Content`，客户端**立即重新发起**同一请求
- 响应体为 receipt **数组**（可有 0 到多条）：

```json
[ { "cursor": 1, "msg": { } }, { "cursor": 2, "msg": { } } ]
```

- 客户端 `cursor` 初值为 `0`（拉取房间内全部消息）
- 客户端**必须**按 `cursor` 升序处理，并用 `(from, seq)` 去重

> **待验证**：Cloudflare Workers 的 HTTP 请求是否有单请求 wall-clock 上限会截断 25 秒长轮询（免费版 CPU 时间限制与 wall-clock 等待是两回事，但需要实测确认挂起 25 秒不会被平台提前断开）。若会被断开，把挂起上限降为实测安全值，并保持"客户端收到 `204` 立即重试"的语义不变。

#### 3.3.3 `DELETE /room/{room_name}`

正常传输结束后由发起方调用，语义为**立即销毁**：

- 删除全部消息与房间状态
- 幂等：房间不存在也返回 `204`
- **销毁是终态**：之后对同一 `room_name` 的 `POST` 返回 `404`，**不得**自动重建房间

> 这条规则很重要：它保证"用完即焚"不会被"后续请求自动重建"悄悄破坏。

### 3.4 房间生命周期与限额

| 参数 | 值 | 说明 |
|---|---|---|
| `ROOM_TTL` | `900000` ms（15 分钟） | 自**最后一次** `POST` 或 `GET` 起算 |
| `ROOM_MAX_MSGS` | `100` | 超过则 `429` |
| `ROOM_MAX_BODY` | `8192` 字节 | 单条消息上限 |
| `GET_HOLD` | `25000` ms | 长轮询挂起上限 |
| 速率限制 | 每 IP 60 次/分钟（`GET`）、20 次/分钟（`POST`） | 超出返回 `429` + `Retry-After`（**待验证**：具体阈值需按 Worker 平台能力调整） |

**TTL 与"用完即销毁"的关系**：TTL 是**兜底**，不是正常路径。正常路径是发起方在传输结束后主动 `DELETE`。TTL 只用于处理"对方再也没来"或"进程被强杀"的情况。

### 3.5 消息类型枚举（封闭集合）

`FLICKER/1` 定义以下 7 种类型。**这是封闭集合**，任何实现**不得**新增承载文件内容的类型。

| `type` | 方向 | 用途 | 关键 `body` 字段 |
|---|---|---|---|
| `HELLO` | 双向 | 宣告存在、角色、套件列表 | `suites[]`, `token?`, `endpoints[]?` |
| `AUTH_REQ` | 接收方 → 发起方 | 挑战 + 选定套件 | `suite`, `nonce_r`, `mac_r` |
| `AUTH_OK` | 发起方 → 接收方 | 应答 + 会话确认 | `nonce_i`, `sid`, `mac_i` |
| `ENDPOINT` | 发起方 → 接收方 | 告知如何直连发起方 | `urls[]`, `expires_in` |
| `READY` | 接收方 → 发起方 | 已连上传输层，请求开始 | `transport`, `resume_at?` |
| `ERROR` | 双向 | 错误通知 | `code`, `detail?`, `fatal` |
| `BYE` | 双向 | 正常结束，可以销毁房间 | `reason` |

#### 3.5.1 `HELLO`

```json
{
  "suites": ["FLICKER/3", "FLICKER/1"],
  "token": "7f3a9c1e4b8d2a60",
  "endpoints": ["https://192.168.1.5:8443"],
  "agent": "flicker/0.1.0 node24 win32"
}
```

| 字段 | 必需 | 说明 |
|---|---|---|
| `suites` | 是 | **强度降序**的套件列表 |
| `token` | 否 | 一次性访问令牌。仅当 L0 由 relay 托管接收页时需要（§4.4.2） |
| `endpoints` | 否 | 发起方的可达地址候选。仅会合模式使用（§3.6） |
| `agent` | 否 | 实现标识，纯诊断用途。**接收方不得据此改变行为** |

#### 3.5.2 `ENDPOINT`

```json
{
  "urls": ["https://192.168.1.5:8443", "https://[2408:...]:8443"],
  "expires_in": 600
}
```

| 字段 | 必需 | 说明 |
|---|---|---|
| `urls` | 是 | 按**可达性优先级降序**排列（公网 IPv6 → 局域网 → 公网 IPv4:port） |
| `expires_in` | 是 | 秒。接收方在此之后不应再尝试 |

接收方**按顺序逐个尝试** `urls`，第一个 TLS 握手成功且 `GET /session` 返回 200 的胜出。全部失败 → `ERROR(E_NO_ROUTE)`，并在 UI 上给出可操作建议（改局域网 / 做端口转发）。

#### 3.5.3 `ERROR`

```json
{ "code": "E_MAC_MISMATCH", "detail": "attempt 2 of 5", "fatal": false }
```

| 字段 | 必需 | 说明 |
|---|---|---|
| `code` | 是 | 见 §8 错误码表 |
| `detail` | 否 | 人类可读补充，**不得包含密码、密钥、文件内容或文件名** |
| `fatal` | 是 | `true` = 会话立即销毁；`false` = 可重试 |

> **`detail` 的脱敏是硬要求**。relay 与浏览器控制台都可能记录它。

### 3.6 无 relay 的直连模式（局域网 / 端口转发）

会合层是**可选**的。当接收方已经能直接访问发起方时，**L1 整体跳过**：

```
直连模式：
  接收方 ──GET /session──> 发起方 HTTPS 服务     （代替 HELLO，直接拿到 salt/suites/sid）
  接收方 ──POST /auth───> 发起方                 （代替 AUTH_REQ）
  接收方 <── 200 + nonce_i, mac_i ── 发起方       （代替 AUTH_OK）
  接收方 ──GET /chunk───> 发起方                 （L5 数据面）
```

**协议层面必须满足的一致性要求**：直连模式的**握手载荷字段与会合模式完全相同**（同样的 `suite`、`nonce_r`、`mac_r`、`nonce_i`、`sid`、`mac_i`），只是承载在 HTTP 请求/响应体里而不是 relay 消息里。这样：

- 同一套 `lib/handshake.js` 可用于两种模式
- 加入 relay 不需要新写密码学代码
- 测试可以只测一种承载，另一种自动被覆盖

| 模式 | 触发条件 | 是否需要 relay | 数据面 |
|---|---|---|---|
| **LAN 直连** | 双方同网段（发送端打印局域网地址） | 否 | `https-chunk` 直连 |
| **端口转发 / 公网 IPv6** | 发起方有可达公网地址 | 否 | `https-chunk` 直连 |
| **会合（relay）** | 上两者都不可达 | **是** | `https-chunk` 直连（地址由 relay 告知） |

> 注意最后一行：**即使使用 relay，数据面仍然是直连。** relay 的作用仅仅是"让双方知道对方地址"，它从不进入数据路径（§3.1）。

### 3.7 站点本地界面端点（明确不在本协议范围内）

站点模型下，程序会在 `127.0.0.1` 上再起一个**本地界面服务**（供 GUI 前端使用，见 `架构决策.md` §2.2 方案 C）。

**本协议不规定它的任何行为。** 理由：

- 它只服务本机浏览器，不跨机器通信，因此**不存在互通问题**，定义它没有价值
- 它可能随界面需求频繁变化，把它写进协议只会制造无意义的兼容负担
- 它与数据面是**两个独立的 HTTPS 服务**，端口、生命周期、证书策略都不同

**唯一的协议级要求**：本地界面服务**必须只监听 `127.0.0.1`**（或 `::1`），不得监听 `0.0.0.0`。否则同网段的任何人都能访问站点界面 —— 那是重大安全缺陷。这条要求之所以写进协议，是因为它一旦写错，影响的是整个会话的安全性，而不只是一个界面的可用性。

> ✅ **已验证（2026-10）**：`架构决策.md` §2.3 要求的"浏览器探测 + 显式降级 + 诚实告知"
> 在接收页里已经落实，而且按 §2.3 的原则做到了"**能力检测优先于 UA 判断**"：
>
> | 要求 | 实现 |
> |---|---|
> | 不猜浏览器名字，实测 API | `const CAN_STREAM = typeof window.showSaveFilePicker === 'function'` |
> | 能力不足时**醒目提示**，而不是默默失败 | 探测失败时在**密码屏**插入一条 `note warn` 横幅（不是等传失败了才说） |
> | 说清后果与建议 | 文案 `recv.go.noStreamWarn`：不支持流式写盘 → 超过约 1 GB 可能失败 → 建议用 Edge/Chrome |
> | 大文件再补一刀 | `total > 900 MB` 时把说明换成 `recv.go.bigWarn`（带具体体积） |
>
> 用例见 `test/protocol-facts.test.js`（断言探测方式、横幅位置、文案键，以及"不许用 UA 判断"）。

## 3R. 中继转发层（实际使用的跨网络方案）

> 这一章记录**已实现并实测通过**的跨网络传输。完整部署说明见
> [`中继部署.md`](中继部署.md)；这里是协议级定义。

### 3R.1 为什么需要它

会合模式（§3）要求发送端有一个接收端够得着的地址。本机实测三条全不满足
（CGNAT + 无全局 IPv6），所以数据**继续走中继**。
代价是中继承担全部带宽；收益是**不依赖任何打洞成功率**。

### 3R.2 端点

```
POST   /r/:room              创建房间（幂等）
POST   /r/:room?seq=N        放入第 N 条消息（逐条；seq 由调用方指定）
POST   /r/:room/batch        放入一批消息（seq 由**服务端**按到达顺序分配）
GET    /r/:room?seq=N        取走第 N 条消息（不删除）
POST   /r/:room/ack?upTo=N   前缀确认并删除
GET    /r/:room              房间状态
DELETE /r/:room              销毁房间
GET    /health               健康检查 + **能力声明**（无副作用，就绪探测用）
```

房间号 `:room` = **64 位十六进制**（128 bit），由密码经 HKDF 派生
（`HKDF(V, "flicker/1/room")`）。它只出现在链接的 `#` 之后，
**浏览器不会把 fragment 发给服务器**。知道房间名 ≡ 知道密码，
所以中继不需要第二套授权机制（早先的"授权密钥登记"方案有个先到先得的竞态，已废弃）。

### 3R.3 消息格式

房间搬运不透明字节，第一个字节是类型标记：

```
0x01 + salt(16) + iv(12) + tag(16) + 密文     清单（salt 与加密清单一起放）
0x02 + tag(16) + 密文                          一个文件分块
```

`/batch` 的请求体是若干条消息按顺序拼接，每条前加 **4 字节大端长度**：

```
[4B len][msg][4B len][msg]...
```

一批最多 64 条；单条上限见下面「块大小与能力协商」。

**块大小与能力协商（2026-10 新增，向后兼容）**

一条消息就是一个文件分块，所以"单条消息上限"就等于"**最大的块**"。
这个上限**不是协议常量**：中继可以收得更大，但必须**声明**自己的上限，
发送端据此选块大小。

| 位置 | 字段 | 说明 |
|---|---|---|
| `GET /health` | `maxMessageBytes` | 中继接受的最大单条消息（字节）。同时含 `ok: true`、`protocol: 1` |
| `POST /r/:room`（不带 `seq`，创建/幂等） | `maxMessageBytes` | 同一个值，随创建响应一起给（发送端一定会走这一步，不必多发请求） |

规则：

1. **协议保证的最小值**是 `1 MiB + 17`（块 1 MiB + 类型字节 + 16 字节认证标签）。
   任何符合本规范的中继都必须收得下这个大小的消息。
2. 中继**可以**声明更大的值；本项目的部署默认是 `2 MiB + 17`
   （实测：往返 195 ms、链路 29.5 MB/s 时，块 1 MiB 端到端 18.9 MB/s、
   2 MiB 是 26.3 MB/s、4 MiB 没有额外收益）。
3. 发送端取 `min(它想要的块大小, 对方声明的上限 − 17)`，
   并夹在 `[64 KiB, 8 MiB]` 之内。
4. **读不到这个字段时（老中继、非 JSON 响应、探测失败）一律按 `1 MiB + 17` 走。**
   这条是硬要求：它保证"升级客户端"不会把已部署的老中继打死（否则会被 413 拒收）。
5. 接收端不需要参与协商 —— 块大小写在清单的 `files[].chunkBytes` 里，
   它按清单解密即可（IV 只由块号派生，AAD 只绑文件下标、块号、总块数与明文长度，
   **都与块大小无关**）。

一批最多 64 条。

### 3R.4 投递模型：拉取式 + 在途窗口

```
seq 0        清单 —— 房间建立时放入
seq 1..N     分块 —— 按窗口投递，默认窗口 8
```

**为什么"一批一次 POST"而不是"并发发 N 条 `?seq=N`"**：
中继要求严格按序投递，并发请求的到达顺序不保证，必然撞 `409 BAD_SEQ`；
而且服务端给所有撞车请求报的是**同一个**期望序号，它们重试时又撞在一起。
让服务端在一批内依次分配序号，是"严格按序"与"高吞吐"共存的唯一干净解法。

**窗口的意义**：窗口 1 就是停等，吞吐被死锁在 `块大小 ÷ 往返延迟`。
实测 195 ms 下 4.72 MB/s，改成窗口 8 + 批量投递后 **20.75 MB/s（4.4×）**。
`--window 1` 可退回停等。代价：中继上最多同时存在 8 MiB 在途密文。

### 3R.5 四条判据（都是踩过坑才定下来的）

| 判据 | 违反它会怎样 |
|---|---|
| 待投递序号以服务端 `nextSeq` 为准，不用本地计数 | 本地计数与服务端不一致时报"序号不连续" |
| `ack` 是**前缀删除**，删后**不重新编号** | 早先删前缀后重新编号，接收端记的序号全部错位 |
| 完成判据是 `ackedBase >= total`，不是 `posted >= total && pending === 0` | 接收端取走最后一条但还没 ack 时会误报完成并销毁房间 —— 那条数据永远拿不到 |
| **销毁前等在途的那一批投递结束** | `putBatch` 在 `await` 读分块期间会让出控制权（它不是原子的）。此刻若用户点"取消"，DELETE 会**先于**那条 batch POST 到达服务端：房间被删、随后那条 POST 拿到 404，一次**正常取消**被报成中继错误。修法：`destroy()` 先把在飞的那一批等完再删房间，投递循环每一轮重新问一次中止判据 |

> 第四条是端到端测试用**精确的顺序断言**抓出来的 —— 靠读代码看不出来，
> 因为每一行单独看都是对的。

### 3R.6 "用完即销毁"在中继上的落点

| 时机 | 发生什么 |
|---|---|
| 每条消息被 ack | 中继立刻删除它（前缀删除） |
| 传输完成 | 发送端 `DELETE /r/:room` |
| 15 分钟无活动 | 房间整体过期（TTL 兜底） |
| 中继进程重启 | 所有房间消失（**消息只在内存里，不写磁盘**） |

`test/relay-protocol.test.js` 会检查 `relay/worker.js` 里没有 KV / D1 / R2 /
Durable Objects —— 有人加持久化设施就会失败，提醒他重新审视这个承诺。

## 4. 会话层（Handshake）

### 4.1 前置条件与输入

| 输入 | 来源 | 说明 |
|---|---|---|
| 密码 `P` | 发起方终端输入；接收方页面输入 | 双方必须完全一致（区分大小写与空格） |
| 盐 `S` | 发起方随机生成（16 字节） | 必须传递给接收方：嵌入链接 fragment，或由 `GET /session` 返回 |
| `suite_id` | §2.5 协商结果 | |
| `suite.protocol` | 常量 `"FLICKER/1"` | 进 MAC 的域分隔前缀 |

### 4.2 密钥派生（两阶段）

```
阶段 1（昂贵，只做一次）：
    V = suite.pdf(P, S)                       // FLICKER/1: PBKDF2-SHA256, 600000 轮, 32 字节

阶段 2（廉价，从 V 派生三把互不相关的钥匙）：
    K_room = suite.kdf(V, "room")             // 房间名，永不当密钥用于加密
    K_auth = suite.kdf(V, "auth")             // 握手 MAC
    K_enc  = suite.kdf(V, "enc")              // 文件加密（作为 K_job 的输入）

    // 会话级密钥（握手完成后，见 §4.5）
    K_job  = HKDF-Expand(HKDF-Extract(salt = "", IKM = K_enc), info = SID, L = 32)
```

**为什么有 `K_job`**：`K_enc` 由密码派生，因此**同一对密码 + 同一 `S`**（几乎不会发生，但理论上可能被强制构造）会得到同一把密钥。把 `SID` 绑进 `K_job` 确保**每个会话的加密密钥唯一**，彻底排除跨会话重放。`K_job` 是实际用于分块加密的密钥；`K_enc` 只作为它的输入。

**为什么只有三把钥匙（一条被否决的设计）**：曾考虑额外派生一把 `K_aux = kdf(V, "aux")` 作为"预留给未来 SAS 用途"的第四把钥匙。**该设计被否决**，原因是一个死锁：

- 若 `K_aux` **不是**线格式的一部分（它不是 —— 它从不出现在线上），那么 `FLICKER/1` 的实现是否派生它，对互通**毫无影响**
- 因此"现在派生它"既不能强制未来实现也派生它，也不能阻止未来实现改用别的 label
- 结果是：它现在的唯一作用是在各自的进程里多算 32 字节，未来的套件仍须在自己的规范里重新定义它

**结论**：预留 label 是无效的保险。将来需要第四把钥匙时，由**新套件的规范**定义（例如 `FLICKER/4` 规定 `K_aux = kdf(V, "aux")`），由于套件协商已决定用哪个套件，老实现不会被牵连。这正是套件层存在的意义 —— **不需要靠"提前多做无用功"来买兼容性**。

> 这条记录在此，是为了防止后来者"好心"把 `K_aux` 加回来。

#### 4.3.1 MAC 的精确定义（逐字节）

```
MAC_RECV_DOMAIN = "flk1-recv"     // ASCII, 9 字节: 66 6C 6B 31 2D 72 65 63 76
MAC_SEND_DOMAIN = "flk1-send"     // ASCII, 9 字节
ROLE_RECV       = "recv"          // ASCII, 4 字节
ROLE_SEND       = "send"          // ASCII, 4 字节

mac_r = HMAC-SHA-256(
          key  = K_auth,
          data = MAC_RECV_DOMAIN ‖ suite_id_ascii ‖ ROLE_RECV ‖ nonce_r
        )

mac_i = HMAC-SHA-256(
          key  = K_auth,
          data = MAC_SEND_DOMAIN ‖ suite_id_ascii ‖ ROLE_SEND ‖ nonce_i ‖ SID
        )
```

| 组成 | 为什么必须有 |
|---|---|
| `MAC_*_DOMAIN` | **域分隔**。防止把 recv 方向的 MAC 重放到 send 方向（没有它，两个方向的 MAC 输入结构相同，只是 nonce 不同，会留下可乘之机） |
| `suite_id` | 绑定协商结果 → 使 §2.6 的降级攻击可被检测 |
| `ROLE_*` | 角色绑定。防止双向反射攻击 |
| `nonce_r` / `nonce_i` | 新鲜性。每次会话随机 → 抗重放 |
| `SID`（仅 `mac_i`） | 让发起方对"本次会话的最终标识"作出承诺。接收方在收到 `mac_i` 前就已经能算出 `SID`，因此可以校验 |

> **`nonce_i` 只出现在 `mac_i` 中，`nonce_i` 本身随 `AUTH_OK` 明文发送。** 这是安全的：`nonce_i` 不是秘密，它的作用是新鲜性。安全性来自 `K_auth`，而 `K_auth` 永不上线。

> ### ✅ 与实现的差异已处理（2026-10，见 §4.5.1）
>
> 上面那段是**设计意图**。实现从 2026-10 起用**两种具名构造**，细节与取舍见 §4.5.1：

>                     mac_i = HMAC(K_auth, "FLICKER/1\nsend\n" ‖ nonce_i)
> v1（兼容旧对端）：  mac_r = HMAC(K_auth, "flicker/1/recv\n" ‖ nonce_r)

> #### 4.5.1 握手 MAC 的两种构造与降级保护（2026-10 实现）
>
> **背景**：§2.6 要求"防降级靠把 `suite_id` 绑进被认证的材料"。但线上已经跑着只认
> 旧构造的实现（尤其是**中继托管的那份接收页**：老中继 = 老页面），直接改字节会让
> 所有老部署互相报"密码不一致"。所以做成两种具名构造 + **回执**：
>
> | 构造 | MAC 输入 | 用在哪 |
> |---|---|---|
> | `v2` | `utf8(suite_id ‖ "\n" ‖ role ‖ "\n")` ‖ nonce | 默认。套件 id 进被认证材料 |
> | `v1` | `utf8("flicker/1/" ‖ role ‖ "\n")` ‖ nonce | **0.1.0 发布时的字节**，只为与老对端互通 |
>
> **流程**（局域网模式的挑战—应答；`role` = `recv` / `send`）：
>
> 1. 发送端在 `/api/auth/start` 的响应里**报价**：`macProfiles: ["v2","v1"]`（新增可选字段）
> 2. 接收端挑第一个自己认识的构造，用它在 `/api/auth/finish` 里算 MAC，
>    并**如实回执** `macProfile`
> 3. 发送端按**回执的那套**构造校验，并用同一套构造回送自己的应答
>    （响应里也带 `macProfile`，接收端据此核对）
>
> **降级检测的判据**（TLS 的 downgrade sentinel 是同一个思路）：
>
> | 收到什么 | 发送端怎么做 |
> |---|---|
> | 回执 `v2` | 正常（用的是绑定构造） |
> | **没有回执** | 判定为**老对端**：按 `v1` 继续，但把 `macProfile='v1'` 记下来，**UI 明确告警**"本次防降级保护不成立" |
> | 回执 `v1`（而我报了 `v2`） | **中止**，`ERROR(E_DOWNGRADE)`，提示"协商被篡改，可能是中间人" —— **不得**退化成"密码错误" |
> | 回执别的值 | 中止（`BAD_PROFILE`）——不认识的一律拒绝，不许"尽力而为" |
>
> **这套保护管不到什么（必须写清，别当万能）**：
>
> - **中继模式下接收页由中继托管**。一个恶意中继可以直接换掉页面代码 ——
>   那时任何协议层保护都没有意义。这套机制挡的是"**诚实但版本不齐**的对端"
>   与**链路中间人**，不是"对端代码被换掉"。
> - 中继模式**没有挑战—应答**（房间名由密码派生、清单用会话密钥 AEAD），
>   所以那里没有 MAC 可绑。好消息是：套件不同 ⇒ KDF 标签不同 ⇒ **房间名不同** ⇒
>   接收端找不到房间 —— 套件在中继模式下是**隐式绑定**的。
> - 攻击者若能同时改两条报价，仍可让双方一致地选到弱套件（这需要同时控制双向链路
>   且不破坏 MAC —— 那已经超出"协商降级"的范围）。

### 4.4 盐 `S` 与令牌 `token` 的分发

`S` 必须让接收方拿到，但**不能**让 relay 之外的无关方拿到（虽然 `S` 泄露不致命，但会削弱抗预计算能力）。

#### 4.4.1 局域网 / 直连模式（首选）

`S` 由发起方在**连接内**提供：接收方 `GET /session` 的响应体里带 `salt`。链接本身只含地址与令牌：

```
https://192.168.1.5:8443/?k=7f3a9c1e4b8d2a60
```

#### 4.4.2 relay 托管页面模式

接收页由 relay 托管，因此 `S` 必须**随链接**到达（**不能**放在 relay 的 URL path 或 query 里 —— 那会被 Worker 日志记录）：

```
https://<relay>/#k=<房间名 64 hex>&s=<盐 32 hex>
              └─ URL fragment：浏览器不会把它发给服务器
```

| URL 片段 | 含义 |
|---|---|
| `k`（64 hex） | 房间名 —— 由密码派生，中继靠它找到房间 |
| `s`（32 hex） | 盐 `S`（16 字节） |

> **为什么用 fragment 而不是 query**：URL fragment（`#` 之后）**永远不会出现在 HTTP 请求里**，因此不会进入 relay 的访问日志。这是把 `S` 和 `token` 送到浏览器的唯一安全通道。
>
> ~~**待验证**：`token` 与 `S` 放在同一个 fragment 里意味着……~~
>
> ✅ **已验证（并且有测试守着）**：relay 托管页拿到 fragment 后**不把它写入任何持久化存储**。
> 页面上唯一会写存储的地方是语言偏好，而接收端用的是 `sessionStorage`（关标签即消失）。
> 见 `test/receiver-page.test.js` 的「链接里的凭据不会被写进任何存储（fragment 只读不存）」。
>
> 原疑问保留在此以便追溯：`token` 与 `S` 放在同一个 fragment 里意味着"拿到链接的人"
> 同时拿到两者 —— 这符合一次性令牌的定位（链接本身就是凭据），
> 但前提是页面绝不把它落盘，否则"一次性"凭据就变成了躺在磁盘上、能被翻出来的东西。

#### 4.4.3 一次性令牌 `token` 的语义

| 规则 | 说明 |
|---|---|
| 生成 | 发起方随机生成 **16 字节**，用 **base64url** 编码（22 个字符，进链接的 `?k=`） |
| 用途 | 让接收方（或 relay 托管页）向发起方证明"我是拿到链接的人" |
| 消费 | **首次 `GET /`（打开页面）**时作废；此后再访问返回 `410 TOKEN_USED`。`GET /api/session` **只校验、不消费** |
| 失败 | `token` 不符 → `403 TOKEN_INVALID`，且**不消耗**消费机会（防止猜测把合法用户挤掉） |

> ✅ **「同一连接上的后续请求不算新消费」这条例外已被删除（2026-10 实测核查）。**
>
> 它从来没有被实现过，而且**不应该**被实现：
>
> 1. **它要解决的问题不存在。** 原文给的理由是"避免断点续传被令牌卡住" ——
>    但续传用的是 **`SID`**，不是 `token`。`consumeToken()` 只在 `GET /`（页面本身）
>    这一处被调用（见 `src/server.js`），它从来不参与分块下载。
> 2. **它会让行为变得不确定。** 浏览器刷新时是否复用同一条 TCP 连接，取决于
>    keep-alive 的当前状态、代理、以及浏览器自己的策略 —— 于是"刷新后能不能继续"
>    会变成一个时灵时不灵的行为。**时灵时不灵比确定地失败更糟**：用户无法形成预期，
>    我们也没法写文档、没法写测试。
> 3. 实测确认现在是**确定的**：即使显式复用同一条 keep-alive 连接，
>    第二次 `GET /?k=…` 也一定返回 `410 TOKEN_USED`（见
>    `test/protocol-facts.test.js`）。而页面上本来就有"本页刷新后将无法再次访问"的提示
>    （`UI设计.md` §2.2 ④），`设计文档.md` §7 也写明了这一点。

### 4.5 会话 ID 与子密钥的最终定义

```
SID   = SHA-256(nonce_r ‖ nonce_i)[0 .. 16)          // 前 16 字节
K_job = HKDF-SHA-256(salt = "", IKM = K_enc, info = SID, L = 32)
```

| 量 | 长度 | 用途 |
|---|---|---|
| `SID` | 16 字节 | 会话标识；进入每个块的 AAD；进入 manifest |
| `K_job` | 32 字节 | **实际的分块加密密钥**（AES-256-GCM 的 key） |

**销毁要求**：`V`、`K_auth`、`K_enc`、`K_job`、`nonce_r`、`nonce_i` 全部在会话结束时 `fill(0)` 覆写（见 `设计文档.md` 第六章）。

### 4.6 失败处理

| 情形 | 行为 |
|---|---|
| `mac_r` 不符 | 发起方 `failCount++`；回 `ERROR(E_MAC_MISMATCH, fatal=false)`；**不**进入 L5 |
| `mac_i` 不符 | 接收方 `failCount++`；回 `ERROR(E_MAC_MISMATCH, fatal=false)`；**不**进入 L5 |
| `failCount >= 5` | 发起方发 `ERROR(E_TOO_MANY_FAILURES, fatal=true)`，**立即销毁会话**：清零全部密钥、关闭监听、`DELETE` 房间、进程退出 |
| 重放（同一 `nonce_r` 第二次出现） | 视为失败尝试，`failCount++`，回 `E_REPLAY_DETECTED` |
| 握手超时 | 收到 `AUTH_REQ` 后 **60 秒**内未完成 → `ERROR(E_HANDSHAKE_TIMEOUT, fatal=true)` |
| 会话总超时 | 从生成密码起 **600 秒**（10 分钟）→ 销毁 |

**握手阶段的额外延迟（强制）**：每次 `E_MAC_MISMATCH` 后，发起方在响应前**必须**等待

```
delay_ms = min(1000 * 2^(failCount-1), 8000)
```

即 1s、2s、4s、8s、8s。目的是让在线暴力枚举在 5 次机会内无法完成有意义的搜索量。

> **注意**：这个延迟只在**握手阶段**（`AUTH_REQ` 处理）生效，**不得**施加于 L5 的数据块请求，否则会严重影响正常吞吐。

### 4.7 直连模式的握手（字段完全一致）

直连模式下，会合层被跳过，但**握手载荷完全相同**：

| 会合模式 | 直连模式 |
|---|---|
| `POST /room/{rn}` 的 `HELLO` | `GET /session` 响应中的 `{sid?, suite, salt, suites, manifest_ct}` |
| `POST /room/{rn}` 的 `AUTH_REQ` | `POST /auth` 请求体：`{suite, nonce_r, mac_r}` |
| `POST /room/{rn}` 的 `AUTH_OK` | `POST /auth` 响应体：`{nonce_i, sid, mac_i}` |

**直连模式下 `GET /session` 的响应体**（**与实现一致，2026-10 核对过**）：

```json
{
  "suite": "FLICKER/1",
  "salt": "<BASE64, 16 字节>",
  "room": "<64 hex，房间标识；仅供日志与 UI 显示，不是 SID>",
  "manifest": { "iv": "<BASE64>", "ct": "<BASE64>", "tag": "<BASE64>" },
  "kdf": { "name": "PBKDF2-SHA256", "iterations": 600000 },
  "chunkBytes": 1048576
}
```

> ⚠️ **本节此前与实现不一致，已按实现改正（2026-10）。** 原文列的是
> `protocol` / `suites` / `session` / `manifest`（BASE64 字符串）/ `files` / `bytes`
> 六个字段，而实现发的是上面这六个。差异逐条说明，因为每一条都有原因：
>
> | 文档原字段 | 实现 | 原因 |
> |---|---|---|
> | `protocol` | 只有 `suite` | 两个字段说的是同一件事，留一个。协商用的版本号在 `suite` 里 |
> | `suites`（协商列表） | 无 | **没有实现套件协商**。`FLICKER/1` 是唯一套件，假装有协商列表只会让客户端写出多余的代码 |
> | `session`（16 hex，供显示） | `room` | 同一个用途，改了名字。`room` 同时用于中继模式的地址，一个名字两处通用 |
> | `manifest`（BASE64 字符串） | `{iv, ct, tag}` 对象 | 三样东西分开传，客户端不必再切分一段 base64。**中继模式的线上格式是拼在一起的**（salt‖iv‖tag‖ct，见 §3.2），那是为了少一次往返；直连模式没有这个约束 |
> | `files` / `bytes`（明文摘要） | **不发送** | 见下 |
> | — | `kdf` / `chunkBytes` | 客户端需要知道迭代次数与分块大小才能正确解密；这两样不是秘密 |
>
> #### 关于 `files` / `bytes`：不发送，比"要求先认证"更彻底
>
> 原文写着"`files` / `bytes` 是明文摘要，用于在**输入密码之前**就展示'对方想给你 3 个文件，
> 共 2.32 GB'"，并在下面标注待验证"未认证时返回明文摘要构成轻微信息泄露，
> 缓解手段是要求先提交 `token`"。
>
> **实现选择了第三条路：这两个字段根本不发。** 文件数量与总大小都在**加密的清单**里，
> 而清单的密钥由密码派生 —— 所以"拿到链接但没拿到密码"的人什么也看不到。
> 这比"先认证再给"更彻底，也正好符合 `使用手册.md` §10.4 对用户的承诺：
> 「只能看到一个要求输入密码的页面，**看不到任何文件信息** —— 连文件名和文件数量都看不到」。
>
> 代价是**密码输入页无法显示"共几个文件、多大"**（`UI设计.md` §2.2 ① 曾要求显示文件列表，
> 那条已按实现更正）。换取的是：链接被转发给无关的人时，对方连"这是几个文件"都不知道。
> 在这个产品里，"拿不到密码就什么都看不到"是承诺的核心，比"提前看到数量"更重要。
>
> ✅ **实测确认（2026-10）**：未认证时 `GET /session` 返回 `403 TOKEN_INVALID`，
> 响应体里**没有**任何摘要字段；即使令牌正确但没先打开页面，也一样是 403。
> 用例见 `test/protocol-facts.test.js`。

## 5. 数据面（分块 / IV / AAD / 续传 / 背压）

### 5.1 `seq` 的定义（64 bit 单一整数）

```c
seq = (fileIndex << 16) | chunkIndex      // 大端 BE64 编码后传输
```

| 位域 | 宽度 | 范围 | 含义 |
|---|---|---|---|
| 高 48 bit | 48 | `0 .. 281474976710655` | `fileIndex`：文件在 manifest 中的序号（从 0 开始） |
| 低 16 bit | 16 | `0 .. 65535` | `chunkIndex`：文件内的块序号（从 0 开始） |

**由低 16 bit 推出两条硬性上限**：

| 上限 | 值 | 后果 |
|---|---|---|
| 单文件最大块数 | `65536` | 超过则 `E_FILE_TOO_LARGE` |
| 单文件最大字节数 | `65536 × 1 MiB = 64 GiB` | 同上 |
| 单次会话最大文件数 | `2^48`（理论） | 实际由 manifest 大小与内存限制约束 |

> 一个 64 GiB 的单文件上限对本项目定位（几百 MB 到几十 GB）是足够的。若将来要突破，方案是**新增套件**（`chunkSize` 是套件成员）或新增 `seq` 编码，**不得**偷偷改成 4 字节块号 —— 那会破坏线格式。

#### 5.1.1 实现警告：`seq` 在 JavaScript 中必须用 `BigInt`

`seq` 是 **64 bit 无符号整数**，而 JavaScript 的位运算符（`<<`、`|`、`>>>`）**强制把操作数转换为 32 bit 有符号整数**。因此下面这种写法是**错的**，会在 `fileIndex >= 32768` 时静默产生错误结果：

```js
// ✗ 错误：JS 位运算会截断到 32 bit
const seq = (fileIndex << 16) | chunkIndex;

// ✓ 正确：用 BigInt 全程保持 64 bit 语义
const seq     = (BigInt(fileIndex) << 16n) | BigInt(chunkIndex);
const buf     = Buffer.alloc(8);
buf.writeBigUInt64BE(seq);                       // Node 侧序列化
const back    = buf.readBigUInt64BE(0);          // Node 侧反序列化
const fileIdx = Number(back >> 16n);             // 仅在确认范围后再降为 Number
const chunkIdx= Number(back & 0xFFFFn);
```

浏览器侧同样必须用 `BigInt`（WebCrypto 的 `additionalData` 是字节串，因此**序列化后**再传入，不要在数值域上做位运算）。

> **建议的单元测试**：取 `fileIndex = 65535`、`chunkIndex = 65535`，断言往返序列化/反序列化结果一致。这个用例能捕获上述 32 bit 截断缺陷。

**保留值**：

| `seq` | 含义 |
|---|---|
| `0xFFFFFFFFFFFFFFFF`（全 1） | **manifest 专用**（§6.3） |
| 其余 | 正常数据块 |

### 5.2 帧格式（单块）

```
┌──────────────────────┬───────────────────────────────┬──────────────┐
│ seq (8 字节 BE)       │ ciphertext (chunkLen 字节)     │ tag (16 字节) │
└──────────────────────┴───────────────────────────────┴──────────────┘
```

| 字段 | 长度 | 说明 |
|---|---|---|
| `seq` | 8 | `BE64(seq)`，**明文**（接收方需要它来派生 IV 与 AAD） |
| `ciphertext` | `chunkLen` | 明文长度 `chunkLen`，等于 `min(chunkSize, fileSize - chunkIndex × chunkSize)` |
| `tag` | 16 | GCM 认证标签，由 AEAD 输出 |

**帧总长** = `8 + chunkLen + 16`。

> `seq` 明文不构成泄露：它只暴露"文件序号与块序号"，而"文件的数量与总大小"本来就是明文摘要（§4.7）。**文件名与此无关，且已经被加密。**

### 5.3 IV 派生（12 字节，确定性）

```
IV = ivSalt(4 字节) ‖ BE48(seq)(6 字节) ‖ [0x00] * 2
```

| 部分 | 长度 | 来源 |
|---|---|---|
| `ivSalt` | 4 | **每个会话随机生成一次**，随 `GET /session` 的响应体下发（字段 `iv_salt`，BASE64）。**在会话生命周期内必须保持不变** —— 断点续传时若重新生成，接收方将无法重算 IV |
| `BE48(seq)` | 6 | `seq` 的高 48 bit 大端。恰好放得下 `seq` 的 48 位有效范围 |
| 填充 | 2 | 全零 |

**为什么这样构造**：

| 设计点 | 原因 |
|---|---|
| 确定性（不随块随机） | 断点续传时接收方必须能**独立重算**任意 `seq` 的 IV。若 IV 随机，则必须随包传输并额外保存 |
| `ivSalt` 每会话随机 | 保证**不同会话**（即使密码相同）的 IV 空间不重叠。这是 GCM 的**绝对要求**：同一 key 下 IV 复用会直接摧毁 GCM 的安全性 |
| IV 与 `seq` 一一对应 | 只要 `K_job` 唯一（§4.2 已保证），同一 key 下每个 IV 只出现一次 |

> **必须同时满足的两个唯一性前提**：① `K_job` 每会话唯一（靠 `SID` 混入）；② `ivSalt` 每会话随机（4 字节 = 2³² 空间，会话数远小于此，碰撞概率可忽略）。**只要有一条被违反，GCM 就会灾难性失效**。实现时必须把这两条写成断言 + 测试。

### 5.4 AAD 内容（28 字节）

```
AAD = SID(16 字节) ‖ BE64(seq)(8 字节) ‖ BE32(totalChunks)(4 字节)
```

| 部分 | 长度 | 绑定的东西 |
|---|---|---|
| `SID` | 16 | **会话绑定**：跨会话搬运块会失败 |
| `BE64(seq)` | 8 | **坐标绑定**：乱序、重排、跨文件拼接会失败 |
| `BE32(totalChunks)` | 4 | **长度绑定**：截断攻击会失败（若攻击者删掉尾部并声称文件更短，`totalChunks` 变化导致 AAD 不符） |

**这 28 字节是整条数据面安全性的核心。** 它把"这一块密文"钉死在"哪个会话的哪个文件的第几块、该文件共几块"上。任何挪动都会在解密时被 GCM 标签拒绝。

> `totalChunks` = `ceil(fileSize / chunkSize)`，由 manifest 提供。

### 5.5 分块大小与内存

| 量 | 值 | 说明 |
|---|---|---|
| `chunkSize` | `1048576`（1 MiB） | 套件成员 |
| 单块密文帧上限 | `8 + 1048576 + 16 = 1048600` 字节 | |
| 发送端缓冲 | 1 块（复用后清零） | 见 `设计文档.md` 第六章 |
| 接收端内存 | `O(chunkSize)`，与文件大小**无关** | 靠流式写盘实现（§5.7） |

**分块大小的权衡（记录下来，供将来调参）**：

| 更小（如 256 KiB） | 更大（如 4 MiB） |
|---|---|
| 续传粒度更细；请求数更多、每块固定开销占比更高 | 请求数更少、吞吐更高；续传重传浪费更多 |

1 MiB 是这两者的折中。**注意 `chunkSize` 是套件成员，因此不同套件可以有不同分块大小**，但同一会话内必须一致。

### 5.6 断点续传（RESUME）

接收方在连接中断后重连时，通过 transport 层表达"我已经有多少"：

**模式 A：`https-chunk`（P0/P1/P2 唯一实现）**

```http
GET /chunk?seq=12345 HTTP/1.1
```

- 接收方**逐块请求**，因此"已经收到的块"天然由它自己掌握 —— 无需 RESUME 消息，只需**跳过已完成的 `seq`** 即可续传
- 这是 `https-chunk` 相对流式传输的一个结构性优势：**续传是免费获得的**

**模式 B：`wss-stream`（预留）**

流式模式下没有天然的块边界，必须显式协商：

```json
{ "type": "RESUME", "at": { "fileIndex": 2, "chunkIndex": 1400 } }
```

| 字段 | 说明 |
|---|---|
| `fileIndex` | 从此文件的此块继续 |
| `chunkIndex` | 已成功解密并写盘的**下一块**序号（即需要重发的最小序号） |

**接收方的续传前提**：必须是**已验签并已写盘**的块才算"收到"。**绝不能**把"TCP 收到了但 GCM 校验失败"的块算作已完成。

**写盘与续传的交互（重要）**：

| 情形 | 行为 |
|---|---|
| 使用 `showSaveFilePicker` + `createWritable` | 写入是流式的（append），续传时**可以**从上次位置继续追加 —— 前提是浏览器保留同一个 `FileSystemFileHandle` 且页面**未被刷新** |
| 页面被刷新 | `FileSystemFileHandle` 丢失 → **必须从头开始**。把 handle 存进 IndexedDB 看起来能救，但**救不了** —— 见下面的说明 |
| Blob 兜底路径（Firefox/Safari） | 全部在内存 → 刷新即全丢，续传不可能 |

> ⚠️ **本机无法验证（需要真机 Chromium + 手动刷新）**：`FileSystemFileHandle` 存入
> IndexedDB 后跨刷新恢复的**可用性**。注意即使它可用，**也解决不了续传** ——
> 真正的拦路虎不是 handle，而是 `createWritable()` 每次调用都会**截断文件**，
> 浏览器没有"从第 N 字节接着写"的接口。这一点已经在浏览器 API 层面查清并逐条写在
> `路线图.md` 第 5 项里（那里也解释了为什么它只在 Chromium 的流式写盘路径上有讨论余地）。
> 现在的行为是明确的：刷新后必须从头开始，页面上有"本页刷新后将无法再次访问"的提示。


### 5.7 写盘路径（接收端）

| 浏览器 | 路径 | 内存占用 | 上限 |
|---|---|---|---|
| Chromium 桌面 | `showSaveFilePicker()` → `createWritable()` → 逐块 `write()` → `close()` | `O(chunkSize)` | 受磁盘限制（几十 GB 可行） |
| Firefox / Safari | 累积 `BlobPart[]` → `new Blob()` → `URL.createObjectURL()` → `<a download>` | `O(fileSize)` | **本机无法验证**：具体阈值随设备内存浮动，需要真机实测；实现上不依赖这个数字 —— 超过 900 MB 时页面就明确警告并建议改用 Edge/Chrome |

检测方式：`typeof window.showSaveFilePicker === 'function'`。**不可用时必须提前警告**，而不是传到一半再崩。

### 5.8 背压与 ACK

**`https-chunk` 模式下背压天然成立**：每个块是一个独立的 HTTP 请求，接收方**不请求下一块就不会收到数据**。因此：

- **不需要显式 ACK 消息** —— 请求本身就是 ACK
- **不需要缓冲水位控制** —— 浏览器不会主动拉取超过它处理能力的数据
- 发送端的并发控制：**推荐串行**（一次一个块）。并发虽然能提高吞吐（尤其在 RTT 较大时），但会让"已完成块"的记账变复杂，且增加接收端内存峰值

| 并发度 | 建议 |
|---|---|
| `1`（串行） | **默认**。吞吐由带宽决定，局域网下可达 100+ MB/s |
| `2~4` | 可选优化。**未启用，也不需要** —— 见下面的实测结论 |

> ✅ **已用实测数据定案（2026-10）**：这一条问的是"要不要为 RTT 做并发投递"。
> 答案是不需要：中继模式的瓶颈**不在并发度，而在在途窗口**。
> 实测把窗口从 1 放宽到 8（停等 → 批量投递）就拿到了 **4.72 → 20.75 MB/s（4.4×）**，
> 而在途窗口本身就是"并发"的另一种形态（`/batch` 一次投多条，序号由服务端分配）。
> 再往上加并发只会让"已完成块"的记账变复杂、抬高两端内存峰值，
> 收益远小于已经拿到的那 4.4 倍。详见 `路线图.md` 第九·补章与
> `_lab/bench-window-sweep.mjs`（窗口 1/2/4/8 的实测曲线）。


**`wss-stream` 模式（预留）需要显式 ACK**，因为流式发送无天然背压：

```json
{ "type": "ACK", "seq": 12345 }        // 累计确认：<= seq 的全部块已验签并写盘
```

发送端维护 `inflight` 计数，窗口满则等待 ACK。窗口大小建议 `8` 块（8 MiB）。
（中继转发模式下的实际实现见 §3R.4：同样的窗口语义，但用"一批一次 POST"批量投递。）

### 5.9 transport 层接口（两种模式统一）

```
transport.request(seq) → frames          // https-chunk: GET /chunk?seq=N
transport.resume(at)   → void            // wss-stream: 发 RESUME
transport.ack(seq)     → void            // wss-stream: 累计确认
transport.close()      → void
```

**L5 的代码只依赖这个接口**，因此新增 transport 实现不需要改动分块/加密逻辑。

## 6. 应用层：manifest

### 6.1 manifest 结构

**下面这份是实现的真实输出**（`src/manifest.js` 的 `toWire()`，2026-10 用真实代码生成后贴进来的）：

```json
{
  "v": 1,
  "suite": "FLICKER/1",
  "sentAt": "<ISO 时间戳>",
  "files": [
    {
      "kind": "file",
      "name": "旅行记录 2024.mp4",
      "rel": "旅行记录 2024.mp4",
      "size": 2480340992,
      "chunks": 2366,
      "chunkBytes": 1048576,
      "sha256": "<64 hex>",
      "chunkHashes": ["<64 hex>", "…"]
    }
  ],
  "totalBytes": 2480340992,
  "totalChunks": 2366,
  "gift": null
}
```

| 字段 | 类型 | 必需 | 说明 |
|---|---|---|---|
| `v` | number | 是 | 清单格式版本，当前恒为 `1`。**不认识就拒绝**（`fromWire` 直接抛错，不猜） |
| `suite` | string | 是 | 协商结果，`"FLICKER/1"` |
| `sentAt` | string | 是 | ISO 时间戳，仅供显示 |
| `files[]` | array | 是 | **数组顺序就是传输顺序**；接收端按 `chunks` 累加算出每文件的起始块号 |
| `files[].kind` | string | 是 | `"file"` / `"flicker-station-sea"` / `"flicker-station-source"`（后两者是赠品，见 §9） |
| `files[].name` | string | 是 | 文件名（`rel` 的最后一段），仅供显示 |
| `files[].rel` | string | 是 | **相对路径**：写盘的唯一依据，**不可信输入**，见 §6.2 |
| `files[].size` | number | 是 | 字节数（整数，`>= 0`） |
| `files[].chunks` | number | 是 | `size === 0 ? 1 : ceil(size / chunkBytes)` —— **空文件也占一块**（整数，`>= 1`） |
| `files[].chunkBytes` | number | 是 | 分块大小。**不再恒为 1048576**：发送端按中继声明的上限与链路情况选（`1 MiB` 或 `2 MiB`，见 §3R.3），接收端按它分块 —— IV/AAD 都与块大小无关，所以换值不影响解密 |
| `files[].sha256` | string | 是 | 64 位十六进制，整个文件明文的 SHA-256 |
| `files[].chunkHashes` | string[] | 是 | 每块明文的 SHA-256（十六进制），**长度必须等于 `chunks`** |
| `totalBytes` | number | 是 | 所有 `size` 之和 |
| `totalChunks` | number | 是 | 所有 `chunks` 之和 = 全局块序号的上界 |
| `gift` | object \| null | 是 | 赠品摘要，见 §9；不带赠品时是 `null` |

> ⚠️ **本节此前与实现不一致，已按实现改正（2026-10）。**
> 原文写的是另一套字段：`protocol` / `session` / `sid` / `created` / `totalFiles` /
> `files[].path` / `files[].index` / `files[].merkle` / `files[].mode` / `files[].mtime`，
> 以及每个文件上的 `files[].gift` 布尔 —— 这些**实现里都没有**。
> 照旧文档写客户端会**解析失败**（`fromWire` 认的是 `v` 与 `rel`）。
>
> 几个容易踩的差异单独说清：
>
> | 旧文档 | 实现 | 说明 |
> |---|---|---|
> | `protocol` | 只有 `suite` | 两个字段说的是同一件事，留一个 |
> | `session` | `room` | 只出现在 `GET /session` 的响应里（§4.7），**清单里没有这个字段** |
> | `files[].path` | `files[].rel` | 同一个东西。实现里叫 `rel`（相对路径），§6.2 的规则作用在它上面 |
> | `files[].index` | 无 | 序号就是**数组下标**（接收端按顺序处理），不必也不该单独发一个字段 —— 发了就有"字段与下标不一致"的可能 |
> | `files[].merkle` | `files[].chunkHashes` | 实现发的是**逐块哈希数组**，接收端逐块校验；没有 Merkle 根 |
> | `files[].mode` / `mtime` | 无 | **不保留权限位与修改时间**（见 `行为与运行.md`：接收端只写文件内容） |
> | `files[].gift` | `files[].kind` | 赠品用 `kind` 区分（`flicker-station-*`），不是布尔 |
> | — | `totalChunks` / `chunkBytes` | 接收端要用它们算块序号与内存占用 |

**未知字段必须忽略**（§0.1）。接收方**不得**因为 manifest 里出现不认识的字段而报错。

### 6.2 路径安全规则（**安全边界，不是 UI 细节**）

`files[].rel` 是**不可信输入**（发起方可能被攻击者控制，或用户误传了恶意目录）。接收方必须在写盘前执行以下**全部**校验，任何一条不符即 `ERROR(E_PATH_UNSAFE, fatal=true)` 并中止整个会话：

| 规则 | 检查 |
|---|---|
| R1 非绝对路径 | 拒绝以 `/`、`\` 开头 |
| R2 非盘符路径 | 拒绝匹配 `^[A-Za-z]:` |
| R3 非 UNC 路径 | 拒绝以 `\\` 或 `//` 开头 |
| R4 无上跳 | 拒绝任何路径段等于 `..` |
| R5 无当前目录段 | 拒绝任何路径段等于 `.`（规范化后再判） |
| R6 无 NUL | 拒绝含 `\u0000` |
| R7 长度 | 拒绝超过 255 字节的单个路径段，或超过 4096 字节的整体路径 |
| R8 保留名（Windows） | 拒绝段名匹配 `CON|PRN|AUX|NUL|COM[1-9]|LPT[1-9]`（不区分大小写，含带扩展名形式） |
| R9 非法字符（Windows） | 拒绝含 `< > : " \| ? *` |
| R10 结尾 | 拒绝以空格或 `.` 结尾的段（Windows 会静默截断） |
| R11 分隔符统一 | 先把 `\` 归一化为 `/`，再分段校验 |
| R12 去重 | 同一规范化路径出现两次 → `ERROR(E_MANIFEST_DUPLICATE_PATH)` |

**规范化顺序（必须严格执行）**：

```
1. 归一化分隔符：把所有 '\' 替换为 '/'
2. 按 '/' 切分
3. 丢弃空段（处理 "a//b"）
4. 逐段执行 R4/R5/R6/R8/R9/R10
5. 重新用 '/' 连接
6. 对结果执行 R1/R2/R3/R7/R11/R12
```

> **顺序很重要**：先归一化再校验，否则 `a/./../b` 这类输入会绕过逐段检查。

#### 实现说明（唯一实现在 `src/path-safety.js`）

| 决策 | 内容 | 为什么 |
|---|---|---|
| **R9/R10 是改写，不是拒绝** | 非法字符换成 `_`、去掉结尾的点与空格 | Linux/macOS 上 `a:b.txt`、`report.` 都是**正常文件名**，发送端按自己的平台规则看它们没问题，于是原样写进清单。接收端若直接拒绝，一次**完全正常**的传输就会整个失败 |
| **R8 是拒绝，且不靠改名绕过** | `CON` 不能改成 `_CON` 放行 | 改名会骗到用户（他以为收到了 `CON`，而那个名字在 Windows 上根本创建不出来） |
| **R5 分两种模式** | 接收端（`strict`）拒绝裸的 `.` 段；发送端折叠 | 发送端扫自己的文件时 `./dir/a.txt` 很自然；接收端看的是不可信输入，按协议拒绝 |
| **R7 按字节，不是字符** | 单段 >255 **字节**、整体 >4096 **字节** | 中文按 UTF-8 是 3 字节。旧实现用的是"1024 字符"，比本协议更严 —— 实现与协议不一致时以协议为准 |
| **R12 的比较键 = NFC + 大小写折叠** | 见下 | 见下 |

#### R12 与 Unicode 规范化（**已实测确认，不再是待验证项**）

比较两个路径是否"会落成同一个文件"时，键必须先做 **Unicode NFC 规范化**，
再做**大小写折叠**。理由不是理论洁癖，而是三种真实存在、后果都是**静默丢文件**的情形：

| 情形 | 来源 | 不处理的后果 |
|---|---|---|
| `café`(NFC) 与 `café`(NFD，`e`+U+0301) | macOS 的 HFS+/APFS 用 NFD | 在 macOS 接收端是**同一个文件**，后写的覆盖先写的 |
| `Readme.md` 与 `readme.md` | Windows / macOS 默认大小写不敏感 | 同上 |
| `a:b.txt` 与 `a_b.txt` | 前者在 Windows 上被 R9 改写成 `a_b.txt` | 改写本身没错，错的是**没发现改写之后重名了** |

**接收端必须在开始传输之前就把冲突查出来并中止**（`E_MANIFEST_DUPLICATE_PATH`），
而不是等到写盘时才发现 —— 那时用户已经等了几十 GB，而覆盖是**没有提示**的：
界面上写着"传输完成"，磁盘上少了一个文件。

比较键只用于**判断**，不改写要写盘的名字（用户看到的名字与发送端一致）。
发送端的去重（`a.txt` → `a (1).txt`）用的是**同一个键**，否则发送端认为不冲突、
接收端却只写出一个 —— 这正是"两份实现"最典型的坏结果。

#### 页面里那份规则是**内联**的，不是另一份实现

真正决定文件落到用户磁盘上叫什么的，是 `web/receiver.html` 里跑的那份代码，
而不是 Node 里的 `src/manifest.js`。这两个地方**从前各写了一份，规则还不一样**：

```
src/manifest.js      12 条规则基本齐
web/receiver.html    rel.replace(/[<>:"|?*\x00-\x1f]/g, '_')      ← 只有一行
```

后果是同一条清单在 Node 测试里通过、在浏览器里丢文件。
现在规则只在 `src/path-safety.js` 里写一次，由 `gen/inline-path-rules.mjs`
**原样**内联进页面，`--check` 守住同步（与 i18n、PWA 的内联同样的做法）。
`test/path-safety.test.js` 会把页面里那段脚本放进一个**没有 `Buffer`/`process` 的沙箱**
里执行，并与 Node 那份逐条比对行为 —— 只检查"两边都有这个函数"是不够的，
从前两边也都有各自的实现。

### 6.3 manifest 的加密与传输

```
manifest_seq = 0xFFFFFFFFFFFFFFFF        （全 1，保留）
manifest_pt  = UTF-8(JSON(manifest))
manifest_aad = SID(16 字节)               （无 seq、无 totalChunks —— 见下）
manifest_ct  = AEAD.seal(K_job, IV_manifest, manifest_pt, manifest_aad)

IV_manifest  = ivSalt(4) ‖ [0xFF] * 6 ‖ [0x00] * 2      （12 字节）
```

**`IV_manifest` 的特殊性**：§5.3 的通用公式产生的 IV 中，中间 6 字节等于 `BE48(seq)`。`IV_manifest` 把中间 6 字节设为全 `0xFF`，等价于 `BE48(0xFFFFFFFFFFFF)`。因此它与数据块 IV 冲突的条件是：

```
fileIndex = 0xFFFFFFFFFFFF      （即 seq 高 48 bit 全 1）
且 chunkIndex 的高 2 字节与 0xFFFF 的对应位一致
```

而 §5.1 已经**硬性禁止** `fileIndex` 接近该值 —— 实现必须带断言 `fileIndex < 0xFFFFFFFFFFFF`。在这个约束下，`IV_manifest` 与任何数据块 IV **不会冲突**。

> **实现要求**：这条断言不是"防御性编程"，而是 GCM 安全性的前提之一（IV 在同一 key 下不得复用）。必须写成启动期检查 + 单元测试，不能只写在注释里。

#### 6.3.1 两种 AAD 的差异（必须分清，容易实现错）

manifest 与数据块使用**不同长度**的 AAD。这是刻意的，因为 manifest 没有"文件内块坐标"这个概念：

| 对象 | AAD 长度 | 内容 |
|---|---|---|
| **数据块** | 28 字节 | `SID(16) ‖ BE64(seq)(8) ‖ BE32(totalChunks)(4)` |
| **manifest** | 16 字节 | `SID(16)` |

两者都绑定 `SID`（因此都不能跨会话搬运），区别在于数据块还绑定了"坐标"与"文件长度"。

> **不得**为了让两种 AAD 长度一致而给 manifest 补零到 28 字节 —— 补零会引入"某个 `seq`/`totalChunks` 组合的全零 AAD 与 manifest 的 AAD 相同"的理论冲突面。**让它们长度不同，反而消除了歧义。**

**manifest 的传输路径（两条）**：

| 路径 | 时机 | 说明 |
|---|---|---|
| 内联在 `GET /session` 响应 | 直连模式 | 接收方**在读密码之前**即拿到 `manifest_ct`；文件数量与总大小以**明文摘要**另外提供（§4.7） |
| 作为保留 `seq` 的块 | 会合模式 / 流式模式 | relay 模式下 manifest 也可能内联在 `GET /session` 里，因为数据面本来就走直连 |

**接收方的处理顺序（强制）**：

```
1. 从 GET /session 拿到 manifest_ct、iv_salt、salt、suite
2. 用户输入 P
3. 算 V → K_auth / K_enc（此步可能耗时，需 UI 提示）
4. 握手（§4）→ 得到 SID、K_job
5. 解 manifest_ct，校验 manifest.sid === SID（不符 → E_SID_MISMATCH，中止）
6. 执行 §6.2 的全部路径校验（不符 → E_PATH_UNSAFE，中止）
7. 校验 files[].chunks === ceil(size / chunkSize)（不符 → E_MANIFEST_INVALID）
8. 开始 L5 传输
```

> **第 5 步不可省**：它把 manifest 钉死在这个会话上，防止 relay 用**另一个会话**的 manifest 做替换攻击（虽然 relay 拿不到 `K_job`，但防御性校验成本极低）。

### 6.4 Merkle 根的定义

> ⚠️ **这一节是原设计，`FLICKER/1` 最终没有采用它（2026-10 核对）。**
>
> 实现里**没有任何 Merkle 树**（`src/`、`web/` 全搜 `merkle` 命中 **0**），
> manifest 里也**没有 `merkle` 字段** —— 逐块校验用的是 `files[].chunkHashes`
> （逐块 SHA-256 数组），§6.1 的"旧文档 → 实现"对照表里已经写明这一点。
>
> 所以下面这套叶子/内部层/根的构造**不是线上格式的一部分**。本节保留作为设计记录，
> 它也解释了这个结论的来由（见本节末尾的 ✅）。
> **照本节去实现一个 Merkle 根是白做工**：对方不会发这个字段，也不会校验它。

```
叶子层:  leaf[i]  = SHA-256( BE32(i) ‖ BE32(chunkLen_i) ‖ plaintext_i )     i = 0 .. chunks-1
内部层:  node     = SHA-256( left ‖ right )
        （奇数个节点时，最后一个节点**直接上提**，不复制自身 —— 避免 CVE-2012-2459 式的歧义）
根:      merkle   = 最终的单个 32 字节
```

| 参数 | 值 |
|---|---|
| `chunkLen_i` | `min(chunkSize, size - i × chunkSize)` |
| 空文件 | `chunks = 0`，`merkle = SHA-256("")`，`sha256 = SHA-256("")` |
| 单块文件 | `merkle = leaf[0]` |

**Merkle 根的用途**（原设计）：
- 让接收方可以**逐块验证**（收到一块即可验证其叶子哈希，无需等整个文件）
- 支持"只重传损坏块"的精细化恢复（P1 可选优化）
- `files[].sha256` 是整体校验，`merkle` 是分块校验，两者**都要校验**（逐块那一半实际由 `chunkHashes` 承担）

> ✅ **已定案（2026-10）**：这一条问的是"树形结构的逐块验证要不要认证路径"，
> 答案是**不需要**，`FLICKER/1` 的做法已经够用：
> 接收方逐块算叶子哈希并缓存，全部收完后重算整棵树与 manifest 里的根比对。
> 也就是说：**分块级**的篡改能被定位到具体是哪一块（因为每块都单独 AEAD 认证，
> 且 manifest 里有 `chunkHashes` 逐块指纹），而**树结构本身**的完整性由根保证。
>
> 需要认证路径的是"只拿到一部分块就要证明某一块的合法性"那种场景
> （轻客户端 / 随机访问）—— 本产品是**一次收完整个文件**，没有这个场景。
> 真要支持，做法是给 manifest 新增一个 proof 字段（符合 §0.1 的可扩展规则），
> 属于 P1 之后的可选扩展，不是当前的缺口。

## 7. 传输层端点（发起方 HTTPS 服务）

### 7.1 端点表

> ⚠️ **这张表整张写错过（2026-10 核对改正）**：路径少了 `/api/` 前缀、`/auth` 其实分成

> `TransferServer`，逐个请求，确认不是"没有这个接口"）。

| 方法 | 路径 | 认证要求 | 作用 |

| `GET` | `/api/chunk?seq={N}` | `SID` | 返回单块密文帧（§7.3） |
| `POST` | `/api/done` | `SID` | 接收方宣告完成 |
| `GET` | `/api/health` | 无 | 就绪探测：纯文本 `ok`；**无副作用、不泄露任何会话信息** |

> 另外两条不走会话：`GET /index.html` 与 `GET /` 等价；`GET /favicon.ico` 回 `204`。
> 其余任何路径/方法 → `404 {"error":"NOT_FOUND"}`。
>
> ⚠️ **服务端不校验 HTTP 方法**（路由只看路径），所以 `GET /api/auth/finish` 也能用。
> 表里那一列写的是**客户端应当用的**方法。

#### 7.1.1 为什么 `/api/session` 只认令牌而不认 `SID`

存在一个**先有鸡还是先有蛋**的顺序问题：`SID` 是握手的产物，而接收方需要先 `GET /api/session` 才能拿到 `salt`、`suite` 与 `manifest` 密文，然后才能开始握手。

```
接收方必须先 GET /api/session  →  才能握手  →  才能得到 SID
         └─ 此刻它还不可能持有 SID
```

因此认证分工必须严格按此划分：

| 端点 | 凭什么认证 | 理由 |
|---|---|---|
| `GET /`（页面） | **`token`**，且**在这里消费** | 证明"持有链接"；此刻 `SID` 尚不存在 |
| `GET /api/session` | 只要求 `token` **已被消费** | 它本身不消费令牌 —— 否则一次页面预取就能把用户的链接烧掉 |
| `GET /api/auth/start`、`POST /api/auth/finish` | **无**（握手本身即认证） | 其安全性来自 `mac_r` 的知识证明，不来自传输层身份 |
| `GET /api/manifest`、`GET /api/chunk`、`POST /api/done` | **`SID`** | 会话已建立，用会话秘密保护数据面 |

**`token` 在 `GET /`（打开页面）那一刻消费**，不是在这里（§4.4.3）。
`GET /api/session` 只**校验**它已经被消费过；令牌为空或还没打开过页面 → `403 TOKEN_INVALID`，
不得降级为"无认证放行"。

### 7.2 认证方式（`SID` 的传递）

`SID` 是 16 字节秘密（只有双方知道）。**两种服务用两种方式传**（2026-10 按实现核对 —— 从前这里只写了请求头，那对发起方服务是错的）：

| 服务 | 怎么传 | 实现位置 |
|---|---|---|
| 发起方服务（§7） | **查询参数** `?sid=<SID>` | `url.searchParams.get('sid')`（`src/server.js`）；接收端页面就是这么拼 URL 的（`web/receiver.html`），`/api/done` 用 `sendBeacon` 也是 |
| 接收方服务（§7R） | **请求头** `X-Flicker-Sid: <SID>` | `req.headers['x-flicker-sid']`（`src/upload-server.js`） |

**两种都用常数时间比较**校验（`timingSafeEqual`）。不匹配 → `401 {"error":"BAD_SID"}`。
⚠️ SID 不匹配**不计入** `failCount` —— 那套失败计数是给**密码猜测**用的（§4.6），不是给 SID 的。

> **为什么不用 Bearer token**：`SID` 本身就是会话秘密，再引入一个独立的 token 会增加状态而没有任何安全性提升。
>
> **关于将来的 WebSocket（`wss-stream`，未实现）**：那种形态下 `SID` 的传递要改成**首帧认证**
> （HTTP 头只在握手时出现一次，之后无法再改）。这是**设想中的扩展点**，不是当前的缺口 ——
> 记录在此只是为了让将来做它的人知道这里要动，而不是留一个待办。


### 7.3 `GET /api/chunk?seq=N` 的响应

> ⚠️ **本节也是 2026-10 按实现改正的**：从前写的响应头（`X-Flicker-Seq` / `X-Flicker-Len`）、
> `429` 令牌桶、以及 `E_BAD_SEQ` / `E_UNAUTHORIZED` / `E_SOURCE_CHANGED` 那套错误码
> **在实现里都不存在**（那套码属于会合模式的设计，见 §8.2 的说明）。照原文写客户端，
> 它一个响应头都读不到、一个错误码都认不出来。

| 状态码 | 含义 | 响应体 |
|---|---|---|
| `200` | 成功 | 单块密文帧（§5.2），`Content-Type: application/octet-stream` |
| `401` | `SID` 不符，或还没通过认证 | `{"error":"BAD_SID"}` / `{"error":"NOT_AUTHED"}`（§7.2） |
| `416` | `seq` 非法或超出 `totalChunks` | `{"error":"RANGE"}` |
| `500` | 服务端读文件失败（文件被移动/删除/改动） | `{"error":"INTERNAL"}` |

**响应头**（`seq` 不在这里回显 —— 客户端请求哪个 `seq` 自己就知道）：

```http
Content-Length: <密文长度>
X-Flicker-Tag: <BASE64(GCM tag)>
X-Flicker-File: <文件下标>
X-Flicker-Chunk: <该文件内的块号>
Cache-Control: no-store, no-cache, must-revalidate
```

> `Cache-Control: no-store` 是**安全要求**：任何中间缓存（浏览器缓存、代理）持有密文块都会削弱"用完即销毁"。虽然密文本身是加密的，但缓存的存活时间超出会话生命周期，违背产品承诺。
>
> 明文长度**没有单独的头**：客户端按清单里的 `chunkBytes` 与 `size` 自己算最后一块
> （`plainLen = ci === chunks-1 ? size - (chunks-1)*chunkBytes : chunkBytes`）。

**没有速率限制响应码。** 限速（`--rate`）是**发送端主动放慢**（`src/rate.js`：加密之前 sleep），
不是"先收下再回 `429`"。所以服务端不会返回 `429`、也没有 `Retry-After` —— 它只是慢。

### 7.4 TLS 与证书信任

数据面必须走 HTTPS。原因不是"更安全"这么笼统，而是一条**硬性平台约束**：接收端要用 `crypto.subtle`（WebCrypto），而浏览器只在**安全上下文（secure context）**中提供它。

| 来源 | 是否安全上下文 | `crypto.subtle` |
|---|---|---|
| `http://127.0.0.1` | ✅ 是（loopback 被规范列为 potentially trustworthy） | 可用 |
| `http://192.168.1.5` | ❌ 否 | **`undefined` → 加密功能直接不可用** |
| `https://192.168.1.5` | ✅ 是 | 可用 |

所以加密协议**必须**跑在 HTTPS 上，而证书必须被浏览器接受，否则整个局域网主场景无法工作。

#### 7.4.1 两种证书策略

| 策略 | 做法 | 状态 |
|---|---|---|
| **A. 手动信任引导**（保底） | 运行时生成自签证书，用户在浏览器中手动点"高级 → 继续前往"，页面给出分步引导 | 行为已明确，具体文案待 P0 实测 |
| **B. 会话级 CA 自动装卸**（`架构决策.md` 的目标方案） | 生成两级结构（会话根 CA + 由它签发的服务器证书），把**根 CA** 装入当前用户信任库，退出时卸载 | ⚠️ **本机实测未通过**，见 §7.4.2 |

策略 B 的两级结构是**必要**的：若只生成一张自签证书并把它自己装进信任库，验证会以 `DEPTH_ZERO_SELF_SIGNED_CERT` 失败。必须"CA 进信任库、服务器证书由该 CA 签发"。

#### 7.4.2 证书信任的本机实测结果（重要，与 `架构决策.md` §4.3 的预期不符）

> ✅ **后续进展（2026-10）：这个问题已经解决了，下面是当时的过程记录。**
> 根因是**生成的 CA 少了 CA 标志**（`basicConstraints` 里必须有 `ca=1`）——
> 补上之后，用真实交互式验证在 Windows + Edge 155 上**全部零警告通过**
> （headless / 可见窗口 / app 无地址栏窗口三种模式，回环与真实局域网 IP 两种地址）。
> 所以本节那些 ❌ **并不代表现在的行为**，它们记录的是"当时漏掉那个标志时看到的景象"。
> 结论与证据见 §12.1 的 Q1 与 `_lab/实测报告-证书信任.md`。
>
> **为什么还留着这一段**：它是一份"看着像结论、其实是错误归因"的样本 ——
> 当时差点把"浏览器不认自签 CA"写成平台限制，而真正的原因只是自己漏了一个扩展字段。

在**本机**（Windows 10 19044，非管理员）实测，得到三条结论：

**① `certutil` 装卸当前用户 Root 库确实不需要管理员权限 —— 可行性成立**

```
当前用户是否管理员              否
certutil -addstore -user Root  退出码 0，Root 库证书数 49 → 50，证书确实存在
certutil -delstore -user Root  退出码 0，50 → 49，完全恢复
```

**② 但 PowerShell 的 `Remove-Item` 无法删除 Root 库中的证书**

```
Remove-Item Cert:\CurrentUser\Root\<指纹>
  → The operation is on user root store and UI is not allowed.
```

**这是一个必须写进实现的操作约束**：卸载证书**只能**用 `certutil -delstore -user Root <指纹>`，不能用 `Remove-Item`。`架构决策.md` 指定的正是 `certutil`，此处得到验证 —— 但原因比预想的更硬：不是"习惯用它"，而是**别的办法根本不行**。

> **由此推出一个可靠性要求**：卸载只能靠外部进程调用。若程序在装入证书后被强杀（`Ctrl+C` 之外的 `taskkill`、断电、崩溃），**没有任何机制能保证证书被卸载**，用户的信任库里会永久残留一个他不认识的根 CA。
>
> 这会直接违背"用完即销毁"的产品承诺，而且是**安全层面**的残留：一个被遗忘的、私钥已丢失的根 CA 虽然无法被用来伪造证书，但它出现在信任库里本身就会让用户警觉。
>
> **建议**：装机时把 CA 指纹与卸载命令一起打印到终端并写入日志文件；启动时**先扫描本机是否残留上次的会话 CA**，若有则提示并提供一键清除。

**③ 装上根 CA 后，浏览器仍然拒绝连接 —— 目标方案的核心体验未达成**

测试方法（每种组合使用**全新 profile**，排除配置缓存）：

```
1. 生成会话根 CA + 由它签发的 127.0.0.1 服务器证书
2. certutil -addstore -user Root 装入根 CA
3. Node 起 HTTPS 服务（私钥不落盘，仅内存）
4. 用 Edge (--headless=new) 打开 https://127.0.0.1:8443/ 并 dump DOM
```

| 变体 | 结果 |
|---|---|
| 基准（CA 在信任库，新 profile） | ❌ 拒绝 |
| `--disable-features=NetworkServiceSandbox` | ❌ 拒绝 |
| `--no-sandbox` | ❌ 拒绝 |
| `--disable-features=CertificateTransparencyEnforcement` | ❌ 拒绝 |
| 基准重复（排除缓存） | ❌ 拒绝 |
| **对照：`--ignore-certificate-errors`** | ✅ **成功渲染** |

对照组成立，证明**服务器、私钥、证书链、网络路径全都正确**，唯一的变量就是"浏览器是否认可信任库中的 CA"。**结论是：在本机环境下，把 CA 装进 Windows 当前用户 Root 库，不足以让 Edge 接受该证书。**

> **这不能直接推广成"方案 B 一定行不通"**，因为存在几个未排除的变量：
> - Edge 的 `--headless=new` 模式可能不读 Windows 信任库
> - Chrome/Edge on Windows 已知会**缓存证书验证结果**，可能需要在新装 CA 后重启浏览器进程；本实验虽用新 profile，但同一台机器上先后跑了 5 个实例
> - 证书透明（CT）策略、或两级链中缺少 `authorityKeyIdentifier` 等细节
>
> **因此准确定论是："方案 B 的零警告体验（`架构决策.md` §4.3 第 3 步）在本机未获证实。"**
>
> **必须由一次真实交互式验证来裁决**（用真实 Chrome、关掉它、装 CA、再打开、肉眼确认是否有警告），这是 **P0 的阻塞项**（见 §12.1 Q1）。

#### 7.4.3 基于实测的落地建议

1. **P0 先用策略 A**（自签 + 引导），保证主链路能走通，不被证书问题卡住
2. **策略 B 作为 P2 的目标**，但必须先通过真实浏览器的交互式验证，再决定是否让它成为默认
3. **`--no-cert-install` 开关是必需的**，不是可选：会有用户不接受任何程序改自己的证书库，且从本机实测看，这个方案的可靠性还不足以让它成为唯一路径
4. **无论用哪种策略，CA 必须是会话级、私钥绝不落盘**（仅内存持有），且启动时清理上次残留（§7.4.2 ②）

| 模式 | 证书 |
|---|---|
| 局域网 / 端口转发 / 公网 IPv6 | 会话级证书（策略 A 或 B），含本机所有 IP 的 `subjectAltName` |
| relay 托管页面 | relay 提供正常证书；数据面仍是站点自己的会话级证书 |
| **站点自身的 GUI 界面**（`127.0.0.1`） | **不需要证书** —— loopback 本身就是安全上下文。GUI 与数据面是**两个不同的 HTTPS 服务**，不要混为一谈 |

## 7R. 接收模式端点（接收方 HTTPS 服务，手机上传）

> **为什么单列一章**：§7 是"发起方开 HTTPS 服务、对端来**取**"（`GET /chunk?seq=N`）。
> 手机当发送端时方向反过来 —— 手机不能监听端口（浏览器做不到），所以**由电脑起服务、手机把块推上来**（`PUT /up/chunk?f=&c=`）。
> 密码学**一个字都没变**：同一套 `FLICKER/1`（§2）、同一套挑战—应答与降级保护（§4）、同一个清单加密（§6.3）、同一套块 IV/AAD 绑定（§5.3、§5.4）。
> 变的只有"谁监听、谁请求"和 7 个端点的名字。实现：`src/upload-server.js`（HTTP 层）、`src/recv.js`（证书、链接、销毁）。

### 7R.1 与 §7 的分工

| | §7 发起方服务 | §7R 接收方服务 |
|---|---|---|
| 谁监听 | 发送端（手里有文件的一方） | 接收端（要文件的一方，这里是电脑） |
| 对端怎么拿数据 | `GET /chunk?seq=N` **拉** | `PUT /up/chunk?f=&c=` **推** |
| 清单谁发给谁 | 发起方 → 对端 | 手机 → 电脑 |
| 谁先拿到清单 | 对端（密文清单随 `GET /session` 一起给） | 电脑（手机主动 POST 上来） |
| 密码学 | §2–§6 全套 | **完全相同，一行都不改** |
| 端点前缀 | 无（`/session`、`/auth`…） | `/up/`（`/up/session`、`/up/auth`…） |

**一句话**：两个方向共用 L3（套件）与 L4（会话），区别只在 L5 的搬运方向。

### 7R.2 端点表

| 方法 | 路径 | 认证要求 | 作用 |
|---|---|---|---|
| `GET` | `/` | 无 | 返回手机上传页（自包含 HTML，不含任何秘密） |
| `POST` | `/up/session?k={token}` | **仅 `token`** | 发挑战 + 报价上限；手机据此派生密钥 |
| `POST` | `/up/auth` | 无（这就是认证本身） | 手机证明知道密码；电脑回自己的应答与 `SID` |
| `POST` | `/up/manifest` | `SID` | 收加密清单；**开工前**把能查的全查掉 |
| `PUT` | `/up/chunk?f={fileIndex}&c={chunkIndex}` | `SID` | 推一块密文；**幂等** |
| `GET` | `/up/status` | `SID` | 已收到哪些块（断线续传用） |
| `POST` | `/up/finish` | `SID` | 收尾：整文件摘要校验 → 定稿改名 |

> 这张表与 `src/upload-server.js` 的 `RECV_ROUTE_TABLE` 是**同一个来源**，
> 由 `gen/check-recv-protocol-doc.mjs` 逐行比对 —— 文档里多一个端点、少一个端点、写错路径，
> 它都会失败（那类错误本机测试全绿，只有照文档写客户端的人会撞上）。

### 7R.3 `token` 的消费点与认证分工（与 §7.1.1 的差别）

两种模式**消费 `token` 的位置不同**，这是最容易写错的一处：
§7 的发送端服务是在 **`GET /`（打开接收页）**那一刻消费的（`/api/session` 只校验、不消费）；
接收模式则是在 **`POST /up/session`** 成功那一刻消费 ——
`GET /`（页面）**不消费**，它只是一份静态 HTML，谁拿到都不算数。

| 端点 | 凭什么认证 | 理由 |
|---|---|---|
| `GET /` | 无 | 只是一个 HTML 页面，里面没有任何会话秘密 |
| `POST /up/session` | **`token`** | 证明"持有链接"；此刻还没有任何共享密钥 |
| `POST /up/auth` | **无**（握手本身即认证） | 安全性来自知道密码，不来自传输层身份 |
| 其余 4 个端点 | **`SID`**（`X-Flicker-Sid`，同 §7.2） | 会话已建立，用会话秘密保护数据面 |

`token` 是 16 字节随机数的 base64url（22 个字符），进链接的 `?k=`。
**第二次 `POST /up/session` 一定 `410 TOKEN_USED`** —— 没有"同一 TCP 连接不算新消费"的例外
（刷新页面 = 新连接 + 已消费的令牌 = 410，这是确定行为，不是偶发）。

### 7R.4 `POST /up/session` 的响应

请求体为空。成功后（`200`）：

```json
{
  "suite": "FLICKER/1",
  "salt": "ZkmFadmDN+pVRpeI54+bzA==",
  "challenge": "HLLzVkKjpcxukQXjsNxrDZpRyxWGjNGBqo+CCK02J4U=",
  "macProfiles": ["v2", "v1"],
  "limits": {
    "maxFiles": 5000,
    "maxBytes": 214748364800,
    "maxChunkBytes": 2097169,
    "maxPlainChunkBytes": 2097152
  }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `suite` | string | 固定 `"FLICKER/1"`（套件协商见 §2） |
| `salt` | string | `BASE64(S)`，16 字节；PBKDF2 的盐（§4.2） |
| `challenge` | string | `BASE64(nonce_r)`，32 字节（§4.3） |
| `macProfiles` | array | 本机支持的握手 MAC 构造，按优先级排列（§4.3 的降级保护） |
| `limits` | object | 本机报价的上限，见下表 |

| `limits` 字段 | 含义 |
|---|---|
| `maxFiles` | 一次会话最多几个文件（默认 5000） |
| `maxBytes` | 一次会话最多多少字节（默认 200 GiB） |
| `maxChunkBytes` | **线上一条消息**的上限（含 17 字节固定开销） |
| `maxPlainChunkBytes` | **明文块**的上限 —— 清单里的 `chunkBytes` 受它约束 |

> **为什么两个块上限都要报价**：只给 `maxChunkBytes` 的话，客户端必须自己减掉那个 17
> （类型字节 + GCM tag）—— 那是实现细节，客户端没有理由知道它。
> 2026-10 的真机演练就是在这里撞上的：页面按 `maxChunkBytes` 声明块大小，服务端按 `+17` 全部拒绝，
> 表现是"清单被拒，一块都发不出去"。**报价里给一个还需要客户端做减法的数，早晚要在真机上炸。**

### 7R.5 `POST /up/auth`

请求体是 JSON（≤ 4096 字节），字段与 §4.3 的直连握手**完全一致**：
`mac`（`BASE64(mac_s)`）、`challenge`（`BASE64(nonce_r)`）、`macProfile`（回执的构造，可选）。
成功后（`200`）：

```json
{
  "sid": "9q3_vM3n0LQATNZhkMsspQ",
  "mac": "p6SUyxX+DDkvQwyT5F4KZtQ5RwSAbIWScDjzvvTM3lQ=",
  "macProfile": "v2"
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `sid` | string | 会话 ID（实现是 16 随机字节的 base64url）。后续请求把它**原样**放进 `X-Flicker-Sid`（§7.2）—— 客户端不需要理解它的编码 |
| `mac` | string | `BASE64(mac_i)` —— 电脑证明它也知道密码，手机**必须**核对（否则对面可能是钓鱼页） |
| `macProfile` | string | 这一次实际用的握手构造（`v2` / `v1`） |

> ⚠️ **角色是反的**：这里电脑是 `receiver`、手机是发送端。所以电脑验的是 `senderMac`、回的是 `receiverMac`；
> 两个方向分开算以防反射（§4.5）。密码不一致 → `401 BAD_PASSWORD` 并按 §4.6 计数，
> 第 5 次失败销毁会话（`410 TOO_MANY_FAILURES`）。

### 7R.6 `POST /up/manifest`

请求体 = `iv(12) ‖ tag(16) ‖ 密文`（**与 §6.3 同一个顺序**），AAD = `"flicker/1/manifest"`。
明文是一个 JSON —— 它是 §6.1 线格式的**减法版**（字段见下面第二张表）。
成功后（`200`）：

```json
{
  "accepted": [
    { "index": 0, "rel": "note.txt", "renamedFrom": null },
    { "index": 1, "rel": "photo.bin", "renamedFrom": null }
  ],
  "skipped": [],
  "totalChunks": 3,
  "diskFree": 79984742400,
  "partSuffix": ".flicker-part"
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `accepted` | array | 电脑**接受**的条目：`{index, rel, renamedFrom}`（`renamedFrom` 非空 = 因重名改过名字） |
| `skipped` | array | 被跳过的条目：`{index, rel, reason}`（同名且用户选了"跳过"） |
| `totalChunks` | number | 接受部分的总块数（进度条的分母） |
| `diskFree` | number\|null | 目标磁盘可用字节数；文件系统不支持查询时为 `null` |
| `partSuffix` | string | 半成品后缀，固定 `.flicker-part` |

清单**明文**（手机发上来的那个）的字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `files[]` | array | 每个文件一个条目 |
| `files[].index` | number | 文件下标，就是 `f` 参数的取值（从 0 起） |
| `files[].rel` | string | **只能是单段文件名**：含 `/` 或 `\` 一律 `400 E_PATH_UNSAFE` |
| `files[].size` | number | 明文字节数 |
| `files[].chunks` | number | 总块数，必须等于 `ceil(size / chunkBytes)`，否则 `400 BAD_CHUNKS` |
| `files[].chunkBytes` | number | 每块明文字节数，不得超过 `maxPlainChunkBytes`，否则 `400 BAD_CHUNK_BYTES` |
| `files[].sha256` | string | 整文件 SHA-256 的 `HEX`；`finish` 时按磁盘顺序重算比对（§7R.9） |
| `totalBytes` | number | 所有文件字节数之和 |
| `totalChunks` | number | 所有块数之和 |

> **为什么这条路的清单更小**：手机只能选文件、选不了文件夹（浏览器限制），所以没有
> `kind`、`name`、`chunkHashes`、`gift`、`sentAt` —— 目录树重建与自赠程序在这条路上不存在。
> **这不是"还没做"，是这条路不需要**（§7R.12）。
>
> 路径规则比 §6.2 更严：过完 `sanitizeRelPath` 那 12 条之后，**还要求不含路径分隔符**。
> 命中任何一种都是**中止整个会话**且**一个字节都还没写** —— 因为全部检查都发生在清单阶段、
> 任何数据到达之前。

### 7R.7 `PUT /up/chunk?f={fileIndex}&c={chunkIndex}`

请求体 = `tag(16) ‖ 密文`（**tag 在前**，与 §5.2 一致）。
IV 与 AAD 的算法与 §5.3、§5.4 **完全相同**（AAD = `fileIndex ‖ chunkIndex ‖ totalChunks ‖ plainLen`）。
成功后（`200`）：

```json
{ "ok": true, "f": 0, "c": 0 }
```

| 情况 | 响应 |
|---|---|
| 首次收到这一块 | `200 {ok:true, f, c}` |
| **同一块重发**（手机上重试是常态） | `200 {ok:true, already:true, f, c}` —— **不重写**，幂等 |
| `f` 不在清单里 | `404 BAD_FILE_INDEX` |
| `c` 超出该文件的块数 | `404 BAD_CHUNK_INDEX` |
| 密文验不过（GCM tag 不符） | `400 E_CHUNK_AUTH`，并计数 |
| 连续失败达到上限（默认 10） | `400 TOO_MANY_BAD_CHUNKS`，**会话销毁** |

> **块级认证是这条路上唯一能"当场发现"损坏的地方**：一块错了当场被拒、不写盘；
> 整文件摘要要等到 `finish` 才验（§7R.9）。两层都要 —— 少一层就会把坏数据当成功。
>
> **幂等的意义**：弱网下手机重发是常态。没有幂等，重发要么报错、要么把同一块写两遍。

### 7R.8 `GET /up/status`

成功后（`200`，下面是"块都收齐了、还没 finish"的真实状态）：

```json
{
  "files": [
    { "index": 0, "rel": "note.txt", "chunks": 1, "received": 1, "receivedBytes": 25, "size": 25, "missing": [] },
    { "index": 1, "rel": "photo.bin", "chunks": 2, "received": 2, "receivedBytes": 69857, "size": 69857, "missing": [] }
  ],
  "totalChunks": 3,
  "totalBytes": 69882,
  "receivedChunks": 3,
  "receivedBytes": 69882,
  "finished": false
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `files[]` | array | 每个被接受的文件一行 |
| `files[].index` | number | 文件下标（与 `f` 参数一致） |
| `files[].rel` | string | 落盘用的名字 |
| `files[].chunks` | number | 总块数 |
| `files[].received` | number | 已收到的块数 |
| `files[].receivedBytes` | number | 已收到的明文字节数 |
| `files[].size` | number | 该文件声明的总字节数 |
| `files[].missing` | array | 还缺哪些块号；**最多列 64 个**，只是给人看的 |
| `totalChunks` / `totalBytes` | number | 全部接受部分的总量 |
| `receivedChunks` / `receivedBytes` | number | 已经收到的量 |
| `finished` | boolean | 是否已经 `finish` 过 |

> 手机页面**不依赖**这个端点决定补哪些块（它自己记着发过哪些，见 `web/phone.html`）；
> 它用这个端点做两件事：断线回来时**如实告诉用户"还剩多少"**，以及把进度对齐。
> 客户端要补块，请按 `chunks - received` 算 —— `missing` 会被截断到 64 项。

### 7R.9 `POST /up/finish`

请求体被忽略（手机发 `{}`）。电脑在这里做**最后一层校验**，成功后（`200`）：

```json
{
  "done": [
    { "rel": "note.txt", "bytes": 25, "renamedFrom": null },
    { "rel": "photo.bin", "bytes": 69857, "renamedFrom": null }
  ],
  "failed": [],
  "skipped": []
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `done` | array | 校验通过并已定稿的文件：`{rel, bytes, renamedFrom}` |
| `failed` | array | **整文件摘要不符**的：`{rel, reason}` —— 半成品**故意留在磁盘上**（见下） |
| `skipped` | array | 清单阶段就被跳过的文件 |

**定稿规则**（四条，都是判据）：

1. 必须**一块不缺**，否则 `409 INCOMPLETE`（附"还缺多少、缺在哪个文件"）—— 缺块是让客户端补发，不是"当作成功"。
2. 校验方式是**按磁盘上的顺序重读** `.flicker-part` 算 SHA-256，与清单里的 `sha256` 比对 —— **不依赖分块的到达顺序**（顺序错了这一关也会抓住）。
3. 通过 → `rename` 成正式名字；不通过 → **不改名**，`.flicker-part` 留在原地当证据：既不污染正常文件，也让人查得出来。
4. 重复调用 → `409 ALREADY_FINISHED`。

> **数据先落盘、最后才对名字负责**：`.flicker-part` → 正式文件这一步是整个流程里唯一的"定稿"动作。
> 收到一半中断时，磁盘上只会多出一个一眼能认出来的后缀文件，
> 绝不会出现"看起来正常、内容是坏的"文件。

### 7R.10 错误与状态码

响应体与 §7 一样：`{"error": "<码>", "message": "<给人看的一句话>"}`。

| 码 | HTTP | 何时 | 客户端该怎么办 |
|---|---|---|---|
| `TOKEN_INVALID` | `403` | `?k=` 缺失或不匹配 | 提示重新扫码 |
| `TOKEN_USED` | `410` | `token` 已被消费过一次 | 提示在电脑上重新发起 |
| `NOT_AUTHED` | `401` | 还没过握手就访问要 `SID` 的端点 | 先走 §7R.5 |
| `BAD_SID` | `401` | `X-Flicker-Sid` 不对（**没带也算**：空串同样不匹配） | 重新握手。⚠️ 握手**之前**访问这些端点是 `NOT_AUTHED`，不是 `BAD_SID` |
| `CHALLENGE_MISMATCH` | `401` | `challenge` 不是刚发的那个 | 中止（可能是重放） |
| `BAD_PROFILE` / `E_DOWNGRADE` | `500` | 回执了不认识的构造 / 报价被改过 | 中止（§4.3 的降级保护）。⚠️ 见下面那条注明：这两个码**没登记**进接收模式的映射表，所以状态码是兜底的 `500`，不是 `400` —— 客户端按"中止"处理，别依赖这个数字 |
| `BAD_PASSWORD` | `401` | 手机算的 MAC 不对 | 重试（区分大小写与空格）；第 5 次销毁 |
| `TOO_MANY_FAILURES` | `410` | 失败到达上限（5 次） | 会话已销毁，去电脑上重新发起 |
| `DESTROYED` | `410` | 会话已销毁 | 同上 |
| `BAD_MANIFEST` | `400` | 清单解不开（密码不一致或被改过） | 会话销毁；提示重新发起 |
| `EMPTY_MANIFEST` | `400` | 清单里一个文件都没有 | 中止（少选了一些？） |
| `MANIFEST_TWICE` | `409` | 清单发了第二次 | 客户端缺陷（清单是原子的） |
| `TOO_MANY_FILES` / `TOO_MANY_BYTES` | `413` | 超过 `limits` 报的上限 | 少选一些再发 |
| `E_PATH_UNSAFE` | `400` | 文件名带分隔符或不过那 12 条规则 | **中止整个会话**，未写任何字节 |
| `E_MANIFEST_DUPLICATE_PATH` | `400` | 清单里有重名 | 同上 |
| `BAD_CHUNK_BYTES` / `BAD_CHUNKS` | `400` | 分块参数不自洽 | 中止（AAD 绑了总块数，硬发必然失败） |
| `BAD_CHUNK` | `400` | 分块请求体太短（< 16 字节，连 tag 都装不下） | 中止；正常客户端不会触发 |
| `NO_SPACE` | `507` | 可用空间 < 总量 × 1.1 | **开工前**拒绝；清出空间后重来 |
| `NO_MANIFEST` | `409` | 还没发清单就来发块、或直接收尾 | 客户端顺序错了（清单必须先发） |
| `INCOMPLETE` | `409` | `finish` 时还缺块 | 先 `GET /up/status`，补发缺的块 |
| `ALREADY_FINISHED` | `409` | 重复 `finish` | 客户端缺陷 |
| `E_CHUNK_AUTH` | `400` | 单块认证失败 | 重发这一块 |
| `TOO_MANY_BAD_CHUNKS` | `400` | 连续坏块到达上限（10） | 会话销毁 |
| `BODY_TOO_LARGE` | `413` | 请求体超过该端点的上限 | 中止（正常客户端不会触发） |
| `NO_PAGE` | `404` | 服务没配页面（纯接口形态） | 只在自测与自动化里出现 |
| `NOT_FOUND` | `404` | 没有这个端点或方法 | 客户端缺陷 |

> **与 §8.2 的关系（如实说明）**：§8.2 那张 `E_*` 表是 L1/中继消息帧层面的**规划用**码表，
> 而 §7 与 §7R 这两个直连 HTTPS 端点实际回的是**上面这张表**的码 ——
> 唯一来源是 `src/session.js` 的 `errorBody()` 与 `src/upload-server.js` 的 `RECV_ERROR_STATUS`
> （接收模式独有的码只在后者登记，握手那几个码沿用前者，避免同一个码在两处给不同状态码）。
> 两套命名目前**并不统一**，这一点不掩饰：照 §8.2 去写直连客户端是错的，照本节写才对。
>
> **另一处如实说明**：**两张表都没登记**的码会落到 `errorBody()` 的兜底 `500`
> （上表里的 `BAD_PROFILE` / `E_DOWNGRADE` 就是这种情况）—— 那是"实现没登记"的结果，
> 不是设计。客户端遇到 `500` 应当按"中止"处理，而不是按"服务端故障、可以重试"去分类。
>
> 上面这张表**不是手写猜测**：`gen/check-recv-protocol-doc.mjs` 会拿
> `RECV_ERROR_STATUS` 加上那条兜底规则，把每一行的状态码逐条核对 ——
> 客户端要知道的确切数字，与实现必须来自同一个地方。

### 7R.11 TLS、证书与链接

与 §7.4 同一条硬约束：接收模式**必须**走 HTTPS，因为手机页面要用 `crypto.subtle`（WebCrypto），
而浏览器只在**安全上下文**里提供它 —— `http://192.168.1.5` 不是安全上下文，`crypto.subtle` 直接是 `undefined`。

| 项目 | 接收模式的做法 |
|---|---|
| 监听地址 | 默认 `0.0.0.0`（局域网可达），端口默认**随机** |
| 证书 | 会话级 CA + 由它签发的服务器证书，`subjectAltName` 含本机全部 IPv4 与 `127.0.0.1`、`localhost` |
| 装入本机信任库 | **默认不装**（`--trust` 才装）。手机那边装不了任何证书，所以装了也帮不到手机 |
| 手机第一次打开 | 必然看到一次"不安全"提示 → 点「高级 → 继续前往」。页面上必须把这句话写清楚，否则用户以为程序坏了 |
| 链接形状 | `https://{本机IPv4}:{port}/?k={token}`（与 §7 同一个 `?k=` 形状） |
| 等对方发来 | 默认 10 分钟没人连上就销毁 |
| 结束后的销毁链 | 会话密钥与验证值清零 → 服务关闭 → 一次性链接失效 → 会话证书从信任库/个人库移除 → 临时证书目录删除 → **收到的文件保留在目标目录**（这一条与发送端**措辞相反**：发送端说"原始文件未被改动"，接收端必须说"收到的文件已保留在 …"） |

> **为什么接收模式默认不装信任库**：证书要装进**手机**的信任库才有用，而手机那边做不到
> （iOS/Android 都不允许网页或程序静默装根 CA）。所以这条路的设计前提就是"用户点一次继续前往"，
> 而不是假装能做成零警告。装到电脑自己的信任库只对"用本机浏览器自测"有意义。

### 7R.12 这条路不做什么（诚实清单）

| 不做的 | 原因 |
|---|---|
| 目录树 / 文件夹上传 | 手机浏览器只能选文件、选不了文件夹 —— 这是浏览器限制，不是没做 |
| 自赠程序（gift） | §9 的 gift 是"发送端把自己送给对方"；这条路的方向反了，手机上也没有可执行产物 |
| 断点续传的**块级跨会话**恢复 | 手机切后台回来能续（同一会话内先问 `/up/status`）；但关掉页面再回来 = 新会话 = 令牌已消费，做不到（同 §5.6 的限制） |
| 中继形态的接收模式 | 手机 → 中继 → 电脑 这条还没做（设计草稿里的 M3） |
| 多设备同时上传 | 一个接收服务只服务一个会话；`token` 一次性，5 次密码失败即销毁 |
| 真机（手机）实测 | ⏳ **还没做**：目前验到的是"手机页在真浏览器（headless Edge）里逐字节跑通"（`_lab/e2e-phone-browser.mjs`），**需要一台真手机**才能确认锁屏/切后台、iPhone、真实磁盘写入这些事（见 `路线图.md` 第 7b 项） |

## 8. 错误码表

### 8.1 编码规则

```
E_<UPPER_SNAKE>
```

- 每个错误码有**唯一**含义，不复用
- 新增错误码不构成协议破坏（接收方遇到不认识的码，按 `fatal` 字段处理即可）
- `fatal = true` 的错误**必须**立即触发销毁流程

| `E_ROOM_GONE` | ✅ | 会合 | 会话已超时或已被销毁，请重新发起 | 中止 |
| `E_ROOM_FULL` | ❌ | 会合 | 会合消息过多 | 重试一次后中止 |
| `E_TOKEN_INVALID` | ❌ | 会合 | 链接无效或已被使用 | 提示重新获取链接 |
| `E_TOKEN_CONSUMED` | ❌ | 会合 | 该链接已被使用过 | 提示重新获取链接 |
| `E_MAC_MISMATCH` | ❌ | 握手 | **密码不一致** | `failCount++`，按 §4.6 延迟后允许重试 |
| `E_REPLAY_DETECTED` | ❌ | 握手 | 检测到重复的握手请求 | `failCount++` |
| `E_TOO_MANY_FAILURES` | ✅ | 握手 | 失败次数过多，会话已销毁 | 立即销毁 |
| `E_HANDSHAKE_TIMEOUT` | ✅ | 握手 | 握手超时 | 立即销毁 |
| `E_SESSION_TIMEOUT` | ✅ | 会话 | 会话超过 10 分钟未完成 | 立即销毁 |
| `E_SID_MISMATCH` | ✅ | 清单 | 会话标识不一致 | 中止（可能是替换攻击） |
| `E_MANIFEST_INVALID` | ✅ | 清单 | 文件清单格式错误 | 中止 |
| `E_MANIFEST_DUPLICATE_PATH` | ✅ | 清单 | 清单中存在重复路径 | 中止 |
| `E_PATH_UNSAFE` | ✅ | 清单 | 清单包含不安全的路径，已拒绝 | 中止（**不显示具体路径**，避免诱导用户手动创建） |
| `E_FILE_TOO_LARGE` | ✅ | 清单 | 单个文件超过 64 GiB 上限 | 发起方在扫描阶段即报错 |
| `E_CHUNK_AUTH_FAILED` | ❌ | 数据面 | 数据块校验失败 | 重试该块；连续 3 次 → `E_TRANSFER_ABORTED` |
| `E_GIFT_UNSIGNED_ONLY` | ✅ | 应用 | 对方声称赠送的程序带签名，而本版本无法验证签名 | 中止。**不得**降级为"当作可信"或"当作普通文件" |
| `E_GIFT_PLATFORM_MISMATCH` | ❌ | 应用 | 赠送的程序与本机平台不符 | **仅在协议层校验失败时使用**（如 SEA 形态却填 `any`）。仅平台不同的正常情形**不报错**（G7） |
| `E_BAD_SEQ` | ❌ | 数据面 | 请求的数据块序号非法 | 接收方修正后重试；不应发生，属实现缺陷 |
| `E_UNAUTHORIZED` | ❌ | 数据面 | 会话未认证 | 接收方重新握手 |
| `E_SOURCE_CHANGED` | ✅ | 数据面 | 源文件在传输过程中被修改或删除 | 中止（**不重试** —— 重试会得到不一致的数据） |
| `E_RATE_LIMITED` | ❌ | 数据面/会合 | 请求过于频繁 | 按 `Retry-After` 等待后重试 |
| `E_NO_ROUTE` | ✅ | 传输 | 无法连接到对方 | 提示改用局域网或配置端口转发 |
| `E_DISK_FULL` | ✅ | 写盘 | 磁盘空间不足 | 中止，提示清理空间 |
| `E_USER_CANCELLED` | ✅ | 任意 | 用户取消了传输 | 立即销毁 |
| `E_DESTROYED` | ✅ | 任意 | 会话已销毁 | 正常终态，UI 显示销毁清单 |

### 8.3 错误消息的线格式

```json
{
  "v": 1,
  "type": "ERROR",
  "seq": 7,
  "from": "i",
  "ts": 1765500000000,
  "body": {
    "code": "E_MAC_MISMATCH",
    "detail": "attempt 2 of 5",
    "fatal": false,
    "retry_after_ms": 2000
  }
}
```

| `body` 字段 | 必需 | 说明 |
|---|---|---|
| `code` | 是 | §8.2 中的码 |
| `detail` | 否 | **必须脱敏**：不得含密码、密钥、文件名、文件内容 |
| `fatal` | 是 | 是否终止会话 |
| `retry_after_ms` | 否 | 建议的重试等待 |

## 9. 自赠程序（Program Gift）

> **对齐说明**：本节的协议部分已与 `架构决策.md` 第三章（自赠程序）**对齐完成**，对齐结论如下：
>
> | 架构决策 | 协议落点 |
> |---|---|
> | §3.2 自赠是"清单里的一个普通文件条目"，默认开启但可关闭 | §9.2 的 `gift` 对象 + `files[].gift` 标记；**是否附带由用户界面决定，协议层不强制** |
> | §3.3 送什么取决于程序自身的分发形态 | §9.1 的三种 `kind`/`platform` 组合 |
> | §3.4 SEA 单文件可执行程序是自赠的真正价值 | §9.2 的 `platform` 字段与 `entry` 指向的可执行文件 |
> | §3.5 链式传播 | 无需协议支持 —— 每个收到 gift 的站点自然获得完整的发起方能力 |
> | §5.3 自赠文件名带版本号 | `entry` 建议形如 `flicker-1.0.0-windows-x64.exe`，便于接收方一眼看出新旧 |

### 9.1 概念

**gift** 是 manifest 里被标记为「程序」的条目。它让发起方可以把自己**运行的这个程序**随文件一起送过去，从而使对方：
1. 在**没有**发送方在场时也能独立发起传输
2. 在支持自动下载程序的浏览器上**一键获得站点能力**

**协议层的核心约束：gift 在线上与普通文件**完全相同** —— 同样的分块、同样的加密、同样的完整性校验。**协议不为 gift 引入任何特殊分块、特殊通道或特殊权限。**

#### 9.1.1 送出什么形态，取决于站点自己是什么形态

`架构决策.md` §3.3 要求程序能分辨"我是怎么被分发的"，据此决定赠品形态：

| 站点自身的形态 | `gift.kind` | `gift.entry` 指向 | `gift.platform` | 对方拿到后 |
|---|---|---|---|---|
| **单文件可执行程序**（SEA 打包） | `"flicker-station-sea"` | 该可执行文件自身 | `win32-x64` 等 | 双击即可运行，**零依赖** ⭐ |
| **从源码目录运行** | `"flicker-station-source"` | 打包后的源码归档 | `any` | 需先装 Node.js 24+，归档内含 `启动.cmd` 引导 |
| **npm 全局安装** | `"flicker-station-source"` | 同上的源码包 | `any` | 同上 |

| `kind` 值 | 含义 |
|---|---|
| `"flicker-station-sea"` | 单文件可执行站点（无外部依赖） |
| `"flicker-station-source"` | 源码形态站点（依赖 Node.js 24+） |
| 其他 | 保留。接收方遇到不认识的 `kind` 时，**按普通文件处理**，不做"可运行"提示 |

实现判断方式：探测 `process.execPath` 与 `process.argv[1]` 的关系，判断自己是被 SEA 打包的单文件还是普通脚本（`架构决策.md` §3.3）。

> **`gift.platform` 与 `kind` 的组合语义**（本规范新增，用于消除歧义）：
>
> | `kind` | `platform` 取值 |
> |---|---|
> | `"flicker-station-sea"` | **必须是具体平台**，如 `win32-x64`、`darwin-arm64`、`linux-x64` |
> | `"flicker-station-source"` | **必须是 `"any"`** —— 源码形态与平台无关
>
> `platform` 为 `"any"` 时，`E_GIFT_PLATFORM_MISMATCH` 永不触发（§8.2）。

### 9.2 manifest 中的表达

> ⚠️ **本节此前与实现不一致，已改正（2026-10）。** 分两部分说清楚：
>
> **① 实现真正下发的 `gift` 字段**（`src/prepare.js`，2026-10 用真实代码核对）：
>
> ```json
> "gift": {
>   "name": "flicker-1.0.0-windows-x64.exe + flicker-1.0.0-source.fkz",
>   "names": ["flicker-1.0.0-windows-x64.exe", "flicker-1.0.0-source.fkz"],
>   "kind": "flicker-station-sea",
>   "platform": "win32-x64",
>   "note": "对方双击即可运行，不需要安装任何东西",
>   "count": 2
> }
> ```
>
> 它只是**给接收端看的一行摘要**（界面上显示"对方还送了你什么"）。
> 赠品在 `files[]` 里就是**普通文件**，靠 `files[].kind` 区分
> （`"flicker-station-sea"` / `"flicker-station-source"`），**没有** `files[].gift` 布尔。
>
> **② 下面这套（`entry` / `signed` / G1–G7 / `E_GIFT_*`）是设计，尚未实现。**
> 保留它是为了说明"赠品要做成什么样子才算安全"，但**不要照它写客户端** ——
> 代码里没有 `E_GIFT_*` 这些错误码，接收端也不做这些校验。
> 真的要做时必须先补实现，再改这一节的措辞（顺序不能反）。
>
> 设计稿如下（`platform` 的取值规则见 §9.1.1，那部分是**已实现**的）：

```json
{
  "gift": {
    "kind": "flicker-station-sea",
    "platform": "win32-x64",
    "version": "1.0.0",
    "sha256": "<BASE64, 32 字节>",
    "signed": false,
    "entry": "flicker-1.0.0-windows-x64.exe"
  },
  "files": [
    {
      "index": 3,
      "rel": "flicker-1.0.0-windows-x64.exe",
      "size": 41943040,
      "chunks": 40,
      "sha256": "<BASE64>",
      "chunkHashes": ["<BASE64>"],
      "kind": "flicker-station-sea"
    }
  ]
}
```

| 设计稿字段 | 类型 | 必需 | 说明 |
|---|---|---|---|
| `kind` | string | 是 | 程序种类，见 §9.1.1。`FLICKER/1` 定义 `"flicker-station-sea"` 与 `"flicker-station-source"`。其他值保留 |
| `platform` | string | 是 | `<os>-<arch>` 或 `"any"`，见 §9.1.1 |
| `version` | string | 是 | 程序版本 |
| `sha256` | string | 是 | BASE64 的 32 字节。**必须等于**对应 `files[].sha256` |
| `signed` | boolean | 是 | 是否有可信签名。`FLICKER/1` **一律为 `false`** |
| `entry` | string | 是 | 相对路径，**必须**匹配 manifest 中某个 `files[].rel` |

**一致性校验（接收方必须执行，按顺序）—— ⚠️ 以下是设计，代码里还没有这些校验：**

```
1. gift === null  → 无 gift，跳过本节全部逻辑
2. gift.kind 不在已知集合中 → 按普通文件处理，不做"可运行"提示，跳过 3~6
3. gift.signed !== false → ERROR(E_GIFT_UNSIGNED_ONLY)
     FLICKER/1 无法验证签名；若对方声称 signed=true，说明它用了更新的协议，
     而我们无法验证该声称。绝不能因为"它说有签名"就当作可信 → 必须终止
4. gift.sha256 !== 对应 files[].sha256 → ERROR(E_MANIFEST_INVALID)
5. gift.entry 未出现在任何 files[].rel 中 → ERROR(E_MANIFEST_INVALID)
6. 不存在 files[].kind === "flicker-station-*" 且 rel === gift.entry → ERROR(E_MANIFEST_INVALID)
7. gift.kind 为 "flicker-station-sea" 且 gift.platform === "any" → ERROR(E_MANIFEST_INVALID)
8. gift.platform !== "any" 且与本机平台不符 → 不报错，仅取消"可运行"提示（G7）
```

### 9.3 接收端的识别与处理规则

> ⚠️ **这一节同样是设计，代码里只有 G2/G3/G4/G5 的精神被实现了**
> （不自动执行、不静默覆盖、路径规则一视同仁、整体校验一视同仁 —— 但它们不需要
> `gift` 字段就能做到，因为赠品在实现里就是**普通文件**）。
> G1/G6/G7 依赖 `files[].gift` / `gift.signed` / `gift.platform` 这些**尚未实现**的字段，
> 照它写客户端会读到 `undefined`。

| 规则 | 内容 |
|---|---|
| **G1 识别** | `manifest.gift !== null` 或存在 `files[].gift === true`（设计稿；实现里看 `files[].kind`） |
| **G2 绝不自动执行** | 接收方**永不**自动运行、自动打开、自动注册 gift。必须由用户显式操作 |
| **G3 永不自动覆盖** | 若目标路径已有同名文件，必须走普通的重名处理（重命名 / 询问），**不得**静默覆盖 |
| **G4 路径规则同样适用** | gift 的 `rel` 必须通过 §6.2 **全部**校验。**gift 不享有任何豁免** |
| **G5 完整性校验不可省** | gift 文件的 `sha256` 与 `chunkHashes` 校验与其他文件**完全相同**。校验失败 → `E_CHUNK_AUTH_FAILED` |
| **G6 UI 必须区分** | gift 在 UI 上必须与普通文件**明显区分**，并标注"未经验证"（因为 `signed = false`） |
| **G7 平台不匹配不报错** | 若 `gift.platform` 与本机平台不符（且不为 `"any"`），**仍然正常传输文件**，只是不做"可运行"提示。**这不是错误**，不进错误码表 |
| **G8 可选下载不算 transfer 成功** | 用户拒绝保存 gift **不构成**传输失败。其他文件照常校验与完成 |
| **G9 不影响会话生命周期** | gift 的有无**不改变**销毁时机与销毁范围 |

> **`signed = false` 的含义必须诚实呈现**：接收方无法通过密码学手段确认这个程序真的来自"闪传官方"。密码认证只证明**双方知道同一个密码**，不证明**发送方身份**。UI 上必须说清楚这一点，不能因为"有哈希校验"就让用户以为程序是可信的 —— 哈希只证明"传输没有损坏"，不证明"来源可信"。

### 9.4 与"站点模型"的关系

gift 的**分发通道**与**站点模型**相关（L0 载具层的三种来源，§1.1）：gift 让站点模型从"必须有 relay 托管页面"降级为"可以由对方直接给你程序"。

### 9.5 对齐状态：已完成

`架构决策.md` 第一章（站点模型）与第三章（自赠程序）已定稿，与协议的对应关系如下：

| 架构决策中的要求 | 协议如何满足 | 是否需要改协议 |
|---|---|---|
| C2：两侧对等，同一份程序两种角色 | 握手本就**角色无关**：`HELLO.from` 与 MAC 中的 `ROLE_*` 显式表达角色，`AUTH_REQ`/`AUTH_OK` 的方向由角色决定而非由"谁是服务端"决定 | **不需要**。协议从一开始就是对称的 |
| C3：自赠程序作为可选清单项 | §9.1–§9.4 | **不需要**。gift 就是普通文件 + 标记 |
| §3.5 链式传播 | 每个收到 gift 的站点即获得完整发起方能力，无需协议参与 | **不需要** |
| §2.4 GUI 与 CLI 共用内核 | GUI 是**前端**，通过进程内事件流取数据，不经线协议 | **不需要** |
| §4.3 会话级证书自动装卸 | §7.4 定义了证书策略与实测结论 | **不需要改线格式**，但阻塞 P0 的可行性验证 |

> **结论**：`架构决策.md` 没有引入任何新的线上行为。协议无需为站点模型、GUI 或自赠程序做结构性改动 —— 这也验证了 §2.1 把套件层与流程层分离、以及本协议一开始就采用角色无关握手的价值。

**唯一需要留意的边界**：站点本地界面服务（`127.0.0.1`）明确不在协议范围内，仅有一条硬性要求 —— **只监听 loopback**（§3.7）。

     │ room_name = HEX(K_room)  │                          │
     │                          │                          │
     │ ══ L1 会合 ══             │                          │
     │ 终端显示：密码 + 链接 + 二维码（链接含 token 与 S）      │

     │                          │                          │
     │ 发 ENDPOINT{urls}        │                          │

     │                          │     B 从 fragment 读 S 与 token

## 11. 安全考量

### 11.1 relay 在信任边界中的位置

**明确假设：relay 是不可信的（untrusted）。**

| relay 能看到 | relay 看不到 | 原因 |
|---|---|---|
| `room_name`（64 hex） | 密码 `P` | `room_name = HEX(HKDF(PBKDF2(P,S)))`，单向 |
| 消息的**大小**与**时间** | 盐 `S`、令牌 `token` | 放在 URL fragment，不进 HTTP 请求（§4.4.2） |
| 双方消息的 `type`、`ts`、`from` | 会话密钥 `K_auth`/`K_job` | 永不上线 |
| 连接双方的 IP 与 UA | **文件名** | manifest 整体加密（§6.3） |
| 明文摘要：文件数量与总字节数 | **文件内容** | L5 分块加密；且**数据根本不经过 relay**（§3.1） |
| `agent` 字符串（若发送） | 目录结构 | 在加密的 manifest 中 |

**relay 能做的攻击**：

| 攻击 | 是否可行 | 缓解 |
|---|---|---|
| 读取文件内容 | ❌ 不可能 | 数据不经过 relay + 端到端加密 |
| 修改文件内容 | ❌ 不可能 | GCM 标签 + AAD 绑定 `SID` |
| 学习密码 | ❌ 不可能 | 密码从不上线 |
| 拒绝服务（不回消息） | ✅ 可行 | 表现为超时，UI 明确报错；可换 relay 重试 |
| 削成套件列表（降级攻击） | ✅ **但会被检测** | `suite_id` 绑定在 MAC 中（§2.6）：双方选的套件不同 → MAC 必然失败 |
| 用旧会话的 manifest 替换 | ✅ 尝试 | `manifest.sid === SID` 校验（§6.3 第 5 步） |
| 观察元数据（谁在传、多大） | ✅ **不可避免** | 见下表 §11.2 |

### 11.2 元数据泄露（诚实清单）

以下信息**必然**被 relay 观察到，无法通过加密隐藏：

| 泄露项 | 严重性 | 可能的缓解（未实现） |
|---|---|---|
| 通信双方 IP、时间 | 中 | 用 Tor / VPN（超出本项目范围） |
| 传输文件的数量与总大小 | 低-中 | 填充（padding）到固定档位（**未实现**，会牺牲带宽） |
| 房间名（随机 64 hex） | 低 | 无法避免（relay 必须能路由） |
| 传输持续时间 | 低 | 无法避免 |

**缓解元数据泄露的手段明确不在 `FLICKER/1` 的范围内。** 若将来要加填充，那是**新增字段**（符合 §0.1），不是修改现有行为。

### 11.3 抗重放

| 层面 | 机制 |
|---|---|
| 握手 | `nonce_r` / `nonce_i` 每次随机 32 字节；`mac_r` 里含 `nonce_r` |
| 会话 | `SID` 混入 `K_job`，跨会话密钥不同 |
| 数据块 | AAD 含 `SID` 与 `seq`，块不能跨会话或跨位置搬运 |
| 会话内块重放 | `seq` 唯一 + IV 由 `seq` 派生 → 同一 `seq` 的块只能有一份合法密文 |
| 房间消息重放 | relay 的 `cursor` 单调 + 客户端按 `(from, seq)` 去重 |

### 11.4 抗篡改

| 目标 | 机制 |
|---|---|
| 密文篡改 | GCM 标签（16 字节） |
| 块重排 | AAD 含 `BE64(seq)` |
| 跨文件拼接 | AAD 的 `seq` 高 48 bit 是 `fileIndex` |
| 截断 | AAD 含 `BE32(totalChunks)` |
| 文件替换 | `files[].sha256` + `files[].chunkHashes` |
| manifest 替换 | `manifest.sid === SID` 校验 |
| 套件降级 | `suite_id` 绑定在 `mac_r`/`mac_i` 中 |
| 路径穿越 | §6.2 的 12 条规则（安全边界） |

### 11.5 密码永不上网线（完整论证）

```
线上出现过的所有与密码相关的量：
  ① room_name = HEX(HKDF(PBKDF2(P,S,600000),"room"))     → 单向，不可反推
  ② mac_r / mac_i = HMAC(K_auth, ...)                     → 单向，且 nonce 一次性
  ③ manifest_ct / 密文块 = AEAD(K_job, ...)               → 单向

从未出现在线上的量：
  P（密码）、S（在 fragment 或 TLS 内）、V、K_auth、K_enc、K_job、nonce_i 的原始值（明文发送但不敏感）
```

**抓包者能得到的结论**：只有"有人在做一次传输"。它无法离线暴力破解出密码，因为：
- 唯一的密码相关输出是 `room_name`，而它是一个 HKDF 输出，**PBKDF2 的结果 `V` 从未暴露**
- 即使拿到 `mac_r`，要验证一次密码猜测需要：猜 `P'` → PBKDF2 60 万轮 → HKDF → HMAC → 比较。**每次猜测的成本 = 60 万轮 PBKDF2**
- 而 `nonce_r` 是一次性的，所以预计算表**无效**

> **残余风险**：**弱密码**。若用户把密码设成 `123456`，攻击者抓到 `mac_r` 后可以离线枚举（每次 60 万轮 PBKDF2 约 0.1~0.5 秒，`123456` 只需一次尝试）。这就是为什么发送端**默认生成强密码**（4 词 ≈ 52 bit）且**必须二次确认**。**这是本协议唯一无法用密码学解决的风险，只能靠 UI 引导。**

### 11.6 前向保密（诚实说明）

`FLICKER/1` **不提供前向保密（forward secrecy）**。原因：密钥完全由密码派生，没有 Diffie-Hellman 交换。若密码事后泄露，且攻击者保存了当时的密文，则可以解密。

**缓解**：
- 会话生命周期以分钟计（10 分钟超时），且 `ivSalt` 与 `S` 每会话随机
- 密码默认随机生成，用完即弃
- `FLICKER/4`（X25519）将引入前向保密

**不得在 UI 或文档中宣称本协议提供前向保密。**
