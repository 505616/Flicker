# 跨网络中继：部署与原理

> 相关文档：`设计文档.md` 第三章（连接策略）、`行为与运行.md`（运行时行为）、`使用手册.md`（用户操作）

---

## 一、为什么需要它

**你不需要它，只要两台电脑在同一个网络下。** 同网络时用局域网直连，更快、更简单、什么都不用部署。

**只有当两台电脑在不同网络时**（一个在家、一个在公司），才需要中继。原因是物理性的：

```
实测你这台机器（见 设计文档.md 第二·补章）：
  出口公网 IP   122.195.16.66
  路径：192.168.1.1 → 192.168.1.1 → 100.111.216.1（运营商大内网）
  全局 IPv6     无
```

`100.64.0.0/10` 是运营商级 NAT 的专用段 —— 也就是说**你分到的公网 IP 是和别人共用的**。
发送端**没有任何可以被外部访问的地址**，所以必须有第三个人帮忙传话。

**但中继不是"看过内容再转发"，它搬的是箱子：**

```
发送端 ──密文──▶ 中继（按序号存放）──密文──▶ 接收端
         ↑                                    ↑
      密钥只在这里                        密钥只在这里
```

## 二、部署（一次，约 3 分钟）

> **⚠️ 先读这一段：默认地址可能"装好了却连不上"**
>
> 部署出来的默认地址是 `https://<名字>.<你的子域>.workers.dev`。
> 而 **`*.workers.dev` 这个域名在部分网络下被整体屏蔽** ——
> 2026-10 实测（国内网络）：它被解析到 `199.16.156.103`（**不属于** Cloudflare 的地址，是污染结果）、
> 443 端口超时；而同一时刻 Cloudflare 的**接口** `api.cloudflare.com` 是通的
> （所以部署能成功，访问却不行）。
>
> **如果两台电脑都在这种网络里，这个默认地址两边都连不上。**
> 中继本身没坏，是"这个域名到不了"。
>
> 两种应对，按省事程度：
>
> 1. **给它绑一个自己的域名**（约 30–60 元/年）。中继**不用重装**，只是换个地址 ——
>    见下面「想让地址稳定可用：绑一个自己的域名」。
> 2. **同一个网络就不用中继**：两台电脑在同一个 WiFi/内网时直接 `flicker send "文件"`，更快也更简单。
>
> 部署脚本现在会在装好后**自动探一次**那个地址：连不上会当场把原因和出路打出来，
> 不会让你对着一个"✅ 完成"却怎么都连不上。

```powershell
node relay/deploy.mjs
```

它会依次做：生成接收端页面模块 → 生成 `wrangler.toml` → 检查 wrangler → 引导登录 → 部署 → 打印地址 → **探一次地址是否可达**。

**需要一个免费的 Cloudflare 账号**（不需要信用卡）：<https://dash.cloudflare.com/sign-up>

只检查环境不部署：

```powershell
node relay/deploy.mjs --check
```

#### 如果登录卡住：改用 API 令牌（实测过的一条路）

国内网络上，Cloudflare 的**控制台域名** `dash.cloudflare.com` 经常连不上，而它的**接口** `api.cloudflare.com` 是通的（实测：控制台 12 秒超时，接口 HTTP 200）。而 wrangler 的浏览器登录**必须**走控制台域名 —— 症状是：浏览器里点了「允许」，命令行这边却报
`Could not reach the Cloudflare auth server … (UND_ERR_CONNECT_TIMEOUT)`，授权断在半路。

这时改用 **API 令牌**即可绕开（部署只走接口）：

1. 用 **Edge** 打开 <https://dash.cloudflare.com/profile/api-tokens>（Firefox 打不开这个页面时换 Edge —— 实测有效）
2. `Create Token` → 模板选 **Edit Cloudflare Workers** → `Continue` → `Create Token`
3. 复制那串字符，粘进 `relay/api-token.txt` 并保存（该文件被 `.gitignore` 与赠品的排除清单挡在外面，有机器判据盯着"凭据绝不许进赠品"）
4. 重新跑 `node relay/deploy.mjs` —— 它会自动读到令牌、跳过浏览器登录

> 两个常见前提：新账号要**先验证邮箱**才允许创建令牌；账号还要注册一个 `workers.dev` **子域名**（首次发布 Worker 的前提）。子域名也能用令牌调接口注册，不必开浏览器：
> `node _lab/cf-register-subdomain.mjs <账号ID> <想要的子域名>`（账号 ID 在部署报错里能看到）。
> 令牌用完可以在同一页面 `Delete` 作废 —— **作废不影响已经装好的中继**。

### 想让地址稳定可用：绑一个自己的域名

默认的 `*.workers.dev` 地址在部分网络里到不了（见本章开头那段）。**中继不用重装**，绑一个域名就换个地址：

1. **准备一个域名**（约 30–60 元/年，`.top`/`.xyz`/`.com` 都行）
2. **把域名加进 Cloudflare**：控制台 → `添加站点` → 填域名 → 按提示到域名商那里把 **NS（名称服务器）**改成 Cloudflare 给的两个地址 → 等它显示 `活动`（通常几分钟到几小时）
3. **把域名绑到这个 Worker**：控制台 → `Workers 和 Pages` → 选 `flicker` → `设置` → `域和路由` → `添加` → `自定义域` → 填 `relay.你的域名`（这个子域名可以随便起）→ 保存

绑好后地址就变成 `https://relay.你的域名`，发送时照旧：

```powershell
flicker send "D:\文件.zip" --relay=https://relay.你的域名
```

> ⚠️ 老实说：**这条不保证一定通**。国内到 Cloudflare 的链路时好时坏，但按实测经验，
> 自己的域名比 `*.workers.dev` 好得多（后者是被整体屏蔽的）。
> 绑好之后可以马上验一次：用浏览器打开 `https://relay.你的域名/health` ——
> 看到 `{"ok":true,...}` 就是通了；也可以用仓库里的脚本跑一次真实传输：
> `node _lab/verify-remote-relay.mjs https://relay.你的域名`。

### 部署之后怎么用

```powershell
flicker send "D:\文件.zip" --relay=https://flicker-relay-xxxxx.你的用户名.workers.dev
```

命令会打印一个链接。**把链接发给对方，密码用另一种渠道发**（比如链接发微信、密码打电话说）。
对方用浏览器打开链接、输入密码，文件就开始传。

**"一次"的意思是**：这个部署是永久的，之后每次传输都直接用那个地址，不再需要重复任何步骤。

### 免费额度

| 项 | 免费额度 | 一次传输的消耗 |
|---|---|---|
| 请求数 | 10 万/天 | 每个分块 1 次确认 + 1 次投递 ≈ 每 MiB 2 次请求 |
| 流量 | 无明确上限（按请求计） | 约等于文件大小 |

按"每 MiB 两次请求"算，10 万请求约合 **50 GB/天**。个人用途远远够用。

> 想更省：调大分块大小（`src/suite/flicker1.js` 的 `chunkBytes`）。
> 代价是内存占用和断点续传的粒度都变粗。

### 也可以不部署：局域网内的本地中继

```powershell
node relay/local.mjs --port=8787 --verbose
```

它和 Cloudflare Worker 用的是**同一份协议实现**，所以行为完全一致。
在同一个网络里，另一台电脑用 `--relay=http://<你的IP>:8787` 就能连上 ——
本质上和局域网直连一样，但可以顺带观察中继上发生了什么（`--verbose` 会打印每条转发的序号与长度）。

## 三、中继能看到什么、不能看到什么

这是设计的一部分，不是巧合。

| 中继**能看到** | 中继**看不到** |
|---|---|
| 一个 128 bit 的随机房间名 | 文件内容（AES-256-GCM 端到端加密） |
| 消息的序号与长度 | 文件名与文件大小（清单本身也是加密的） |
| 消息到达的时间 | 密码（**从不传输**） |
| 双方的 IP（网络层必然可见） | 盐（放在 URL fragment 里，浏览器不发给服务器） |

**把中继换成一台被完全攻破的机器，它能做到的只有两件事：**
拒绝服务、记录元数据。它改不了内容 —— 每个分块都有 GCM 认证标签，
任何一个字节被改动都会在接收端解密时被发现。

### 房间名就是凭据

房间名不是随机分配的，而是**由密码派生**的：

```
密码 → PBKDF2(60万次, 盐) → V → HKDF("room") → 房间名（64 位十六进制 = 128 bit）
```

于是：
- 只有知道密码的人算得出房间名（**这就是"两台电脑密码必须一致"的落点**）
- 房间名是单向的，反推不出密码
- 128 bit 让它不可枚举（早期版本用的是 64 bit，理论上可暴力尝试，已经加长）
- 它只出现在 URL 的 `#` 之后，**浏览器不会把 fragment 发给服务器**

所以中继不需要第二套授权机制：**知道房间名 ≡ 知道密码**。
而加密密钥（`HKDF("enc")`）与房间密钥是分开派生的，所以中继知道了房间名也解不开任何东西。

> **一个踩过的设计弯路**：最初给中继加了"授权密钥"（房间创建时登记，之后每个请求出示）。
> 测试立刻暴露了一个**先到先得的竞态**：房间不存在时，第一个到达的请求决定了登记哪把密钥 ——
> 攻击者用自己派生的密钥抢先建了同名房间，就能把真正的发送端挡在外面。
> 换成"房间名即能力"之后这个问题自然消失了。

## 四、协议

```
POST /r/:room              创建房间（幂等；返回 created 与当前进度）
POST /r/:room?seq=N        放入第 N 条消息（逐条投递；seq 由调用方指定）
POST /r/:room/batch        放入**一批**消息（序号由**服务端**按到达顺序分配）
GET  /r/:room?seq=N        取走第 N 条消息（接收端，不删除）
POST /r/:room/ack?upTo=N   确认并删除前缀（接收端）
GET  /r/:room              房间状态（两端用它对齐进度）
DELETE /r/:room            销毁房间
GET  /health               健康检查（无副作用）
GET  /                     接收端页面
```

`/batch` 的请求体是若干条消息按顺序拼起来的，每条前面加 4 字节大端长度：

```
[4 字节长度][消息][4 字节长度][消息]...
```

所以要它、而不是让发送端并发发 N 条 `?seq=N` 的原因：
**中继要求严格按序投递**，而并发请求的到达顺序不保证，
必然撞 `409 BAD_SEQ`（而且服务端给所有撞车请求报的是同一个期望序号，
它们重试时又撞在一起）。让服务端分配序号，是"严格按序"与"高吞吐"
能共存的唯一干净解法。一批最多 64 条。

### 消息格式

房间只搬运**不透明的字节**，不理解内容。但接收端需要区分类型，所以第一个字节是标记：

```
0x01 + salt(16) + iv(12) + tag(16) + 密文     清单
0x02 + tag(16) + 密文                          一个文件分块
```

**单条消息上限与能力协商（2026-10）**：一条消息就是一个分块，所以"单条上限"
就是"允许的最大的块"。中继必须在 `GET /health` 的响应里声明
`maxMessageBytes`（创建房间的响应里也带一份）：

```json
{ "ok": true, "maxMessageBytes": 2097169, "protocol": 1 }
```

- 协议**保证的最小值**是 `1 MiB + 17`（块 + 类型字节 + 认证标签）——
  任何符合规范的中继都要收得下它，客户端在**读不到**声明时也按它走。
- 本项目的部署默认声明 **`2 MiB + 17`**（实测：往返 195 ms、链路 29.5 MB/s 时，
  块 1 MiB 端到端 18.9 MB/s、2 MiB 是 26.3 MB/s、4 MiB 没有额外收益）。
- 想改这个值就改 `RoomStore` 的 `maxMessageBytes`
  （`relay/local.mjs` 与 `relay/worker.js` 都用默认值）。
- **客户端会自动适配**：发送端取 `min(想要的, 你声明的)`，
  所以你把上限调大调小都不会让谁的传输失败；老部署不声明也不会 ——
  那正是这条协商存在的理由。

### 投递模型：拉取式 + 在途窗口

分块**按需投递**，不是一次性全推上去：

```
seq 0        清单 —— 房间一建立就放进去
seq 1..N     分块 —— 根据"接收端消费到哪了"按窗口投递
```

发送端保持"未确认的消息不超过 `windowSize` 条"（默认 8）。好处：
- 发送端内存恒定（不为整份文件排队）
- 接收端慢的时候发送端自然停下来等
- 中继上任何时刻只有有限条在途密文（默认最多 8 MiB）

> **为什么不是 1**：窗口 1 就是停等协议，速度被死锁在 `块大小 ÷ 往返延迟`。
> 实测 195 ms 延迟下只有 4.72 MB/s，而同一链路本身能跑 29.5 MB/s ——
> 瓶颈在实现。改成窗口 8 并**批量投递**后实测 20.75 MB/s（**4.4×**）。
> `--window 1` 可以退回停等（低带宽省流时有用）。


### 三个判据（都是踩过坑才定下来的）

| 判据 | 为什么 |
|---|---|
| **待投递的序号由服务端的 `nextSeq` 决定**，不是本地计数 | 本地计数一旦与服务端不一致（重连、并发），下一个分块就会报"序号不连续" |
| **`ack` 是前缀删除，且删后不重新编号** | 早先的实现删掉前缀后把剩余消息重新编号，于是接收端记着的序号全部错位 |
| **完成的判据是 `ackedBase >= total`** | 最初用 `posted >= total && pending === 0`，会在"接收端取走了最后一条但还没确认"时误报完成，然后销毁房间 —— 那条数据对方永远拿不到 |
| **销毁前要等在途的那一批投递结束** | 批量投递在 `await` 读分块期间会让出控制权（`putBatch` 不是原子的）。此刻若用户点"取消"，DELETE 会**先于**那条 batch POST 到达服务端：房间被删，随后到达的 POST 拿到 404，一次**正常取消**被报成中继错误。所以 `destroy()` 先把在飞的那一批等完再删房间，投递循环每轮重新问一次中止判据。这个竞态是端到端测试用精确的顺序断言抓出来的，读代码看不出来 |

## 五、"用完即销毁"在中继上的体现

| 时机 | 发生什么 |
|---|---|
| 每条消息被确认 | 中继立刻删除它（**前缀删除**） |
| 传输完成 | 发送端 DELETE 房间 |
| 15 分钟无活动 | 房间整体过期（中继侧的 TTL 兜底） |
| 中继进程重启 | 所有房间消失（消息只在内存里） |

**中继不写磁盘。** 这一条有测试盯着：`test/relay-protocol.test.js` 会检查
`relay/worker.js` 里没有出现 KV / D1 / R2 / Durable Objects ——
如果有人加了持久化设施，测试会失败，提醒他重新审视这个承诺。

## 六、安全边界（诚实清单）

**不防的：**
- **中继能看到元数据**：有人在这个时间传了东西、传了多大（按消息数与长度可估）
- **中继能拒绝服务**：它不转发，两端就连不上
- **弱密码**：房间名由密码派生，弱密码理论上可枚举（默认生成的 4 词密码约 52 bit，
  配合 128 bit 房间名与短 TTL，实际不可行）
- **端点被控**：木马能看到一切，加密解决不了这个

**防的：**
- 中继读不到文件内容、文件名、文件大小
- 中继拿不到密码，也拿不到盐
- 中继改不了内容（每块都有认证标签，改动必然被发现）
- 房间不可被他人认领或抢占（没有"先到先得"的登记过程）

## 七、故障排查

| 现象 | 原因与处理 |
|---|---|
| `中继错误：房间不存在或已过期` | 房间 15 分钟无活动自动清理；或发送端已退出。重新发起传输 |
| 一直停在"等待对方连接" | 对方还没打开链接，或没输密码。检查你给的链接是否完整 |
| 对方说"房间已经不存在了" | 发送端已退出或超时。用 `--timeout=30m` 拉长 |
| `中继探测未通过` | 地址写错、或中继没部署成功。浏览器打开那个地址应该看到接收页 |
| 大文件传到一半断了 | 检查发送端是否还在运行。接收端会等（有重试），但发送端退出房间就没了 |
| `--relay` 地址是 http 而不是 https | 本地中继可以，公网中继必须是 https（浏览器要求安全上下文） |
| 部署成功、但那个地址**打不开**（两边都连不上） | 你的网络可能屏蔽了 `*.workers.dev`。**实测（2026-10，国内网络）**：域名被解析到 `199.16.156.103`（**不是** Cloudflare 的地址，是污染结果），443 端口超时；同一时刻 `api.cloudflare.com` 是通的。中继本身没坏，是这条网络到不了它。两条出路：给它绑一个**自己的域名**（Workers → 自定义域，域名通常不被这样挡），或改用自建中继（需要域名 + 证书才有 https） |
| 部署时报 `Could not reach the Cloudflare auth server` | 连不上控制台域名 `dash.cloudflare.com`（接口却是通的）—— 见上面"如果登录卡住：改用 API 令牌"。另外新账号还要**先验证邮箱**、并注册一个 `workers.dev` 子域名，否则创建令牌或发布都会失败 |
