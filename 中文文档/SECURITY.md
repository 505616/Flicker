# 安全模型与威胁模型

> 本文说明闪传（Flicker）**保护什么、不保护什么**，以及为什么。
> 结论都对应到具体代码与测试，你可以逐条自行核验（见 §8）。
>
> **一句话**：文件内容用 AES-256-GCM 端到端加密，密钥由密码派生、只存在于两台电脑上；
> **中继会经手全部密文，但读不出内容、看不到文件名**。密码从不上线。

---

## 1. 设计目标与非目标

### 要保护的

| 目标 | 手段 |
|---|---|
| **文件内容**不被中继、网络中间人读到 | AES-256-GCM，密钥只存在于两端内存 |
| **文件名与目录结构**不被中继读到 | 整个清单（manifest）加密后再上传 |
| **密码**不泄露给任何第三方 | 密码从不上线：两端各自用它做挑战—应答 |
| **"必须两台电脑密码一致"** 这条约束 | 房间名 = HKDF(密码派生密钥)，算不出来就找不到房间 |
| **用完即销毁** | 传输完成即删除房间；密钥清零；会话证书移除 |

### 明确**不是**目标的

| 不防 | 为什么 |
|---|---|
| **弱密码被猜到** | 见 §4.2。程序默认生成强密码，但不强制 |
| **两端电脑本身已被控制** | 键盘记录器、木马、恶意浏览器扩展 —— 任何软件都防不住 |
| **流量分析** | 中继能看出"有人在传、有多大、传了多久" |
| **中继拒绝服务** | 中继可以随时不服务（它是不可信的，只要求它不**能读懂**） |
| **接收端本地的取证痕迹** | 文件按用户选择落盘，程序不负责擦除 |
| **量子计算** | 见 §6.4 |

## 2. 信任边界

```
┌─────────────┐         ┌──────────────┐         ┌─────────────┐
│  发送端      │         │    中继       │         │  接收端      │
│  (Node)     │         │ (Cloudflare) │         │  (浏览器)    │
├─────────────┤         ├──────────────┤         ├─────────────┤
│ 明文        │         │ 只看到密文     │         │ 明文        │
│ 密码        │  ────▶  │ 房间名         │  ────▶  │ 密码        │
│ 密钥        │  密文    │ 消息长度/时序  │  密文    │ 密钥        │
│ 原始文件(只读)│        │ 两端 IP        │         │ 落盘文件     │
└─────────────┘         └──────────────┘         └─────────────┘
       ▲                                                ▲
       └──────────── 密码只在两端的这条虚线之外 ───────────┘
                  （它从不经过中间那条线）
```

**核心假设：中继完全不可信。** 它可以记录一切、可以篡改一切、可以随时停止服务。
加密的设计不依赖它的诚实。

### 2.1 发送端有两种形态（2026-10 起）

上面的图里发送端是"Node 程序"。从 2026-10 起，**发送端也可以是中继托管的网页**
（`/send`，用于手机传给手机 —— 两边都只有浏览器时没有别的办法）。

| | 发送端 = 本机程序 | 发送端 = 中继托管的页面 |
| --- | --- | --- |
| 明文与密钥在哪 | 用户自己的电脑内存里 | 浏览器标签页的内存里 |
| 你要信谁的代码 | 你下载/构建的那个程序 | **中继运营者发给你浏览器的那份页面代码** |
| 中继能不能看到内容 | 不能（只有密文） | 不能（只有密文） |
| 密钥会不会经过网络 | 不会（密码只在两端，中继看不到） | 不会（房间名与盐在 `#` 之后，浏览器不发给服务器） |

⚠️ **这条差别必须说清**：网页发送端把"你信任的代码"从"自己机器上的程序"扩到了
"中继发的那份 HTML"。自己部署中继（本项目的默认用法）时这两者是同一个主体；
用**别人的**中继时，你等于同时信任他的页面代码 —— 这跟用别人的接收页是同一个假设，
不是新出现的能力，但以前发送端不受它影响。用户手册里已明确写出这一点，
不想接受这个假设的人仍然可以只用自己的程序发送。

其它不变：网页发送端同样**在出门前加密**（`src/suite/flicker1.js` 的同一套参数，
页面里是 `web/phone-core.js` 的实现，两边做过逐字节比对），中继拿到的仍然只有密文。

## 3. 密码学构造（精确参数）

| 项 | 值 |
|---|---|
| 套件标识 | `FLICKER/1` |
| 密钥派生 | `V = PBKDF2-HMAC-SHA256(密码, salt, 600000 次, 32 字节)` |
| salt | 16 字节随机，**放在 URL 的 `#` 之后**（浏览器不会把 fragment 发给服务器） |
| 派生三个密钥 | `HKDF-SHA256(V, label)`，label 分别为 `flicker/1/room`、`/auth`、`/enc` |
| 内容加密 | AES-256-GCM |
| 分块大小 | 1 MiB（可配） |
| 每块 IV | 12 字节 = `[4 字节 0][8 字节大端块序号]`。**确定性**，不随块随机 |
| 每块 AAD | 28 字节 = `文件序号‖块序号‖总块数‖明文长度`（全大端） |
| 认证标签 | 16 字节（每块独立） |
| 清单 AAD | 18 字节 ASCII `flicker/1/manifest`（**长度刻意与块的 28 字节不同**） |
| 逐块完整性 | 每块明文 SHA-256 放进（加密的）清单 |
| 整文件完整性 | 整文件 SHA-256，接收端边收边算增量摘要 |
| 双向认证 | HMAC-SHA256 挑战—应答，域分隔串 `flk1-recv` / `flk1-send`，并绑定套件号 |

### 为什么 IV 是确定性的（这点常被质疑）

块序号是唯一的，所以 `(密钥, IV)` 组合**永不重复** —— GCM 的安全性要求正是这一点。
接收端必须能**独立重算**任意块的 IV（断点续传时只能拿到部分块），
若 IV 随机就必须随包传输并额外保存。确定性在这里是**必需**，不是图省事。

代价：同样内容的两块（同序号）会产生相同密文 —— 但序号唯一，
且每块 AAD 绑定了长度，所以这个"相等"不泄露有意义的信息。

### 为什么清单的 AAD 长度与块不同

AAD 长度不同可以**防止跨类型混淆攻击**：把一个块的密文当成清单、或反过来，
认证会失败。18 与 28 是刻意选的 —— `src/suite/flicker1.js` 里有一条自检
（`MANIFEST_AAD.length === 28` 就报错），确保这个差异不会被以后的人无意改掉。

## 4. 威胁分析

### 4.1 恶意中继（最主要的威胁）

中继能看到什么、不能看到什么：

| 中继能看到 | 中继**不能**看到 |
|---|---|
| 房间名（64 位十六进制，128 bit） | 文件内容（只有密文） |
| 每条消息的大小与时间点 | 文件名、目录结构 |
| 消息总条数 | 文件个数、总大小 |
| 两端 IP 地址 | **密码**（从不上线） |
| salt？**看不到** —— 它在 URL fragment 里 | 密钥（只在两端内存中） |

**中继能做的攻击，以及为什么无效：**

| 攻击 | 结果 |
|---|---|
| 读取消息 | 拿到密文。没有密钥，AES-256-GCM 不可解 |
| **篡改**消息 | 每块有 16 字节认证标签，接收端验签失败 → 中止，**不写盘** |
| **丢弃**消息 | 传输卡住，用户看到"等不到下一块"。可用性受损，**机密性不受损** |
| 重放旧消息 | 块序号唯一且参与 AAD，重放会与期望序号不符 |
| 冒充接收端 | 房间名即能力凭据（见下），算不出房间名就找不到房间；且密码不参与传输 |
| 把两端引到**错误的房间** | 房间名由密码派生，中继无法构造一个"密码相同但房间不同"的情形 |

**"房间名即能力凭据"是一个刻意的设计选择。** 早期版本给中继加了"授权密钥登记"，
测试立刻暴露了**先到先得的竞态**：房间不存在时，第一个到达的请求决定了登记哪把密钥 ——
攻击者用自己派生的密钥抢先建了同名房间，就能把真正的发送端挡在外面。
换成"房间名即能力"之后这个问题自然消失了：房间名本身是 128 bit、
单向、不可枚举，算得出它就等于知道密码。

### 4.2 密码猜测

派生一次要 **600,000 次 PBKDF2 迭代**，这是为了抬高离线暴力破解的成本。

| 密码强度 | 风险 |
|---|---|
| 程序生成的随机密码（默认） | 实际上不可猜 |
| 用户自选的长口令（≥ 5 个随机词） | 很安全 |
| 用户自选的短密码 / 常见词 | **有风险** —— 攻击者拿到密文后可离线暴力尝试 |

在线尝试被限制：**连续 5 次密码错误，会话自动销毁**（这不是 bug，是特性）。
但离线攻击不受此限制 —— 若中继记录了密文，攻击者可以在本地慢慢算。

> **所以：别用"123456"。** 程序默认会生成一个强密码，直接用就好。

### 4.3 网络中间人

| 场景 | 是否安全 |
|---|---|
| 局域网模式（HTTPS + 自签证书） | 加密，但证书是**会话自签**的，浏览器信任它是因为程序把它装进了当前用户的信任库 |
| 中间人替换证书 | 装证书这一步是**本地**的（写入当前用户 Root 库），网络上的中间人无法替换已装的证书 |
| 跨网络模式 | 两端各自与中继建立 HTTPS；**内容仍是端到端加密的**，所以即使 TLS 被破，文件内容依然安全 |

**注意**：局域网模式下，如果用户手动接受了一个**伪造**的证书警告，那就失去了保护。
程序装的是会话级自签证书，退出时会移除（见 §5.3）。

### 4.4 端点被控

如果发送端或接收端电脑已被控制，**一切都不成立** ——
攻击者可以直接读明文、读密码、读密钥。这不是本程序的弱点，是所有加密软件的共同边界。

### 4.5 流量分析

中继（以及路径上的观察者）能推断：**有人在传、大概多大、传了多久、两端 IP**。
这无法在不牺牲可用性的前提下消除。若这一点对你不可接受，请用局域网模式
（数据不出本地网络），或自建中继。

### 4.6 本机残留

| 项 | 处理 |
|---|---|
| 会话证书 | 退出时从当前用户 Root 库移除；`Cert:\CurrentUser\My` 里的中间证书也清 |
| 临时目录 | 程序创建的 `flicker-cert-*` 目录在启动与退出时清理 |
| 中继上的消息 | 每条被确认即删除（前缀删除）；传输完成删除房间；15 分钟无活动整体过期 |
| 密钥 | 销毁流程里显式清零 |
| **原始文件** | **只读，永不改动、删除、移动** |
| **接收的文件** | 按用户选择的位置落盘，程序**不**负责擦除 |
| JS 字符串 | **无法可靠清零**（语言限制）。只能把窗口压到最小 |

## 5. 已知弱点与未缓解的风险

### 5.1 JS 字符串无法可靠清零

密码在 V8 里以字符串形式存在，垃圾回收前可能留下副本。
这是语言层面的限制，已把暴露窗口压到最小（派生完立即丢弃引用），但**无法保证**。

### 5.2 极端情况下证书可能残留

进程被强杀、断电、蓝屏时，销毁流程不会跑，证书库可能多一张无害的证书。
程序下次启动会清理；也可用 `--no-cert-install` 完全不碰证书库。

### 5.3 `--no-cert-install` 的模式下浏览器会显示警告

这是**有意**的：不装证书就没有中间人保护。适合"我只想在可信网络里传一次"的场景。

### 5.4 接收端无法验证发送端身份

只有密码这一条共享秘密。知道密码的人就能伪装成发送端。
这是"两台电脑 + 一个密码"这个模型的内在限制，不打算加 PKI。

### 5.5 中继可拒绝服务

中继可以丢弃全部消息。传输会失败，但**不会静默损坏** ——
每块都有认证标签，缺失或篡改都会被发现。

### 5.6 不是 PAKE：密码弱就能被离线爆破

闪传的密钥派生是 **共享密码 → PBKDF2-SHA256（60 万轮）→ HKDF**，
不是 SPAKE2 那类 **PAKE**（magic-wormhole 用的是 SPAKE2）。

区别在这里：拿到会话参数（盐、房间名）和一段密文的攻击者，
**可以在本地反复猜密码、每次只花一次 PBKDF2 的代价**，不需要和任何一端交互。
60 万轮把单次尝试的成本抬高了约三个数量级，但**它不改变"可离线爆破"这个性质**。

| 密码来源 | 实际风险 |
|---|---|
| 程序默认生成的 4 词口令 | 熵足够（离线爆破成本远高于收益），可用 |
| 用户自己设的短密码 / 生日 / 手机号 | **真实可被爆破**。这是本项目最需要用户注意的一条 |

缓解措施（已实现）：密码默认由程序生成、失败 5 次即销毁会话、密码从不上网线。
**没有做**的是换成真正的 PAKE —— 那是一次协议级改动，记在
[`路线图.md`](路线图.md) 第七章"要诚实承认的差距"里，不要以为它已经被缓解了。

### 5.7 没有第三方审计

"端到端加密"目前是**我们自己说的**。代码开源、密码学集中在独立模块里、
测试里有针对性的断言 —— 这些能让审计变容易，但**都不能替代审计**。
在用于高价值数据之前，请把这一点算进你的判断。

### 5.8 对手里有什么是我们没有的（诚实对照）

同类工具里有几件事做得比我们好，评估时应当一并考虑：

| 能力 | 谁有 | 我们的状态 |
|---|---|---|
| 真正的 PAKE（SPAKE2） | magic-wormhole | ❌ 见 5.6 |
| 跨会话断点续传（含块粒度） | croc、dropwire 等 | ⚠️ 只有同一次会话内、文件粒度的续传（`createWritable()` 顺序写且截断，浏览器层面做不到块粒度） |
| 手机当发送端 | LocalSend、PairDrop | ❌ 发送端要跑 Node |
| 对方离线也能取 | Wormhole.app、Send、网盘 | ❌ 有意不做：那需要把文件存在某处（见 [`路线图.md`](路线图.md) 第六章） |
| 匿名投递 | 一次性链接类服务 | ❌ 中继知道两端 IP |

## 6. 边界情况

### 6.1 传输中途文件被改动

发送端发现读到的字节数与清单不符就中止，并明确报出是哪个文件哪一块。

### 6.2 磁盘满 / 写盘失败

接收端中止，已收到的数据不落盘（或落盘但整体校验会失败）。
**不会**给出一个"看起来成功但内容不全"的文件。

### 6.3 时钟

不依赖双方时钟同步。超时判据用的是**空闲时长**（有没有进展），不是墙上时间。

### 6.4 后量子

AES-256 对 Grover 算法仍有 128 bit 有效强度（够用）。
但 **PBKDF2/HKDF 的强度会被 Shor 算法击穿** —— 届时需要换成后量子 KEM。
当前不提供，也不声称提供。

## 7. 报告安全问题

请**不要**开公开 issue。用 GitHub 的私有漏洞报告（Security → Report a vulnerability），
或在仓库里找联系方式私下沟通。

报告时请附上：复现步骤、影响范围、你是如何验证的。
我们会在确认后：
1. 尽快回复（通常几天内，这是业余项目，请见谅）
2. 修复并在 `SECURITY.md` 里记录
3. 若你愿意，在发布说明里致谢

**明确不在范围内**（见 §1 的非目标）：弱密码被猜、端点被控、流量分析、拒绝服务。
