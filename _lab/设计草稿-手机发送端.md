# 设计草稿：手机当发送端（局域网，纯网页）

> **状态：M1、M2a、M2c 已完成（2026-10）；只剩 M2b（真机实测）。**
> 目标场景：**手机拍的照片/视频传到电脑**。手机端永远是浏览器（不装任何东西），电脑端是我们这个程序。
> 相关：`中文文档/路线图.md` §四（移动端应用）、`中文文档/使用手册.md` §5.6、`中文文档/中继部署.md`（跨网络那条路）

---

## 一、为什么是这个方案，而不是别的

| 需求 | 浏览器能不能做 | 结论 |
|---|---|---|
| 手机**选文件**（相册/文件选择器，多选） | ✅ 能 | 没问题 |
| 手机**选整个文件夹** | ❌ 不能 | 只能一个个选文件（或按相册多选） |
| 手机**起一个服务**让电脑来取 | ❌ **不能**（硬卡点） | **所以反过来**：让电脑起服务，手机**上传** |

于是这个方案的核心一句话：**把"发送端起服务"改成"接收端起服务"，手机只负责推**。

好处：
- 完全复用现有的证书、密码、加密、销毁那一整套（不新造协议）
- 速度是**局域网速度**，不经过公网、不依赖 Cloudflare、不需要域名
- 纯网页：不装 Android Studio、不签名、**iPhone 也能用**
- 不碰项目的底线"**接收端零安装**"——这里"接收端"是我们的程序（电脑上），手机端始终是浏览器

代价（如实写）：
- 手机上传**大文件时必须亮着屏**：切后台/锁屏会被浏览器暂停（下面有对策）
- 手机不能"选文件夹"，所以清单里只有文件名，没有目录结构
- 手机上比原生 App 慢一些（加密与哈希要在浏览器里做）

## 二、用户看到的样子

### 电脑端（命令行）

```
flicker recv                      ← 现在：打开一个链接
flicker recv --listen             ← 新增：起一个"接收服务"，等对方来发
```

> 命名说明：`recv` 现在几乎没人用（接收端本来就不需要跑程序），所以**扩展它的含义**而不是加新命令，
> 更容易记：不带参数就是"我准备好收东西了"，带链接就是老行为（打开链接）。
> 图形界面里则是在首页加一个大按钮「**接收文件**」，与「发送文件」并列。

电脑屏幕显示：

```
  闪传 Flicker —— 接收模式（等对方发给我）

  让手机打开：  https://192.168.1.5:54713/?k=r-hGTJ4D2GRWGINLLwE7kg
  [二维码]

  一次性密码：  phone2026
  保存到：      D:\照片\手机传输\2026-10-16_2013

  ⏳ 等待对方连接…（超时 30 分钟后自动销毁）
```

### 手机端（浏览器页面）

1. 打开链接 → 提示"不安全" → 继续（自签证书，同现在）
2. 输入电脑屏幕上的密码
3. **选择要发的文件**：一个大按钮「选择照片/视频」（`<input type="file" accept="image/*,video/*" multiple>`，
   安卓会打开相册选择器，iPhone 打开照片），旁边一个小按钮「选择其他文件」
4. 显示已选 **N 个文件 / 共 X GB**，可以逐个删掉
5. 点「开始发送」→ 进度条（当前文件 + 总进度 + 速度 + 剩余时间）
6. 期间提示：**"请保持屏幕亮着，不要切到别的应用"**（能拿到屏幕常亮就自动拿）
7. 传完 → 「全部完成」+ 电脑那边弹出"已收到 N 个文件"

## 三、协议：复用哪些、新增哪些

**复用（一行都不改）**：套件 `FLICKER/1`（PBKDF2 600k → HKDF → AES-256-GCM）、
清单加密（`MANIFEST_AAD`）、分块的 IV/AAD 绑定（`chunkAAD` = 文件下标+块号+总块数+明文长度）、
房间/密码派生方式、整文件 SHA-256（页面里那份纯 JS 实现，Worker 里跑，已有测试）。

**新增（只在电脑端加，因为方向反了）**：

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/up/session` | 手机报"我要发 N 个文件"，电脑返回盐与挑战 |
| POST | `/up/auth` | 手机算 MAC → 电脑核对（失败计数、超限销毁，同现有 `Session`） |
| POST | `/up/manifest` | 手机发**加密清单**（文件名/大小/分块数/逐块哈希/整文件哈希） |
| PUT | `/up/chunk?f=<文件号>&i=<块号>` | 上传一块密文；**幂等**（同一块重复 PUT 直接覆盖） |
| GET | `/up/status` | 电脑已收到哪些块（用于断线续传与进度显示） |
| POST | `/up/finish` | 手机宣布发完；电脑校验整文件哈希后落盘定稿 |

设计要点：
- **清单先行**：电脑先知道"要收几个文件、叫什么、多大、多少块"，才能提前检查磁盘空间、拒绝非法文件名
- **逐块校验 + 整文件校验**：与现在完全相同的两层判据（块级 GCM tag 验真，整文件 SHA-256 验全）
- **PUT 幂等**：手机重试同一块不会出错（现在中继那条路的幂等经验可以直接照搬）
- **续传**：手机崩溃/切后台回来后，先 `GET /up/status` 问"你已经有哪些块了"，只补缺的

## 四、电脑端怎么落盘（这部分最需要小心）

1. **路径安全**：手机传来的文件名走**现有那 12 条规则**（`sanitizeRelPath`）后才允许写 —— 一个字节都不放宽。
2. **不覆盖**：目标已存在同名文件时**自动改名**（`照片.jpg` → `照片 (2).jpg`），复用现有的去重函数；
   想覆盖得显式加 `--overwrite`。
3. **先写 `.part` 再改名**：收到一半中断时留下 `xxx.jpg.flicker-part`（一眼能认出、不会污染你正常的文件）。
4. **边收边写**：不给整份文件开内存缓冲，收到一块写一块；同时增量算整文件摘要。
5. **开工前查磁盘空间**：清单里已经有总大小，不够就**当场拒绝**并说明差多少（而不是传到一半失败）。
6. **上限**：`--max-bytes`（默认 200 GB）与 `--max-files`（默认 5000），防止局域网里有人乱灌。
7. **销毁清单要多一条**：现在的清单写着"原始文件未被改动（本程序只读）"—— 这是**发送端**的话，
   接收模式要换成「**收到的文件已保留在 <目录>**」，否则用户会以为程序把收到的文件也销毁了。

## 五、手机上必须处理好的四个现实问题

| 问题 | 对策 |
|---|---|
| **锁屏/切后台被暂停** | 尽量申请"屏幕常亮"（`navigator.wakeLock`，Chrome 安卓支持，**需要 HTTPS**）；页面上明确写"别切走"；切回来先问 `/up/status` 续传。iOS Safari 没有 wakeLock → 只能提示 |
| **大视频不能进内存** | 一律**流式分片**：`file.slice(a,b)` → 加密 → 上传 → 释放。手机发 4 GB 视频，页面内存仍然只有几块 |
| **手机算得慢** | 逐块哈希用原生的 `crypto.subtle.digest`（快）；整文件哈希用现有那份 Worker 里的纯 JS 实现（分块增量，实测桌面 252 MiB/s，手机上会慢些，**需要真机量一个数字**） |
| **选不到文件夹** | 手机上只能选文件，所以清单里只有文件名；同名文件自动改名。iPhone 的 HEIC 原样传（不转格式），但**电脑上可能预览不了 HEIC**，要在文档里说明 |

## 八、已拍板的决定（2026-10，用户定的）

1. **存到哪里**：**这台电脑的"下载"目录**（`%USERPROFILE%\Downloads` / `~/Downloads`）。
   不按次建子文件夹 —— 传过来的文件**直接进下载目录**。`--dir=` 可以改到别处；
   以后要是觉得"下载目录太乱"，加一个 `--subdir` 开关就能变成"每次建一个以时间命名的子文件夹"（改动很小）。
2. **图形界面一开始就做**（不是等命令行跑通再补）：用户以后是用鼠标收文件，界面入口属于这一轮的范围。
3. **同名文件：停下来问我**。因为文件直接落在下载目录（那里本来就杂），所以这个提示要**做成不卡住的三选一**：

   ```
   手机要发的 照片.jpg 在电脑上已存在（2026-09-01 那次下载的）
     [ 换个名字（照片 (2).jpg） ]   [ 覆盖它 ]   [ 跳过这个文件 ]
   手机那边同时显示：正在等电脑确认（还有 12 个文件在传）
   ```

   - 默认按钮（回车）= **换个名字**（最安全）
   - 手机端**不阻塞**：其他文件继续传，只把撞车的那一个挂起等确认
   - 超时（默认 5 分钟）没人点 → 按"换个名字"处理，并在结束时如实告诉用户"有几个文件是自动改名的"
   - 图形界面里就在同一个窗口里弹；命令行模式打印提示并等待按键（`--no-ask` 则一律自动改名，供无人值守使用）

> ⚠️ 这三条改动把里程碑的顺序调了一下：**M2 与 M3 合并做**（页面 + 图形界面入口一起），
> 因为界面入口是用户实际要用的那个面；后端接口（M1）不变，仍然先做，因为它决定成败。

## 十、M1 实施时对上面设计的两处修正（如实记录）

### 修正 1：同名文件的"三选一"发生在**清单阶段**，不是传输中间

原设计写的是"手机那边同时显示：正在等电脑确认（还有 12 个文件在传）" —— 意思是
**边传边问**，只挂起撞车的那一个。实现时改成：**在清单阶段一次问完**（此时一个字节都还没开始收）。

为什么改：
- **协议形状决定的**：`POST /up/manifest` 是一个原子步骤，返回"接受了哪些文件、各自叫什么名字"。
  手机拿到这份答复才开始发块。要做到"边传边问"，就得让清单答复里出现第三种状态（"这个先挂着"），
  再为它加一个查询/更新端点 —— 复杂度和风险都上去了，换来的是"用户少等几秒"。
- **更安全**：撞车的名字在**任何数据落盘之前**就定了。不存在"传到 80% 才问要不要覆盖"，
  也就不存在"用户中途关掉页面，留下半覆盖的文件"。
- 代价如实说：撞车的文件多时，提问会**串行**出现，第一个问题没回答之前，整批数据都不开始传。
  这正是 `--no-ask`（一律自动改名）存在的理由。

### 修正 2：默认密码用**6 位短码**，不是 4 个单词

`suggestCode()` → `k7m-3fq`（字母表 31 个字符，去掉了 0 O 1 l I o 这些长得像的）。
原来的 4 词密码（26 个字符）是给**电脑上打**的；这个密码要在**手机键盘**上敲，
而且敲错一次就消耗一次"失败额度"（错 5 次整个会话销毁）。

不是拍脑袋的短，理由可算：
- 31 个字符取 6 位 ≈ 2^29.7 种；
- 每次会话只允许 5 次尝试，随后会话销毁 → 单次会话被猜中 ≤ 5 / 8.9e8 ≈ 5.6e-9；
- URL 里还有一次性令牌，攻击者得先在同一个局域网里、还得先拿到链接；
- 想更强就 `--password=` 自己指定，程序不做任何限制。

## 十一、做 M2a（手机页面）时撞出来的三件事

### 1. 块大小的报价少了一个数，页面因此一块都发不出去

真机演练第一次跑就失败：页面按电脑报价的 `limits.maxChunkBytes` 声明块大小，
服务端却按 `chunkBytes + 17 > maxChunkBytes` 拒绝 —— 那个 17 是**线上一条消息的固定开销**
（类型字节 + GCM tag），是实现的细节，客户端没有理由知道它。

修法不是"让页面去减 17"，而是**把两个数都报价**：`maxChunkBytes`（一条消息的上限）
与 `maxPlainChunkBytes`（明文块的上限，清单里声明的就是它）。
顺带把默认上限从 1 MiB 明文提到 **2 MiB 明文**（与局域网发送端一致）——
块大一点请求数就少一半，手机上每一次往返都要唤醒射频，这个差别比桌面上明显。

**教训**：报价里只给一个"上限"，而客户端必须做减法才能用 —— 这种接口早晚会在真机上炸。

### 2. 整文件校验值必须在清单**之前**算完，这是"读两遍"的代价

清单里每个文件都带整文件 SHA-256，而清单必须在任何数据之前发出（电脑据此先查空间与重名）。
所以手机上要先读一遍文件算摘要，再读第二遍上传。4 GB 的视频在手机上大约要多花一到两分钟。

**为什么接受这个代价**：省掉它等于砍掉第二层校验（整文件摘要）。而这一层的意义是
"电脑收到的字节就是你要发的字节"—— 只靠逐块 AEAD 挡不住"发送过程中文件被别的应用改写"。
所以：**选完文件立刻开始算**（用户还在看列表、还在输密码时就算完了），进度如实显示
（"正在计算校验值 3/12"），而不是假装发送马上开始。

### 3. `input.files` 在读之前就被清空了 —— 验证脚本自己踩的坑

页面的 change 处理器在收下文件后会 `input.value = ''`（这样用户能再选同一个文件）。
验证脚本第一版在注入文件后读 `input.files.length`，于是永远是 0 —— 而页面其实收下了 3 个文件、
并且完整传完了。判据改成看**页面自己的列表**（`#fileList li` 的条数）之后才对。

**教训**：验证脚本的判据也要能被证伪 —— "注入失败"和"注入成功但读数太晚"看起来一模一样。

### 还没写进设计的：PWA "分享 → 闪传"（记下来，M2 之后再做）

安卓的浏览器支持 **Web Share Target**：装了 PWA 之后，在相册里点"分享"能直接看到"闪传"。
对"发几张照片"这个场景，这比"扫码 → 打开页面 → 选文件"少三步。

但有两个前提，所以放在 M2 之后：
