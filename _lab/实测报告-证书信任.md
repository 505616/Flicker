# 证书信任机制 —— 实测报告

> 本文件记录对"会话级证书 + 当前用户信任库"方案的**实测验证过程与结论**。
> 复现命令：`node _lab/lab-cert.mjs [--lan] [--no-install] [--ignore-cert] [--window]`
>
> **结论已回写进 `架构决策.md` §4.3、`行为与运行.md` §1.3、`使用手册.md` §10.3。**

---

## 一、要回答的问题

局域网模式下接收端必须访问 `https://<发送端IP>:端口`。为了让对方**看不到"您的连接不是私密连接"的警告**，
方案是生成一张会话级证书并装入 `Cert:\CurrentUser\Root`。

**需要验证：浏览器到底认不认这张证书？**

测试方法不靠肉眼，而是用 **CDP（Chrome DevTools Protocol）直接读取浏览器对证书链的验证结论** ——
看 `Network.responseReceived` 里的 `securityDetails`，以及 `Network.loadingFailed` 的错误码。

环境：Windows 10 (19044) · Edge 155.0.4283.45 · Node v24.21.0 · **非管理员身份**

---

## 二、实测结果

| 变体 | 模式 | 地址 | CA 带 `CA=TRUE` | 装入 Root 库 | 浏览器结果 |
|---|---|---|---|---|---|

| 变体 2 | headless | 127.0.0.1 | ❌ 无 | ✅ | ❌ `net::ERR_CERT_INVALID` |

| B（对照） | headless | 127.0.0.1 | ✅ 有 | ❌ 未装 | ❌ `net::ERR_CERT_AUTHORITY_INVALID` |
| C（对照） | headless | 127.0.0.1 | ✅ 有 | ✅ | ✅ 正常（`--ignore-certificate-errors`，证明服务端无问题） |

**所有模式均已验证**：headless · 真实可见窗口 · app 无地址栏窗口（最接近"装成桌面应用"的形态）。

> **对照 H 是本次最重要的一个用例。** 它证明测试脚本**能识别安全警告页** ——
> 如果没有它，前面那些"通过"就无法排除"检测器太宽松、把警告页也判成通过"的可能。
> 每次做肯定性结论时，都必须有一个"应当失败"的用例来校准测量工具。

## 三、四条结论

### 1. ✅ 方案成立

会话 CA（带 `CA=TRUE`）+ 由它签发的服务器证书，只把 **CA** 装进 `Cert:\CurrentUser\Root`，
浏览器**完全接受，零警告**。**headless 模式确实读取 Windows 信任库**（这一点原本存疑，现已排除）。

**真实局域网 IP 同样通过**（实验组 D），说明"接收端访问 `https://192.168.1.5:端口`"这个核心场景成立。

### 2. ⚠️ 真正的地雷是证书生成，不是信任库

最初两次失败（变体 1、2）的唯一原因是证书生成方式：

```powershell
# ❌ 错误：生成出来的 CA 没有 CA 基本约束（Subject Type 显示为 End Entity）
-TextExtension @('2.5.29.19={text}critical:ca2')

# ✅ 正确：显式设置 ca=1，并标记 critical
-TextExtension @('2.5.29.19={critical}{text}ca=1')
```

没有 `CA=TRUE` 的"CA"不是一个 CA，用它签发的服务器证书整条链无效，
浏览器报 `ERR_CERT_INVALID` —— **含义是"证书本身是坏的"**，而不是"签发者不认识"。

**这两种错误在浏览器页面上长得几乎一样，但原因和修法完全不同。**

### 3. ✅ 对照组 B 是决定性证据

同一个证书，**不装 Root 库时**报的是 `ERR_CERT_AUTHORITY_INVALID`（签发者不受信任），
而**装了但证书有缺陷时**报的是 `ERR_CERT_INVALID`（证书本身损坏）。

> **错误码从"签发者不认识"变成"证书坏了"，这一变化本身就证明了装信任库确实生效。**

没有这个对照组，极容易把"证书生成错了"误判成"信任库机制不生效" —— 这正是本次差点发生的误判。

**方法论教训：做否定性结论时，必须有一组"只改一个变量"的对照。**
本次两个对照（B 不装证书、C 忽略证书错误）分别锁定了"信任库是否生效"和"服务端是否有问题"。

### 4. ⚠️ 卸载只能靠 `certutil`

```powershell
Remove-Item Cert:\CurrentUser\Root\<指纹>
# → 失败: The operation is on user root store and UI is not allowed.
```

这不是习惯问题，**是别的办法根本不工作**。因此推出一个可靠性缺口：
**装入后被强杀（任务管理器结束进程、断电）则证书永久残留。**

**应对：每次启动时扫描并清理 `subject` 含 `Flicker Session` 的残留证书。**

## 四、由此确定的实现约束

| # | 约束 | 针对的失败 |
|---|---|---|
| 1 | 生成证书后、启动服务前，**自检证书链**（CA 有 `CA=TRUE` 且 critical、有 `keyCertSign`、服务器证书有 SAN 且含目标 IP、有 EKU serverAuth） | 挡住本次踩到的坑 |
| 2 | **启动时扫描并清理上次残留** | 强杀导致的永久残留 |
| 3 | **先装证书，再监听端口** | 浏览器缓存证书错误导致装证书也不生效 |
| 4 | 自检失败 → **明确报错并降级到手动信任引导**，绝不让用户面对看不懂的浏览器错误 | 兜底 |

**关于 `--no-cert-install`**：它不只是"给不接受改证书库的用户"用的，
实际上也是**保底方案** —— 即使证书方案在某个用户的机器上因策略限制失败，程序仍然可用，只是多一次点击。

## 四·补、"第一次打不开、刷新才好" —— 一个真实缺陷的定位

用户报告：测试时浏览器显示"无法打开"，刷新一下就正常了。

**先否定了一个假设**（`lab-repro.mjs`）：

| 假设 | 测试 | 结论 |
|---|---|---|
| H1：profile 缓存了上次的证书拒绝结果，装了 CA 也不生效 | 用**同一个 profile**：先制造拒绝 → 关浏览器 → 装 CA → 重开 | ❌ **不成立**。首次访问直接正常，即使中途点过"继续访问"也一样 |
| H2：全新 profile 也会出问题 | 全新 profile + CA 已装 | ❌ 不成立，首次访问正常 |

**然后复现了真正的原因**（`lab-race.mjs`）：

| 步骤 | 用户看到的 |
|---|---|
| **A** 浏览器已打开，HTTPS 服务尚未启动 | `嗯… 无法访问此页面` + `net::ERR_CONNECTION_REFUSED` |
| **B** 服务启动后，用户按 F5 | ✅ `证书验证页` |
| **C** 服务就绪**之后**才打开浏览器 | ✅ `证书验证页` |

**根因：竞态。** `--app=<url>` 的浏览器窗口**一启动就导航**。
窗口存在的那几秒里服务还没监听，于是页面停在连接被拒绝的错误页，
而它**不会自己重试** —— 必须手动刷新。

**这正是"刷新一下就好了"的准确解释**，也正好是最容易在真实 GUI 里踩到的坑
（先拉窗口、再初始化服务是自然的写法）。

**产品侧的修复（已写进 `行为与运行.md`）**：启动顺序必须是

```
装证书 → 监听端口 → 探测确认真的返回 200 → 才允许打开浏览器窗口
```

**绝不能存在"窗口已存在但服务还没准备好"的窗口期。**

## 五、仍未验证的事（诚实标注）

| # | 事项 | 为什么没验 | 怎么验 |
|---|---|---|---|
| 1 | **macOS 证书信任** | 无该平台环境 | 命令已确定：`security add-trusted-cert -r trustRoot -k ~/Library/Keychains/login.keychain-db ca.pem`。**注意 `man security` 明确写了改用户信任设置必须经过一次认证对话框**，所以这一步没法做成静默的 |
| 2 | **Linux 证书信任** | 无该平台环境 | 命令已确定，但**没有零依赖路径**：Chromium 读 NSS 库（M146 起 `~/.local/share/pki/nssdb`，之前 `~/.pki/nssdb`），要 `certutil`（来自 `libnss3-tools`/`nss-tools`，默认不装）；Firefox 另有自己的库。见 [Chromium 官方文档](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/docs/linux/cert_management.md) |
| 3 | Chrome（非 Edge） | 本机只装了 Edge | 同一套内核，风险低；但严格说未验 |
| 4 | macOS / Linux 上的**证书生成** | — | ✅ **已不再是未知项**：生成改成纯 JS（`src/x509.js` + `src/session-cert.js`），三平台同一份代码，判据是真实 TLS 握手（`test/session-cert.test.js`、`test/readiness.test.js`）。CI 在 macOS/Linux 上真的跑这些用例 |

> ⚠️ **不能假设 Windows 的结论适用于 macOS/Linux。** 三者的信任机制完全不同。
> 在各自实测通过之前，这两个平台应默认使用 `--no-cert-install`；
> 程序会把手动安装的确切命令打印出来（`trust.manualTrustHint()`），但不代跑。

### 测试过程中修正的两个自身缺陷（记录教训）

这两个 bug 都属于"看起来在测 A，其实在测 B"，如果不核对输出就会得出错误结论：

| # | 缺陷 | 后果 | 发现方式 |
|---|---|---|---|
| 1 | `flag()` 只匹配 `--app`，而调用时传的是单横线 `-app` | `-app` 被静默忽略，实际跑成了 headless —— **等于没测 app 模式** | 核对输出里的「模式」栏，发现显示的不是 app |
| 2 | 用 `splice(1, 0, '--app=…')` 插入参数，而 `--app` 原本就在索引 0 | 参数被自己的 splice 删掉 | 同上，第二次核对 |

**教训：测试脚本必须把「它实际在做什么」打印出来并逐次核对。**
两次都是靠"读输出里的模式栏"发现的，而不是靠推理。

## 七、补充：实现阶段发现的一个真实泄漏

证书方案验证通过之后，在实现阶段又发现了一个**同类但更隐蔽**的问题。

### 现象

跑完整测试后核对系统状态，发现：

```
Cert:\CurrentUser\My   里有 148 张 CN=Flicker Session CA
%TEMP%                 里有 84 个 flicker-cert-* 目录
```

### 根因

`New-SelfSignedCertificate` 会把**会话 CA 和服务器证书都放进 `Cert:\CurrentUser\My`**。
装入信任库（`Root`）只是**额外**加了一份信任项。

早期实现只清理了 Root 库里的 CA（因为"信任项"是显眼的那个），
**My 库里的副本从来没被碰过** —— 于是每跑一次就多留一张。

### 为什么测试没抓到

最初的测试只断言了一条：**Root 库证书数必须还原**。
而那个断言一直是绿的 —— 因为它检查的地方恰好是被正确清理的那一处。

> **教训：验证"不留痕迹"时，必须把每一处可能留下痕迹的地方都断言到。**
> 只查一处等于没查，而且会给出虚假的安全感。

### 修复

1. 会话对象记住两个指纹（CA 与服务器证书），销毁时**两个库都清**；
2. `generateSession().cleanup()` 同时清 Root 与 My；
3. 新增 `findMyLeftovers()` / `myLeftoverCount()` 用于检测；
4. 新增 `cleanAllLeftovers()` 与 `cleanTempDirs()`，在**每次启动**时自愈式清理；
5. 测试的 `after` 钩子加严为三条断言：
   Root 库还原 · **My 库残留为 0** · 临时目录为 0。

### 验证

```
修复前：跑一轮测试 → My 库 +4，临时目录 +3
修复后：跑一轮测试 → My 库 5 → 0，临时目录 5 → 0（连上一轮的遗留也一并清掉）
连跑两轮：Root 49 · My 0 · 临时 0，稳定
```

> 顺带说明：这个泄漏在**真实使用中也会发生**，不只是测试问题 ——
> 用户关掉程序窗口时如果走到非正常路径，证书同样会残留。
> 所以修复落在了产品代码里（启动自愈 + 退出兜底），而不只是测试里。
