# Building a single-file executable

> This document is for people who **want to build it themselves**. If you only want to use it, just download the prebuilt artifact from Releases.
>
> Related documents: `架构决策.md` chapters 3 and 5 (why single-file, how it is distributed), `行为与运行.md` (how the artifact behaves at runtime)

---

## 1. Why this exists

The single-file program is the **complete form** of the “self-gift program” feature:

| Form | What the recipient has to do with it | Suitable for |
|---|---|---|
| **Single-file `.exe`** | **Double-click**. Nothing to install | ⭐ First choice |
| Source package `.fkz` | Install Node.js 24+ first, then double-click the launch script | Developers, people who want to read the code |

Without the single-file form, “handing the program to the other person” is only half done —
the recipient still has to go to the Node website, download and install it, and the vast majority of non-technical users give up at that step.

In the single-file form, the sender **does not need Node installed** either. This is its most practical value.

## 2. The build

### Prerequisites

| Requirement | Notes |
|---|---|
| Node.js 24+ | Uses SEA (Single Executable Application) |
| Network | The first injection needs to download `postject` (a build-time tool) |

### Commands

```powershell
node gen/build-sea.mjs              # build the current platform
node gen/build-sea.mjs --no-inject  # stop at the blob, convenient for troubleshooting
node gen/build-sea.mjs --keep       # keep the build directory, for inspecting things afterwards
```

The artifact lands in `dist/`:

```
dist/flicker-0.1.0-windows-x64.exe     about 90 MB
```

### Why 90 MB

The artifact = **a complete Node runtime** (`node.exe` on this machine is 89.2 MB) + the embedded code and assets.

That is the price of “the other side installs nothing”, and it is the most central trade-off of all: trade size for zero installation.
Switching to a dynamically linked Node would be far smaller, but that goes back to the old problem of “the other side has to install a runtime first”.

## 3. The pipeline (every step verified, failure stops everything)

```
① Bundle the module graph     → app.cjs (CommonJS)
② Prepare the build directory → app.cjs / sea-entry.cjs / version.json / the various assets
③ Generate the SEA blob       → node --experimental-sea-config
④ Copy the Node runtime       → use it as the base
⑤ Inject the blob             → postject
⑥ Self-check the artifact     → really run --version and --help once
```

Step ⑥ is not optional. A build-tool error does not make the program crash, it only produces an artifact that will not run —
so running it once at build time to verify is far better than finding out when the user double-clicks.

## 4. SEA's three hard limits (all of them measured the hard way)

These three determine the shape of the whole build scheme; please read them all before changing anything.

### Limit 1: only one JS entry

SEA accepts only one entry file, while this project has ten modules.
Node's module system cannot resolve `./xxx.js` from an in-memory blob, so the module graph must first be flattened into one file.

→ This is why `gen/bundler.mjs` exists.

**Why not use esbuild/rollup**: that would turn “zero third-party dependencies” into an empty phrase.
The bundler supports only the syntax this project actually uses (static import/export, no circular dependencies),
and **would rather fail the build than produce a bad artifact**.

### Limit 2: no resolution by package boundary — ES modules will not load

The measured error:

```
Warning: Failed to load the ES module: ...\main.js.
Make sure to set "type": "module" in the nearest package.json file
```

It is the same even when `package.json` says `"type": "module"` — SEA's module loader does not look at package boundaries.

→ So **the artifact entry must be CommonJS** (`entry/sea-entry.cjs`),
and the bundled artifact is loaded as “embedded asset + `module._compile`”, not by `require()`-ing a file.

Incidentally this also rules out a scheme that looks more elegant: using `package.json`'s `imports` conditional mapping
to pick the asset loader by condition (perfectly usable under ordinary Node). Under SEA it does not hold.

### Limit 3: `require()` only knows built-in modules

The measured error:

```
Error [ERR_UNKNOWN_BUILTIN_MODULE]: No such built-in module: ...\app.cjs
```

→ `app.cjs` must also be stored as an **embedded asset**, and the entry pulls the source out with `sea.getAsset('app.cjs')` and then executes it.

### One more easy trap: `argv[1]` is not empty

I originally assumed that under SEA `process.argv[1]` would be `undefined` (the script path is embedded).
The measured result is:

```
argv1    : C:\...\app.exe     ← the executable's own path, not undefined
execPath : app.exe
```

→ Deciding “am I in single-file form” must use the official `sea.isSea()`,
never a guess from `argv`/`execPath`. The entry hangs the result on `globalThis.__flickerIsSea`,
and the rest of the code reads it through `isSingleFile()` in `assets.js`.

## 5. The bundler's five constraints

The bundler uses **topological-order concatenation** to merge the modules into one file. That brings five constraints that must be obeyed,
and a test case watches over each one (`test/bundler.test.js`):

| # | Constraint | How it showed up |
|---|---|---|
| 1 | The entry's shebang gets stripped | After concatenation the shebang lands mid-file → `Invalid or unexpected token` |
| 2 | Modules **must not** use `import.meta` | That object does not exist in CommonJS — an outright syntax error |
| 3 | Statement stripping scans line by line, not by regex | Under Windows CRLF the regex swallowed all of `manifest.js` across lines |
| 4 | Top-level declarations **must not share a name across modules** | `gift.js` and `run.js` each declared `__dirname` → collision |
| 5 | The entry's `await main()` gets turned into a Promise chain | Top-level await is illegal in CommonJS |

Constraint 4 deserves elaboration: it was **not worked around by having the bundler rename things**, but by gathering the duplicated thing into one place
(`rootDir()` in `src/assets.js`). Duplicate declarations are the problem in themselves;
making the bundler auto-rename would only hide the problem.

The bundler's self-check is strict too: after stripping comments it checks for `import.meta`, and hands the artifact to `node --check`
for a real syntax check. **Both false positives and false negatives were hit**:
at first it searched for `import.meta` directly in the original text, and got a false hit from a comment that mentioned it.

## 6. Cross-platform builds

**You must build on the target platform.** SEA works by injecting the blob into **that platform's native Node runtime**,
so:

| Want | Where to build |
|---|---|
| `flicker-x.y.z-windows-x64.exe` | Windows x64 |
| `flicker-x.y.z-macos-arm64` | A Mac with Apple silicon |
| `flicker-x.y.z-macos-x64` | An Intel Mac |
| `flicker-x.y.z-linux-x64` | Linux x64 |

**There is no cross-compilation.** For a release, having CI's three runners each build one is the least painful approach.

> ⚠️ **Nothing except Windows has been measured yet.** The build script itself has no platform-specific branches
> (`postject` supports the PE / ELF / Mach-O formats), but “not measured” is not measured —
> the same as the state of macOS/Linux certificate trust in `架构决策.md`, labelled honestly.
> However, **certificate generation is no longer platform-specific**: it is pure JS (`src/x509.js` +
> `src/session-cert.js`), the same code runs on all three platforms, and on macOS/Linux CI really
> executes it and verifies it with a real TLS handshake. That is to say, in item 8 (measured on all three platforms)
> the “certificate generation” half is already covered by CI; only “the browser trusts it” needs real hardware.
>
> Also, on macOS an unsigned artifact is stopped once by Gatekeeper,
> and the user needs right-click → Open (the same handling as the `.command` in source mode).

## 7. The only external tool at build time: postject

`postject` is the tool that injects the blob, and the only build-time dependency of the whole project besides **zero runtime dependencies**.

**Why use it instead of implementing injection ourselves**: injection has to rewrite three executable formats, PE / ELF / Mach-O,
and writing it ourselves is an error-prone path; what is more, the symptom of an error is “the artifact occasionally will not run”, which is extremely hard to diagnose.
`postject` is the tool specified by the official Node documentation.

It appears only on the build machine; it does not go into the artifact and does not affect users. The build script pulls it in temporarily with `npx --yes postject@1.0.0-alpha.6`
and does not write it into `dependencies`.

### How it is called: never through a shell

```js
// gen/npx.mjs — run npx's JS entry directly with the current node
spawnSync(process.execPath, [npxCliPath, ...args], { shell: false })
```

The original form was `spawnSync('npx', [...], { shell: true })`; it worked, but it had two problems:

1. **Node 24 prints a `DEP0190` warning**: the arguments get spliced into a command-line string, and the escaping responsibility lands on the caller.
   Although here they are only this repository's paths, “it happened not to break, by luck” is not a reason.
2. Going through a shell means passing **cmd.exe's parsing rules** (quotes, `^`, trailing backslashes), and this project's directory is called
   `D:\闪传` while temp directories may also contain spaces — these rules are very easy to trip over.

And that route is a detour to begin with: `npx` is a `.cmd`/shell wrapper, and what actually executes is still `node <npm>/bin/npx-cli.js`.
We already have node in hand (the one running the build script), so we can simply run that.

> ⚠️ **The fallback path must stay.** On Windows, since Node 18.20 / 20.12 / 21.7
> (the fix for CVE-2024-27980), `spawn` is **not allowed** to execute `.cmd`/`.bat` directly;
> without a shell it fails with `EINVAL` — so the fix of “switch to `shell:false` + `npx.cmd`” is **broken**.
> When `npx-cli.js` cannot be found (on some distributions the npm layout is not among the candidates), fall back to the shell form
> and let it print that warning: **working matters more than having no warning**.

## 8. Acceptance

The build script runs two self-checks by itself (`--version` and `--help`). Then run the smoke test:

```powershell
node gen/smoke-sea.mjs
```

It verifies four things, and **the fourth was added in 2026-10, and it is the one most easily missed**:

| # | What it verifies | Why |
|---|---|---|
| ① | `--version` prints the version number | The artifact is alive and the version was injected successfully (`0.0.0` means it was not injected) |
| ② | `--help` produces normal output | Both the code and the assets got packed in |
| ③ | `send --dry-run` can scan out real files | The embedded assets are complete (the place SEA most easily goes wrong) |
| ④ | **`--assets`' fingerprints match the disk** | See below |

### ④ Why “embedded asset fingerprints” are needed

The first three **all passing does not mean the artifact is new**. The tests read the page from disk,
and `--version` / `--help` / `--dry-run` never look at the page content — so “changed the page, forgot to rebuild”
can leave the whole test suite plus the smoke test all green, while an old interface sits in `dist/`.

**In 2026-10 it really slipped through once**: in that 89.5 MB artifact the string `lang-switch` could not even be found
(meaning no i18n, no “clear individually” button, none of the fixes for those relay bugs),
and at the time all 390 cases were green. **The same pit was stepped into a second time later**, see “the gift source pack” below.

The approach is to hook three stages up to the same implementation (`gen/asset-digests.mjs`):

```
at build time   digestAll()        → write the first 16 hex digits of each asset's sha256 into the embedded version.json
at runtime      flicker --assets   → print those fingerprints (source mode has no record, so it computes them on the spot)
at smoke time   compareDigests()   → compare item by item against the files on disk; on any mismatch fail and give the rebuild command
```

**The gift source pack is the same kind of thing and has to be compared separately.** At packaging time the source plus the
Chinese and English docs are packed into `source-pack.fkz` and embedded in the artifact (see `src/gift.js`). It is **not a file
on disk** — it is *computed from the whole source tree* — so:

```
at build time   pack first, then assetFingerprint(pack.bytes) → record it in the same version.json
at runtime      --assets prints one more line, source-pack.fkz
at smoke time   compareSourcePack() → **build the pack again on the spot** and compare fingerprints
                (the same buildSourcePack the real gift uses)
```

Without this, changing a document without rebuilding shows up as: the tests all green and the pages new,
**while the documents inside the gift the other side receives are old** — and the user explicitly required the gift to carry the docs.

```powershell
# manual cross-check (equivalent to step ④ of the smoke test)
dist\flicker-0.1.0-windows-x64.exe --assets
node -e "import('./gen/asset-digests.mjs').then(m=>console.log(m.digestAll()))"
node _lab/verify-pack-digest.mjs     # negative verification: add a line to a doc; this check must complain
```

When they disagree the error looks like this — it points straight at which file, both values, and which command to run:

```
✗ 产物与源码**对不上** —— 这个二进制里内嵌的东西不是磁盘上现在这一版。
  web/station.html
      产物里：f28acb4bf5e836e4
      磁盘上：da5d963146dd9537
      产物里内嵌的是旧版
  请重新构建：node gen/build-sea.mjs
```

Two details are worth writing down:

- **No build time may be written into `version.json`.** It goes into the blob and the blob goes into the artifact — add a timestamp,
  and the same source produces a different binary, and the “reproducible build” is gone (`release.mjs` speaks precisely through
  “identical checksums = built from the same source”). A fingerprint is a pure function of the content, so it is safe.
- **The environment must carry `FLICKER_NO_BROWSER=1` when running `--assets`.** In case what you hit is an **old artifact
  that does not know this switch**, it treats it as an unknown argument and goes all the way to “no arguments at all → open the graphical interface”,
  so it may pop up a window and not exit. With this variable set there is no popup, and a timeout is reported explicitly as “the artifact is too old”.

### Manually verifying the full functionality

```powershell
# send a file with the artifact (no certificate install, no browser, pure command-line verification)
dist\flicker-0.1.0-windows-x64.exe send .\某个文件 --password=test --timeout=5s --no-cert-install --no-qr
```

**The key line to confirm** is the self-gift line:

```
🎁 附带赠送程序：flicker-0.1.0-windows-x64.exe (89 MB)
   对方双击即可运行，不需要安装任何东西
```

If what it shows is `flicker-0.1.0-source.fkz`, the artifact **did not recognize its own single-file form**;
if the version number is `0.0.0`, the version was not injected correctly.

> Both of these really happened:
> the cause of the version-number bug was that `gift.js` read `package.json` from disk by itself —
> in single-file form that file does not exist, so it **silently** fell back to `0.0.0`,
> and the recipient would think this was a very old version. Versions now all go through `version()` in `assets.js`.

## 9. Release packaging

Once the artifact is built, use `gen/release.mjs` to arrange it into a releasable form:

```powershell
node gen/build-sea.mjs        # ① build this platform's artifact → dist/
node gen/release.mjs --check  # ② first see whether anything is missing (generates no files)
node gen/release.mjs          # ③ generate dist/release/
```

`dist/release/` will contain:

| File | Purpose |
|---|---|
| `flicker-<version>-<platform>…` | The artifact itself (copied over from dist/) |
| `flicker-<version>-<platform>….zip` | A compressed copy of the artifact (**the recommended download**: 94.2 MB → 36.0 MB) |
| `SHA256SUMS` | Checksums, format identical to coreutils (`sha256sum -c` works directly) |
| `RELEASE.md` | Release notes: download table, usage, **known limitations**, checksums, build information |

### Why we ship a zip (and why "make the artifact smaller" is a dead end)

Of the 94 MB artifact, **89.2 MB is the Node runtime itself** and only **5.0 MB** is our own content —
so "shrink the artifact" can save at most 5% and is not worth doing. What is worth doing is
**shrinking the download**:

| | Size |
|---|---|
| Uncompressed (the exe) | 94.2 MB |
| The zip | **36.0 MB (38%)** |
| Saved | **62%** |

`.gz` reaches the same number, but **Windows users cannot double-click a `.gz`**, while a `.zip`
opens with a double-click — so there is no real choice of format. The raw artifact is **still shipped**
(for people who would rather not unzip), and the "size" column in `RELEASE.md`'s download table is the
**download size** (the zip), with the raw file listed as well.

The ZIP writer is **our own** (`gen/zip.mjs`): `node:zlib` gives you a deflate stream but not the ZIP
container (headers, central directory, CRC-32), and the project requires zero runtime dependencies
while allowing exactly one third-party build-time tool (postject). The writer implements only the slice
we need, and three criteria hold it up:

| Criterion | Where |
|---|---|
| **A real extraction tool can open it**, byte-for-byte identical afterwards | `node _lab/verify-zip.mjs` (Windows `Expand-Archive` / macOS·Linux `unzip`) |
| An independently written parser reads it back; CRC matches `zlib.crc32` bit for bit | `test/zip.test.js` (8 cases, two of them reverse checks) |
| The same input zipped twice is **byte-identical** | Same file — a ZIP header carries a timestamp, and writing "now" would destroy reproducible builds, so it is pinned to 1980-01-01 |

### `--check` verifies the copies in release/, not just dist/

What gets uploaded for a release is the **copy** in `dist/release/`, so `--check` cross-checks item by item:

| Check | What it guards against |
|---|---|
| Every artifact has a copy, and its hash matches `dist/` | **The artifact was rebuilt and `release.mjs` was not re-run** — same name, different content; a check that only looks at dist/ reports the new hash, everything looks normal, and the one shipped out is the old one |
| Every artifact's **zip is present**, and **the content inside it** matches `dist/` byte for byte | Hashing the zip file alone only proves "the archive was not modified" — it **cannot prove it holds this version's artifact**: users would extract the old program while every check looked normal |
| The values in `SHA256SUMS` match the actual files in release/ (**raw and zip both**) | Miscalculated/mis-pasted checksums. This is worse than having no checksum: users who cannot match it will think the file was tampered with |
| `RELEASE.md` is present | Without it the download page has no known-limitations section |
| release/ contains no artifact that `dist/` does not have | Leftovers from the previous version would be uploaded along with `dist/release/*` |

⚠️ A **missing** `release/` is not counted as a failure (“I just finished building and want to see which platforms are missing” is a legitimate use),
but it says explicitly “no release package has been generated yet” — so that “check passed” is not misread as “the release package is good”.

> This one was also learned the hard way: in 2026-10 the intermediate state of “dist/ has been rebuilt, release/ still holds the old copy”
> occurred **twice**, and both times it was found only by comparing hashes by hand. Now `test/release.test.js`
> has 21 cases watching it (passes when consistent, stale copy, wrong checksum, some other artifact mixed in,
> plus 3 specifically about the zip: **built from a stale artifact / corrupt archive / missing zip**).

### Why checksums are not optional

The artifact is 90 MB, and **nobody is going to read its source code**. So “the binary you downloaded really does come from this source”
can only rest on the checksums — and that is exactly what is most easily forgotten when doing a release by hand.

And a miscalculated checksum is worse than none: when users run `sha256sum` and it does not match, their first reaction is “this file has been tampered with”,
and from then on they stop trusting checksums at all. So `test/release.test.js` has a case that
**computes it independently and then compares against SHA256SUMS**.

### Reproducible build: **the same source must produce the same bytes**

Checksums only mean something under the premise of “reproducible” — otherwise someone else takes this source, builds it themselves,
gets another hash, and thinks the artifact has been tampered with. So the build **may not contain any non-deterministic input**.

In 2026-10, measurement showed that this had once not held: two consecutive builds differed by **7 bytes**,
and the diff was exactly the timestamp in the build directory name:

```
…-1791953763234\sea-entry.cjs      ← the first time
…-1791954696943\sea-entry.cjs      ← the second time
```

The cause was that the build directory is called `flicker-sea-build-<Date.now()>`, while **the entry file name enters the SEA blob as an absolute path**
(error messages and stack traces have to display it). After changing it to be named by platform (`flicker-sea-build-windows-x64`):

```powershell
node gen/build-sea.mjs      # the first time → 02ef812404e2a7b6…
node gen/build-sea.mjs      # the second time → 02ef812404e2a7b6…   byte-for-byte identical ✓
```

Two machine criteria guard it: `test/build-sea.test.js` asserts that `Date.now` / `Math.random` / `randomUUID` may not appear in the build directory name
(verified in the reverse direction: adding the timestamp back turns it red immediately), and `test/asset-digests.test.js` asserts that the embedded `version.json`
may not contain a build time.

> Once the directory name is fixed, the previous run's leftovers must be deleted cleanly first (`rmSync(BUILD)` then `mkdirSync`) —
> otherwise leftover files get mixed into this build's artifact, and the artifact “looks brand new”.

### Why RELEASE.md spells out “which platforms are missing”

SEA **does not support cross-compilation** (see §6). Packaging on a Windows machine can only produce a Windows artifact.
If the notes did not mention this, users would keep hunting for a Linux build in the download list and just think they had missed it.

For the same reason, the notes carry the **known limitations** (the relay handles ciphertext, macOS/Linux not verified on real hardware,
Firefox may fail to receive large files, closing the page prevents resuming, weak-password risk) —
these must be released together with the artifact; users must not be left thinking “end-to-end encryption” means “protected against everything”.

### Publishing

When the script finishes it prints a command you can copy directly:

```powershell
gh release create v0.1.0 dist/release/* `
  --title "闪传 Flicker v0.1.0" `
  --notes-file dist/release/RELEASE.md
```

> The right way to handle missing platforms: **run the build on those platforms** (or wait for CI's matrix to produce them),
> put all the artifacts into `dist/` and then **re-run this script once** — so that a single release covers every platform,
> rather than shipping a Windows-only version first and patching it in later.
