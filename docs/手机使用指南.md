# Using Flicker on a phone

This page covers **the phone side only** —— what you see on the screen, what to tap, and what to check first
when it does not work. Command-line options, relay deployment and protocol details live in
[`使用手册.md`](使用手册.md) and [`中继部署.md`](中继部署.md); they are not repeated here.

## 1. The short version

| What you want | What to run on the computer | How to open it on the phone |
| --- | --- | --- |
| Computer → phone (same WiFi) | `flicker send <file or folder>` | Scan the QR code on screen, or open the link it prints |
| Phone → computer (same WiFi) | `flicker recv` | Scan the QR code or open the link → enter the one-time password |
| Different networks | `flicker send <file> --relay=<your relay address>` | Open the relay link → enter the one-time password |

**The phone never installs anything**: a browser is the whole client —— no app store, no package.
A phone also cannot be the server side (browsers cannot do that), so when the phone sends files it is the
**computer that starts a service** and the phone uploads into it.

## 2. Computer sends, phone receives (same WiFi)

### 2.1 On the computer

```powershell
flicker send "D:\the-file.zip"
```

The screen shows a QR code, a link shaped like `https://192.168.x.x:port/?k=…`, and a one-time password.

### 2.2 On the phone

1. Connect the phone to the **same WiFi** (not mobile data; turn off any VPN or proxy, especially a global one).
2. Scan the QR code. If it will not scan, send the link to the phone and open it there.
3. The first visit shows “This connection is not private” → tap “Advanced” → “Proceed”. Why: section 5.
4. The page lists the files (names and sizes only) → enter the **one-time password** from the computer → tap “Start”.
5. The files are downloaded to the phone (usually “Downloads” on Android, the Downloads folder in the Files app on iPhone).

## 3. Phone sends, computer receives (same WiFi)

### 3.1 On the computer

```powershell
flicker recv
```

The screen shows a QR code, a link, a one-time password, and which folder the files are saved into.

### 3.2 On the phone

1. Connect to the same WiFi, scan the QR code or open the link (handle the “not private” warning the same way).
2. Enter the one-time password → tap “Connect”.
3. Tap “Choose photos / videos”, or “Choose other files”. Multiple files are fine, but **not a whole folder**.
4. Tap “Start sending”, and **do not switch apps and do not let the screen sleep** —— browsers freeze background pages.
5. When it finishes the computer opens the save folder and prints what was destroyed. On a name clash the computer stops and asks (rename / overwrite / skip).

## 4. Different networks (relay)

Deploy the relay once (see [`中继部署.md`](中继部署.md)), then keep using the same address:

```powershell
flicker send "D:\file.zip" --relay=https://your-relay.your-name.workers.dev
```

The link it prints looks like this (both the room name and the salt sit after `#`, so the relay cannot see them):

```text
https://your-relay.your-name.workers.dev/#k=<64 hex chars>&s=<32 hex chars>
```

Open that link on the phone and enter the one-time password. **The relay forwards opaque bytes only** —— file data never goes through it.

## 5. Should you click through “not private”?

Yes. In LAN mode the computer generates a certificate that is **valid for this session only** ——
browsers always stop first at a certificate they have not seen in their official list.

- Tap “Advanced” → “Proceed”. The data itself is encrypted; when the session ends or times out, the certificate and keys on the computer are destroyed.
- The one case worth hesitating about: **the machine you reached may not be the one you think** (someone else on the same WiFi).
  Command-line receiving (`flicker recv <link>`) makes a human compare an 8-digit fingerprint; a phone browser can only judge by “is this the right address”,
  so **never take such a link from a stranger**.
- Relay mode uses a real HTTPS certificate and shows no such warning.

## 6. What a phone can and cannot do

| It can | It cannot (browser limits, not laziness) |
| --- | --- |
| Select several photos, videos or other files at once | Select a whole folder —— so the computer only gets file names, without directory structure |
| Hand a received file to another app with “Share” | Push a file directly into some app |
| The page requests “keep the screen awake” (works on Android) | iPhone Safari has no such API; you have to keep the screen on yourself |
| HEIC photos from an iPhone arrive as-is | No format conversion —— the computer may not preview them |

## 6.5 Phone to phone (without a computer)

**This works now**, as long as you have a relay (see [`中继部署.md`](中继部署.md)).

> ⚠️ **This has not been verified on real phones, nor against a real relay**: it was driven byte for
> byte with two browser tabs **on the same machine** plus a relay running on that machine. No relay
> was available and there was no second phone, so the "across the internet" step is still pending ——
> if what you see differs, please open an issue. The technical trade-offs are in
> [`架构决策.md`](架构决策.md) §8.

1. Both phones open `/send` on the relay address (e.g. `https://your-relay.your-name.workers.dev/send`).
2. On the sending phone: pick files → type a one-time password → tap start → wait for the link.
3. Give the **link** and the **password** to the other phone **separately** (link by chat, password by voice).
4. On the receiving phone: open the link → type the same password → start receiving.

**What that page cannot do** (browser limits, not laziness):

| It cannot | Why |
| --- | --- |
| Pick a whole folder | A web page only gets the files you selected, not the directory structure |
| Resume after a reload | Keys and the room name live only in the current page |
| Start big files instantly | Every file must be read once to compute checksums (SHA-256) before sending |
| Keep going with the screen off | Browsers freeze background pages; it resumes when you return, but not if the system kills it |

> Why a relay is required: **a phone browser cannot be a server** (it cannot listen on a port).
> For two phones to talk directly, something both of them can open has to relay the bytes —— that is
> the relay. It only forwards ciphertext: no file names, no sizes, no contents.

## 7. Cannot open it / transfer stalls: check in this order

1. Is the phone on the **same WiFi** as the computer (a LAN address does not open over mobile data).
2. Is the program still running on the computer (closing the window or terminal destroys the session).
3. Windows Firewall: if it asked, choose “Allow access”; if it never asked, tick “Flicker” in “Allow an app through Windows Firewall”.
4. Is the computer on a “Public” network? Windows blocks incoming LAN connections there —— switch it to “Private”.
5. Turn off any VPN or proxy on the phone (a global one especially blocks LAN addresses).
6. If the QR code will not scan, **use the link**: the code was fixed in this session (verified module by module with an independent decoder),
   but camera apps differ in tolerance, and the link is always the surest path.

## 8. Putting the icon on the home screen (optional)

- **Chrome on Android**: ⋮ → “Install app” (some versions say “Add to Home screen”).
- **Safari on iPhone**: Share → “Add to Home Screen”.
- **Chrome / Edge on Windows**: menu → “Apps” → “Install this site as an app”.

Three known imperfections (none of them affects transferring files):
① on iPhone the icon is currently most likely a **screenshot of the page** (`apple-touch-icon` is an SVG, and iOS has traditionally required a PNG);
② a LAN session address **changes every time**, so an icon pinned to it only works once —— the address actually worth pinning is the **relay address** (fixed);
③ there is no “Install” button in the page: Android relies on the browser's own prompt, while desktop and iOS mean digging through a menu.

## 9. Real-device checklist (run it whenever phone-related code changes)

| Scenario | How to check | Passing means |
| --- | --- | --- |
| Phone receives | `flicker send` a small file on the computer, receive it on the phone | The list appears, downloading starts after the password, and the file opens on the phone afterwards |
| Phone sends | `flicker recv` on the computer, send one photo from the phone | The computer receives it, the whole-file hash printed matches, and an iPhone HEIC arrives unchanged |
| Lock / background | Lock the phone for 30 seconds in the middle of a transfer | The page resumes, or states clearly “interrupted, retry” —— it must **never** silently claim success |
