## In one sentence

While Flicker is running it holds keys and chunk ciphertext in memory and listens on one network
port, **creates no temporary files**, **modifies no user files** and **writes no logs**; on exit it
zeroes the keys in memory, closes the port and removes the session certificate.

---

## 1. File behaviour: which files it touches

> **The difference in single-file form**: the single-file (SEA) build embeds both the code and the
> page assets inside the executable, so it **does not even need to read files in its own
> directory**. Its behaviour is exactly the same as in source mode — still no temporary files,
> still nothing written to disk. The only difference is that it does not read `web/*.html` from
> disk but takes them from the embedded assets. See `构建单文件.md`.

### 1.1 Sender

| Path | Behaviour | When |
|---|---|---|
| File/folder specified by the user | **Opened read-only**, read sequentially, closed after reading | During the transfer |
| Temporary directory (`%TEMP%`, `/tmp`) | Exactly one **session-certificate directory** `flicker-cert-XXXX/` holding a single `ca.cer` (≈1 KB); the whole directory is removed by the destroy chain | While generating the certificate; see 1.1.1 |
| Current working directory | If the user passes `--card=x.png`, this file is created | Only when the user explicitly asks |
| Log file | **Not written** | Never |

> ⚠️ **This row used to say "Creates no files at all" — that was wrong**, corrected 2026-10.
> The session certificate is generated in pure JS (`src/trust.js`) and its CA DER is then written
> into a temporary directory, because the Windows trust-store operations (`certutil`) need a
> **file path**. So a `flicker-cert-XXXX/` directory *does* appear in the temporary directory, and
> is deleted when the session is destroyed.
> If the process is killed forcibly (`kill -9`, Task Manager), that instance cannot clean up —
> the next run **sweeps leftovers of the same kind that are older than 60 seconds**
> (`trust.cleanTempDirs()`), but between "the last crash" and "the next run" it sits there.
> That does not conflict with "destroyed when done" (the only content is a public CA certificate,
> and it is cleaned automatically), but stating "never" as a fact was simply wrong — anyone who
> looks at their `%TEMP%` deserves to know what that directory is.

**Core design promise: fully streamed, never written to disk.**
The sender reads one chunk → encrypts it in memory → sends it over HTTPS → immediately zeroes that
chunk buffer → reads the next chunk.
So even when transferring a 50 GB file, the process's memory usage stays in the tens of MB, and no
copy of that file ever appears on disk.

> **Why this matters**: if the program first copied the file to some temporary location and sent it
> from there, a second plaintext copy would exist on this machine, and "destroyed when done" would
> be an empty phrase — you would never know when that copy gets cleaned up or whether another
> program has read it. So we **ruled that possibility out architecturally**: not one line of code
> ever calls a file-writing API (except `--card`).

#### 1.1.1 What actually appears in the temporary directory (measured 2026-10)

A user looked at their `%TEMP%` and found **over a thousand files, 2.8 GB**, nearly all of it ours.
There were two causes, different in nature, and both deserve to be stated plainly:

| Source | What it is | When it is left behind |
|---|---|---|
| The product's session-certificate directory | `flicker-cert-XXXX/` holding one `ca.cer` (≈1 KB) | Created on every run; deleted by the destroy chain, but a **forcibly killed process leaves one behind** (the next run sweeps anything older than 60 seconds) |
| **Development / test tooling** | A copy of the artifact per smoke run (93 MB each), browser profiles (50 MB each), rehearsal and test directories | Only if you run `gen/`, `_lab/` or `node --test` from source — **users of the single-file artifact never see these** |

**99% of that 2.8 GB was the second kind**: every `gen/smoke-sea.mjs` run copies the 93 MB artifact
into a temporary directory, and its cleanup was `rmSync(..., { force: true })` with the exception
**swallowed** — while on Windows a just-killed process keeps the exe locked for a moment. So 22 smoke
runs left 22 copies: 2.1 GB. A tool that does not clean up after itself is the same offence as a
product dumping files on someone's machine.

There are now three lines of defence:
1. **Register at creation time**: `makeTempDir()` in `gen/tmp.mjs` — one place deletes everything on
   exit (Ctrl+C included), and reports anything it could not delete;
2. **Clean up afterwards**: `node gen/clean-temp.mjs` (report only) / `--yes` (actually delete) —
   it only claims prefixes we have registered;
3. **A check watches it**: `gen/check-temp-dirs.mjs` requires every `mkdtemp` prefix to be registered
   (wired into `npm run check`), and `gen/run-tests.mjs` sweeps leftovers older than an hour on every
   test run.

### 1.2 Receiver (browser)

| Path | Behaviour |
|---|---|
| Save location chosen by the user | The file is created only **after the user explicitly clicks "Save"**, and only decrypted content is written |
| Browser download directory | Used only when the user did not choose a save location |
| Browser cache / IndexedDB / localStorage | **Nothing** is written — no transfer data and no keys |

**About leftovers on the receiver's disk**: the file the receiver eventually saves does stay on
disk — that is the result the user wanted, not a leftover.
Apart from it, every intermediate product (chunk ciphertext, keys, manifest) exists only in memory.

### 1.3 Changes to system state (the only place where the system is changed)

| Item | Change | When it is undone |
|---|---|---|
| **Current-user certificate store** (Windows `Cert:\CurrentUser\Root`) | Adds one session-level certificate authority certificate | Removed when the session is destroyed; **on startup it also scans for and cleans up whatever a previous abnormal exit left behind** |
| **Current-user personal certificate store** (Windows `Cert:\CurrentUser\My`) | Adds the server certificate and its private key | Removed when the session is destroyed |
| **Firewall rules** | **Not added automatically.** On first run the operating system shows its standard authorisation dialog and the user decides | Managed by the user |

**The full sequence of certificate operations** (the order matters, and **three of these were added only after hitting a real problem**):

```
1. Generate the session CA + server certificate
2. [self-check] Verify that the certificate chain is actually valid   ← blocks the most insidious class of failure
3. [cleanup] Scan for and remove **every** certificate trace left by the previous run
      · Root store (trust entry)
      · My   store (the certificate itself and its private key)       ← this one used to be missed; 148 leftovers accumulated in measured runs
      · leftover temporary certificate directories
4. Install the CA into Cert:\CurrentUser\Root                         (certutil -user -addstore -f)
5. Start the HTTPS listener
6. [readiness probe] Request our own address once, until it really returns 200
7. Open the browser window                                            ← must come after step 6
...
8. Uninstall the CA (certutil -user -delstore)
9. Remove the server certificate and its private key (My store)
10. Remove the local copy of the session CA (My store)                ← this step was once missing
11. Delete the temporary certificate files
12. Fallback: scan both stores once more (so that even abnormal paths leave no trace)
```

**Why certificates have to be cleaned out of "two places"** (this is an implementation defect that really existed):

`New-SelfSignedCertificate` puts **both the session CA and the server certificate into `Cert:\CurrentUser\My`**;
installing into the trust store (`Root`) merely adds one extra trust entry.
The early implementation cleaned up only the CA in the Root store, so the My store accumulated
**148 `CN=Flicker Session CA` certificates** and 84 temporary directories — and that is exactly what
"destroyed when done" is supposed to prevent.

> **This defect was exposed by a test**: the test only asserted that the number of certificates in
> the Root store was unchanged, so it went unnoticed. Once the assertion "the number of leftovers in
> the My store must be 0" was added, the problem showed up immediately.
> The lesson: **when you verify "no trace left behind", you must assert on every place that could
> leave a trace**; checking only one place is as good as not checking at all.

**Step 3 ("read the certificate stores") can itself fail, and when it does it must not pretend to be clean** (measured 2026-10):

Reading `Cert:\CurrentUser\Root` / `Cert:\CurrentUser\My` relies on Windows PowerShell's `Cert:` drive
(provided by `Microsoft.PowerShell.Security`). **Modules are resolved in `PSModulePath` order** —— when the
program is started from certain developer tools, the inherited path contains PowerShell 7's copy of that same
module *ahead of* 5.1's own module directory, so 5.1 cannot load it and the `Cert:` drive does not exist at all:

```
Cannot find drive. A drive with the name 'Cert' does not exist.
```

Worse, it has **two different appearances**, and the second one is extremely dangerous:

| Form | Consequence |
|---|---|
| `Get-ChildItem Cert:\… -ErrorAction SilentlyContinue` (or no error action at all) | **exit code 0 with zero rows** —— the caller reads "the store is empty / there are no leftovers", so the CA left behind by the previous run silently stays on the user's machine |
| `Get-ChildItem Cert:\… -ErrorAction Stop` | exit code 1 with a clear message —— which is what makes it discoverable |

So there are now two hard rules: **the child process explicitly puts 5.1's own module directory first in
`PSModulePath`**, and **every command that reads a certificate store carries `-ErrorAction Stop`**
(one case in `test/trust.test.js` guards this, and another reproduces the failure inside a polluted
environment). If it still cannot be read, the startup path **says so explicitly** —— "the leftover scan was
skipped this time" —— instead of letting the program look clean.

> ⚠️ **Two sessions running at once on the same machine delete each other's certificate** (a known limitation, recorded 2026-10).
> The "leftover scan" matches by certificate name (`Flicker Session CA`) and cannot tell "left behind by a crash last time"
> from "**just installed by another session that is still running**". So:
> - when two sessions run at once, the one started later deletes the earlier one's CA →
>   the earlier session's **readiness probe fails** (and its browser may show a certificate warning);
> - the same applies to the cleanup performed on exit.
>
> That is the inherent price of cleaning up by name. Workarounds: **run one session at a time on a machine**,
> or give one of them `--no-cert-install` (that session's receiver will see a "Proceed" prompt).
> The limitation is real and is written down here rather than hidden —— it is also part of this program's
> "one transfer at a time" design stance.

**Why step 5 must come after the certificate installation**: browsers cache the result of
certificate validation.
If the port started listening before the certificate was ready, the browser may already have cached
a "not trusted" verdict, and installing the certificate afterwards would have no effect — the user
sees an inexplicable warning.

**Why step 7 must come after the "readiness probe"** (this one was added after measuring a real defect):
a browser window in `--app=<url>` mode **navigates to that address the moment it starts**.
If HTTPS is not listening yet, what the user sees is an
**"Hmm… can't reach this page" (`ERR_CONNECTION_REFUSED`) error page**, and it stays there —
recovery requires pressing F5 by hand.

Measurement confirmed this causal chain: browser opened first and the service started after → error
page; press F5 → normal; open the browser after the service is ready → normal.

**So the hard constraint on startup order is: certificate installed → port listening → probe confirms it really returns 200 → only then may the window open.**
There must never be a window of time in which "the window exists but the service is not ready".

**Why the self-check in step 2 is necessary**: measurement showed that a CA generated in certain
ways **can lack the "CA basic constraints" flag**, which invalidates the whole certificate chain and
makes the browser report `ERR_CERT_INVALID` (meaning "the certificate itself is broken", not "the
issuer is unknown").
The two errors look almost identical in a browser, but their causes and their fixes are completely
different.
With the self-check in place, this class of problem is found at startup instead of turning into a
"Your connection isn't private" message on the user's screen.

> ⚠️ **Why firewall rules are not added automatically**: changing the firewall automatically is
> impolite and requires administrator rights.
> We let the operating system show its standard authorisation dialog and leave the decision to the
> user. If the user declines, the receiver cannot connect — and the program prints explicit advice
> on how to fix it (see 使用手册 §2.3).

> **Can the certificate step be skipped altogether**: yes. `--no-cert-install` skips all certificate
> operations; the price is that the receiver sees one security warning on first access.
> See 使用手册 §10.3.
>
> **Current platform support**: the certificate trust mechanism **has been measured and verified on
> Windows**. Certificate **generation** is the same pure-JS code on every platform (it does not call
> `openssl` or PowerShell) and its criterion is a real TLS handshake; but **installing the CA into
> the system trust store is implemented on Windows only**.
> **macOS and Linux have not been measured yet**, and each has a hard reason (macOS inevitably shows
> an authentication dialog; Linux needs at least `libnss3-tools`/`nss-tools` installed before it can
> write to the browser's NSS store) — so on those two platforms please use `--no-cert-install` and
> the program will print the exact commands for installing by hand.
> See `架构决策.md` §4.3 and "the real capability boundary of the three platforms" in `路线图.md`.

### 1.4 Things it does not touch at all

Listed explicitly, because these are exactly what people worry about most:

- ❌ Does not read the user's browser data, cookies or password vault
- ❌ Does not read files the user did not specify (only paths given on the command line / in the UI)
- ❌ Does not write the registry (Windows)
- ❌ Does not install services, does not set run-at-startup entries, does not add scheduled tasks
- ❌ Does not go online to check for updates (there is no auto-update mechanism)
- ❌ Does not send any telemetry, statistics or crash reports
- ❌ Does not modify PATH or any environment variable

## 2. Network behaviour: which ports it opens, what it connects to

### 2.1 What the sender listens on

| Item | Value | Notes |
|---|---|---|
| Protocol | HTTPS (TLS 1.2+) | Plain HTTP cannot use the browser's crypto API, see below |
| Default bind | `0.0.0.0` (all network interfaces); **`::` (dual stack) when this machine has a global/ULA IPv6** | Only then can the other side connect over the LAN; narrow it with `--bind`. Binding `::` makes the same port accept IPv4 and IPv6 — which is what gives the certificate's IPv6 SANs meaning. If the system has IPv6 disabled it falls back to `0.0.0.0` **and drops IPv6 from the links** (it never advertises an address it is not listening on) |
| Default port | **A random high port** (assigned by the system) | Avoids conflicts and avoids being found by scans of fixed ports |
| Lifetime | This session only | Closed on exit |

**Why HTTPS is mandatory**: the receiver's page needs the browser's `crypto.subtle` (WebCrypto),
and browsers make it available only in a **secure context**. `http://192.168.x.x` is not a secure
context, so `crypto.subtle` would be `undefined` and encryption would simply not work.

> Only `http://127.0.0.1` is treated by browsers as a secure context — so the graphical interface
> can use HTTP, but **a receiver on the LAN must go over HTTPS**. This explains why the certificate
> business cannot be avoided.

### 2.2 The sender's outbound connections

| Scenario | Connects to | Content |
|---|---|---|
| LAN mode | **No external address at all** | — |
| Cross-network mode | The relay address the user gives with `--relay` | **All transfer data (ciphertext) goes through here**, see below |

**About "automatically detecting the public IP"**: many tools contact an external service at startup
to look up their own public IP, and that is itself an information leak (it tells a third party "this
machine is using this tool right now").
Flicker's approach is: **this lookup is done only when needed and only after telling the user
explicitly**, and it prints "looking up public IP, target: xxx".

### 2.3 What the traffic consists of in cross-network mode

The relay in cross-network mode **forwards all the data**. This has to be said clearly, with no vagueness:

| Traffic | Goes through the relay? | Notes |
|---|---|---|
| **File content** | ✅ **Goes through (but only as ciphertext)** | Every chunk is AES-256-GCM ciphertext; the relay has no key |
| File names / directory structure | ✅ Goes through (ciphertext) | The manifest itself is encrypted, so the relay cannot see the file names |
| File size / chunk count | ❌ Does not go through | These are inside the encrypted manifest |
| Password | ❌ **Never goes through** | The password never goes on the wire: each end uses it for challenge-response, see `PROTOCOL.md` |
| Room ID | ✅ Goes through | Derived from the password via HKDF (128 bit, one-way). **It is the capability credential** |
| Salt | ❌ Does not go through | Placed after the `#` in the URL, and **browsers do not send the fragment to the server** |

**What the relay can know**: the room ID, the size and timing of every message, the IPs of both ends.
**What the relay cannot know**: file content, file names, the password. What it receives is opaque
ciphertext, and changing any single byte is rejected by the receiver's authentication tag.

> **Why not do "hole punching for a direct connection"**: the early design wanted the relay to do
> only the rendezvous while the two ends connected directly (which would use less relay bandwidth).
> Measurement showed that this path does not work under current network conditions: the user's uplink
> is behind CGNAT and there is no global IPv6 (see the reality check in `路线图.md`). So we settled on
> the **relay forwarding** path, which is certain to work, and we write the cost here honestly:
> **the relay carries all the bandwidth and can see that a transfer is happening and how large it
> is**. If you want to avoid that, run your own relay (`中继部署.md`, one command to deploy into your
> own Cloudflare account).
>
> One more thing: relay forwarding does not weaken the encryption promise. The constraint "the two
> computers can only transfer if their passwords match" is guaranteed by **cryptography** (you cannot
> compute the room name = you cannot even find the room; you cannot derive the key = you cannot
> decrypt the ciphertext), not by "the data never passed through a third party".

### 2.4 The receiver's network behaviour

The receiver is a browser page, so its network behaviour is governed by the browser:

- It sends requests only to the sender's address (or the relay address)
- **It loads no third-party resources** — the page is a single file, styles are inlined, no CDN, no fonts, no analytics scripts
- **It uses no cookies, localStorage or IndexedDB** to store anything related to the transfer

> **Why this matters**: in LAN mode the receiver may have **no internet access at all**.
> A single line of code referencing an external resource would give the other side a blank page.
> Zero external dependencies is a hard requirement.

## 3. The complete lifecycle of the keys

### 3.1 Timeline

```
① The user types the password
      ↓  converted to a byte array immediately; the password is no longer held as a string
② Compute the verifier V = PBKDF2(password, salt, 600000)     [exists only in the sender's memory]
      ↓  only the salt is sent to the receiver (the salt is not a secret)
③ Derive three keys: K_room / K_auth / K_enc                  [HKDF-SHA256, three labels]
      ↓  K_room is used to compute the room ID (the relay can see the room ID but cannot reverse it into the password)
④ Challenge–response handshake
      ↓  the receiver first proves with K_auth that it knows the password; then the sender proves it
⑤ Encrypt the file chunk by chunk with K_enc                  [independent IV per chunk, sequence number written into the AAD]
      ↓  ciphertext lives in memory only until it is written out
⑥ Session ends
      ↓  everything is zeroed (see section 4)
```

### 3.2 How long keys stay in memory

| Key | Lifetime | Basis |
|---|---|---|
| Salt | The whole session (it is not a secret, but there is no need to keep it either) | Random value |
| V (password verifier) | From password entry to session destruction | PBKDF2 result |
| K_auth | From the start of the handshake to its end | HKDF output |
| K_enc | From the end of negotiation to the last chunk being sent | HKDF output |
| Chunk plaintext buffer | **The duration of one chunk** (milliseconds) | The same buffer is reused |
| Chunk ciphertext | Until that chunk is written out | The buffer is reused |

### 3.3 An honest note about "zeroing memory"

This is where every program that claims "secure erasure" tends to be vague, so let us be clear:

**What can be reliably zeroed:**
- Memory allocated by `Buffer` / `Uint8Array` / `ArrayBuffer`
- Method: `buf.fill(0)`

**What cannot be reliably zeroed (an inherent limitation of the JavaScript language):**
- **Strings**. JS strings are immutable, the runtime may copy them during garbage collection, and the
  historical copies are beyond the program's reach
- Therefore: **the password is converted to a `Uint8Array` immediately after being read in, and the
  string reference is dropped at once**, shrinking the "cannot be zeroed" window to milliseconds
- By the same token, any key material that ends up in string form is a design defect, and code review
  should look for it specifically

**This cannot be made theoretically perfect**; it can only be made engineering-optimal. If an
attacker can read this process's memory while the process is running, then in many cases he has
already won — that is not something encryption can solve.

## 4. Destroy: what is destroyed, when, and how

### 4.1 What triggers destruction

Any one of these starts the destruction process:

| Trigger | Notes |
|---|---|
| The transfer completed normally | The most common case |
| The user presses `Ctrl+C` | A deliberate abort |
| The user clicks "cancel and destroy" | In the graphical interface |
| Timeout waiting for the other side to connect | 10 minutes by default |
| An error during the transfer | Network drop, verification failure, the other side closing the page |
| Five failed password attempts in a row | Anti-brute-force |
| The process receives `SIGTERM` / the window is closed | Best effort |

### 4.2 The destroy action list

```
 1. Zero K_enc, K_auth, V, the salt and the chunk buffers   ← Buffer.fill(0)
 2. Drop every reference to key material held as a string
 3. Revoke the one-time tokens (invalid within the session, cannot be used again)
 4. Stop accepting new HTTPS connections
 5. Close the listening socket; forcibly drop every established connection
 6. Tell the relay to delete the room (if a relay was used)
 7. Remove the session certificate from the current-user certificate store
 8. Delete the private key from memory (it was never written to disk in the first place)
 9. Flush and close every open file handle
10. Print the destroy report (below) and exit the process
```

**This report is printed on the terminal**, and that is deliberate — so that "destroyed" is a fact
the user can see, rather than a promise:

```
  ✓ Destroyed: session keys · password verifier · chunk buffers
  ✓ Service closed, the link is no longer valid
  ✓ Session certificate removed from the system
```

### 4.3 Destruction in unexpected situations

| Situation | What happens |
|---|---|
| The process crashes / is force-killed (`SIGKILL`, ending the process from Task Manager) | **Step 7 (removing the certificate) may not have run.** The keys and ciphertext are reclaimed by the operating system together with the process memory and do not stay on disk; but the certificate may remain in the certificate store |
| The computer loses power / blue-screens | Same as above. The contents of memory vanish with the power; the certificate may remain |
| The browser is force-closed | The receiver's keys vanish with the page's memory; the sender detects the broken connection and starts destruction |

**Therefore: in extreme cases the certificate may remain.** How to remove it:

```powershell
# Windows: find and delete the certificate issued by Flicker Session
certutil -user -delstore Root <certificate thumbprint>
```

**This is also why there is no need to worry about clearing memory**: what is in memory is gone the
moment the power goes, and what the user really needs to care about is the certificate store, the one
persistent change — and that is exactly the one we clean up proactively.

### 4.4 What destruction does not affect

| Thing | Why it is kept |
|---|---|
| The sender's original files | Flicker is **read-only** towards user files and never deletes them |
| Files the receiver has already saved | That is the result the user wanted |
| The text printed in the terminal | It stays in the terminal's scrollback buffer (if that bothers you, just close the terminal window) |

> **Again: Flicker will never delete your original files.** No argument can make it do that.
> A feature like "delete the source automatically once the transfer is done" looks convenient, but
> one mistaken operation is unrecoverable, and it is not something a transfer tool should do.

## 5. Process behaviour: signals, exit codes, exceptions

### 5.1 Signal handling

| Signal | Behaviour |
|---|---|
| `SIGINT` (Ctrl+C) | Runs the full destroy sequence, then exits with exit code `130` |
| `SIGTERM` | Runs the full destroy sequence, then exits with exit code `143` |
| `SIGHUP` | Same as `SIGTERM` |
| `SIGKILL` | **Cannot be caught**; the process dies immediately (see §4.3) |
| Uncaught exception | Best-effort destroy sequence, prints the error, exits with exit code `1` |

**Pressing `Ctrl+C` twice**: the first press triggers a graceful destroy; if destruction gets stuck,
the second press forces an immediate exit.
(This is to avoid "getting stuck at the certificate removal step, with the user wanting to abort and
unable to".)

### 5.2 Exit codes

| Exit code | Meaning | Common causes |
|---|---|---|
| `0` | Success | The transfer completed and was destroyed |
| `1` | General error | Bad arguments, file does not exist, disk full |
| `2` | Usage error | Misspelled command, missing argument |
| `3` | Network error | Port already in use, bind failure |
| `4` | Authentication failure | Password mismatch, too many failed attempts |
| `5` | Integrity check failure | The transferred data was corrupted or tampered with |
| `6` | Timeout | No connection from the other side |
| `130` | Interrupted by the user | `Ctrl+C` |
| `143` | Terminated | `SIGTERM` |

> In scripts, use `$LASTEXITCODE` (PowerShell) or `$?` (bash) to judge the result.
> **Note that `4` and `5` are security-related failures**, and scripts should treat them differently.

### 5.3 What is inside the process

| Item | Notes |
|---|---|
| Threads | The main thread plus a few internal Node threads (the libuv thread pool) |
| Child processes | `certutil` is called once, for certificate operations only (Windows); no child processes otherwise |
| Resident in the background | ❌ None. The process exits = everything is over |
| Run at startup | ❌ None |

## 6. Logging and output

### 6.1 Output channels

| Channel | Content |
|---|---|
| Terminal stdout | Progress, status, link, QR code, destroy report |
| Terminal stderr | Errors and warnings |
| Graphical interface page | A structured version of the same stdout content |
| **Files** | **None** — the program writes no log file of any kind |

### 6.2 What is in the output and what is not

| Is printed | Is not printed |
|---|---|
| File names, sizes, counts | ❌ The password (in any form) |
| Transfer speed, progress, elapsed time | ❌ Keys, salt, verifier |
| The other side's IP and browser information | ❌ File content (not even a fragment) |
| The checksum (SHA-256, for verification) | ❌ Full file paths (only file names are shown) |
| Certificate thumbprint | ❌ One-time tokens❓ (see below) |

**About the link and the token**: the terminal **does** show the full link (otherwise the user could
not send it to the other side), but that means **the terminal output itself is sensitive information**.
If you redirect the output to a file or paste it into a chat window, the link is leaked. The program
prints a reminder about this next to the link.

**About `--quiet`**: it omits the progress refresh and the QR code and prints only the final link,
the password and the destroy report.

### 6.3 Advice for managed environments

If Flicker is to go onto a company's managed machines:

- It writes no files, writes no registry keys and installs no services → normally no special uninstall process is needed
- **Exception**: writes to the certificate store may be blocked by endpoint management software. In that case use `--no-cert-install`
- To turn off every persistent change, add `--no-cert-install`

## 7. Resource usage

| Resource | Usage | Notes |
|---|---|---|
| **Memory** | Around 40–80 MB, constant | **Unrelated** to file size (chunked streaming; the receiver additionally holds a chunk prefetch buffer, see below) |
| **CPU** | One core near saturation while encrypting | AES-NI hardware acceleration; the receiver's whole-file hash runs in a **Web Worker**, off the main thread |
| **Disk** | **0 bytes of extra usage** | No temporary files are created |
| **File handles** | 1 per file being sent | Files are handled one at a time, not all opened at once |
| **Network** | Fills the available bandwidth by default | Can be rate-limited with `--rate` |

**About why memory is constant**: the chunk buffer size is fixed (**1 MiB or 2 MiB, as negotiated**), so whether you transfer
1 MB or 50 GB the memory usage curve is flat. This is the fundamental reason "large files do not
crash it", and also the precondition that makes "no temporary files" possible.
The receiver's chunk prefetch is the one part of that promise that needs spelling out: it holds at
most **6 chunks** (the default depth) × the chunk size, i.e. **6 MiB or 12 MiB** (the latter with the
default 2 MiB chunks), a **hard ceiling** —— the criterion is
"the size of the pending table", not "the number of requests in flight", so it cannot pile up when
the consumer slows down. Raising the depth further buys nothing: a browser opens at most 6
concurrent connections per origin.
The whole-file hash's Web Worker holds no extra data: chunks are **transferred** to it (zero-copy on
the streaming-write path) and dropped as soon as they are hashed.

**About concurrency**: the current version handles only one transfer at a time and one file at a time
(at any one moment). Concurrency is not done so that the logic of progress, rate limiting and
destruction stays predictable.

## 8. Error handling and failure modes

### 8.1 Error categories and handling principles

| Category | Examples | Handling |
|---|---|---|
| **Security** | Password mismatch, MAC verification failure, hash mismatch | **Abort immediately**, no retry, and state clearly that "no data was transferred and no file was written" |
| **Transient** | Network jitter, connection reset, DNS blip, 5xx/429 | **Automatic retry with exponential backoff** (starting at 400ms, doubling, capped at 8s); present on both ends |
| **Configuration** | Port in use, file does not exist, disk full | Fail immediately with actionable repair advice |
| **Timeout** | The other side never shows up | Abort and destroy according to the timeout setting |

**The "transient" category was added in 2026-10, and it fixes a real defect.**
Previously a single network hiccup would terminate the whole transfer — and that is precisely the
most common cause of failure in long transfers (far more common than "the other side closed the
program"). Losing tens of GB at 99% because Wi-Fi blipped for a moment is unacceptable.

The criterion for retrying is in `isTransientError()` (implemented in `src/relay/core.js`; `src/relay/client.js` only re-exports it):
only transient failures are retried; `NO_ROOM` / `EXPIRED` / `GONE` / `BAD_SEQ` / user cancellation
**all fail immediately** — taking an unrecoverable error into a retry only makes the user stare at
the screen through four pointless rounds of backoff.

> **A less obvious difficulty**: when `POST /batch` fails you cannot tell directly whether it was
> committed or not (the request may have succeeded and only the response was lost on the way back).
> Blindly resending would put duplicate messages at the tail of the room.
> The solution comes from the protocol itself — **sequence numbers are assigned by the server**:
> before retrying, read `nextSeq` once; if it has risen to `startSeq + count`, the previous attempt
> was in fact committed, so return success directly.


### 8.2 Three important failure behaviours

1. **When the password is wrong, nothing should happen.**
   The receiver creates no files and writes no data. The error page says explicitly:
   "No data was transferred and no file was written to disk." — that sentence is there to stop the
   user from panicking.

2. **When verification fails, the data already received is not written to disk.**
   Integrity checking runs the whole way through (a per-chunk GCM authentication tag plus a final
   whole-file SHA-256).
   Any single bad chunk aborts it, and **the chunks already received are not written to the target file**.

3. **Security-category errors are not retried.**
   A MAC verification failure is not retried. Retrying would only give an attacker more information.
   Abort, destroy, start over.

## 9. Security boundary and threat model

### 9.1 Protection goals

| Goal | Means |
|---|---|
| File content is not eavesdropped | AES-256-GCM end-to-end encryption |
| The password is not eavesdropped | Challenge–response; the password never goes on the wire |
| Content is not tampered with | A per-chunk GCM authentication tag + the sequence number written into the AAD (prevents reordering / replay / splicing) |
| The complete file is not substituted | A final check of the whole-file SHA-256 hash |
| Someone without the password sees no information at all | The manifest (file names / sizes) is itself encrypted |
| No trace after use | See section 4 |
| Resistant to brute force | PBKDF2 with 600,000 iterations + automatic destruction after 5 failures + a short session lifetime |

### 9.2 Trust assumptions

Understanding this program requires accepting the following assumptions:

| Assumption | If it does not hold |
|---|---|
| The browser/Node runtime on both ends is trustworthy | Nothing holds at all (this is the shared precondition of all web encryption) |
| The operating system's random number generator is trustworthy | Keys become predictable (every modern operating system satisfies this) |
| The user exchanges the password over a trusted channel | Password leaked = file leaked (for example, sending the link and the password in the same WeChat message) |
| The system clock is roughly correct | Affects timeout decisions, does not affect encryption |

### 9.3 Attacks we explicitly do not defend against

| Attack | Why it cannot be prevented |
|---|---|
| The endpoint is already controlled (keylogging, a trojan, screen recording) | Encryption addresses the transfer, not endpoint security |
| A weak password is guessed | A `123456` the user chose themselves cannot be remedied by technical means (the default password is strong) |
| Traffic analysis and metadata | One can tell that "encrypted traffic is being transferred", not what the content is |
| Denial of service | The other side can simply not connect, or can disconnect midway |
| The relay provider turns malicious | What it can do is **deny service** or **observe metadata**; it cannot alter file content (every chunk has an authentication tag) and cannot read the file |
| The user leaks it themselves | Sending the link and the password off together, or screenshotting the terminal |

### 9.4 One concrete adversarial scenario

**Assume the relay server is completely untrustworthy.** What can it do?

1. ❌ Read file content — it cannot; the data does not pass through it
2. ❌ Tamper with file content — it cannot; every chunk has a GCM authentication tag, so any change is bound to be detected
3. ❌ Obtain the password — it cannot; the password is never transmitted
4. ⚠️ See metadata (that a device is communicating, the time, the IP) — it can; that is its inherent position
5. ⚠️ Deny service (not forwarding messages) — it can; but the user sees "cannot connect" rather than "transferred the wrong data"
6. ⚠️ Introduce itself to both sides (man in the middle) — theoretically possible, but because the room ID
   is derived from the password, an attacker who does not know the password cannot enter the room.
   To close this off completely, a **short authentication string** (both sides compare 6 digits) could
   be added in the future as an optional enhancement; see the suite extension section of `PROTOCOL.md`

## 11. Audit checklist you can verify yourself

Do not trust the document, go and verify. Every item below can be confirmed by hand:

| # | How to verify | Expected result |
|---|---|---|
| 1 | Transfer a large file while watching the size of the `%TEMP%` directory | It does not grow (one `flicker-cert-XXXX/` appears, holding a ≈1 KB CA); it is gone when the transfer ends |
| 2 | Use `netstat -ano \| findstr <PID>` to look at the listening port | Exactly one random high port, gone after exit |
| 3 | Search the whole disk for files created during the transfer | Only the one file the receiver saved |
| 4 | Filter `WriteFile` operations in Process Monitor (Procmon) | No writes to any temporary directory at all |
| 5 | After the transfer, check `certmgr.msc` → Trusted Root Certification Authorities | No `Flicker Session` leftovers |
| 6 | Look at Task Manager → startup items / services | Nothing related to Flicker |
| 7 | Capture packets (Wireshark) to see cross-network-mode traffic | On the relay you **can see the bytes of the file data**, but **they are all ciphertext**: you can neither reconstruct the content nor see the file names. To confirm this, search the captured packets for any plaintext fragment of your file or for its file name |
| 8 | Run LAN mode with the network disconnected | **It works completely normally** (proof that it depends on no external service) |
| 9 | Run with `--no-cert-install` and watch the certificate store | No change at all |
| 10 | Search the source for `fs.write` / `fs.createWriteStream` | They appear only in the `--card` export and the receiver's save path |

**The correct expectation for item 7**: the relay **really does forward all the data** (that is its
job), so the capture will contain a lot of bytes — the point is that those bytes **cannot be
decrypted**.
Item 8 proves that LAN mode has nothing to do with any of this: unplug the network cable and the
transfer still works.

## 12. Honesty list: known limits and things we cannot guarantee

We would rather say this clearly up front than have you discover it by accident while using it.

| # | Limit | Impact | Is there a way to solve it |
|---|---|---|---|
| 1 | **In extreme cases the certificate may remain** (process force-killed, power loss) | One harmless extra certificate in the certificate store | Delete it by hand, or use `--no-cert-install` |
| 2 | **JS strings cannot be reliably zeroed** | In theory a copy of the password may be left in memory | A language limitation; the window has already been shrunk to the minimum; see §3.3 |
| 3 | **Cross-network mode requires a relay** | The user has to deploy one once (free) | No solution. An inherent limitation of NAT; the local broadband connection was measured to be CGNAT |
| 4 | **Receiving large files is limited in Firefox / Safari** | Above roughly 1 GB it may fail | Use Edge / Chrome |
| 5 | **Using a phone as the sender is limited** | Cannot pick a folder and send it automatically | A browser platform limitation; needs a mobile shell (P4) |
| 6 | **No defence against a controlled endpoint** | A trojan can see everything | No solution; beyond the scope of encryption |
| 7 | **No defence against weak passwords** | If the user sets a weak one themselves, it is dangerous | The default password is strong; a password-strength check could be added |
| 8 | **The relay can see metadata** | It knows that someone transferred something at this time | Use the same LAN, or run your own relay |
| 9 | **Only one transfer at a time** | Cannot send to several people at once | A current design trade-off, extensible in the future |
| 10 | **The terminal output contains the full link** | Redirecting it to a file would leak the link | The program gives a reminder; `--quiet` mode could be considered to reduce the output |

## Appendix: the one-minute version

If you only want to know the few things that matter most:

1. **No temporary files** — even a large file only takes a fixed amount of memory, and no copy ever appears on disk
2. **Your original files are untouched** — read-only, never deleted
3. **No logs, no online update checks, no telemetry**
4. The **only system change** is one session certificate, removed automatically when done; `--no-cert-install` turns it off completely
5. **Exit means the end** — no background process, no service, no run-at-startup entry
6. **Unplug the network cable and LAN transfer still works**
