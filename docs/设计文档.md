# One-Shot File Transfer Program — Design and Implementation Plan

> Source of requirements: [`AUTHOR-NOTES.md`](../AUTHOR-NOTES.md) (the author's original request)
> Goal: get a file from this machine to another computer, with **no program installed on the receiver**, where the transfer only happens if **both computers enter the same password**, and **everything is destroyed the moment it has been used**.

---

## 1. Requirement Breakdown (Turning a Casual Request into Technical Constraints)

| Original requirement | Technical constraint | Design decision it affects |
|---|---|---|
| "The target computer must not download a program" | The receiver's only runtime is a **browser** | The receiver is a pure web page (HTML+JS); the sender must be able to serve that page to the receiver |
| "Choose the file to send" | The sender needs a way to pick files | Pass a path on the command line / drag it into the web page (the page only passes the path back, see 5.3) |
| "Set a password" | The password is set on the sender | Typed into the sender's terminal, then "armed" after a second confirmation |
| "Both computers must enter the same password before anything can be transferred" | **Mutual authentication**, not one-sided verification | Challenge–response handshake; the password itself never touches the wire (see Chapter 4) |
| "The two computers definitely have to be linked together first" | A transport channel is needed | ①direct connection on the same LAN ②WebRTC hole punching ③port forwarding (see Chapter 3) |
| "Everything used for the transfer is one-shot and destroyed once it has been used" | Nothing written to disk, no residue, the session burns down with itself | Keys exist only in memory; streaming encryption creates no temporary files; on completion everything is wiped and the server is shut down (see Chapter 6) |

The broadband line the sender sits on was measured, and the results immediately ruled out two paths:

```
Public egress IP   (redacted: it was the author's home uplink; the exact value does not affect any conclusion)
Local address      192.168.1.5

Traceroute (tracert to 114.114.114.114):
  Hop 1   192.168.1.1      <1 ms    ← your router
  Hop 2   192.168.1.1       <1 ms    ← there is one more router upstream
  Hop 3   100.64.x.x         6 ms    ← carrier equipment; 100.64.0.0/10 is the range reserved for carrier-grade NAT
  Hop 4   timeout

Global IPv6        none (Test-NetConnection 240c::6666 → unreachable)
Router UPnP        no response to SSDP probe (unavailable)
```

**Three conclusions, all of them hard facts:**

1. **The public IPv4 sits behind the carrier's big NAT (CGNAT)** — the public address you are assigned is an address shared by many users. Doing port forwarding on your own router **is meaningless**, because the request never even reaches your home router (there is `192.168.1.1` and the carrier's layer in between).
2. **There is no public IPv6** — Layer 3 (port forwarding / direct connection) is completely infeasible.
3. **Double NAT + UPnP unavailable** — even the "open the port automatically" fallback is cut off.

### Therefore, for this machine, only one path across the internet is left: **relay (rendezvous point)**.

This is not a design preference; it is the only answer the network environment forces. Chapter 4 explains in detail what a relay is and why it is indispensable.

## 3. Connectivity: A Three-Tier Fallback Strategy

For the two computers to connect, **at least one** of the following must hold. The program probes automatically and hands you the one that works.

### Layer 1: Same LAN (recommended — most reliable, fastest)
The sender starts an HTTPS server on `0.0.0.0:随机端口`, and the receiver's browser opens `https://192.168.1.5:<port>/?k=<一次性令牌>`.
- Speed = LAN bandwidth (usually 100MB/s+, several GB in seconds)
- No public network needed, no relay needed, no WebRTC needed
- ⚠️ On Windows a firewall authorization dialog pops up the first time; just click "Allow" (a one-click `netsh` allow script can be attached)

### Layer 2: Different networks — relay forwarding (**implemented, and different from the original idea**)

> **⚠️ This section is the original design idea; implementation overturned it. It is kept to record the decision process.**
>
> Original idea: the relay only does rendezvous; once the receiver has the sender's address it **connects directly** to the sender, and data never passes through the relay.
> The precondition is that the sender has an address the receiver can reach (public IPv6 / same subnet / port forwarding).
>
> **Measurement knocked all three of these down**: the user's egress is CGNAT (the public IP is shared with others), and there is no global IPv6.
> So "connect directly after the introduction" had no line to introduce at all.
>
> **Final implementation: the relay forwards all the data** (`src/relay/`).
> The cost is recorded honestly: the relay carries the entire bandwidth, and it can see that "someone is transferring something, and how big it is".
> What that buys is **guaranteed availability** — no dependence on any hole-punching success rate.
> The encryption promise is unchanged: everything the relay handles is ciphertext, and the keys exist only at the two ends.
>
> For the decision process see `架构决策.md`; for the protocol see `中继部署.md` and `PROTOCOL.md`.
> To avoid the relay altogether, use LAN mode or self-host a relay.

<details>
<summary>The original idea follows (no longer applicable; expanding this is only for the archive)</summary>

Both ends connect to a **relay (rendezvous point)**, exchange SDP, and then use a WebRTC DataChannel to establish a peer-to-peer channel between the browser ↔ **sender**.

But as Chapter 2 says, the sender has no WebRTC. **The data plane is therefore changed to: an encrypted chunked HTTP stream between the browser ↔ sender**, and the relay is only responsible for "steering the receiver to the sender":

```
Receiver browser ──opens the relay page (room ID derived from the password hash)
                     │  relay tells the sender "someone has entered room N"
Sender (Node) ───────┘  the sender posts an invitation "how to reach me directly" into the room
Receiver reads the invitation ──> browser fetch connects straight to the sender ──> chunked encrypted download
```

What goes into this invitation post? Ordered by reachability priority:
1. The sender's address on **public IPv6** (IPv6 has no NAT, it is directly reachable, and it is the cleanest)
2. The sender's address on the **LAN** (this hits when the two sides are in fact on the same subnet; in that case the relay only acted once as the "matchmaker")
3. The sender's public `IP:port` (when the user has set up port forwarding on the router)

If all three are unreachable, the browser's fetch fails — the program tells the user clearly to choose Layer 1 or Layer 3, and **does not pretend to have succeeded**.

> Why not fall back to a TURN relay? Because public TURN services need accounts/credentials, which counts as "depending on a third-party service", and long-term reliability cannot be guaranteed. Better to give a clear failure message plus an actionable alternative path.

</details>

### Layer 3: Port forwarding / public IPv6 direct connection (**ruled out by measurement on this machine**)
The sender prints the public IP + port, the user forwards that port to this machine on the router, and the receiver just opens the link.
- Precondition: an **exclusive public IPv4** at home (so you can do the port forwarding yourself), or **public IPv6** on both sides
- **Not satisfied here, as measured**: CGNAT (the public IP is shared with others) + no IPv6 → this layer is unavailable
- If you switch broadband (to one with a public IP) or call the carrier to enable public IPv4/IPv6, this layer becomes available again automatically
- This layer is kept implemented in the code, because it is an effective fallback for "someone else's broadband"

### Key design point: the relay does the data plane (**the opposite of the original idea**)

> The original idea's three "benefits" rested on "the relay does not touch the data"; after implementation they do not hold. Point by point:

| Benefit as originally assumed | Actual situation |
|---|---|
| Free quota is more than enough | ❌ **Does not hold**: all data goes through the relay. The free quota is enough for everyday use, but for large files you have to do your own sums |
| The relay cannot obtain the file contents | ✅ **Still holds**, but it relies on **encryption** rather than on "not passing through": what the relay gets is ciphertext |
| The room is destroyed immediately after the transfer | ✅ **Still holds**: a DELETE goes out as soon as the transfer completes, with a 15-minute TTL as a backstop |

**Conclusion**: the security promise has not changed (it is in fact stated more clearly now); what changed is that **the bandwidth cost is carried by the relay**.
So "self-hosting the relay" went from "optional" to "something people who care about cost and metadata should do".

## 3 (Addendum). What Exactly Is a Relay (In Detail)

> **⚠️ The diagram in this section describes the old "connect directly after the introduction" design. The actual implementation is "the relay forwards the data".**
> Step ④, "the two sides connect directly and the relay drops out", **did not happen** —
> under the real conditions of CGNAT + no IPv6, after the introduction they still cannot connect,
> so the data keeps going through the relay (it is just ciphertext the whole way). **When reading this section, replace step ④ with
> "the data is forwarded through the relay, and what the relay sees is ciphertext"**. What the earlier sections say about "why a relay is needed and
> why you have to self-host it" still holds completely.

### 1. Why it is indispensable

Your home router gives you a **private address**, `192.168.1.5`. That address **does not exist** on the internet at large — it is a door number inside your own LAN, and nobody recognizes it once it leaves the router.

So the computer on the receiver's side has **no way whatsoever to connect on its own to the machine behind your home router**. It does not even know the address, and even if it did, it could not be routed there.

So what do you do? **Both sides connect outward on their own initiative.**

```
   Your home (192.168.1.5)                    Cloud                Peer's home
         │                                        │                               │
         │ ① Connect outbound (it isn't blocked)  │                               │
         ├───────────────────────────────────────>│<──────────────────────────────┤
         │                                        │  ① Connect outbound           │
         │                                        │                               │
         │ ② "I am A, my password hash is X"      │ ② "I am B, hash is X too"     │
         ├───────────────────────────────────────>│<──────────────────────────────┤
         │                                        │                               │
         │ ③ relay tells A where B is             │ ③ relay gives B A's address   │
         │<───────────────────────────────────────┤──────────────────────────────>│
         │                                        │                               │
         │ ④ Both sides know each other's address; connect directly (relay exits) │
         └───────────────────────────────────────────────────────────────────────>│
```

**This is the relay: a middleman that "both sides can reach", whose job is to make the introduction — and then it leaves.**

### 2. Why you have to deploy it yourself

Because that "point in the cloud" must **stay online at all times**, be **reachable by both sides**, and be **stable over the long term**.

- Use someone else's public service? It may shut down tomorrow, and it may log your room ID. Not controllable.
- Use your own computer as the relay? Your home computer is itself behind NAT, so others cannot reach it either — an infinite loop.
- **So it can only be your own small program on a free cloud service.** That is the real meaning of "deploy once": put your own 120 lines of code on a free machine that is online 24 hours a day.

### 3. The concrete deployment steps (the actual actions when the time comes)

### 4. Just how small is the thing that runs inside the relay

```
Responsibilities (exactly three):
  ① Host the receiver's single page (for when it is inconvenient for the sender to serve it)
  ② Forward a few rendezvous messages between the two ends that share a room ID
  ③ Delete rooms automatically on expiry (TTL as a backstop) + support an explicit DELETE (burn after use)

What it does not do:
  ✗ Does not touch file data
  ✗ Does not save anything to disk
  ✗ No database, no login, no domain name needed
```

**It is not a file server; it is a message passer.** The entire traffic of one transfer is a few rendezvous messages, maybe a few KB.

### 5. Why not use an off-the-shelf solution (all were considered and rejected)

| Option | Why it is not used |
|---|---|
| Google Drive / WeChat / cloud drives | The file has to land on a third-party server, which violates "destroyed once used" |
| Public TURN / WebRTC relay services | They need account credentials, and long-term reliability is not controllable |
| A public MQTT broker as the rendezvous point | Unexpected disconnects, no TTL guarantee, and it exposes the room ID to a stranger's infrastructure |
| Tunnels such as ngrok / cloudflared | They count as "installing a third-party program", and the free tiers have all kinds of limits |
| Tailscale | The receiver would have to install it — **a direct violation of your requirement 1** (this one is a hard veto) |
| Handing over a public IP and letting the other side connect | Measured on this machine, it is CGNAT, so it cannot connect at all (see Chapter 2 Addendum) |

### 6. The final conclusion for your home network

| Scenario | Usable? | Which path |
|---|---|---|
| The two computers are on **the same WiFi / the same router** | ✅ Perfect | Layer 1 LAN direct connection, the fastest, **nothing to deploy at all** |
| The two computers are on **different networks** (one at home, one at the office/away) | ✅ But it requires | Layer 2: the free relay must exist first |
| Relying on port forwarding alone, without a relay | ❌ Impossible | CGNAT + no IPv6; ruled out by measurement |

**So the relay is the only ticket for "across networks", while "same network" is completely free.** If your everyday scenario is transferring between two computers at home, finishing the P0 stage is already enough, and the relay can wait until later.

## 4. The Password: Why "Both Computers Enter the Same Password" Can Be Enforced by Cryptography

It cannot just be "compare the strings on the page", because then the password would cross the wire in the clear. A **challenge–response** scheme is used, and the password itself is never transmitted:

```
1. The sender sets a password P and a random salt S (16 bytes)
   Computes V = PBKDF2-SHA256(P, S, 600000)        ← 32 bytes, never leaves the sender's memory
2. The sender derives three mutually unrelated keys from V with HKDF-SHA256:
       K_room = HKDF(V, "room")     → room ID → the two computers only land in the same room if their passwords match
       K_auth = HKDF(V, "auth")     → handshake authentication
       K_enc  = HKDF(V, "enc")      → file encryption
3. Handshake (the receiver proves first that it knows the password):
      receiver → sender : nonce (random 32 bytes)
      receiver → sender : MAC_r = HMAC(K_auth, "recv" ‖ nonce)
      sender verifies MAC_r; on success it replies MAC_s = HMAC(K_auth, "send" ‖ nonce)
      receiver verifies MAC_s
4. Mutual authentication complete; both sides share K_enc and the transfer begins
```

The properties of this design:
- **The password never touches the wire**: packet capture yields neither the password nor a directly reusable credential (the nonce is one-shot, so replay is resisted)
- **Password agreement is a mathematical result**, not a UI hint: different passwords → different room ID (the two sides never find each other) or a failed MAC check (aborted immediately)
- **The receiver is authenticated as well**: the sender verifies the receiver too, which keeps third parties out of the room
- **Resistant to offline brute force**: PBKDF2 with 600,000 iterations; the room TTL is only a few minutes, and failed attempts are capped in number
- A weak password is the only residual risk → the sender can generate a strong random password (a suggested value is given by default)

> On Windows/macOS browsers are forbidden from letting `fetch` reach self-signed HTTPS — so Layer 1 uses a **runtime self-signed certificate** and gives a one-time "continue anyway" walkthrough on the page. The certificate is likewise session-scoped and destroyed after use. (This point needs end-to-end verification with a real Chrome at implementation time.)

## 5. Transport Layer Design

### 5.1 Division of roles (because the sender has no WebRTC)
- **Sender (Node)**: reads the file, encrypts in chunks, serves the HTTP chunk API, controls the rate, computes checksums, destroys
- **Receiver (browser)**: decrypts, verifies tags, writes to disk, shows progress
- **relay (optional)**: rendezvous only

### 5.2 Chunked encryption (supports files of any size)
```
Chunk size       1 MiB
Per chunk        ciphertext = AES-256-GCM(K_enc, IV = f(fileIndex, chunkIndex), plaintext, AAD = fileIndex‖chunkIndex‖totalChunks)
Tag              16 bytes (GCM authentication tag)
```
- **The AAD binds the chunk's coordinates** → out-of-order delivery, replay, cross-file splicing and truncation are all rejected at decryption time
- Each chunk is authenticated independently → a mid-transfer failure allows a **resume** (the receiver reports `RESUME(文件序号, 块序号)`)
- The server side also holds only ciphertext in memory and **never writes a temporary file**

### 5.3 The receiver writing to disk (the key to large files)
The “hundreds of MB to tens of GB” scale means **the whole file cannot be piled up in memory**:

| Browser | Disk-writing method | Capability |
|---|---|---|
| Chrome / Edge (desktop) | `showSaveFilePicker()` + `createWritable()` | Writes to disk while receiving, constant memory footprint, supports tens of GB |
| Firefox / Safari | Accumulate a Blob → trigger a download | Limited by memory, roughly a 1~2 GB ceiling; the program warns in advance |

> Verified: the File System Access API (`showSaveFilePicker`) is **supported only in Chromium-based browsers**; Firefox takes a negative position and Safari is explicitly opposed ([Web features explorer](https://web-platform-dx.github.io/web-features-explorer/features/file-system-access/)). So both paths have to be implemented, with the receiver page detecting API availability and choosing automatically.

### 5.4 Integrity
- When pre-scanning the file, the sender computes the SHA-256 and the chunk hashes (the Merkle tree root), then sends the **encrypted manifest** first (file name, size, root hash)
- The receiver **computes SHA-256 as it receives**, compares when it is done, and aborts immediately with a message if they do not match
- The manifest itself is encrypted → file names never leak onto the network

### 5.5 Multiple files and folders
The manifest carries relative paths, and the receiver writes to disk along those relative paths (under Chromium it can optionally use `showDirectoryPicker()` to rebuild the directory tree).
Path safety: `..`, absolute paths and characters that are illegal on Windows are rejected — preventing a malicious manifest from writing files outside its scope.

## 6. How "Destroyed Once Used" Is Actually Implemented

| Object | When it is destroyed | Destruction action |
|---|---|---|
| Password verification value V, K_auth, K_enc | Transfer completes / user presses Ctrl+C / timeout / error | Overwritten in memory with `fill(0)`, references released |
| Chunk ciphertext buffer | Immediately after each chunk is sent | The buffer is reused and zeroed |
| Session keys, room ID | Same as above | Zeroed |
| Sender service | Triggered as soon as the transfer completes | Stop listening, forcibly close session sockets, exit the process |
| Temporary files | **Never created** | There is no temporary file to destroy (this is a design goal, not a coincidence) |
| relay room | Explicit DELETE from the sender + server-side TTL as double insurance | Deleted immediately; expired ones are cleaned up automatically |
| Receiver web page | Regenerated on every start, carrying a one-time token `?k=` | Invalid as soon as it is closed; the token is void after a single use |
| Files the receiver has already saved | **Not destroyed** (this is the result the user wanted) | The session and keys are destroyed; the file stays where the user chose |

The sender **leaves the original file untouched**: the program only reads the original, never copies it and never moves it to a temporary directory, so there is no "leftover copy" problem.

## 9. Known Limitations (An Honest List)

1. **Crossing the internet requires a relay; that is a mathematical necessity, not laziness.** The root cause: the receiver has to run a piece of software (the web page in the browser), and **the source of that software must be a public address the receiver can reach**. A party without a public address can never be the party that is "reached". The only alternative is to have the receiver **install** a program — which directly violates requirement 1 (this is why Tailscale, Syncthing and the like are out). Therefore: "across networks" = "a relay is mandatory".
2. **The sender must have Node 24+** (the receiver installs nothing at all). If the sender should also need zero installation, packaging it as a single-file exe in P3 does that.
3. **The cross-network path on this machine has been narrowed by measurement to the relay alone**: the public IPv4 is behind the carrier's CGNAT (relayed through carrier equipment; see the Chapter 2 addendum), there is no global IPv6, and there is double NAT with the router's UPnP unavailable — port forwarding and IPv6 direct connection are both ruled out (see Chapter 2 Addendum for details).
4. **Within the same LAN no internet connection is needed at all**: no relay, no public network, no deployment of any kind, and the speed is limited only by your switch/router (usually above 100MB/s).
5. **Firefox / Safari are limited by memory when receiving large files** (they do not support the streaming disk-write API), with a ceiling of roughly 1~2 GB; use Chrome / Edge on the receiver. The program detects this automatically on the page and warns in advance.
6. In the **self-signed certificate** scenario the browser shows a security warning once (once per session). This point needs a real end-to-end measurement in Chrome during P0 to confirm.
7. A receiver page served over HTTPS exists only in the **current session**, and the link dies the moment the process exits — that is exactly what "one-shot" means, but it also means **refreshing an old link fails**.
