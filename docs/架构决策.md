# Architecture decisions: station model · GUI · self-gift · certificate trust

> This document extends `设计文档.md`. The design document answers "**how do we get the file across**",
> this one answers "**what the program looks like, how people start using it, and how it spreads**".

---

## 1. Station model: from "sender/receiver" to "peer station"

### 1.1 The implicit assumption in the original requirements

The earliest requirement said "the computer that starts the transfer has this program", i.e. **the sender is installed, the receiver runs bare**.
That holds for "I send something to someone else", but it collapses as soon as any of the following appears:

- The other side has finished receiving and now wants to send me a file too → they have no program
- Both computers are mine and I want two-way sync → I have to decide which one gets the install
- I want to send a file from my phone to my computer → the phone cannot run Node

### 1.2 Decision: one executable, two roles, decided at runtime

```
                     ┌─────────────────────────┐
                     │    Flicker Station      │
                     │                         │
     CLI / GUI ─────▶│  ┌───────┐  ┌────────┐  │
                     │  │ Sender│  │Receiver│  │
                     │  └───┬───┘  └───┬────┘  │
                     │      └────┬─────┘       │
                     │      ┌────▼─────┐       │
                     │      │ Session  │       │  ← crypto / chunking / manifest / destroy
                     │      └────┬─────┘       │     all role-independent
                     │      ┌────▼─────┐       │
                     │      │Transport │       │  ← LAN / relay / direct
                     │      └──────────┘       │
                     └─────────────────────────┘
```

**Key property: the session kernel is completely independent of role.** Who initiated is just a flag; the handshake, encryption, chunking and destruction code
is shared by both sides. Not to save code, but because **cryptographic protocols are symmetric by nature** (challenge–response is inherently two-way).

This yields three usage patterns, **all covered by one program**:

| Use case | How | Who needs to install the program |
|---|---|---|
| Me → someone else | I run `send`, they open a browser | Only me |
| Someone else → me | **They have the program installed too**; they `send`, I wait to receive | Both sides (though the "self-gift" can turn it into this) |
| Me ⇄ me | Both machines run `flicker`; either can initiate | Both sides |
| Phone → computer | Phone browser upload (limited, see §5.4), or the P4 mobile shell | The computer |

> ✅ **Both halves shipped in 2026-10, on top of one implementation**:
> · **The command line (`flicker recv <link>`) receives with the program**: Node downloads, verifies every
>   chunk, checks the whole-file hash, writes to disk under `src/path-safety.js`'s rules, and tells the other
>   side when it is done. It used to be just `openBrowser(link)`, which handed the link to a browser —— so
>   "both sides have the program" made no difference at all.
> · **The GUI (the station page's "Or, receive from a link") is in place too**: paste the link and the
>   one-time password → click "Connect and show the fingerprint" → check those 8 characters → start. The
>   page makes **no** cross-origin request: it only talks to the local service on `127.0.0.1`
>   (`/api/pull/*`), and the fetching is still done by **the very same** `src/pull.js` inside Node. So the
>   two blockers in §1.3 (CORS and the self-signed certificate) are sidestepped without touching the
>   protocol. Judgement: `test/pull-gui.test.js` (a real sender plus a real GUI, including the reverse
>   checks "no fingerprint check means no start" and "stop really interrupts").
>
> This path also **only takes direct links** (`https://<addr>:<port>/?k=…`). A relay link
> (`/room/<room>#<salt>`) receives inside the page, which the program does not implement —— open those in
> a browser.

### 1.3 How it shows up in the UI: the station page

The GUI is not a "send screen" but a **station page (Station)**; the moment you open it you see two groups of actions:

> ✅ **Filled in during 2026-10**: the early sketch below ("enter the password → start receiving") is
> today's "**Or, receive from a link**" panel (paste the link plus the password → check the certificate
> fingerprint → start). There are two receive entries today; keep them apart: **someone sends to me (phone
> scans a code)** and **receive from a link (the other side has the program too)**.
>
> Why the page cannot simply `fetch` the other side's API (two real blockers, unchanged):
>
> 1. **Cross-origin**: the station page is at `http://127.0.0.1:<port>`, the other side's API is at
>    `https://192.168.x.x:<port>`, and `src/server.js` **sends no CORS headers at all** —— the browser's
>    `fetch` is refused outright.
> 2. **Certificate**: the other side uses a **self-signed certificate**, and the CA is installed only on
>    **their** machine. This machine's browser does not trust it, so the `fetch` fails with a certificate
>    error —— and browsers do not offer "proceed anyway" for XHR.
>
> The fix was to **change the executor, not the protocol**: the page only talks to the local `127.0.0.1`
> service (`/api/pull/probe|start|stop|open`), and the real fetching is done by `src/pull.js` in Node ——
> **the same implementation** as `flicker recv <link>` (single source). The certificate hurdle moved from
> "change the trust store" to "**a human compares 8 characters**": the interface shows the probed
> fingerprint, and the user either clicks "Fingerprint matches" or types the one on the other side's
> screen; "Skip the check and start" is the equivalent of `--insecure` and leaves a line in the log.
> Judgement: `test/pull-gui.test.js` (4 cases, including the reverse checks).

```
┌────────────────────────────────────────────────┐
│  Flicker                            ● idle     │
├────────────────────────────────────────────────┤
│                                                │
│   ┌── I want to send files ────────────────┐   │
│   │  Drop files here, or [ Choose files ]  │   │
│   └────────────────────────────────────────┘   │
│                                                │
│   Or, let someone send to me                   │
│   ┌── phone → this computer ──────────────┐   │
│   │  Phone scans it and pushes photos over │   │
│   │  [ Receive files ]                     │   │
│   └────────────────────────────────────────┘   │
│                                                │
│   Or, receive from a link                      │
│   ┌── the other side has Flicker too ──────┐   │
│   │  Paste their link + 1-time password    │   │
│   │  [ Receive from a link ]               │   │
│   └────────────────────────────────────────┘   │
│                                                │
└────────────────────────────────────────────────┘
```

**Why the receive area must live permanently on the first screen**: because I, as the "installed side", may have someone wanting to send me something at any moment.
Receiving is not an appendage of the send flow; it is a first-class citizen.

## 2. GUI: decision and rationale

### 2.1 Three candidates

| Option | Approach | Pros | Fatal flaw |
|---|---|---|---|
| **A. Native window (Electron/Tauri)** | Bundle Chromium / use a Rust shell | A real desktop app | Size 80–150 MB; pulls in a large number of third-party dependencies; conflicts with the "zero dependency" principle; high cross-platform packaging maintenance cost |
| **B. WebView2 shell** | Use `msedgewebview2.exe --app=` to pull up a window | Small; no runtime to install (built into Win10+) | **Windows only**; no macOS/Linux equivalent; depends on the system runtime version |
| **C. Local web UI + browser** | Node starts a service listening only on `127.0.0.1`, opened in a browser | Consistent across platforms; the same UI serves both receiver and sender; can be "installed as an app"; zero new dependencies | Not a "native" app; requires picking the right browser |

### 2.2 Decision: **C** as the main path, **B** as an optional enhancement on Windows

**Rationale:**

1. **The receiver is a web page to begin with.** If the sender is a web page too, then **the whole product has only one set of UI code** —
   the send screen and the receive screen can share every design token, component and progress-display logic. That is a huge simplification.
2. **The sender's UI can naturally access local files.** Because it runs on `127.0.0.1`, the browser allows it to use
   `showSaveFilePicker()` / `showOpenFilePicker()`, which means **when the sender itself receives someone else's file,
   it also gets streaming writes to disk**, with no memory limit. (This matters: under the station model the sender is also a receiver.)
3. **It can be "installed" as a desktop app without an installer.** Edge/Chrome support "Install this site as an app",
   producing a Start menu icon, a standalone window and no address bar. To the user it feels like desktop software,
   and we did not write a single extra line of code.
4. **A Windows enhancement**: when WebView2 is detected, `msedgewebview2.exe --app=<url>` can pop a frameless window directly,
   which looks nothing like a browser. This is an optional path, not a required one.

### 2.3 One reality we have to handle: **the default browser may be Firefox**

Measured on this machine:

```
Default browser   Firefox (registry UserChoice = FirefoxURL-...)
Edge installed    155.0.4283.45   ← Program Files (x86)
WebView2 runtime  154.0.4258.62   ← installed
```

And **Firefox does not support the File System Access API** (`showSaveFilePicker`), nor does it have an `--app` mode.
That means:

- If we blindly open the GUI in the system default browser, the user falls into the "large files will not transfer" pit, and **will not know unless we tell them**
- If we hard-require Edge/Chrome, Mac users (Safari does not support it either) are in for a bad time

**Decision: browser probing + explicit degradation + honest disclosure.**

```
Probe order when launching the GUI:
  1. Look for a Chromium-family browser such as Edge / Chrome / Brave (registry + common install paths)
  2. Found → open it and pass --app=<url> to get a standalone window
  3. Not found → open the system default browser, and show a prominent notice on the page:
        ⚠️ The current browser does not support streaming writes to disk for large files
           Receiving files larger than about 1 GB may fail
           Switching to Edge or Chrome is recommended
  4. Always show the current browser's capability detection result on the page (do not guess; measure whether the API exists)
```

**Principle: capability detection always beats UA sniffing.** Plain `typeof window.showSaveFilePicker === 'function'`
is far more reliable than guessing from the browser name.

### 2.4 The relationship between the GUI and the command line

**Not two programs, but two front ends over one kernel.**

```
                     ┌──────────────┐
        --gui  ─────▶│ GUI frontend │──┐
                     │  (browser)   │  │
                     └──────────────┘  │      ┌──────────────┐
                                       ├─────▶│Session kernel│
                     ┌──────────────┐  │      │ + event bus  │
        default ────▶│ TTY frontend │──┘      └──────────────┘
                     │  (terminal)  │
                     └──────────────┘
```

- The kernel broadcasts outward through one **event stream** (progress, state, errors, peer connected, password check result)
- The TTY front end renders those events as box drawing and progress bars; the GUI front end renders the same events as a web page
- The two front ends **can coexist in the same process**: refreshing progress in the terminal while a browser window is open

This design means the GUI does not need to reimplement any business logic, and the CLI stays usable on servers with no graphical interface.

## 3. Self-gift: letting the program spread itself

### 3.1 Requirement

> "The program can be transferred from the end that transfers the file to the end being transferred to, so that other people can use this program too; this is not mandatory."

This is **the most far-sighted item** in the original requirements: what it really solves is not a technical problem but a **distribution problem**.
A one-shot transfer tool's use case is inherently point-to-point; if every time you have to teach the other side to go download it from GitHub,
the tool will forever circulate only among the people who already know how to use it.

### 3.2 Decision: an optional extra manifest entry

In the UI it appears as a checkbox that is on by default:

```
┌─ Transfer options ─────────────────────────────┐
│  ☑ Also give "Flicker" to the other side       │
│     They can then send files to others         │
│     About 18 MB (not part of this transfer)    │
└────────────────────────────────────────────────┘
```

In the protocol, it is just **an ordinary file entry in the manifest** (see the self-gift section of `PROTOCOL.md`),
carrying a special flag that the receiver recognises and turns into an extra explanatory card.

**Why on by default**: 18 MB is negligible against modern transfer sizes, and it turns the receiver from "can only receive" into "can also send".
But **it must be possible to turn it off** — a corporate environment may have rules, or the other side simply does not want it.

### 3.3 Key design: what you give away depends on what form the program itself is in

The program must be able to tell "how was I distributed":

| Which form am I | What I should send | How the other side uses it |
|---|---|---|
| **Single-file executable** (`flicker.exe`) | Send **myself** directly | Double-click and it runs; nothing to install ⭐ best |
| **Run from a source directory** (`node flicker.js`) | Package **the source needed to run + `启动.cmd`** | Node.js must be installed first; the launcher script detects this and guides the user |
| **Global install** (`npm i -g`) | The same source package as above | Same as above |

In implementation this is: probe the relationship between `process.execPath` and `process.argv[1]`,
decide whether you are a SEA-packaged single file or an ordinary script, and pick the gift's form accordingly.

### 3.4 Single-file executable — this is where the self-gift really earns its keep

Node.js 24 has built-in **SEA (Single Executable Applications)**, which can pack the Node runtime and the code
into **a single executable file**, with no need for the other side to install Node.

```
Build artifacts (shipped with the GitHub Release):
  flicker-windows-x64.exe     about 80 MB
  flicker-macos-arm64         about 75 MB
  flicker-macos-x64           about 78 MB
  flicker-linux-x64           about 80 MB
```

**Conclusion: the P3 stage must produce SEA packaging.** — ✅ **Done**, see `构建单文件.md`.
The measured artifact `flicker-0.1.0-windows-x64.exe` is about 94 MB,
and the self-gift recognises that it is a single-file form and **gives away the program itself** (rather than a source package). Otherwise the "self-gift" feature is half-finished —
with a source package the other side still has to go to the Node website to download and install it, and the vast majority of non-technical users give up at that step.

This also incidentally removes the "the sender must have Node installed" limitation: with the single-file build, the sender needs zero installation too.

### 3.5 Chain propagation: a natural consequence of the design

```
Me ──file+program──▶ colleague ──file+program──▶ their friend ──▶ ...
```

Every time the program is given away, the receiver gains one more complete station.
**This is the project's only promotion mechanism**, and it is the biggest experiential difference from cloud-drive-style tools:
a cloud drive is centralised, and the more you use it the more you depend on that centre; Flicker is **the more you use it, the less you need Flicker itself** (because everyone has it installed).

> A side benefit: the self-gift package should carry a trimmed-down `使用手册.md` and this repository's address.
> Once the other side has the program, they know at first glance how to use it and where it came from. This is also the natural exposure path for an open-source project.

## 4. HTTPS and certificate trust: an experience problem we have to solve

### 4.1 Why we cannot get around HTTPS

The receiver's web page needs `crypto.subtle` (WebCrypto). And browsers require:
**`crypto.subtle` is only available in a secure context.**

- `http://127.0.0.1` ✅ treated as a secure context
- `http://192.168.1.5` ❌ **not** a secure context → `crypto.subtle` is `undefined` → encryption is simply unavailable
- `https://192.168.1.5` ✅ secure context

And LAN mode is precisely the **main scenario**; the receiver must visit `https://192.168.1.5:port`.
**So one way or another we need an HTTPS server, and its certificate must be trusted by the browser.**

### 4.2 Comparing the three routes

| Approach | User experience | Verdict |
|---|---|---|
| Self-signed certificate, ignore trust | Every browser pops "Your connection is not private" | ❌ The other side thinks they caught a virus; the product dies on the spot |
| Guide the user to click "continue" manually | You have to teach the other side to click "Advanced → Proceed" | ⚠️ Workable but awful, and some browsers give no "proceed" button |
| **Install the certificate into the current user's trust store** | **No prompt at all, just like a normal site** | ✅ **Measured and confirmed** (see §4.3) |

### 4.3 Decision: session-scoped certificate + automatic install + automatic uninstall (**measured and verified**)

> **The conclusions in this section come from measurements on this machine, not inference.** Test method: use CDP (Chrome DevTools Protocol)
> to read the browser's verdict on the certificate chain directly, rather than eyeballing the page.
> Test script: `_lab/lab-cert.mjs` (repeatable).

#### 4.3.1 Measured results

| Variant | CA carries the `CA=TRUE` flag | Installed into the Root store | Browser result |
|---|---|---|---|
| Variant 1 | ❌ no (`Subject Type=End Entity`) | ✅ installed | ❌ `net::ERR_CERT_INVALID` |
| Variant 2 | ❌ no | ✅ installed | ❌ `net::ERR_CERT_INVALID` |
| **Experiment group A** | ✅ **yes** (`Subject Type=CA`) | ✅ installed | ✅ **page renders normally, fetch 200, CDP sees SSL details, zero failure events** |
| Control group B | ✅ yes | ❌ not installed | ❌ `net::ERR_CERT_AUTHORITY_INVALID` |
| Control group C | ✅ yes | ✅ installed | ✅ normal (`--ignore-certificate-errors`, proving the server side itself is fine) |

Environment: Windows 10 19044 · Edge 155.0.4283.45 · Node v24.21.0 · non-administrator

**Four conclusions:**

1. **✅ The approach works.** A session CA (with `CA=TRUE`) + a server certificate, installing only the CA into
   `Cert:\CurrentUser\Root`, is **fully accepted by the browser, zero warnings**. headless mode **really does read the Windows trust store**.
2. **⚠️ The real landmine is certificate generation, not the trust store.** The sole cause of the two failures was that the CA I initially generated with
   `New-SelfSignedCertificate -TextExtension '2.5.29.19={text}critical:ca2'`
   **lacked the CA basic constraint** (`Subject Type` showed `End Entity`),
   which made the whole chain invalid and the browser reported `ERR_CERT_INVALID` ("the certificate itself is broken").
   The correct form is `'{critical}{text}ca=1'` — note that `ca2` is wrong and `ca=1` is right.
3. **Control group B is the decisive evidence.** The same certificate, when not installed into the Root store, reports
   `ERR_CERT_AUTHORITY_INVALID` ("issuer is not trusted") rather than `ERR_CERT_INVALID`.
   **The error code changing from "the certificate is broken" to "the issuer is not recognised" is itself proof that installing into the trust store really took effect.**
   Without that control, it is very easy to misdiagnose "the certificate was generated wrongly" as "the trust store does not work".
4. **Uninstalling only works via `certutil -delstore`.** `Remove-Item Cert:\CurrentUser\Root\<fingerprint>`
   fails and reports `The operation is on user root store and UI is not allowed.`
   — this is not a matter of habit; the other approaches simply do not work.

#### 4.3.2 Three implementation constraints that follow

**Constraint 1: certificate generation must set the basic constraints explicitly and correctly.**
From this measurement comes an important implementation decision — **do not hand-roll X.509, and do not call `New-SelfSignedCertificate` raw**;
instead centralise certificate generation into a testable module, and **self-check immediately after generation**:

```
After generating the certificate, and before starting the service, we must verify:
  ✓ The CA's basicConstraints must include CA=TRUE, and be critical
  ✓ The CA must include keyUsage = keyCertSign
  ✓ The server certificate must have a SAN, and that SAN must include the exact IP the receiver will visit
  ✓ The server certificate must have EKU serverAuth
  ✓ Use Node's X509Certificate.verify() to check whether the chain holds
  ✓ The server certificate must not also be usable as a CA
Self-check fails → report a clear error and fall back to "manual trust guidance"; never leave the user facing a browser error they cannot understand
```

This self-check blocks exactly the pit we fell into here — and it costs almost nothing.

**Constraint 2: we must scan for and clean up certificates left over from last time.**
Because uninstalling only works via `certutil`, once the certificate is installed and the process is force-killed (ended from Task Manager, power loss, blue screen),
the certificate is left behind for good. So **on every startup, first scan the Root store for certificates whose subject contains `Flicker Session`,
and clean up any leftovers**. This lets "one-shot" heal itself even on abnormal paths.

**Constraint 3: the startup order must be "install the certificate first, then listen on the port".**
Otherwise the browser may open a connection before the certificate is ready, receive an untrusted response and cache the verdict
(Chrome is known to cache certificate errors), and installing the certificate afterwards has no effect — the user sees one inexplicable warning.

**Constraint 3b: the browser window may only be opened after the readiness probe succeeds.** (**a real defect reproduced by measurement**)
A browser window in `--app=<url>` mode **navigates to that address the moment it starts**.
If HTTPS is not yet listening at that point, the user sees **"Hmmm… can't reach this page" (`ERR_CONNECTION_REFUSED`)**.
And it **just sits there and never retries on its own**; the user has to press F5 manually.
Measured causal chain: browser opened first + service started after → error page; press F5 → normal; open after the service is ready → normal.
**So there must never be a window in which "the window exists but the service is not ready yet".**
Reproduction script: `_lab/lab-race.mjs`.

#### 4.3.3 Key parameters

```
On startup:
  1. Generate a session-specific root CA (CA=TRUE, keyCertSign) + a server certificate
     — the server certificate's SAN must include the IP the receiver actually visits; one certificate covers every LAN address on this machine
  2. Self-check the certificate chain (see constraint 1); fall back if it fails
  3. Scan for and clean up leftovers from last time (see constraint 2)
  4. certutil -user -addstore -f Root <ca.cer>   ← no administrator rights needed (measured)
  5. Start the HTTPS listener
  6. [Readiness probe] request our own address once, until it really returns 200 (see constraint 3b)
  7. Open the browser window (GUI mode only)     ← must come after step 6
  8. Print the CA fingerprint in the terminal, for advanced users to verify by hand

On teardown:
  9. certutil -user -delstore Root <fingerprint>  ← the only workable way to uninstall
 10. Delete the server certificate's private key from Cert:\CurrentUser\My
 11. Delete the private key material in memory
```

**Why this matters especially for this project:** it extends "destroy when done" from the **file level** to the **system trust level**.
After the program exits, every trace it left on your computer (keys, certificates, trust entries, services, temporary files) is gone.

**We must provide a `--no-cert-install` switch**: some users will not accept any program touching their certificate store.
In that case it degrades to "self-signed certificate + in-page guidance for manual trust", with the differences spelled out clearly.
**That switch also doubles as a fallback** — even if the certificate approach fails on some user's machine because of policy restrictions,
the program is still usable, at the cost of one extra click.

> **Things still unverified** (flagged honestly):
> ① ~~a real interactive browser window~~ — ✅ **verified**. I ran two extra real-window forms:
>    a **visible window** (127.0.0.1) and an **app window with no address bar** (127.0.0.1 and the real LAN IP `192.168.1.5`, once each),
>    all passing with zero warnings. I also used a set of "should fail" controls (app mode + CA not installed) to confirm that the test script
>    **can correctly detect the security-warning page**, ruling out a false positive from an over-permissive detector.
>    With that, every mode on Windows + Edge (headless / visible window / app window) and both address forms are verified.
> ② **macOS / Linux are unverified.** This conclusion became clearer in 2026-10:
>    certificate **generation** has already been moved to pure JS (`src/x509.js` + `src/session-cert.js`),
>    the same code on every platform, verified with a real TLS handshake — that is, **"generation" is no longer the weak spot on any platform**.
>    What remains is "install into the system trust store", and each of the two platforms has a hard reason, not an engineering-effort problem:
>    · **macOS**: `security add-trusted-cert` ships with the system and needs no third-party tool, but `man security` says it plainly —
>      *"When modifying per-user Trust Settings, user authentication is required via an
>      authentication dialog"*, and modifying the admin domain requires root. **There is no option that takes effect silently**,
>      which conflicts with the "works as soon as it starts" positioning.
>    · **Linux**: **there is no zero-dependency path**. Browsers do not read the system CA directory — Chromium reads the NSS Shared DB
>      (from M146, `~/.local/share/pki/nssdb`; before that, `~/.pki/nssdb`), and writing to it needs `certutil`
>      (from `libnss3-tools` / `nss-tools`, **not installed by default**); Firefox has its own profile store on top of that.
>      Source: [Chromium's official `docs/linux/cert_management.md`](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/docs/linux/cert_management.md).
>    · So the program was changed to **print the exact commands for manual installation** (`trust.manualTrustHint()`) instead of running them itself,
>      and both platforms keep defaulting to `--no-cert-install`. **Cross-platform certificate trust must be measured platform by platform;
>      the Windows conclusions cannot be carried over.**

## 5. Packaging and distribution

### 5.1 Three distribution forms

| Form | Target users | Size | Dependencies |
|---|---|---|---|
| **Single-file exe / executable** | ⭐ everyone (recommended) | 75–80 MB | **none** |
| **Source + launcher script** | developers, people who want to read the code | about 200 KB | Node.js 24+ |
| **npm global install** | developers | about 200 KB | Node.js 24+ |

### 5.2 Launcher scripts (rescuing the experience in source form)

```
启动.cmd          ← double-click this (Windows)
启动.command      ← double-click this (macOS)
启动.sh           ← ./启动.sh (Linux)
```

The script does three things:
1. Check whether `node` exists and whether the version is ≥ 24
2. Not present → print clear Chinese guidance (including the official site address) + automatically open the download page, then exit
3. Present → launch the GUI

**Why this script is mandatory**: in source form, if you tell the other side "open a command line, cd into the directory, type node flicker.js",
95% of people get stuck. Double-clicking a file is a basic human expectation.

### 5.3 Versioning and naming

```
flicker-0.1.0-windows-x64.exe
flicker-0.1.0-macos-arm64
flicker-0.1.0-macos-x64
flicker-0.1.0-linux-x64
```

For the self-gift, putting the version number in the filename lets the receiver see at a glance what is new and what is old — which decides whether everyone ends up on the latest version as it propagates through the chain.

### 5.4 The mobile boundary (stated honestly)

| Direction | Feasibility | Notes |
|---|---|---|
| Computer → phone | ✅ **fully feasible** | The phone browser opens the link, enters the password, receives; use the Web Share API to save into the photo library / Files app. **This is the "transfer computer files to the phone" you asked for** |
| Phone → computer | ⚠️ **limited** | Browsers **cannot read files at arbitrary paths** (platform limitation). The user can only pick manually in the file picker; there is no "pick a folder and send it automatically" |
| Phone → phone | ⚠️ **limited** | Same as above, and a phone cannot be an HTTPS server |
| Installing Flicker itself on a phone | ❌ not doing it | Requiring an app install would violate the core premise of "zero installation on the receiver" |

**Conclusion: the correct positioning for mobile is "an excellent receiver + a limited sender".**
The main path "computer → phone" can be made as good as the desktop, and that is where the requirement is satisfied.
Being a sender on a phone belongs to P4 (mobile shell packaging) and is out of scope for now.

## 7. Updated implementation stages

| Stage | Content | New/changed |
|---|---|---|
| **P0** | Cryptography and chunking kernel + LAN HTTPS transfer + destruction flow | unchanged |
| **P1** | Receiver dual write-to-disk paths + resumable transfer + integrity check | unchanged |
| **P2** | **GUI front end** (station page) + browser probing + certificate trust | ⬅ new, moved up to P2 |
| **P3** | relay Worker + cross-network | moved later |
| **P4** | self-gift + SEA single-file packaging + launcher scripts | ⬅ new |
| **P5** | Public IPv6 / port-forwarding detection, PWA, Web Share API, i18n | extended |

**Why the reordering**: the GUI is the threshold for "can other people actually use this program", and it affects real usage more than cross-network does.
On your own machines the LAN is already enough; but the GUI decides whether you **are willing to recommend it to others**.
The self-gift decides whether it **can spread on its own**. Both outrank relay.
