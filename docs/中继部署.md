# Cross-network relay: deployment and how it works

> Related documents: `设计文档.md` chapter 3 (connection strategy), `行为与运行.md` (runtime behaviour), `使用手册.md` (user operations)

---

## 1. Why you need it

**You do not need it as long as the two computers are on the same network.** On the same network, use a LAN direct connection: faster, simpler, nothing to deploy.

**Only when the two computers are on different networks** (one at home, one at the office) do you need a relay. The reason is physical:

```
Measured on your machine (see 设计文档.md, chapter 2 supplement):
  Egress public IP   (redacted: it was the author's home uplink; the exact value does not affect any conclusion)
  Path: 192.168.1.1 → 192.168.1.1 → 100.64.x.x (carrier-grade NAT)
  Global IPv6     none
```

`100.64.0.0/10` is the block reserved for carrier-grade NAT — which is to say **the public IP you were assigned is shared with other people**.
The sender **has no address that can be reached from outside at all**, so a third party has to carry the messages for it.

**But the relay is not "read the content, then forward it" — what it moves is boxes:**

```
sender ──ciphertext──▶ relay (stored by sequence number) ──ciphertext──▶ receiver
             ↑                                    ↑
      key only here                        key only here
```

## 2. Deploy (once, about 3 minutes)

> **⚠️ Read this first: the default address may be "deployed but unreachable"**
>
> The default address a deployment gives you is `https://<name>.<your-subdomain>.workers.dev`.
> The **`*.workers.dev` domain is blocked outright on some networks** ——
> measured in 2026-10 on a mainland-China network: it resolved to `199.16.156.103` (**not** a Cloudflare
> address —— a poisoned answer) and port 443 timed out, while Cloudflare's **API** host
> `api.cloudflare.com` stayed reachable (which is why deploying succeeds while access does not).
>
> **If both computers are on such a network, that default address is unreachable from either side.**
> The relay itself is fine; it is the name that cannot be reached.
>
> Two ways to deal with it, cheapest first:
>
> 1. **Bind a domain of your own to it** (roughly 30–60 CNY/year). The relay **does not need redeploying**,
>    it simply answers on a different address —— see "Want a stable address: bind a domain of your own" below.
> 2. **On the same network you do not need a relay at all**: two computers on one WiFi/LAN can just use
>    `flicker send "file"`, which is faster and simpler.
>
> The deploy script now **probes that address itself** right after deploying: if it cannot be reached it prints
> the cause and the way out on the spot, instead of leaving you with a cheerful "✅ done" that never connects.

```powershell
node relay/deploy.mjs
```

It does the following in order: generate the receiver page module → generate `wrangler.toml` → check wrangler → guide you through login → deploy → print the address → **probe whether that address is reachable**.

**You need a free Cloudflare account** (no credit card required): <https://dash.cloudflare.com/sign-up>

To check the environment only, without deploying:

```powershell
node relay/deploy.mjs --check
```

#### If login gets stuck: use an API token (a path that was measured)

On mainland-China networks the Cloudflare **dashboard** host `dash.cloudflare.com` is often unreachable while its **API** host
`api.cloudflare.com` works (measured: dashboard times out after 12 s, API returns HTTP 200). wrangler's browser login **must**
go through the dashboard host —— the symptom is that you click "Allow" in the browser while the command line reports
`Could not reach the Cloudflare auth server … (UND_ERR_CONNECT_TIMEOUT)`, and the authorization dies halfway.

Switching to an **API token** avoids it (deployment only uses the API):

1. Open <https://dash.cloudflare.com/profile/api-tokens> in **Edge** (when Firefox cannot open that page, Edge can —— measured)
2. `Create Token` → pick the **Edit Cloudflare Workers** template → `Continue` → `Create Token`
3. Copy the string and paste it into `relay/api-token.txt`, then save (that file is kept out of `.gitignore`-tracked content and out of the gift pack's include list; a machine check guards "credentials must never enter the gift")
4. Run `node relay/deploy.mjs` again —— it picks the token up automatically and skips the browser login

> Two common prerequisites: a new account must **verify its email** before it may create tokens, and it must register a
> `workers.dev` **subdomain** (required before publishing any Worker). The subdomain can also be registered through the API
> with the same token, without opening a browser:
> `node _lab/cf-register-subdomain.mjs <account_id> <wanted_subdomain>` (the account id appears in the deploy error).
> You can `Delete` the token on that same page afterwards —— **deleting it does not affect the relay that is already deployed**.

### Want a stable address: bind a domain of your own

The default `*.workers.dev` address cannot be reached from some networks (see the note at the top of this chapter).
**The relay does not need redeploying**; binding a domain simply gives it another address:

1. **Get a domain** (roughly 30–60 CNY/year; `.top`, `.xyz` or `.com` all work)
2. **Add the domain to Cloudflare**: dashboard → `Add a site` → enter the domain → change the **nameservers** at your registrar to the two Cloudflare gives you → wait until it shows `Active` (usually minutes to hours)
3. **Bind the domain to this Worker**: dashboard → `Workers & Pages` → pick `flicker` → `Settings` → `Domains & Routes` → `Add` → `Custom Domain` → enter `relay.your-domain` (the subdomain name is up to you) → save

The address then becomes `https://relay.your-domain`, and sending looks the same as before:

```powershell
flicker send "D:\file.zip" --relay=https://relay.your-domain
```

> ⚠️ To be honest: **this is not guaranteed to work**. The path from mainland China to Cloudflare is
> inconsistent, but in practice a domain of your own is far better than `*.workers.dev` (which is blocked outright).
> Once bound, verify it immediately: open `https://relay.your-domain/health` in a browser —— seeing
> `{"ok":true,...}` means it works; or run a real transfer with the script in the repository:
> `node _lab/verify-remote-relay.mjs https://relay.your-domain`.

### How to use it after deploying

```powershell
flicker send "D:\文件.zip" --relay=https://flicker-relay-xxxxx.你的用户名.workers.dev
```

The command prints a link. **Send the link to the other person, and send the password over a different channel** (for example the link over WeChat and the password over a phone call).
The other person opens the link in a browser and enters the password, and the file starts transferring.

**"Once" means**: this deployment is permanent; every transfer from then on uses that address directly, and no step ever has to be repeated.

### Free tier

| Item | Free tier | Cost of one transfer |
|---|---|---|
| Requests | 100,000/day | 1 acknowledgement + 1 delivery per chunk ≈ 2 requests per MiB |
| Traffic | No explicit limit (counted by request) | About equal to the file size |

At "two requests per MiB", 100,000 requests work out to about **50 GB/day**. Far more than enough for personal use.

> To save more: increase the chunk size (`chunkBytes` in `src/suite/flicker1.js`).
> The price is that both memory usage and the granularity of resume get coarser.

### You can also skip deployment: a local relay inside the LAN

```powershell
node relay/local.mjs --port=8787 --verbose
```

It uses **the same protocol implementation** as the Cloudflare Worker, so the behaviour is exactly the same.
Inside one network, another computer connects with `--relay=http://<你的IP>:8787` —
it is essentially the same as a LAN direct connection, except that you can also watch what happens on the relay along the way (`--verbose` prints the sequence number and length of every message it forwards).

## 3. What the relay can and cannot see

This is part of the design, not a coincidence.

| The relay **can see** | The relay **cannot see** |
|---|---|
| A random 128-bit room name | File contents (AES-256-GCM end-to-end encryption) |
| The sequence number and length of a message | File names and file sizes (the manifest itself is encrypted too) |
| When a message arrives | The password (**never transmitted**) |
| Both sides' IPs (unavoidably visible at the network layer) | The salt (kept in the URL fragment, which the browser does not send to the server) |

**Swap the relay for a machine that has been completely compromised, and there are only two things it can do:**
deny service, and record metadata. It cannot change the content — every chunk carries a GCM authentication tag,
so any single byte that is altered is discovered when the receiver decrypts.

### The room name is the credential

The room name is not assigned at random; it is **derived from the password**:

```
password → PBKDF2(600k rounds, salt) → V → HKDF("room") → room name (64 hex digits = 128-bit)
```

Therefore:
- Only someone who knows the password can compute the room name (**this is where "the two computers must use the same password" actually lands**)
- The room name is one-way: the password cannot be recovered from it
- 128-bit makes it non-enumerable (early versions used 64-bit, which is theoretically brute-forceable; it has since been lengthened)
- It only appears after the `#` in the URL, and **the browser does not send the fragment to the server**

So the relay needs no second authorisation mechanism: **knowing the room name ≡ knowing the password**.
And the encryption key (`HKDF("enc")`) is derived separately from the room key, so even knowing the room name, the relay can decrypt nothing.

> **A design detour we walked into**: the relay was originally given an "authorisation key" (registered when a room is created, then presented with every request).
> Testing immediately exposed a **first-come-first-served race**: when the room does not exist, the first request to arrive decides which key gets registered —
> an attacker who gets there first with a key derived from their own password can create a room with the same name and shut the real sender out.
> Once it became "the room name is the capability", the problem disappeared by itself.

## 4. Protocol

```
POST /r/:room              create the room (idempotent; returns created and the current progress)
POST /r/:room?seq=N        put in message number N (delivered one at a time; seq is chosen by the caller)
POST /r/:room/batch        put in a **batch** of messages (sequence numbers are assigned by the **server** in arrival order)
GET  /r/:room?seq=N        take out message number N (receiver; does not delete it)
POST /r/:room/ack?upTo=N   acknowledge and delete the prefix (receiver)
GET  /r/:room              room status (both sides use it to align progress)
DELETE /r/:room            destroy the room
GET  /health               health check (no side effects)
GET  /                      receiver page
```

The body of a `/batch` request is several messages concatenated in order, each preceded by a 4-byte big-endian length:

```
[4-byte length][message][4-byte length][message]...
```

So the reason for having it, instead of letting the sender fire N concurrent `?seq=N` requests:
**the relay requires strictly ordered delivery**, and the arrival order of concurrent requests is not guaranteed,
so they are bound to hit `409 BAD_SEQ` (and the server reports the same expected sequence number to every colliding request,
so they collide with each other again when they retry). Having the server assign sequence numbers is the only clean solution in which "strictly ordered" and "high throughput"
can coexist. A batch holds at most 64 messages.

### Message format

The room only carries **opaque bytes** and does not understand the content. But the receiver needs to tell the types apart, so the first byte is a tag:

```
0x01 + salt(16) + iv(12) + tag(16) + ciphertext     manifest
0x02 + tag(16) + ciphertext                         one file chunk
```

**Single-message ceiling and capability negotiation (2026-10)**: one message is one chunk, so "the single-message
ceiling" is exactly "the largest chunk allowed". A relay must declare `maxMessageBytes` in the
`GET /health` response (the room-create response carries a copy as well):

```json
{ "ok": true, "maxMessageBytes": 2097169, "protocol": 1 }
```

- **The protocol guarantees** `1 MiB + 17` (chunk + type byte + authentication tag) —— every conforming relay must
  accept that, and a client **that cannot read** the declaration falls back to it.
- This project's deployments declare **`2 MiB + 17`** by default (measured: at a 195 ms round trip and a 29.5 MB/s
  link, a 1 MiB chunk gives 18.9 MB/s end to end, 2 MiB gives 26.3 MB/s, and 4 MiB adds nothing).
- To change it, set `maxMessageBytes` on the `RoomStore` (both `relay/local.mjs` and `relay/worker.js` use the default).
- **Clients adapt automatically**: the sender takes `min(what it wants, what you declared)`, so raising or lowering
  your ceiling never breaks anyone's transfer —— and neither does an old deployment that declares nothing.
  That is precisely why this negotiation exists.

### Delivery model: pull-based + in-flight window

Chunks are **delivered on demand**, not all pushed up at once:

```
seq 0        manifest — put in as soon as the room is created
seq 1..N     chunks — delivered by window, based on "how far the receiver has consumed"
```

The sender keeps "no more than `windowSize` unacknowledged messages" (8 by default). The benefits:
- Constant memory on the sender (it does not queue the whole file)
- When the receiver is slow, the sender naturally stops and waits
- At any moment the relay holds only a bounded amount of in-flight ciphertext (8 MiB at most by default)

> **Why not 1**: a window of 1 is stop-and-wait, and the speed is deadlocked at `chunk size ÷ round-trip latency`.
> Measured at 195 ms latency it managed only 4.72 MB/s, while the same link can carry 29.5 MB/s on its own —
> the bottleneck was the implementation. After switching to a window of 8 with **batched delivery**, the measured result was 20.75 MB/s (**4.4×**).
> `--window 1` falls back to stop-and-wait (useful on a low-bandwidth link when you want to save data).


### Three criteria (all of them settled only after falling into the trap)

| Criterion | Why |
|---|---|
| **The sequence number to deliver next comes from the server's `nextSeq`**, not from a local counter | Once a local counter disagrees with the server (reconnect, concurrency), the next chunk reports "sequence not contiguous" |
| **`ack` is a prefix deletion, and it does not renumber after deleting** | An earlier implementation renumbered the remaining messages after deleting the prefix, so every sequence number the receiver had recorded was shifted |
| **Completion is judged by `ackedBase >= total`** | It originally used `posted >= total && pending === 0`, which falsely reported completion while "the receiver has taken the last message but has not yet acknowledged it", and then destroyed the room — the other side would never get that piece of data |
| **Before destroying, wait for the in-flight batch to finish delivering** | Batched delivery yields control while `await` reads a chunk (`putBatch` is not atomic). If the user clicks "cancel" at that moment, the DELETE reaches the server **before** that batch POST does: the room is deleted, the POST that arrives afterwards gets a 404, and a **normal cancellation** is reported as a relay error. So `destroy()` waits out the in-flight batch before deleting the room, and the delivery loop re-asks the abort criterion every round. This race was caught by the end-to-end tests with exact ordering assertions; you cannot see it by reading the code |

## 5. How "destroy when done" shows up on the relay

| Moment | What happens |
|---|---|
| Each message is acknowledged | The relay deletes it immediately (**prefix deletion**) |
| The transfer completes | The sender DELETEs the room |
| 15 minutes of inactivity | The whole room expires (a TTL safety net on the relay side) |
| The relay process restarts | All rooms disappear (messages live only in memory) |

**The relay does not write to disk.** A test keeps watch on this one: `test/relay-protocol.test.js` checks that
KV / D1 / R2 / Durable Objects do not appear in `relay/worker.js` —
if someone adds a persistence facility, the test fails and reminds them to re-examine this promise.

## 6. Security boundary (an honest list)

**What it does not protect against:**
- **The relay can see metadata**: that someone transferred something at this time, and how big it was (estimable from the message count and lengths)
- **The relay can deny service**: if it does not forward, the two ends cannot connect
- **Weak passwords**: the room name is derived from the password, so a weak password is theoretically enumerable (the 4-word password generated by default is about 52 bit,
  which together with a 128-bit room name and a short TTL is not practical in reality)
- **A controlled endpoint**: malware can see everything, and encryption cannot solve that

**What it does protect against:**
- The relay cannot read file contents, file names or file sizes
- The relay cannot obtain the password, nor the salt
- The relay cannot change the content (every chunk has an authentication tag, so any change is bound to be discovered)
- A room cannot be claimed or pre-empted by anyone else (there is no "first come, first served" registration process)

## 7. Troubleshooting

| Symptom | Cause and what to do |
|---|---|
| `Relay error: room does not exist or has expired` | The room is cleaned up automatically after 15 minutes of inactivity; or the sender has already exited. Start the transfer again |
| Stuck on "waiting for the other side to connect" forever | The other person has not opened the link yet, or has not entered the password. Check whether the link you gave them is complete |
| The other side says "the room no longer exists" | The sender has exited or timed out. Use `--timeout=30m` to stretch it |
| `Relay probe failed` | The address is wrong, or the relay was not deployed successfully. Opening that address in a browser should show the receiver page |
| Deployment succeeded but that address **cannot be opened** (from either side) | Your network may block `*.workers.dev`. **Measured (2026-10, a mainland-China network)**: the name resolved to `199.16.156.103` (**not** a Cloudflare address —— a poisoned answer) and port 443 timed out, while `api.cloudflare.com` stayed reachable. The relay itself is fine; the network simply cannot reach it. Two ways out: bind it to **a domain of your own** (Workers → Custom Domains; such names are usually not blocked this way), or self-host the relay (which needs a domain and a certificate to be https) |
| During deployment: `Could not reach the Cloudflare auth server` | The dashboard host `dash.cloudflare.com` is unreachable (the API host works) —— see "If login gets stuck: use an API token" above. Note also that a new account must **verify its email** and register a `workers.dev` subdomain, or both token creation and publishing will fail |
| A large file breaks off halfway through | Check whether the sender is still running. The receiver will wait (it has retries), but once the sender exits, the room is gone |
| The `--relay` address is http rather than https | Fine for a local relay, but a public relay must be https (browsers require a secure context) |
