# Plugins

> Plugins are **optional**: with none specified, nothing is loaded and the program behaves exactly as before.
> There are two ways to load one, and both are **explicit**: the command line `--plugin=<path>`, or the
> environment variable `FLICKER_PLUGINS`. **Both the command line and the GUI support them** (since 2026-10:
> plugins take effect in the GUI too, and `ctx.log()` output goes to the GUI's log panel).
> **The program never discovers plugins by itself** —— it does not scan
> the current directory, does not read a field from `package.json`, and does not look in `node_modules`.
>
> ✅ **Receive mode (`flicker recv`, phone → computer) supports plugins too, since 2026-10** —— that is the
> fourth plane, and its event table is in §5b below. The shape differs: it has **events only, no contribution
> points** (the on-disk path rules and per-chunk verification are not open to plugins).

The point of a plugin is to add your own actions without touching the core. **Four planes** are supported today:
the **sending side** (the process that sends files), the **relay** (the transit service you deploy yourself),
the **receiver page** (the page the other side opens) and the **receiving side** (the service `flicker recv`
starts). Each plane has its own hooks, and a plugin loaded in one plane can only use that plane's hooks ——
using a hook from another plane fails immediately (since 2026-10 this is really enforced: previously only
*mistyped* names were caught, so a relay plugin subscribing to `run/start` simply did nothing, silently).
**Encryption, path safety and the destroy flow cannot be changed by a plugin** (see "Capability boundaries").

## 1. Three design rules

- **Explicit loading.** A plugin is arbitrary code running with your privileges, and "just load the directory next
  to it" would turn "this program needs no third-party software" into a lie. So there are exactly two sources,
  `--plugin=` and `FLICKER_PLUGINS` (the page plane uses an explicit manifest instead), and **whatever was loaded
  is printed on screen**.
- **Everything must be reclaimable.** The program promises the user that "everything a transfer uses is one-shot
  and destroyed afterwards". If a plugin could leave a timer, a listening port or a temporary file behind, that
  promise would hold only for the core. So every side effect in a plugin goes through `ctx.effect()`, and the
  destroy chain (a relay's shutdown, a page's unload) finishes it off.
- **A typo must fail immediately.** `ctx.on('manifset/scanned')` **throws right away** instead of "never receiving
  an event" —— the latter sends plugin authors hunting for bugs in their own code, which is the most expensive kind
  of investigation.

## 2. How to load

```bash
# sending side: a single plugin
flicker send "D:\video" --plugin=./my-plugin.cjs

# sending side: several plugins (--plugin may be repeated)
flicker send "D:\video" --plugin=./a.cjs --plugin=./b.cjs

# or through the environment (separate paths with ; or :, as the system does)
FLICKER_PLUGINS=./a.cjs;./b.cjs flicker send "D:\video"

# list and validate only, without transferring (plugin authors use this to check their work)
flicker --plugins --plugin=./my-plugin.cjs

# relay: a self-hosted relay uses exactly the same form
node relay/local.mjs --port=8787 --plugin=./my-relay-plugin.cjs

# receiver page: list it in the explicit manifest, then re-inline and rebuild
#   (the page must stay self-contained, so plugins can only be inlined at build time)
#   1) put the plugin path into the plugins array of web/page-plugins.json
node gen/inline-plugins.mjs && node gen/gen-relay-page.mjs
```

A plugin file must be a **CommonJS file** (`module.exports`). It may:

- `require('node:…')` builtins
- **`require('./helper-file-in-the-same-folder')`** —— ✅ **measured working in 2026-10**, including inside the single-file artifact.
  Criterion: `node _lab/probe-plugin-require.mjs` (a control that is self-contained plus a case that
  requires a sibling `helper.cjs`; both must pass —— passing means the require really returned the
  helper's exports rather than being ignored).
  ⚠️ Being able to split ≠ should split: every extra file has to ship with the plugin, and plugins are
  loaded by **explicit path** (no directory scanning) —— one missing file and the plugin fails on
  someone else's machine.

A page plugin is instead **plain browser JS**:
no import/require, no Node APIs —— the inliner checks this at build time.

## 3. Events and contribution points (sending side)

- `mode` is `'lan'` (direct over the local network) or `'relay'` (forwarded through a relay).
- `summary` is the manifest overview: `{ fileCount, dirCount, totalBytes, totalChunks, files[] }`, where each entry
  of `files[]` is `{ name, rel, size, chunks, kind }` —— **metadata only, never content**.
- `ui/message` is a **synchronous** event: the handler must finish synchronously; returning a promise is ignored and
  recorded as a plugin error.

| Name | Kind | When | Data received |
|---|---|---|---|
| `run/start` | event | options parsed, before scanning | `{ mode, inputs, chunkBytes }` |
| `manifest/scanned` | event | manifest and checksums are ready | `{ mode, chunkBytes, summary }` |
| `ui/message` | event (sync) | on every text interface output | `{ level, text }` |
| `transfer/complete` | event | transfer finished, before destruction | `{ mode, ok, reason, bytes, fileCount }` |
| `gift/items` | slot | while the manifest is assembled | return `{ name, data }` or an array of them |

A file added through `gift/items` is an **ordinary file** for the receiver and is written to disk normally; the
name must be a single file name (no path separators) and must not collide with a file already being sent.

## 4. Events and contribution points (relay)

- `relay/route` fires **before any routing** (even `/health` and the landing page pass through it), so "put an
  access check in front of my own relay" needs exactly this one hook.
- Returning `{ status, body, headers }` ends the request right there: a string `body` is sent as-is, an object is
  sent as JSON (tagged with your plugin's name, so you can reconcile later). Returning `undefined` lets it through.
- Room creation and destruction are reported to plugins; **repeated operations are not reported twice** (a room that
  already exists, or one that is already gone, raises nothing).

| Name | Kind | When | Data received |
|---|---|---|---|
| `relay/route` | event | on every request, before routing | `{ method, path, room, query, headers }` |
| `relay/room-created` | event | when a room is really created | `{ room }` |
| `relay/room-destroyed` | event | when a room is really destroyed | `{ room }` |
| `relay/health` | slot | on every `/health` request | return an object whose fields join the response |
| `relay/store` | slot | **once, at relay start-up** | return a storage object that replaces the built-in in-memory store |

Fields added through `relay/health` join the `/health` response (a region, an operator name…).
**Core fields win**: a plugin cannot override `maxMessageBytes` or `protocol` —— those two are what capability
negotiation reads, and overriding them would make the relay lie to clients.

**`relay/store`: replacing *where rooms live*** (2026-10)

The default room store is process memory (`src/relay/room.js`). To use disk, object storage or a database,
have a plugin contribute a storage backend. It must implement:

| Member | Meaning |
|---|---|
| `maxMessageBytes` | The basis of capability negotiation (positive integer). Without it clients can only guess the chunk size, and the symptom is "large files always fail" |
| `ttlMs` | How long a room lives; `status()` must report it truthfully |
| `create(id)` | Create a room (idempotent) → `{created, messages}` |
| `put(id, seq, data)` | Put one message → `{seq, nextSeq}` |
| `putBatch(id, items)` | Put a batch → `{seqs, nextSeq}` |
| `get(id, seq)` | Read one (**does not delete**) → `{seq, data, nextSeq}` |
| `ack(id, upToSeq)` | Prefix-acknowledge and delete → `{ackedBase, nextSeq}` |
| `status(id)` | Room status (pending / ackedBase / nextSeq / age / idle / ttl) |
| `destroy(id)` | Destroy the room |
| `stats()` | For maintenance: room and message counts |

- **Validated at start-up**: one missing method fails immediately, naming both the missing method and the plugin ——
  never deferred to `undefined is not a function` halfway through a transfer.
- **When several plugins contribute, the first one wins**: two storage backends combined make no sense.
- A working example: `examples/plugins/relay-disk-store.cjs` (messages go to disk, and the copy is deleted on ack).
- ⚠️ **Only effective in the self-hosted `relay/local.mjs` shape**: a Worker cannot install plugins loaded from
  disk (it has no disk), so the Worker shape keeps the in-memory store.

## 5. Events and contribution points (receiver page)

- A page plugin's errors **do not interrupt the transfer** —— the opposite of the other two planes.
  Here **the other side is receiving files**, and the plugin is an extension installed by the sender or the
  operator; if it broke the transfer, the person who just wants their files would pay for it. So the page plane
  chooses "swallow it, record it honestly, carry on".
- There is no such thing as loading a page plugin at runtime: the receiver page must stay self-contained (the relay
  sends the HTML directly and the CSP forbids any external script), so page plugins are **inlined at build time**.
- Inlining means **any page plugin changes the page fingerprint** (checkable with `--assets`) —— so "which page the
  other side actually got" always stays verifiable.

| Name | Kind | When | Data received |
|---|---|---|---|
| `page/ready` | event | DOM ready (next tick) | `{ page }` |
| `recv/verified` | event | password verified, manifest decrypted | `{ fileCount, totalBytes, files[] }` |
| `recv/file-done` | event | each file finished (verified, on disk) | `{ name, size }` |
| `recv/complete` | event | everything received | `{ fileCount, totalBytes, seconds }` |
| `page/actions` | slot | rendered when receiving completes | return `{ label, onClick }` or an array of them |

## 5b. Events and contribution points (receiving side, `flicker recv`)

> This is the **fourth plane**, added 2026-10: what a plugin can see when a phone **pushes** files to this
> computer (`flicker recv`, or the GUI's "Receive files" button).

- **Events only, no contribution points.** The on-disk path rules, per-chunk verification, the whole-file
  digest and the destroy order are the receiving side's safety floor; all a plugin can do here is *know what
  happened* (bookkeeping, notifications, writing the manifest into its own audit log). Changing them is
  forbidden by the table in §10.
- **A plugin error does not interrupt receiving**: the other side is pushing files, and one broken plugin
  should not fail that transfer (the same trade-off as the page plane). The error **does not disappear** ——
  it is printed line by line at the end, and recorded in `plugins.errors`.
- **Events never carry the password or the one-time link token**: `receive/ready` gives the directory, the
  port, TLS and the limits, nothing else.
- **The order is real**: plugins are awaited in registration order, so "manifest received" always precedes
  "file finalised" —— an audit log built from these events does not need sorting.

| Name | Kind | When | Data received |
|---|---|---|---|
| `receive/ready` | event | The service is listening and the link and QR code are printed | `{ dir, port, tls, limits: { maxFiles, maxBytes, maxChunkBytes } }` |
| `receive/peer` | event | A phone connected (it has not yet proven it knows the password) | `{ peer: { address, userAgent } }` |
| `receive/auth` | event | The password check passed | `{ peer, macProfile }` (`v1` means the other page is older) |
| `receive/manifest` | event | The manifest is decrypted and every pre-flight check passed | `{ files, skipped, totalBytes, totalChunks, diskFree }` |
| `receive/collision` | event | A same-name file exists (**notification only**; rename/overwrite/skip stays with the user) | `{ rel, existing }` |
| `receive/file-done` | event | Whole-file digest verified and the file got its final name | `{ rel, bytes, renamedFrom }` |
| `receive/file-failed` | event | The whole-file digest did not match (the partial file stays, by design) | `{ rel, reason }` |
| `receive/complete` | event | The session finished successfully | `{ files, bytes, done, failed, skipped }` (the last three are name arrays) |
| `receive/closed` | event | The service is closed and the keys are wiped | `{ reason }` (`finished` or `closed`) |

The smallest useful example (records what this session received):

```js
// recv-log.cjs
const { appendFileSync } = require('node:fs')

module.exports = {
  name: 'recv-log',
  apiVersion: 1,
  apply(ctx) {
    const log = (line) => appendFileSync('recv.log', line + '\n')
    ctx.on('receive/manifest', (e) => log(`manifest: ${e.files} files / ${e.totalBytes} bytes`))
    ctx.on('receive/file-done', (e) => log(`done: ${e.rel} (${e.bytes} bytes)`))
    ctx.on('receive/complete', (e) => log(`finished: ${e.done.length} ok`))
    // When a name collides you want to know which one, but the decision stays with the user
    ctx.on('receive/collision', (e) => log(`collision: ${e.rel} already exists at ${e.existing}`))
  },
}
```

## 6. Writing a plugin: sending side

```js
// my-plugin.cjs —— self-contained, builtins only
const { appendFileSync } = require('node:fs')

module.exports = {
  name: 'my-plugin',          // appears in the interface, the destroy list and error messages
  version: '1.0.0',           // optional, display only
  apiVersion: 1,              // required: a mismatch with the program's version means **refused**

  apply(ctx) {
    ctx.log(`plugin ready (Flicker ${ctx.info.flicker})`)

    ctx.on('run/start', (e) => ctx.log(`mode=${e.mode} chunkBytes=${e.chunkBytes}`))
    ctx.on('manifest/scanned', (e) => ctx.log(`${e.summary.fileCount} files`))
    ctx.on('transfer/complete', (e) => ctx.log(`ok=${e.ok} sent=${e.bytes} bytes`))

    // attach one extra file to this transfer
    ctx.contribute('gift/items', () => ({
      name: 'note.txt',
      data: 'This file was generated by a plugin on the sending side.',
    }))
  },
}
```

The repository ships **six runnable examples**: `examples/plugins/hello-logger.cjs` (records the transfer in a
log), `attach-note.cjs` (attaches a file to the transfer), `relay-gate.cjs` (access control for a relay),
`relay-disk-store.cjs` (a storage backend for the relay: messages go to disk and the copy is deleted on ack),
`page-hello.mjs` (a page plugin that adds a button when receiving completes) and `recv-log.cjs` (the receiving
side: records what this session received).

## 7. Writing a plugin for the relay

```js
// my-relay-plugin.cjs —— access control plus an audit trail for a self-hosted relay
const { appendFileSync } = require('node:fs')

module.exports = {
  name: 'relay-gate',
  apiVersion: 1,

  apply(ctx) {
    const log = (line) => appendFileSync('relay-plugin.log', line + '\n')

    // in front of routing: a wrong token is refused with 403
    ctx.on('relay/route', (e) => {
      if (e.headers['x-relay-token'] !== process.env.RELAY_TOKEN) {
        log(`refused ${e.method} ${e.path}`)
        return { status: 403, body: { error: 'FORBIDDEN' } }
      }
    })

    ctx.on('relay/room-created', (e) => log(`room created ${e.room}`))
    ctx.on('relay/room-destroyed', (e) => log(`room destroyed ${e.room}`))

    // let /health report one more field, handy for checking your own deployment
    ctx.contribute('relay/health', () => ({ operator: 'my-company' }))
  },
}
```

## 8. Writing a plugin for the receiver page

```js
// my-page-plugin.mjs —— inlined into the receiver page at build time
// ⚠️ plain browser JS: no import/require, no Node APIs (checked at build time)
export default {
  name: 'my-page-plugin',
  apiVersion: 1,

  apply(ctx) {
    ctx.log('page plugin ready')

    ctx.on('recv/verified', (e) => ctx.log(`${e.fileCount} files incoming`))
    ctx.on('recv/file-done', (e) => ctx.log(`received ${e.name}`))
    ctx.on('recv/complete', (e) => ctx.log(`done in ${e.seconds}s`))

    // add a button to the "receiving complete" panel
    ctx.contribute('page/actions', () => ({
      label: 'Copy the file list',
      onClick: () => navigator.clipboard?.writeText('the list'),
    }))
  },
}
```

## 9. Reclaimable: ctx.effect

```js
ctx.effect(() => {
  const server = http.createServer(handler).listen(0)   // runs immediately
  return () => server.close()                            // guaranteed to be called on destroy
})
```

`ctx.effect()` **runs the function immediately** and registers the cleanup function it returns with the destroy
chain —— on the sending side that step in the destroy list is called "插件资源已释放" (plugin resources released),
a relay runs it when the service shuts down, and a page runs it on unload. Release order is **reversed** (the last
one built is torn down first), and one plugin failing to clean up does not affect the others.

## 10. Capability boundaries: what a plugin cannot do

| Not allowed | Why |
|---|---|
| Change encryption or the handshake (suite, key derivation, downgrade protection) | That is where the entire security of this program lives; no exceptions |
| Change the receiver's on-disk path rules | That is the only defence against silently overwriting files |
| Change manifest fields such as `sha256` / `size` | The receiver verifies every chunk against them; changing them makes verification lie |
| Override the core fields of the relay's `/health` | Capability negotiation reads them to pick a chunk size; overriding them would make the relay lie to clients |
| Decide the destroy flow or its order | The destroy chain belongs to the core; a plugin may only **register** what it needs cleaned up |

## 12. Security notes

- A plugin is **not sandboxed**: it runs with your privileges and can read and write your files and make network
  requests. Only load plugins you wrote yourself or have read the source of.
- The program (and a self-hosted relay) prints which plugins were loaded; `--plugins` shows them without running a
  transfer.
- A page plugin **changes the receiver page's fingerprint**, and that fingerprint is checkable (`--assets`) —— so
  "who changed the page the other side received" cannot be hidden.
