### Three lying numbers (all were stepped on, all got a machine check)

**① The test count in the documentation goes stale silently.**
`README.md` said "242 cases", when it was already 390; the same paragraph also told people to run
`npm run test:unit` / `npm run test:serial` —— those two scripts **never existed**
(the real ones are called `test:fast` / `test:parallel`). The more precise a number looks, the less anyone doubts it.
Now `gen/run-tests.mjs` additionally attaches a TAP reporter that writes into a temp file,
and once the run finishes it uses `# tests / # pass / # fail / # skipped` to check both READMEs,
printing "which line, what it is now, what it should be changed to" when they disagree. **It only warns, it does not fail the tests** ——
the test count changes every time a case is added, and wedging CI would only push people to delete the number, which is worse.
(It only checks after "one complete round on this platform": `--fast` and `--name-pattern` run a different set of numbers, so comparing against them would mean a false alarm every day.)

**② A file can be written as "opens fine but is all mojibake".**
Using Windows PowerShell 5.1's `Set-Content` (which writes ANSI by default) on a markdown file containing Chinese and
em dashes turns the last byte of every non-ASCII character into `?`
(`e2 80 94` → `e2 80 3f`). The file still opens, still commits, and **not one test fails** ——
it's just that on GitHub the dashes, check marks and Chinese doc names are all garbage.
So `gen/check-line-endings.mjs` now strictly decodes every text file with
`TextDecoder(..., { fatal: true })`: an ordinary `toString('utf8')` only quietly inserts U+FFFD, and **only something that can throw is usable as a criterion**.

**③ A whole family of "current fact" numbers in the docs expires together.**
In 2026-10 the user said "look for errors in the docs" and four kinds surfaced at once: the i18n
string count (it said 171, actually 319), the single-file artifact size (89.5 / 91 MB, actually a
bit over 94 MB), the number of documents (ten each, actually twelve), and the version in sample
output (v1.0.0, actually 0.1.0). They share one property: **the more precise a number looks, the
less anyone questions it**. `gen/check-doc-numbers.mjs` now computes each one and compares it with
the docs: i18n count, criterion count, documents per language, version in sample output, minimum
Node version. Artifact size is checked separately by the Windows CI job after `build-sea.mjs`
(`--artifact`, ±0.1 MB —— the gift source pack carries the docs themselves, so every doc edit
moves it). It also insists that **at least one claim exists**: if the sentence is deleted, the
check reports "no claim found" instead of quietly switching itself off. Reverse verification lives
in `test/doc-numbers.test.js` (8 cases): a broken number must be reported **with file and line**, a
deleted sentence must fail, and touching the old numbers inside a **historical** sentence must
not react (otherwise it would just be a bad "scan every number" check).

> While restoring, I verified this criterion's reliability on the side: copy the repaired `../README.md`,
> run the same two PowerShell operations as back then (`Get-Content -Raw` + `Set-Content -NoNewline`)
> once more, and you get **the same 12076 bytes** and **the same `e2 80 3f` corruption signature** ——
> that is, the restored content is byte-for-byte identical to the original file, not "looks about the same".

### ✅ Done: automatic reconnect on link jitter (5b, 2026-10)

**This is the most common cause of failure in long transfers.** In the original code, a single transient network error
(Wi-Fi jitter, phone switching networks, connection reset, DNS blip) would terminate the entire transfer outright ——
tens of GB thrown away. Whereas the genuinely fatal error, "the other side closed the program", is rare.

Both ends now retry with exponential backoff (starting at 400ms, doubling, capped at 8s, with jitter):

| Location | What it fixes |
|---|---|
| Sender `RelayClient._withRetry` | open / manifest / status / batch all go through retries |
| Receiver `withRetry` (in the page) | `api()` and fetching chunks from the relay all go through retries |

**The key difficulty: the failure semantics of a batch POST are ambiguous.** The request may already have succeeded
on the server, with only the response lost on the way back. Blindly resending adds a batch of duplicate messages at the tail of the room.
The solution came from the protocol itself —— **sequence numbers are assigned by the server**: before retrying, read `nextSeq` once;
if it has grown to `startSeq + count`, the previous attempt did land in the database, so return success directly.
(That design originally existed to solve concurrent collisions, and here it earned a bonus "idempotent retry".)

Classification criterion: only retry transient failures (network-layer exceptions, timeouts, 5xx, 429);
`NO_ROOM` / `EXPIRED` / `GONE` / `BAD_SEQ` / user cancellation **always fail immediately** ——
taking an unrecoverable error into a retry only makes the user stare at the screen through four rounds of pointless backoff.

12 new cases pin down these behaviours; the most important assertion among them is
"**exactly one POST happened**" (not "the retry succeeded", but "the retry caused no duplicate delivery").

### ⚠️ Why "resume across sessions" is 5× harder than expected (item 5)

I originally estimated "half a day: store chunk ranges in IndexedDB, reconcile on reconnect". **Once I actually started, two hard constraints appeared**,
and they are unsolvable at the browser API level —— it is not a question of how much engineering effort it takes:

**Constraint one: only Chromium can possibly do it.**
The receiver has two paths for writing to disk:

| Path | Trigger | After reloading the page |
|---|---|---|
| **Streaming write** (`showSaveFilePicker` → `createWritable`) | Chromium only | the data **is on disk**; as long as the file handle can be restored, it can still be resumed |
| **In-memory Blob** (`Blob` + `<a download>` once receiving finishes) | Firefox / Safari / the fallback path | the data **exists only in memory and evaporates on reload** —— there is nothing to resume from |

So "close the page and keep transferring" is **physically impossible** on Firefox / Safari.
And whether a FileSystemFileHandle can persist across sessions, and how permission is re-acquired when it is reopened,
are unknowns that require per-browser measurement.

**Constraint two: the relay room's 15-minute TTL.**
In the "close the page and come back a while later" scenario, the sender's room has very likely expired and been destroyed.
Resuming requires the sender still to be running and the room to still be alive (or to be rebuilt and re-delivered).
That already goes past "the receiver keeps its own books" and becomes a negotiation between both ends.

**Conclusion and recommended approach** (two steps; the first already captures most of the value):

1. ✅ **Step one is done (2026-10): progress preservation within the same session, at file granularity.**
   The receiver records, per session, the indices of the files that were "fully received and passed whole-file verification"
   (`DONE_FILES` / `fileDoneBytes` / `resetProgressFor()`, see `web/receiver.html`),
   so clicking "retry" no longer re-transfers the dozens of files already written to disk.
   `test/receiver-page.test.js` has a case dedicated to pinning two criteria that degrade easily:
   **it must be recorded per session** (changing origin/room clears it —— carrying over an old set would skip files that were never received at all,
   and the user would be left with an incomplete directory, which is far worse than "transferring it all again"),
   **and it must come after whole-file verification** (putting it before would mark half-received files as complete).
   This is **file granularity only**: `createWritable()` writes sequentially and truncates the file on every call,
   there is no "continue writing from byte N", so chunk granularity is impossible in the browser —— this is not an engineering-effort problem.
2. ❌ **Step two (the truly cross-session one) is not being done** —— **decided by the user, 2026-10**. The two things it originally needed
   (persisting a FileSystemFileHandle + sender support for "re-deliver according to the progress the receiver reports") are not technically
   impossible; the price is **relaxing three promises already written into the docs** (see the last row of the table in §6):
   - `行为与运行.md` §7 says "**uses no cookies, localStorage or IndexedDB** to store anything related to the transfer" ——
     "remember which chunk we got to" has to live in IndexedDB, so that promise stops being true (the file handle goes in there too);
   - "**a one-time link dies on its first visit**" —— reopening the page to resume means the same token has to be accepted again;
   - "**the password and session keys were released with this page**" —— continuing to decrypt means either keeping the session key
     (which contradicts that line) or making the user retype the password (and then resuming is no longer seamless).
   It is also **only possible on the streaming-write path** (Firefox / Safari keep data in memory only), and it has to race the relay
   room's 15-minute TTL.
   **The trade-off**: those three promises are this tool's core selling point, and they are not worth trading for "resume after closing the page" ——
   so the promises stay and the feature is explicitly not done, rather than building it first and rewriting the docs afterwards.
   Everything that works within a session (automatic reconnect on a flaky link, skipping already-finished files) **still holds, unchanged**.

**"Honestly can't" matters more than "pretending it can"** —— this has to go into the user manual.

## 3. Polish (5 items)

> ### ✅ Done (not in the numbered list): generating session certificates in pure JS —— removing the biggest platform gap in one go
>
> **The original problem**: certificate trust was implemented only on Windows (using PowerShell's
> `New-SelfSignedCertificate`). On macOS/Linux `generateSession()` threw
> `NOT_SUPPORTED` outright, **LAN mode was completely unusable**, and item 8 (three-platform measured) had nothing to build on.
>
> **The detour taken**: I first planned to fill in macOS/Linux with the `openssl` command line. Two reasons made me drop it:
> ① what macOS ships is **LibreSSL** (its arguments differ from OpenSSL), and Linux distributions don't necessarily have the
> openssl command line installed —— yet another external dependency; ② **I could not verify it on Windows**,
> which would break this project's rule that "if it isn't measured, it isn't done".
>
> **The final approach: encode X.509 by hand in pure JS** (`src/x509.js` + `src/session-cert.js`).
> The ECDSA signature that Node's `crypto.sign` returns **is itself a DER SEQUENCE** and can go straight into a certificate,
> so "a self-signed CA + one server certificate" is just a few hundred lines of straightforward encoding, needing no parser and no tooling.
>
> **How it was verified is the most important part of this item**: not by looking at what the API returns, but by
> **starting an HTTPS server and connecting to it with the generated CA as the trust root** (`src/session-cert-check.mjs`):
>
> ```
> ✓ 以 CA 为信任根能连上        HTTP 200
> ✓ 错误的信任根会被拒绝         UNABLE_TO_VERIFY_LEAF_SIGNATURE
> ✓ 不提供信任根会被拒绝         UNABLE_TO_VERIFY_LEAF_SIGNATURE
> ✓ 主机名不匹配会被拒绝         ERR_TLS_CERT_ALTNAME_INVALID
> ```
>
> The last three are **negative checks** —— without them, the first one could simply be a false positive where "verification never took effect at all".
>

### ✅ Done: release packaging script (item 14, 2026-10)

`gen/release.mjs` arranges the artifacts in `dist/` into a directly publishable shape:
copies of the artifacts + `SHA256SUMS` (coreutils format) + `RELEASE.md` (download table, usage, **known limitations**, checksums).

Three things it deliberately does, all of them "the easiest to miss when hand-rolling a release":

1. **Compute the checksums**. Nobody reads the source of a 90 MB binary; the checksum is the only proof that
   "this file really came from this source". And **getting it wrong is worse than having none** —— users who can't match it will assume the file was tampered with,
   and stop trusting checksums ever after. So `test/release.test.js` has a case that computes it independently and compares.
2. **State explicitly which platforms are missing**. SEA doesn't support cross-compilation; one machine can only build the artifact for its own platform.
   Without saying so, users would keep hunting the download list for a Linux build, thinking they had missed it.
3. **Carry the known limitations**. The relay handles ciphertext, macOS/Linux are unverified on real hardware, Firefox may fail on large files,
   closing the page cannot resume, weak-password risk —— these must ship alongside the artifact.
   A case checks that all of these keywords are present.

12 cases cover the above behaviours (using a few-KB fake artifact + an injectable directory, so they run in seconds;
a real SEA build takes over a minute, and nobody would run a test like that).

### ✅ Done: installable PWA + Web Share API (item 6, 2026-10)

**Two pieces: installable (PWA) + system share sheet (Web Share API).**

#### Installable: manifest and icons all inlined as data URLs

A conventional PWA needs three extra files (`manifest.webmanifest` + two PNG icons). **This project can't do that** ——
the receiver page is served from two places: the sender serves it directly over **LAN self-signed HTTPS**, the relay serves it over **HTTPS**.
The paths, protocols and reachable files differ between the two; three extra files would mean three more deployment steps for the relay,
and getting any one path wrong means "can't install, with no error reported".

So the entire manifest goes into `<link rel="manifest">` as a **data URL**, and the icons use **SVG data URLs**.
**Not one extra file is needed**, consistent with the page's "single file, zero external requests" constraint (about 5 KB in total).

The app name follows the interface language (Chinese 「闪传」/ English 「Flicker」) —— a static manifest can't do that,
so what's inlined is a **script that assembles the manifest at runtime**, regenerated whenever the language switches.

#### Sharing: offered only when "the content is still in memory"

The Web Share API needs a `File` object, which means it needs **all the bytes**. Yet one of this program's core promises is
"large files don't blow up memory": on the streaming-write path (Chromium + the user picked a directory), the bytes are let go as soon as they are written.

Should we read the whole file back in just to share it? No —— a 40 GB file would take 40 GB of memory, and it directly conflicts with
the "write to disk while receiving" design. So the rule is: **offer sharing when the content is in memory, don't offer it when it isn't, and explain why**.

On phones the memory path is always taken (Safari/Firefox have no streaming write), so "share to Photos/WeChat",
the scenario that needs it most, actually has the highest availability. On desktop Chromium the file is already on disk ——
at that point the user wants the file itself, not a share sheet.

#### Two easy places to get it wrong (both guarded by cases)

1. **You must not just test `typeof navigator.share === 'function'`**. Desktop Chrome has `share()`
   but **doesn't support files**, and each platform has further limits on type/size. You have to ask
   `navigator.canShare({ files: [file] })` first —— if you only check that the API exists, the button does nothing when clicked.
2. **The user tapping "cancel" in the system sheet throws `AbortError`**. That's a normal action and shouldn't pop an error box ——
   otherwise the user thinks they did something wrong.

#### ⚠️ Not verified on real hardware

**This item has never been run on a real phone.** The logic and the generated output are guarded by tests
(manifest field completeness, icon self-containment, the maskable safe area, language following, share capability detection),
but "what it looks like installed on the home screen" and "can WeChat be picked in the share sheet" **can only be seen on a real device**.
Following the project's convention, this is honestly marked: **not measured**.

Also, the "known obstacle" further down in `路线图.md` still holds: a page loaded from **the relay (HTTPS)**
is not allowed to request `http://192.168.x.x` (mixed content), so "a phone on a different network can also receive" still requires
the user to tap "continue anyway" once.

### ✅ Done: bilingual i18n UI (item 10, 2026-10)

**Both interfaces are fully bilingual** (373 strings, Chinese and English side by side). There are three ways to switch language:
automatic detection from the browser language, the switch button in the top-right of the interface, and a choice remembered in sessionStorage/localStorage.

| Part | Notes |
|---|---|
| `web/i18n-strings.mjs` | The string table (171 entries). Placeholders are always `{name}` |
| `web/i18n-runtime.js` | The runtime: substitution, language detection, the switch button, falling back to the key name for missing strings |
| `gen/inline-i18n.mjs` | **Inlines the runtime and the string table back into the page** (the receiver must be a single file with zero external requests) |
| Receiver + sender interfaces | ✅ Every `data-i18n` annotation is in place, and all in-script strings go through `t()` |

**A few deliberate design choices:**

1. **Use `data-i18n` attributes, not dumping all the strings into JS**. The Chinese original stays in the HTML as a **no-script fallback** ——
   when the script hasn't run, the user still sees a complete Chinese interface rather than a screen of blanks.
2. **The receiver doesn't use localStorage**. When I added i18n, my first version used localStorage for the language preference,
   and the case saying "the receiver writes no persistent storage" **caught it on the spot**. The reasoning: the sender is the user's own machine,
   used repeatedly, so remembering the language saves trouble; **the receiver is the other party's one-off page**, and leaving a record
   in someone else's browser is itself a trace, which shouldn't be traded away to save one click. So the receiver uses sessionStorage (gone when the tab closes),
   and **the name localStorage doesn't even appear in the page** —— which lets the static check genuinely take effect,
   rather than relying on a comment explaining "it appears, but isn't used".
3. **Missing strings fall back to the key name** (rather than to blank). Seeing `recv.pw.title` on the interface tells you at a glance which entry is missing.

**Four genuinely hard-to-find pits hit along the way** (all worth recording):

| Pit | Symptom | Cause |
|---|---|---|
| `global.navigator` shadowing the injection | The test injects `en-US`, but the runtime follows `zh` | **`globalThis.navigator` exists in Node** (its value comes from the system locale), so `global.navigator` silently overrode the parameter the test injected. No error, just language detection forever following the host machine |
| The `document` version of the same pit | `apply()` always returns 0, yet the API looks normal | `if (global.document)` is always false in Node → `boot()` never runs; and because the API hangs off globalThis it "looks like it works" |
| An example inside a comment treated as a real element | The test reports "references key `key`, which is not in the table" | The regex matched a `data-i18n="key"` example inside a **doc comment**. Comments must be stripped before checking (the project stepped in the same pit over `import.meta` checks) |
| I wrote the keys first and read the page afterwards | The string table contained 「选择要发送的文件」, a sentence that doesn't exist in the page at all | Inventing key names from imagination = wasted work. **Read the actual strings in the page first, then decide the keys** |

**The lesson (already written into the code comments)**: pass things belonging to the host environment (`document` / `navigator` / `localStorage`)
into a module **as parameters**, rather than fetching them off `global` —— otherwise the code that depends on them
simply cannot be tested in Node, and it fails silently.

### ✅ Done: rate limiting `--rate` (item 9, 2026-10)

**Before this it was a "documented but not implemented" feature** —— section 6.2 of the user manual had long listed
`--rate`, but the CLI treated it as an unknown argument and **silently ignored it**. The user thought they had limited it to 5 MB/s,
while it actually saturated the uplink, and that only gets discovered when a colleague complains the network is slow.
(`--one-file` in the same table had **no implementation anywhere in the codebase**, and was removed from the manual along with it.)

Implementation: a token bucket (`src/rate.js`), shared by both modes. The integration points are
`TransferServer._sendChunk` (LAN, waits before encryption) and
`RelaySender.run` (relay, drawing credit against this batch's **plaintext bytes**).

**Why a token bucket rather than "sleep a fixed time per chunk"**: a fixed sleep locks the rate to
`chunk size ÷ sleep`, which goes wrong the moment the chunk size changes, and it allows no bursts. A token bucket accounts in **bytes**,
so it stays right however the chunk size changes.

**Two pits in opposite directions were stepped in during implementation**, both worth remembering:

1. **Rate limiting had no effect**: the refill amount was written as `Math.min(n, capacity) - tokens`.
   When the bucket is full that is always 0 (capacity − capacity) → `waitMs = 0` → **it never waits**.
   Measured: 384 KiB at 128 KiB/s took only 4ms.
2. **Over-sending**: after fixing pit one, it became "if the request is bigger than the bucket, clamp it to the bucket capacity and let it through".
   That looked solved, but it actually **deducted too few tokens** —— asking for 384 KB deducted only 128 KB,
   and measured, the second request let 384 KB through after waiting only 1038ms (it should have waited 3000ms).

**The correct approach**: the bucket must be able to hold the requested amount —— when the bucket is smaller than the request, **grow it**.
Any "clamp it and let it through" is over-sending. (`test/rate.test.js` now has cases pinning both;
`_lab/check-rate.mjs` lets you look at the numbers directly, steady-state deviation 1–4%.)

Along the way a **build-tool false positive** was fixed: the bundler's "top-level await" check is a line-by-line regex
`/^\s*await\s/m`, which cannot tell "top-level await" from "an await indented shallowly inside a function body".
A line in `rate.js` with an 8-space-indented `await` (class method → try → if → while)
was misjudged, the whole build failed, and the error only said "contains top-level await" without saying which line or which module.
This kind of judgement belongs to `node --check` (a real syntax check) —— it neither false-positives nor misses anything.
For the regression case see 「pit 5c」 in `test/bundler.test.js`.

### ✅ Done: large-file memory (second half of item 9 + item 12, 2026-10) —— and **the original judgement was wrong**

Item 12 said "the single file is 89 MB, and right now it is **read into memory whole** and then sent in chunks".
Measured, **that sentence does not hold**: the sender was streaming all along. When that sentence was written, nobody had measured.

Using `_lab/bench-memory.mjs` I measured two transfer paths across four orders of magnitude (peak physical memory, the Windows
`PeakWorkingSet64` high-water mark; the receiver only feeds plaintext to the hash without keeping it, so what is measured really is the sender):

| File | Direct LAN | Through the relay (the cross-network path) |
|---|---|---|
| 64 MiB | 84.7 MiB | 211.3 MiB |
| 512 MiB | 136.2 MiB | 228.0 MiB |
| **2048 MiB** | **139.9 MiB (6.8% of the file)** | **230.5 MiB (11.3% of the file)** |

The criterion is not "looks small" but the **slope**: for every extra 1 MiB of file, the peak grows by only
**9.9 KiB** (28.5 KiB on the LAN). Had it been read into memory whole, that slope would necessarily be 1 MiB/MiB,
and the peak share would be >100%. What says even more is that **the increment is converging**:

```
LAN:    64→512 MiB   per MiB of file +117.7 KiB
        512→2048 MiB per MiB of file   +2.4 KiB   ← the file is 4× bigger, yet the increment is 50× smaller
Relay:  64→512 MiB   per MiB of file  +38.1 KiB
        512→2048 MiB per MiB of file   +1.7 KiB
```

**This is exactly the difference between "bounded" and "linear"**: a linear implementation's per-MiB increment is a constant,
whereas here it is falling —— meaning the working set has an upper bound (a 1 MiB read buffer + the V8 heap watermark),
so the peak for 20 GiB and for 2 GiB should be in the same order of magnitude.

Relay mode uses about 90 MiB more than the LAN, and that part is **there by design**: an in-flight window of 8 chunks
(8 MiB plaintext + 8 MiB ciphertext), the request body of a batch POST, and one extra HTTP client layer.
It is a constant, and does not grow with the file.

Conclusion: **neither item 9 nor item 12 needs a code change**; what was needed was to measure the numbers and then guard them.
For the full process, the criteria and the pits the script itself stepped in, see [`_lab/实测报告-大文件内存.md`](../_lab/实测报告-大文件内存.md).
So `test/large-file.test.js` was added (7 cases, 0.6 seconds) to pin this property down:

- Dynamic criterion: while hashing a 96 MiB file, this process's RSS growth must be < 48 MiB
- **Positive control**: the same criterion must fire for `readFile(96 MiB)` (> 48 MiB) ——
  without that one, "RSS didn't grow" only proves the measurement can't see it, not that the implementation streams
- Static criterion: `readFile(` **must not appear** in `src/server.js` or `src/relay/client.js`
- The buffer is allocated once, outside the loop; `hashFile` and `hashBuffer` must agree chunk by chunk

`_lab/bench-memory.mjs` does not go into CI (it needs minutes and several GB of disk); it is responsible for producing the conclusions and the numbers;
the test above guards the conclusions from being changed. Usage:

```powershell
node _lab/bench-memory.mjs 64 512 2048            # LAN
node _lab/bench-memory.mjs --relay 64 512 2048    # via a local relay
```

⚠️ One pit in the measurement script itself is worth recording: in relay mode the sender **destroys itself and exits the moment it finishes acking**,
so "read the peak once more after it finishes" reads null (shown as `—` in the table), while LAN mode happens not to expose this because it waits for the
timeout before exiting. A measurement script that is **broken in only one mode** is the most dangerous kind ——
the data looks normal, but it is actually empty. It now uses a resident sampler that samples while the run is in progress.

### ✅ Done (and one real bug fixed with it): the relay room's "three opening cases" (2026-10)

**Source**: checking the `PROTOCOL.md` §3.3.1 item 「to be verified: a malicious party can `POST from:"i"` to preempt the room name,
but the 256-bit room name is unguessable, so the real risk is zero —— to preempt it you must already know the password」.

**That reasoning is wrong**: the room name really is un*guessable*, but it **is right there in the link** (64 hex characters).
Someone who has the link but not the password doesn't need to guess —— and "send the link and the password separately" is exactly this product's recommended usage.

Measured (`_lab/probe-relay-preempt.mjs`, the real `RelayClient` + a local relay):

| Situation | Room state | Old behaviour | Now |
|---|---|---|---|
| An attacker creates a room and holds `seq 0` | `nextSeq=1` (all garbage) | The sender **silently skips the manifest** → the receiver fails to decrypt | Clearly reports `ROOM_TAKEN` + tells the user to start over |
| **The create response is lost on the way back** (no attacker) | `nextSeq=0` (empty room) | The sender **silently skips the manifest** → the receiver waits 2 minutes and times out | Re-delivers the manifest, the transfer proceeds normally |

**The second row is the important one, and it is our own bug**: the old implementation in `open()` looked only at
`created.created`, and if it was falsy it assumed "the room is already ready" and skipped delivering the manifest. But "the room already exists" has **two**
completely opposite meanings —— ① we just created it ourselves (the response was lost on the way back, the room is empty) ② someone else got there first (there is something in the room).
The trigger condition is utterly ordinary: the response to the initial `POST` was lost once. And by then the user **has already sent the link out**,
and what comes back is a "it never arrives" that they cannot make any sense of.

**The fix**: the criterion becomes "is there anything in the room" (`open()` in `src/relay/client.js`):

```
nextSeq === 0  → case ① our own response was lost → re-deliver the manifest
nextSeq >  0  → case ② someone else took it       → throw ROOM_TAKEN (no retry, with actionable advice)
```

5 cases (`test/relay-open.test.js`) pin this down one by one against a **real local relay**, including
"when preempted we did not write a single byte into someone else's room".

**A residual, accepted limitation**: whoever has the link can still keep this session from starting (denial of service).
There is no plan to plug it further —— it requires the attacker to have the link first, and the link is itself a credential; anyone who really has the **password**
doesn't need a DoS at all (they can decrypt everything directly). What was improved is "failing clearly and with guidance".

### ✅ Done: only one implementation of path safety left (2026-10, from a 「to be verified」 in PROTOCOL.md)

**How it started**: at the end of `PROTOCOL.md` §6.2 there was a 「**to be verified**: on macOS, HFS+/APFS Unicode
normalisation (NFD/NFC) may cause same-name file collisions」. Following that thread turned up a bigger problem than the item itself.

#### The real problem was "two implementations, and the rules didn't even match"

| Location | The rules |
|---|---|
| `src/manifest.js` | 12 rules, basically complete |
| `web/receiver.html` | `rel.replace(/[<>:"|?*\x00-\x1f]/g, '_')` —— **just one line** |

And **what actually decides the name the file lands under on the user's disk is the browser's copy**.
So the same manifest is all green in the Node tests, and loses files in the browser:

| Situation | Who hits it | Consequence |
|---|---|---|
| The manifest contains both `a:b.txt` and `a_b.txt` | Linux/macOS sending to Windows | Same name after rewriting → **the later write silently overwrites the earlier one** |
| `café`(NFC) and `café`(NFD) | macOS receiver | There they are **the same file** → the same silent overwrite |
| `A.txt` and `a.txt` | Windows / macOS | Same as above |
| `CON.txt` / `NUL` | Linux sending to Windows | Creation fails, with an error nowhere near "filename" |
| `name.` (ends with a dot) | Linux sending to Windows | Windows silently drops the dot → two files become one |

**What they have in common is "no warning"**: the interface says "transfer complete", and the disk is one file short.
That is far more serious than an error —— with an error the user can try again; a silently lost file is something the user never even learns about.

#### What was done

1. The rules were gathered into `src/path-safety.js` —— **the single implementation**, pure JS (no import allowed, no Buffer),
   so it can be inlined into the page as is.
2. `gen/inline-path-rules.mjs` inlines it into `web/receiver.html`, and `--check` guards the synchronisation
   (the same approach as i18n and the PWA, already wired into `npm run check` and CI).
3. **R12's comparison key = NFC normalisation + case folding**, and the comparison key is used only for judging,
   not to rewrite the name that gets written to disk. The sender deduplicates with **the same key**, otherwise the sender thinks there is no conflict
   while the receiver only writes out one of them.
4. The receiver finds conflicts **before the transfer starts** and aborts (`E_MANIFEST_DUPLICATE_PATH`);
   the page uses the protocol's error code and **does not offer a "retry" button** —— the manifest is fixed, so a retry would necessarily fail the same way,
   and a button that does nothing when pressed is worse than no button.
5. R7 was aligned along the way: the old implementation rejected 1024 **characters**, while the protocol says 255 **bytes** per segment / 4096 **bytes** overall.
   When implementation and protocol disagree, the protocol wins, otherwise anyone writing a client from the docs falls flat.

#### How the tests guarantee "the two sides really are the same"

The two most important cases in `test/path-safety.test.js` (23 cases) are not about "stopping hackers" but about stopping **drift**:

- Take the script inlined in the page, put it in a **sandbox with no `Buffer` and no `process`**, and **really execute** it,
  then compare its behaviour item by item against the Node copy on **the same input table** (34 inputs ×
  windows/posix × strict/lenient, four combinations).
  Asserting only that "both sides have this function" is not enough —— the two sides used to have their own implementations too.
- Positive control: a `readFile`-style approach cannot run here (there is no Buffer in the sandbox),
  so this criterion **can fail**.

> Why not search for `Buffer` with a regex: this very file's comments say "Buffer is not allowed",
> so a regex would be tripped up by its own comment; whereas running it in a sandbox that genuinely lacks Buffer makes any use of it throw.

#### A defect of its own fixed along the way

`safeRelPath`'s **degradation branch** (the fallback when sanitisation fails) used to be
`raw.replace(/\\/g,'/').replace(/^\/+/,'')`, which returned `../../evil.txt` **unchanged** ——
that is, the "safe function" spat out a traversal path in its fallback. **Degrading does not mean giving up on checking**:
the fallback still has to filter `..`, `.`, and empty segments. This one was caught by a test.

#### The same class of fault: the receiver page also used to exist twice

The same thing happened again with **the page**, only in a different form: the receiver page is used from two places ——
for direct LAN connections `src/server.js` reads `web/receiver.html` directly, while across networks the relay Worker
reads the built artifact `relay/page.generated.js`. The artifact is produced by `gen/gen-relay-page.mjs`,
which already wrote **a fingerprint of the source files** into itself, but **nothing ever checked** that fingerprint.

And so a real drift happened: after editing the page I only ran the i18n inlining and forgot to rerun the generation script ——
the LAN had the new version, while **what went out across the network was still the old page**. This kind of difference doesn't error and doesn't fail;
it only surfaces when someone using the relay reports it.

Both paths are now closed:

- `node gen/gen-relay-page.mjs --check`: fails if the fingerprints don't match, and tells you exactly which command to run
  (already wired into `npm run check` and CI)
- A case in `test/receiver-page.test.js` compares the artifact and the source file **character by character** ——
  so when the static check is left out of CI, `npm test` still catches it

> The criterion itself was verified too: append one comment line to the end of `web/receiver.html` and this case goes red immediately;
> restore it and it goes green immediately (the file hash is identical before and after the restore).

## 4. Mobile app (raised by the user; the scope needs redefining)


The user's own words were "make an app on mobile for managing sending and receiving files". That has tension with the project's requirement #1,
so the scope needs to be stated clearly:

| Option | Receive | Send | Cost | Assessment |
|---|---|---|---|---|
| **A. PWA** (do this first, recommended) | ✅ complete | ⚠️ limited | half a day, zero native code | **The receiver is a browser page already; it doesn't need an App** —— adding `manifest.json` + a minimal `sw.js` is enough for "add to home screen", and it feels like an app while **still needing no app store**. | B. Capacitor / Tauri shell | ✅ | ✅ close to desktop | **2–3 weeks** | Requires installing Android Studio / Xcode and maintaining three-platform builds. Only worth it if "the phone must act as the sender" |
| C. An App for the sender only | — | ✅ | 1–2 weeks | If the core need is "send files from my phone to someone else", this is more focused than B |

**Why being the sender on a phone is hard**: a browser **cannot read files from arbitrary paths**, nor can it start a server on a phone.
This is a platform limitation, not a design problem. Only a native shell can get around it.

> **2026-10 update: this has been worked around, and without a native shell.**
> Since the phone cannot start a server, **turn it around —— the computer starts the service and the phone pushes
> files up from its browser**: `flicker recv` opens an HTTPS service on this machine, prints a QR code and a one-time
> password, and the phone scans it, picks photos/videos and sends. The phone side therefore stays a zero-install web
> page (so iPhone works too), reusing the existing certificates, password, encryption and destroy machinery, at LAN
> speed. The costs, stated plainly: **the phone must stay awake while uploading large files** (the browser freezes a
> backgrounded page), and a phone cannot pick folders (file names only, no directory structure).
> The computer side (API + command line + destroy chain) is **done and tested as M1**; the phone-side page is the next
> step (M2). **So options B and C (native shells) are not needed for now** —— unless it later turns out that "must be
> able to choose the save directory" or "must manage received files inside the App" is essential.
> Details in `_lab/设计草稿-手机发送端.md`.

**Suggested order**: do option A first (half a day, covers 80% of scenarios) → once there is clear feedback that it isn't enough, consider B or C.

### A known obstacle (you will run into it when doing A)

When the receiver page is loaded from **the relay (HTTPS)**, the page is **not allowed** to turn around and request `http://192.168.x.x`
(mixed content; the browser blocks it outright). And the LAN sender uses a self-signed certificate ——
installing a root certificate on a phone is far more of a hassle than on a desktop.

**So the "a phone on a different network can also receive" path cannot avoid making the user tap "continue anyway" once.**
When implementing it, make that an explicit button + explanation, rather than a silent failure.

**Re-checked once more in 2026-10** (a dedicated IPv6 script, `node _lab/probe-ipv6.mjs`): this machine still has only
`fe80::` link-local plus `::1` loopback, **no global IPv6**; going out over IPv6 (`api6.ipify.org` / `v6.ident.me`)
returns `ENOTFOUND` for both. The conclusion is unchanged, and the **"unverified" label stays** as well.

**So an IPv6 direct connection still cannot be done right now** —— it is not a code problem, there is simply no v6 on this line.
Consistent with the previous measurement (early 2026-10): **the ISP has to enable it first** (usually free; some regions don't offer it).

The criterion has three layers, all of them required —— and this is also the order to verify in once it is enabled:

| Layer | Criterion | Now |
|---|---|---|
| Has an address | `os.networkInterfaces()` contains a v6 that isn't fe80::/fc00:: | ❌ none |
| Can reach the internet | A TCP connection to a v6 target succeeds (having an address **does not mean** it works; this is the most common pit) | ❌ ENETUNREACH |
| The peer has one too | The target domain has an AAAA record | ❌ not found |

### ✅ Code implemented (2026-10); **a real IPv6 network is still unverified**

This used to say "implementation points, if it is really to be done". In 2026-10 everything that
**can be verified on this machine** was built and verified:

| Implementation point | Status |
|---|---|
| Detect at startup whether this machine has usable IPv6 (excluding `fe80::` link-local, `::1`, IPv4-mapped) | ✅ `trust.localIPv6()` + `classifyIPv6()`, classification pinned case by case (`test/ipv6.test.js`) |

**What has been verified end to end** (over loopback `::1`, which needs no ISP provisioning):
certificate SAN carries IPv6 → bind to `::1` → a real TLS handshake over `https://[::1]:port/`;
**reverse control**: with a certificate that does *not* contain `::1`, the same handshake must be
rejected (otherwise the "it connects" criterion is fake). Under the dual-stack bind, both the v4 and
the v6 loopback accept connections.

**What still cannot be done** (not a code problem — see the three-layer criterion above):
**public IPv6 direct connection**. This machine has no global IPv6 at all, so "both ends have public

```
1. At startup, probe whether this machine has a global IPv6 (excluding fe80:: link-local)   ← implemented
2. If it does → treat [IPv6]:port as one candidate "reachable address"                      ← implemented
3. The receiver tries an IPv6 direct connection first, falling back to the relay on failure  ← not implemented (belongs to the rendezvous layer, see §8 C)
4. Things that need handling:

```

**The benefit**: across networks there is no need to go through the relay, so it is faster, lower latency, and more private.
**But only if both ends have usable public IPv6.**

## 5·Supplement. Speed: measured data and one real bottleneck (important)

### ⚠️ 2026-10 re-check: **relay mode in the browser had never once worked** —— four defects stacked together

This section matters more than all the tuning below, so it goes first.

**How it was found**: every previous relay verification used a **Node-side receiver**
(`test/relay-e2e.test.js`, `_lab/verify-relay.mjs`), and both of those assembled things by hand according to the protocol.
This time I switched to a **real browser** (headless Edge, driven over CDP) running the real page hosted by the relay,
and hit four defects in one go —— none of which **appear at all** in the Node-side verification:

| # | Defect | Why it doesn't appear in the Node-side verification | Real consequence |
|---|---|---|---|
| 1 | The message's **type byte** was not stripped: the relay stores `[type][payload]`, and the page sliced straight into `raw` (salt/IV/tag/ciphertext all off by one byte) | The Node side used `unpackMessage()`, which strips it naturally | Manifest decryption fails, and the interface only reports an "unknown error" with no locating information. **The whole relay receive path was broken from the very start** |
| 2 | **It never sent an ack** (there was only a comment saying "the receiver acks every chunk it fetches") | The Node side acks every chunk | The queue is never reclaimed; the sender stalls once the in-flight window fills; the completion criterion `ackedBase >= total` never holds |
| 3 | The ack's **sequence number is off by one**: fetching a chunk uses `1 + seq` (the manifest occupies seq 0), but the ack used `seq` | Same as above, the Node side loops over message sequence numbers | The last acknowledgement is forever one short → the file is actually fully received, but the sender never finishes and finally reports "no acknowledgement received" |
| 4 | `firstChunk` was assigned only in the **with-gift branch** (`prepare.js`), and the page relies on it to compute chunk numbers | The Node side accumulates from `chunks` itself | With `--no-gift`, or when **gift generation fails** (that path only prints a warning), `seq` becomes `NaN` and not a single chunk can be fetched |

Item 4 is especially worth recording: it turned "the chunk's global sequence number", a protocol element, into a **side effect** of one particular branch,
and since the gift is on by default, that path was never taken.

#### The fix

1. The page's relay chunk fetch: validate and strip the type byte first (`msg[0]` must be `0x01`/`0x02`, then `subarray(1)`).
2. The page sends acks: ack only **after validating and writing to disk** (the relay deletes the message when it receives the ack, so acking early
   would make a chunk that fails midway impossible to ever fetch again); **do not wait on the hot path** —— coalesce into a background send,
   with a few retries at the end to get the last one out.
3. The ack uses the **message sequence number** `1 + chunkSeq`, the same convention as fetching chunks.
4. `prepare.js` computes `index`/`firstChunk` **unconditionally, before encryption**;
   the page **accumulates its own copy too** (not relying on the peer's field), so both sides are firm.

#### The verification method was replaced as well

New `_lab/e2e-relay-browser.mjs`: the real CLI + a real relay + **the real receiver page hosted by the relay** +
**real Edge** (headless, no windows; driven over CDP using Node's built-in WebSocket, zero dependencies).
The criteria are hard and **can only be satisfied by a real browser**:

```
✅ Sender exit code 0          ← it only finishes this way after 「every message has been acknowledged by the receiver」
✅ The receiver page reaches the 「complete」 screen
✅ The file that came back is byte-for-byte identical (identical SHA-256)
✅ No plaintext appeared on the relay side (neither filenames nor the password appeared)
```

Measured, both 4 MiB and 16 MiB pass (16 MiB: **14 MB/s**, byte-for-byte identical).
This script is also the regression test for this group of defects —— before the fix it necessarily fails.

> **Lesson (learned twice now)**: **when the verification script's behaviour differs from the real client's, you have verified a different link.**
> On the relay path, the Node-side receiver differed from the browser page in three things (stripping the type byte, sending acks, computing chunk numbers),
> and so all four defects slipped through. Whenever you want to verify "the real link", the end you are impersonating must do **the same things** as the real client.
> That lesson is already written at the very top of the comments in `_lab/verify-relay.mjs`.

Among these, "the sender falsely reports success" is a separate defect: after the `break` in the loop body, the end of the function **unconditionally**

### ✅ Fixed along with it: the pure-JS SHA-256 in the browser was 2.7× slow (the real LAN ceiling)


Brought out incidentally by `probe-network`: this machine's NIC is **2.5 GbE (≈295 MB/s)**,
while loopback end-to-end only measured 187 MiB/s —— loopback has no link limit, so that is the **implementation ceiling**.

Following it down, the real ceiling is on the receiver side: in the browser **WebCrypto's `digest` cannot be fed incrementally**,
so "hash the whole file while receiving it" can only use the page's own pure-JS implementation. Measured, it does only **92 MiB/s** ——
not even keeping up with 1 GbE's 118 MB/s; adding concurrency or swapping the NIC wouldn't help.

The cause is the most naive line in `_block()`, `const w = new Uint32Array(64)`:
**a fresh 256-byte array allocated every 64 bytes**. 16384 times per MiB of data, 33.55 million times for a 2 GiB file.

| Version | Throughput | Relative |
|---|---|---|
| New `w` per block (original) | 92 MiB/s | 1.00× |
| **Only change it to reuse `this.w`** | **208 MiB/s** | **2.26×** |
| Reuse + a local variable (current) | **252 MiB/s** | **2.73×** |
| Unroll the message schedule too | 244 MiB/s | (slower, in fact; not adopted) |
| Native `node:crypto` (control) | 2370 MiB/s | 25.8× |

Reproduction script `_lab/bench-sha256-variants.mjs` (including a bit-for-bit consistency check: 8 boundary lengths + a 3 MiB large buffer).
The numbers and the conclusion were written into the comment of that class in `web/receiver.html` —— so nobody "tidies it up" back to the old version.

**Where this leaves things after the fix**: on 1 GbE the receiver is no longer the bottleneck (link 118 MB/s < hash 252 MiB/s);
on 2.5 GbE there is still an implementation ceiling of about 175 MiB/s (measured on loopback: fetch + decrypt + hash),
and that is the trade-off "should the receiver prefetch concurrently", see 「not done yet」 below.

### ✅ Fixed (2026-10): window 1 → 8 + batch delivery, measured about 5×

The original sender was **stop-and-wait**: post one, wait for the ack, post the next. The speed was deadlocked at
`chunk size ÷ round-trip latency`. The link itself can do 29.5 MB/s, while the stop-and-wait implementation only reached 5 MB/s ——
**the bottleneck was the implementation, not the network.**

| In-flight window | Measured throughput (195 ms synthetic latency, 32 MiB) | Relative to stop-and-wait |
|---|---|---|
| 1 (stop-and-wait) | 4.72 MB/s (206 ms average per message) | 1.0× |
| **8 (the current default)** | **about 23.9 MB/s** (median of 3 runs 17.9, single run as high as 23.9) | **≈ 3.8–5×** |

**The cost**: up to 8 MiB of in-flight ciphertext on the relay at once (previously 1 MiB).
`--window N` tunes it; `--window 1` is the original stop-and-wait behaviour (useful on low bandwidth to save data).

### 🔬 Throughput has hit the bandwidth wall (measured 2026-10)

Window sweep (median of 3 runs per step, `_lab/bench-window-sweep.mjs`):

| Window | Median throughput | Theoretical ceiling | Reached |
|---|---|---|---|
| 4 | 13.8 MB/s | 20.5 | 67% |
| 8 | 17.9 MB/s | 41.0 | 44% |
| 16 | 23.4 MB/s | 82.1 | 29% |
| 32 | 27.7 MB/s | 164.1 | 17% |

**The key reading is not the "percentage reached" but that "the gain is saturating"**: 16 → 32 gains only 18%,
and the extrapolated asymptote is about **28–30 MB/s** —— exactly equal to the measured steady state of the link (29.5 MB/s).
So **enlarging the window is now pointless; the bottleneck has become the bandwidth itself**.

> ⚠️ A **single run of this synthetic-latency benchmark can vary by up to ±65%** (35.7 and 23.4 were measured back to back with the same configuration).
> It is fine for a rough call on "which window is better", but not for **fine-grained implementation trade-offs**.
> Item 3 below is one lesson of being misled by it.

#### Three pits stepped in during implementation (all worth remembering)

1. **"Allow more in flight" and "actually send concurrently" are two different things.**
   At first I only made the window constant bigger, but each message was still `await`ed before the next was sent ——
   windows 1 through 32 all still measured 4.8 MB/s, 203 ms per message on average, completely unchanged.

2. **The relay requires strictly ordered delivery, so concurrent POSTs necessarily collide.**
   After changing it to "send N at once", the arrival order was not guaranteed, so they collided with 409 `BAD_SEQ`;
   worse, the server reported the **same** expected sequence number to all the colliding requests,
   so their retries collided with each other again (a cascade of measured failures).
   **The clean solution is "one POST per batch"**: the sequence numbers are assigned by the **server** in arrival order
   (`POST /r/:room/batch`), so there are no collisions and it costs only one round trip.

3. **The window is a limit in "chunks", so when "only 1 slot is free" that one round trip is wasted.**
   The `ackedBase` in the `putBatch` response is the reading from the **previous** round, so the free slots computed the next time around the loop
   come out tiny and a batch delivers only 1 chunk —— measured, the chunks per batch were `[7,1,7,1,…]`,
   averaging 4, only half a full window. **The fix**: when the free slots are less than half a window, prefer not to post at all,
   ask for the status once, and post a full window with the fresh ack (plus an anti-stall guard: "force a post after 3 idle rounds").
   After the fix each batch became `[7,8,8,8,1]`, averaging 6.4 chunks.

#### ❌ Optimisations tried but that **did not pay off** (recorded honestly)

To "save the extra round trip each window costs", I tried overlapping the status read with the delivery
(send the probe first, then deliver, then await both and take the newer ack). **Measured: no gain**:
against the sequential version, at windows 4/8/16/32 the numbers were 13.8/17.9/23.4/27.7 versus
15.1/18.0/24.8/28.4 MB/s —— the sequential version was actually slightly better. That change was reverted,
keeping only the parts supported by evidence (the minimum batch threshold + the anti-stall guard).
**Lesson**: on a benchmark with ±65% variation, a difference under 20% cannot be treated as a conclusion.

   **The clean solution is "one POST per batch"**: the sequence numbers are assigned by the **server** in arrival order
   (`POST /r/:room/batch`), so there are no collisions and it costs only one round trip.

A real race was caught along the way as well: `putBatch` yields control while `await`ing the chunk read,
and if the user clicks "cancel" at that moment, the DELETE reaches the server before that batch POST ——
the room gets deleted, the subsequent POST then gets a 404, and a **normal cancellation** is reported as a relay error.
The fix: `destroy()` waits for the in-flight batch to finish before deleting the room, and the delivery loop
re-reads the abort criterion on every round. This bug was caught by an end-to-end test using **precise ordering assertions**;
reading the code would not have revealed it.

### About "transferring abroad"

The path is: sender → Cloudflare edge → relay → receiver.
So the latency is the **sum of two legs**, and an overseas transfer is roughly:

```
China → overseas       150–250 ms per leg
Both legs round trip   400–600 ms
→ stop-and-wait impl   1.7–2.5 MB/s (about 7–10 minutes for 1 GB)
→ current window impl  no longer latency-limited, now limited by **bandwidth**
```

**Note: don't extrapolate overseas speeds from "window × chunk ÷ latency" any more** ——
the local measurement already proved that throughput saturates at 28–30 MB/s (see the previous section),
and that is exactly the **steady state of this machine's link to Cloudflare**. The cross-border bottleneck is the peer's
international egress bandwidth, not this tool, and not latency.

So the honest statement is: **how fast it goes depends on how fast the link between you and the relay is**;
the program's implementation is no longer the bottleneck (on the same link it went from 4.7 to about 24 MB/s, close to the saturation point).

> ⚠️ **That conclusion above needs one caveat**: the 24 MB/s was measured with **16 concurrent chunk fetches on the receiver side**
> (`bench-window-sweep.mjs`'s drain defaults to concurrency 16). The browser receiver fetches chunks **strictly serially**,
> and (before the fix) **did not ack** —— see the start of this section. So that number describes the "link's capability",
> not the "feel the user actually gets". The real numbers after fixing acks need to be re-measured on real hardware.

### ✅ Measured and settled (2026-10): serial fetching is the real cross-network bottleneck, and it is worth fixing

The earlier judgement ("the gain only matters on 2.5 GbE, not worth touching") **was wrong** —— it was wrong because
the benchmark only added latency in the sender's direction (see the revoked hypothesis at the end of this section).
Re-measured with a **real receiver page + real Edge + a two-way delayed relay**
(`_lab/bench-recv-rtt.mjs`, 64 chunks × 1 MiB, link capped at this machine's measured 29.5 MB/s), the conclusion flips.

**① On a cross-network link the real page is locked to "one round trip per chunk"** (before the fix)

| RTT | Real page (before, serial) | Theory = chunk size ÷ RTT |
|---|---|---|
| 0 ms | 20.4 MB/s | not limited by latency |
| 50 ms | 8.9 MB/s | 20.0 MB/s |
| **195 ms** | **4.0 MB/s** | 5.1 MB/s |

The median gap between two chunk fetches is **261 ms** (195 ms round trip + about 66 ms of decrypt/hash/write/UI),
of which only about 20 ms per chunk is actual computation —— **the rest is waiting for a round trip**.

**② Stop serialising and the same link fills up** (pure fetching, no decrypt/hash)

| RTT | K=1 | K=2 | K=4 | K=6 | K=8 |
|---|---|---|---|---|---|
| 0 ms | 21.2 | 29.4 | 29.4 | 29.4 | 29.4 |
| 50 ms | 10.8 | 21.8 | 28.8 | 28.8 | 28.8 |
| **195 ms** | 4.4 | 8.7 | 17.0 | **24.5** | 24.9 |

(Units are MB/s. The K=1 column matches "chunk size ÷ (RTT + chunk transmission time)" exactly:
4.4 measured against 4.34 theoretical at 195 ms.)

**③ One hard constraint: a browser opens at most 6 concurrent connections per origin**

The peak "chunk requests held at once" observed on the relay side: K=6 → 6, and K=8 **also only 6**.
So 1 MiB chunks can have at most 6 MiB in flight at 195 ms ≈ a 30.8 MB/s theoretical ceiling, with 24.5–24.9 measured (about 83%).
**To fill a faster link, the chunk size has to grow too**: 2 MiB × 6 = 12 MiB in flight, and the link becomes the bottleneck again.

**④ ✅ Done (2026-10): a bounded receiver prefetch, measured 3.5–4.3×**

The approach is exactly what is described above: a `createPrefetcher` was added to `web/receiver.html`
(it parallelises **only the fetching**; decryption, per-chunk verification, disk writes and acks still happen
strictly in order, in place —— the two semantics "sequential writes" and "ack only after the write" are unchanged).
The default depth is 6 (using the browser's full 6-connection budget), the buffer ceiling is
depth × chunk size = **6 MiB**, and it can be overridden with `&pf=N` in the link (for A/B runs).

Same benchmark, same link (RTT 195 ms, link capped at 29.5 MB/s), end-to-end readings from the real page:

| Configuration | End to end | Fetch phase | Median gap between fetches |
|---|---|---|---|
| Before (serial) | 4.0 MB/s | 4.2 MB/s | 261 ms |
| Depth 4 | 14.0 MB/s | 15.2 MB/s | 61 ms |
| **Depth 6 (default)** | **13.9–17.0 MB/s** | 16.5–19.3 MB/s | 44–48 ms |

The LAN case was measured as well: at RTT 0, 20.4 → 23.2 MB/s (fetch phase 28.4 MB/s, already against the 29.5 link cap).

> ⚠️ **Honest note on noise**: end to end at 195 ms swings by ±20% (depth 4 gave 14.0 once; depth 6 gave 17.0 and 13.9
> on two runs) —— by this project's rules, **that difference is not yet a conclusion**. The reason for defaulting to 6 is the
> much quieter pure-fetch sweep (K=4 17.0 vs K=6 24.5) plus the fact that 6 is exactly the browser's connection budget.
> Settling 4 against 6 would need several runs each and a median.

**⑤ The cost and the approach** (the four properties kept during the implementation, each with tests):
a bounded out-of-order buffer + in-order disk writes + cleanup on cancel, with the memory ceiling applied to the
**size of the pending table** (not to the number of in-flight requests —— that way already-fetched but unconsumed chunks
pile up without limit); `stop()` must wake the `take()` that is waiting and release the buffer.
Tests live in `test/receiver-prefetch.test.js` (11 cases).

### 📏 Measured and settled (2026-10): how much is a bigger chunk worth? —— **2 MiB is the sweet spot, 4 MiB buys nothing**

Two inequalities decide it: `connections × chunk ≥ bandwidth × round trip` (to fill the link), and
`depth × chunk ≤ the memory budget`. A browser gives one origin 6 connections, so the first one is `6 × chunk ≥ BDP`.

**Same benchmark (real page + real Edge + a two-way delayed relay), 256 MiB, link capped at 29.5 MB/s:**

| Chunk size | RTT 0 (LAN) | RTT 195 ms (cross-network) | Median gap between fetches (195 ms) |
|---|---|---|---|
| 1 MiB | 25.2 MB/s | 18.9 MB/s | 45 ms |
| **2 MiB** | **27.5 MB/s** | **26.3 MB/s** | 74 ms |
| 4 MiB | 26.5 MB/s | 25.8 MB/s | 140 ms |

In the cross-network column: 1 MiB needs 5.75 MiB in flight while `6 × 1 = 6 MiB` is **only just enough**
(hence 18.9); 2 MiB provides 12 MiB in flight (twice the margin) → **26.3 MB/s, 89% of the link ceiling**;
the 24 MiB in flight of 4 MiB chunks **adds nothing at all** and only costs memory.
On the LAN the BDP is ≈ 0, so the chunk size barely matters (25.2 / 27.5 / 26.5 is noise).

**A slow link is the counter-example (5 MB/s, RTT 195 ms, 64 MiB):**

| Chunk size | Throughput | Median gap between fetches |
|---|---|---|
| 1 MiB | 4.6 MB/s | 212 ms |
| 4 MiB | 4.6 MB/s | **837 ms** |

**Throughput is identical** (the link is the bottleneck either way), but a bigger chunk coarsens progress,
retransmission and first-byte granularity by 4×: the interface moves once every 0.84 s, losing one chunk means
re-sending 4× the data, and the first chunk only reaches the disk after `chunk ÷ bandwidth`.
**So "bigger is better" is wrong: past the BDP, the extra chunk size only buys a coarser granularity.**

**Conclusion (this machine, this kind of link): 2 MiB is the sweet spot; the default cannot change yet** —— because of the wall below.

**⚠️ Going to 2 MiB runs into the relay's hard limit (that is what actually blocks it)**

One message is one chunk, and the relay's `MAX_MESSAGE_BYTES = 1 MiB + 17`.
That constant **lives inside the Cloudflare Worker the user deployed**: if the client starts sending 2 MiB by default,
**every already-deployed old relay answers 413** (`TOO_LARGE`), and the user has no way to know they must redeploy.
So the chunk size is not a purely local parameter —— changing it requires a
**capability negotiation** for "how large a message can you accept" (protocol §0.1's "only add, never change"
permits a new optional field), with the sender taking `min(what it wants, what the other side declared)`;
an old relay declares nothing → fall back to 1 MiB, and nothing breaks for anyone.

**Two real bugs fell out along the way (both trigger only when the chunk size ≠ the protocol default)**

| Location | Symptom | Root cause |
|---|---|---|
| `src/server.js` (LAN sender) | A chunk larger than the default is **silently truncated**: the disk read fills only 1 MiB and the rest goes out as zero bytes —— the file arrives corrupted, with nothing reporting an error | The resident read buffer was hard-coded as `Buffer.allocUnsafe(PARAMS.chunkBytes)` while the read used `file.chunkBytes` |
| `src/relay/client.js` (relay sender) | It reports "the file changed during transfer (chunk N)" —— the error points at the user's file, while the buffer was simply half the needed size | The same pit a second time, except this one was caught by a `bytesRead !== plainLen` check |

Both now allocate from **the largest chunk actually used in the manifest**. This class of "the branch outside the
default value has never been walked" is exactly what **nothing counts as done until it is measured** exists to catch ——
measuring the chunk size flushed them out.

> The measurement knob is the `FLICKER_CHUNK_BYTES` environment variable (`bin/flicker.js`), deliberately **not** a
> `--chunk` flag: until capability negotiation exists, letting users raise the chunk size only hands them a mute
> "the other side's relay said 413" error.

### ✅ Done (2026-10): capability negotiation —— which makes 2 MiB chunks safe to enable

The measurement above says "2 MiB is the sweet spot", but its precondition is that **the relay can accept it**:
one message is one chunk, and the relay's ceiling lives inside **the Worker the user deployed**.
Changing the default outright means every old relay answers 413. So what was built is negotiation, not a new constant:

| Role | What it does |
|---|---|
| Relay | **Declares** `maxMessageBytes` in `GET /health` and in the room-create response; this project's deployments default to `2 MiB + 17`, while the protocol's guaranteed minimum stays `1 MiB + 17` |
| Sender | Asks for the capability first, then takes `min(what it wants, the declared ceiling − 17)` clamped into `[64 KiB, 8 MiB]`; **if it cannot read the field it uses 1 MiB** (old relay, non-JSON response and probe failure all fall back) |
| Receiver | Takes no part —— the chunk size travels in the manifest's `files[].chunkBytes` (the IV comes from the chunk index alone and the AAD binds only the file index, chunk index, total chunks and plaintext length, none of which depend on chunk size) |
| User | `--chunk=auto` (default) / `512k` / `2m` / `4m`; a value above the relay's ceiling is **clamped down and explained** rather than sent and rejected |

Measured (256 MiB, 195 ms round trip, link capped at 29.5 MB/s, **going through the product's own default path**):

| Configuration | End to end |
|---|---|
| The earliest serial receiver | 4.0 MB/s |
| Prefetch 6 (1 MiB chunks) | 18.9 MB/s |
| **Prefetch 6 + automatic chunk size (negotiated to 2 MiB)** | **25.5 MB/s (86% of the link)** |
| 4 MiB by hand | 25.8 MB/s (no gain) |

Tests: `test/chunk-size.test.js` (9 cases: the policy and the fallbacks), plus the case in
`test/relay-e2e.test.js` that literally transfers once with a 2 MiB-chunk new relay and once with an old relay
falling back to 1 MiB, comparing byte for byte.

### 🔬 Measured (2026-10): where it jams once the link reaches 2.5 Gbps

Re-running the benchmark with the link cap at **295 MB/s (≈2.5 Gbps)** (256 MiB, round trip 0):

| What was measured | Result | Note |
|---|---|---|
| **Pure fetching** (no decrypt, no verify) | **280.8 MB/s (≈2.25 Gbps, 95% of the link)** | The transport is fine: 6 connections × 2 MiB chunks is enough |
| **Real page, end to end** | **105.1 MB/s (≈0.85 Gbps)** | **The bottleneck becomes the receiver's main-thread per-chunk work** |

Broken down: on the real page each chunk does "WebCrypto decrypt + per-chunk `crypto.subtle.digest` (native) +
**the pure-JS incremental whole-file hash** + disk write / UI", and that pure-JS part measures a 252 MiB/s ceiling
while running entirely on the **main thread**, serialised with everything else.
So at 2.5 Gbps "the NIC is fast enough, the relay is fast enough, the sender is fast enough" —— what saturates first
is that single thread inside the browser.

> ⚠️ Neither number is "the receiver's ceiling" yet: the 105 MB/s run still has this benchmark's own Node relay in the
> path (every 2 MiB message goes through several memory copies). **To measure it properly the relay has to leave the
> path** —— and that run **has since been done**: see "✅ Measured (2026-10): direct LAN, the real page, no relay in the
> path" below. This is written down honestly so that nobody later mistakes 105 MB/s for the product's ceiling.

**The levers, in order, if this is ever pushed further:**

1. **Move the incremental whole-file hash into a Web Worker** (today it is on the main thread at 252 MiB/s, blocking everything);
2. Touch the DOM less per chunk (batch progress updates every N chunks);
3. Adapt the chunk size to the BDP on high-latency links (`6 × chunk ≥ bandwidth × round trip`: 2.5 Gbps × 195 ms ≈ 57.5 MiB,
   i.e. ~10 MiB chunks would be needed, and bigger chunks cost both memory and granularity);
4. For 2.5 Gbps across networks, the browser's hard 6-connection limit becomes a constraint in its own right.

### ✅ Measured (2026-10): direct LAN, a **real page**, with no relay in the path

Those two numbers left one doubt: "how much of that 105 MB/s is this benchmark's own relay?" So this set was added
(`_lab/bench-lan-page.mjs`): a real CLI sender + real Edge + **the real page talking straight to the sender's HTTPS**,
with no relay involved at all. 256 MiB, headless:

| Configuration | End to end | Fetch phase |
|---|---|---|
| 1 MiB chunks, prefetch 6 | 117.4 MB/s | 130.3 |
| 2 MiB chunks, prefetch 6 (default) | 128.6 MB/s | 135.4 |
| 4 MiB chunks, prefetch 6 | 132.5 MB/s | 147.9 |
| 2 MiB chunks, **prefetch 1 (serial)** | 127.6 MB/s | 137.8 |
| 2 MiB chunks, **over the real NIC (2.5 GbE)** | 123.0 MB/s | 140.3 |

> The disk write here uses a **stand-in** (the native save dialog cannot be driven headless): `showSaveFilePicker` is given a
> **counting fake handle**, so the page still goes through its own streaming branch and the bytes are merely counted and dropped.
> This set therefore does not verify what lands on disk —— content correctness is guaranteed by the page's own per-chunk and
> whole-file hashes (any mismatch stops it on the error screen, which the script reports honestly). The script says so in its output too.

**The numbers say three things:**

1. **The bottleneck is neither the NIC nor the sender, but the page's main-thread per-chunk work.**
   Going over the real NIC (2.5 GbE, 295 MB/s theoretical) is only 4% slower than loopback, and the sender itself reaches
   250+ MiB/s on loopback (`bench-lan-parallel.mjs`: fetch-only 253.5, fetch+decrypt+hash 174.7).
2. **Prefetch makes no difference on a LAN** (127.6 vs 128.6) —— loopback round trips are ≈0, there is no latency to hide,
   so all the time goes into the consumer loop's CPU. That matches "prefetch was built for the cross-network case" exactly.
3. **Chunk size barely matters** (117 → 128 → 132) —— again pointing at **per-byte** CPU rather than per-chunk overhead.

**So the real ceiling for the receiver on this machine is ~130 MB/s ≈ 1.04 Gbps**, set by that single serial consumer loop on
the main thread, of which the pure-JS incremental whole-file SHA-256 (252 MiB/s measured alone) is roughly half.
The browser's own fetching is far faster than that (280.8 MB/s measured with the relay's pure-fetch mode).

> **Correcting the wording of the previous section**: at 2.5 Gbps the relay-path "real page 105 MB/s" is about 20% below the
> 128.6 measured here, i.e. **the relay is the small share and the main-thread CPU is the large one**. The caution there was
> right, and these numbers now separate the two shares —— which is exactly the point of this section: getting the benchmark's
> own overhead out of the conclusion.

### ✅ Done (2026-10): moving that main-thread CPU away —— LAN 123 → 208.7 MB/s

Those readings point at the ceiling very clearly: **the bottleneck is the per-chunk work on the receiver's main thread**.
So two things were done (both in `web/receiver.html`):

| Change | Why |
|---|---|
| **The incremental whole-file hash moved into a Web Worker** | It is the biggest single piece of CPU on the main thread: pure-JS SHA-256, measured at 252 MiB/s (about 8 ms for a 2 MiB chunk), and it has nothing to do with fetching or writing. Per-chunk verification already uses `crypto.subtle.digest` (native, off the main thread), so this was the only item that needed moving |
| **Progress repaints throttled to once per 100 ms** | It used to write 5 DOM nodes per chunk (two widths plus three text nodes). At 2 MiB chunks and 300 MB/s that is 150 style/layout updates per second; now at most 10, with one forced repaint at the end so the display still reaches 100% |

**Results** (256 MiB, real page, no relay in the path; same 2.5 GbE):

| Configuration | End to end | Fetch phase |
|---|---|---|
| Before (main-thread hash + per-chunk UI) | 123.0 MB/s | 140.3 |
| **After** | **205.4～208.7 MB/s** | **293.2～300.2** |

A fetch phase of 293 MB/s ≈ **2.35 Gbps**, already against the 2.5 GbE line rate (295 MB/s) —— in other words **the transport
half is essentially saturated**, and the remaining gap (293 → 209) is the decryption, per-chunk verification and disk writes
that still happen on the main thread. The cross-network path benefits too: at a 195 ms round trip with the automatic chunk
size, 25.5 → **26.4 MB/s**.

**A few implementation details that must be remembered together** (all guarded by tests):

- **The Worker's source is assembled from the page's own implementation** (`K256` reconstructed from the runtime array and
  the class body taken from `Sha256.toString()`) —— a hand-copied second implementation would drift sooner or later, and its
  symptom is "the file is perfectly fine but verification fails". `test/receiver-hash-worker.test.js` actually runs that
  source and compares it with `node:crypto` byte for byte.
- **Zero-copy transfer is allowed only on the streaming-write path**: the Blob fallback keeps every chunk's *view* until it
  assembles the Blob at the end, so transferring that underlying buffer to the Worker would move the data away, producing
  **a passing verification and a corrupt file**. Hence `update(pt, { transferable: streamingSink })`, where the switch is
  decided by the sink.
- **No Worker means falling back to the main thread** (CSP, old browsers, creation failure) —— a feature must not disappear
  because of an optimisation. That is why the LAN path's CSP gained `worker-src blob:` (still limited to this page's own blobs).
- **One Worker is shared by the whole page**: creating one per file is wasteful and leaves a pile of `blob:` objects behind ——
  measured: they even fooled the rehearsal script's probe once (it took 8 Worker scripts for "8 extra files received").

**What is left**: the main thread still decrypts (WebCrypto), verifies each chunk (`subtle.digest`, native) and calls the sink.
Going further means parallelising those too (multiple consumer pipelines), which is an order of magnitude more complex and
riskier —— and by the current numbers (LAN at line rate, cross-network at the link) **that gain is not worth the risk**.

**⑥ The benchmark itself stepped into three pits** (recorded so they are not repeated)

1. **The ack ended up on the hot path**: awaiting one ack inside the concurrent fetcher costs a whole extra round trip, so
   "concurrency 8" looked exactly as fast as "concurrency 1" —— **the page made this very mistake once**, and the benchmark made it again.
2. **The sender destroys the room when it times out**: it never sees acks, so it deletes the room and long measurements start
   reporting `NO_ROOM`; only filling the room directly from Node, with no sender involved, gave a clean measurement.
3. **A timer was left running**: in prefill mode there is no sender, so the teardown code reading `sender.cli` threw and skipped
   `clearInterval`, and the script ran through every case without ever exiting —— it hung for nearly an hour and printed nothing.

> ⚠️ **The "rejected hypothesis" at the end of this section should be revoked.** Back then
> `bench-recv-concurrency.mjs` measured "serial is the fastest (29.3 MB/s)" because that benchmark **only added latency in the
> sender's direction**, so the receiver's GETs returned with zero latency —— it could not measure "one round trip per chunk" at all.
> With two-way latency, **the original worry was right**: serial means one round trip per chunk, and that is what locks the
> cross-network case.

## 6. Explicitly **not** doing (so nobody asks later)

| Not doing | Reason |
|---|---|
| Auto-deleting the source files after transfer | A mistake can't be undone, and a transfer tool should not be the one to do it |
| Cloud storage / offline transfer | Then it wouldn't be "one-shot" any more |
| Many-to-many group sending | It would break the simple "two computers, one password" model |
| Remembering the password | It violates the one-shot principle; any persistence weakens the core promise |
| Telemetry / usage statistics | This project should not have any |
| Plugins injecting arbitrary DOM into the page (the "slot UI") | It would mean changing the page structure, and the **risk outweighs the benefit**; page plugins keep the single `page/actions` button slot (decided 2026-10; previously listed in `插件.md` §11) |
| **Cross-session resumption** (close the page, come back later and continue) | It would require **relaxing three promises already written into the docs**: (1) no Cookie / localStorage / IndexedDB —— but "remember which chunk we got to" can only live in IndexedDB (`行为与运行.md` §7); (2) a one-time link dies on its first visit —— but reopening the page means letting the same token work once more; (3) the keys are released with the page —— but continuing to decrypt needs the session key kept (or the user retyping the password). On top of that it is **only possible on Chromium** (Firefox / Safari keep data in memory only) and it has to race the **relay room's 15-minute TTL**. **Decided 2026-10: not doing it**, reasons recorded in §2 (above) |

## 7. Relationship to similar tools (notes from the competing-tools research)

### How it started: a judgement that needed correcting

In 2026-10 there was a line of judgement: "there shouldn't be any file transfer tool like ours, so competing tools should be few."

**That judgement was wrong**, and wrong in a way worth recording —— because it would directly skew the messaging after open-sourcing.
Actually looking into it turns up dozens of similar products, several of which have been around for years with far more users than us.
If the README said "there are no similar tools", anyone knowledgeable would see through it at a glance, and the credibility would be the price.

### Research notes (2026-10, sources at each link)

| Category | Representative | Where it sits | The most crucial difference from us |
|---|---|---|---|
| Browser P2P, zero install on both ends | [PairDrop](https://github.com/schlagmichdoch/PairDrop) (the successor to Snapdrop), [FilePizza](https://github.com/kern/filepizza) | Most similar to our **receiver**, [opens in a browser and just works, nothing to install](https://www.makeuseof.com/using-pairdrop-in-browser-windows/) | Uses a WebRTC DataChannel, receiving into memory and assembling a Blob. PairDrop's issues include [a limit on sending 200 MB to an iPhone](https://github.com/schlagmichdoch/PairDrop/issues/294) —— this is exactly where "tens of GB" parts ways |
| Command line + relay | [croc](https://github.com/schollz/croc), [magic-wormhole](https://github.com/magic-wormhole/magic-wormhole) | Mature, cross-platform, supports resumption, more users than us | magic-wormhole uses **SPAKE2 (a real PAKE)**; we do not. See "gaps to admit honestly" below |
| LAN transfer (phones included) | [LocalSend](https://github.com/localsend/localsend) | Phone↔computer is its main scenario | [Both ends must install an App](https://wiki.archlinux.org/title/LocalSend); we require zero install on the receiver, and the price is that a phone can't be the sender |
| Encrypt, upload to a server, download | [Wormhole.app](https://wormhole.app/), [Send](https://github.com/timvisee/send), cloud drives | The least-effort experience: the sender can close the page once the upload finishes | It is **store-and-forward**: Wormhole.app has [a 10 GB cap and links that expire after 24 hours](https://www.blogdumoderateur.com/tools/wormhole/), and the data must land on its servers first (encrypted). We require both ends to be online at the same time, but the relay only forwards in memory |
| New-generation P2P desktop apps | [dropwire](https://github.com/muhamadjawdatsalemalakoum/dropwire) (based on iroh) and others | End-to-end encryption + resumable; engineering-wise ahead of us | Both ends must install a desktop program; our receiver is a browser |

> For a sense of scale: one French review site lists
> [19 alternatives](https://www.blogdumoderateur.com/tools/productivite/transfert-fichiers/) under the "file transfer" category alone;
> on HN, "the best FOSS file sharing tool" is [a topic discussed year after year](https://news.ycombinator.com/item?id=38876954).

### Our real difference: all four have to hold at once

| Difference | Why competitors can't (or won't) do it |
|---|---|
| Zero install on the receiver **and** writing to disk while receiving | The WebRTC route has to receive into memory first; streaming writes need Chromium's File System Access API, and the entire path (HTTP + chunking + incremental hashing) has to be designed for it |
| The two ends share only a **password** | No account, no room number, no "upload first, download later". The room name itself is derived from the password; without the password you can't even find the room |
| One-shot + **the relay never writes to disk** | The relay's in-memory queue has a 15-minute TTL. Commercial products rely on "storing it" to offer "the other side can fetch it while offline", which is not the model we want |
| Zero runtime dependencies + single file + **a self-hostable relay** | "Host it yourself, trust no company" is a no-go area for business models, and it is also the one part of us that cannot be copied |

**The decision standard is written here**: these four are the reason "it is still worth existing alongside similar tools".
When adding features later, if a change weakens any one of them (say, introducing cloud storage for a better experience,
or giving up password-derived room names so rooms are easier to remember), it should be rejected —— see Chapter 6, "explicitly not doing".

### Gaps to admit honestly (more important than "we're the best")

| Gap | Current state | Corresponds to |
|---|---|---|
| A phone can't be the sender | We can't do LocalSend's / PairDrop's main scenario | item 7 |
| Only Windows has been measured | The first batch of issues after open-sourcing will certainly come from macOS / Linux | item 8 |
| No code signing | SmartScreen will block it, while most similar tools ship signed installers | item 11 |
| **Not a PAKE** | Shared password + PBKDF2 600k rounds + HKDF. A weak password → offline cracking is feasible; the default four-word passphrase has enough entropy, and a weak password the user sets themselves is the weak point (`使用手册.md` §10.5 already states "weak passwords are not defended against") | recorded as a **known weakness**, see `SECURITY.md` |
| No third-party audit | "End-to-end encrypted" is currently only our own claim | Open-sourcing is itself for that purpose; but the audit is still missing |
| Chunk-granularity resumption is impossible | `createWritable()` writes sequentially and truncates each time; at the browser API level there is no "continue from byte N" | item 5 |

### So the messaging at open-source time (already reflected in the README)

1. **Don't write "there are no similar tools"**; write clearly that "this is not the only choice, we are the choice at one particular intersection",
   and **list similar tools by name** (`README.md` / `../README.md` each have a section "where it stands next to similar tools").
2. **Include a table of "when you should use another tool instead"** —— phone as the sender, the other side is offline, you want anonymity,
   you want audited cryptography, you want cross-session resumption, you don't even want to download 90 MB: these six cases point clearly to other tools.
   Actively turning away users this isn't for is far cheaper than explaining afterwards that "actually we're not right for you".
3. Write the gaps into the known weaknesses in `SECURITY.md`, not only in the roadmap —— people assessing security only read that one.

## 9. Two protocol problems caught while writing the rehearsal script (2026-10)

While writing `_lab/rehearsal-lan.mjs`, I ran the full LAN flow with a **real browser** for the first time,
and caught two problems that none of the previous tests could see.

### ① A real bug: the page's handshake MAC was missing the domain-separation prefix → LAN mode could not connect at all

**Symptom**: a real browser opens the LAN link and the correct password is entered, but the page forever shows "passwords don't match".
The probe shows `POST /api/auth/finish → 401`.

**Cause**: the page's `localTransport()` signed the challenge itself
(`sign('HMAC', keys.auth, challenge)`), while the sender computes, per the suite,
`HMAC(K_auth, "flicker/1/recv\n" ‖ challenge)`. The two can never match.

**Why the tests didn't find it**: `test/e2e.test.js` uses the Node-side receiver, which was **written to the protocol**,
while this page's handshake was **written a second time** —— "two implementations" again.
All 390-odd cases were green, because **not one case ever executed that handshake code in the page**.

**The fix and its criteria**:
- The page gains `macInput(role, challenge)`, used in both the `recv` and `send` directions
- Two new cases in `test/receiver-page.test.js`: **pull that function out of the page and really run it**,
  comparing against the suite's `receiverMac`/`senderMac` on **the actual MAC values**; and pin the prefix's literal value down
- Verified in reverse: change the call site back to "sign the challenge directly" and the cases go red immediately
  (which also turned red the criterion for "changed the page but forgot to regenerate the relay page" —— two guards working)

> **Lesson**: another example of "all tests green but the feature is broken". The criterion must sit on
> **the code the real client executes**; testing only "another implementation written to the protocol" is not testing at all.

### ② Documentation and implementation disagree: the MAC construction in `PROTOCOL.md` §4.5 was never implemented

Checking it turned up three things each saying something different:

| Source | MAC input |
|---|---|
| `PROTOCOL.md` §4.5 / appendix B | `"flk1-recv"` ‖ `"FLICKER/1"` ‖ `"recv"` ‖ nonce (`mac_i` also concatenates `SID`) |
| `src/suite/flicker1.js` (**the actual wire format**) | `"flicker/1/recv\n"` ‖ nonce |
| `web/receiver.html` (before the fix) | nonce (nothing else at all) |

The documentation's version is **stronger** (explicitly binding the negotiated `suite_id`, plus a commitment to `SID` inside `mac_i`),
but it was **never implemented**: the current `SID` is generated randomly after authentication, so implementing the documented version would mean making `SID` derivable,
which is a wire-protocol change across both ends plus the page.

**This time I did not "follow the protocol" and just change it**, for these reasons:

1. It is a **wire-format change**, not a bug fix —— both existing ends plus the page all work the implemented way
2. The documentation version's extra strength (`suite_id` binding) **partly exists** in the implementation: the prefix `flicker/1/` already implies the suite name
3. There is really only one decision point: **whether to change the protocol once for the `SID` commitment and explicit suite binding**

**What was done about it** (the documentation must not mislead people before that decision):
- `PROTOCOL.md` §4.5 gained a prominent "differences from the current implementation" paragraph, telling third-party implementers explicitly
  to interoperate using **the construction in the code block**, and listing what each of the two differences implies
- The decision itself stays here; neither side was quietly changed

**Recommendation**: **leave it alone** before the release (the status quo works, is self-consistent, and is tested), and treat it as candidate content for `FLICKER/2` ——
at which point "switch to a real PAKE" can be considered together with it (see `SECURITY.md` §5.6);
since the handshake has to change anyway, one clear change is safer than two.

## 10. Three things from the user's real-world testing (2026-10, all handled)

The user took it for a real test run (transferring files over the LAN) and reported three things. **All three were real**,
and the first was the most serious class of all —— "clicked and nothing happened".

### ① "The sender's destroy does nothing, clicking has no effect" —— two bugs stacked together

**bug A: the button only changed the text, it didn't destroy anything.**
`gui.js`'s `destroyNow()` used `if (!S.run && …)` before setting `phase='destroyed'`.
But `S.run` exists as soon as a transfer starts —— so **it did nothing at exactly the moment this button mattered most**.
And even when the condition held, it only changed the phase text to "destroyed"; the session, the server, the keys and the certificate were all untouched.

The fix: the `onReady` callback was already handing us the `session`, it had just **been thrown away before**.
Now the handle is kept, and destroy calls `session.destroy()` directly; `runSend`'s `waitForCompletion`
checks `session.destroyed` every 200ms, so it immediately runs the whole destruction chain and hands the manifest back.

**bug B (deeper): `/api/start` only responds after the transfer finishes.**
In `startTransfer()` there was `await S.run`, and the HTTP handler only responded after `await startTransfer(...)` ——
so one request just hung there until the transfer ended (minutes, for a large file).
The page polls `/api/state`, so it looked normal, and that is why it never surfaced.
This was also the most time-consuming part of the investigation: **the test script hung on `api('start')` for 8 seconds with no response**,
and at first I thought the destroy hadn't taken effect.

The fix: move the finishing logic into `S.run.then(...)`, so `startTransfer` returns immediately.

**Criteria** (`test/gui.test.js`): go through the same interface the page button calls, and assert
that the phase really becomes `destroyed`, that the message is "destroyed as you requested", that the destruction checklist includes zeroing / closing the server / invalidating the link,
**and that the link really can't be connected to any more** (this is the substantive criterion for "destroyed"), and finally that a reset lets you transfer once more.

### ② "The receiver shows an insecure warning" —— the behaviour is right, but **the sender said nothing at all**

The certificate is installed only on the **initiating** machine, so the receiving machine necessarily sees an "insecure" warning the first time it opens the page.
That is a design trade-off (installing an unknown root certificate on someone else's computer is far more dangerous than clicking "proceed" once), **not a bug**.

The problem was the hint text: the terminal line "the other side will see one security prompt the first time" sat under `if (!trusted)`,
and `trusted` says **whether this machine has the certificate installed** —— the sender has it installed (trusted=true),
so that hint was **not printed**; the sender assumed everything was fine, while the receiver stared at a red warning with no idea what to click.

The fix: print it unconditionally, and give the exact button text (「Advanced → Proceed」);
the GUI's waiting screen got the same hint; `使用手册.md` §10.3 used to say "the other side won't see a red warning when opening the link"
(which only holds on the initiating machine) and was changed to a table of "which computer sees what", explaining why it is deliberately not made "nothing for the other side to click either".
New §8.4.1 (what to do when you see insecure) and §8.4.2 (what "allow modifying files?" means) were added.

A criterion was added to the rehearsal script: the sender's output **must** contain both "insecure" and "proceed" —— missing either one counts as a failure.

### ③ "What it sent wasn't an exe, it was flicker-0.1.0-source.fkz" —— the behaviour was right, the interface was lying

The user was running the source version (`node bin/flicker.js --gui`); the source form can only send the source package `.fkz`,
and the other side needs Node installed first —— that is **correct behaviour**. But the line of explanation on the interface had always been
"the other side can also send the files on to someone else once received, no need to download anything", **one sentence shared by both forms**:
in source mode that sentence is false (the other side gets a `.fkz` that simply won't double-click).

The fix: `giftNoteForUser()` gives two different explanations based on runtime facts (`detectSelf()`);
the single-file version says "what is being sent is this program itself, double-click to run", while the source version says plainly "Node.js 24+ must be installed first;
if you want the other side to just double-click, use the single-file version". The test asserts that this sentence must be truthful.

> **Taken together, these three say one thing**: all those tests and rehearsal scripts covered **the protocol and the data plane**,
> while the user's first real use of the interface ran into **the interface state machine** and **the hint text**.
> Both bugs, in `/api/start` and in `destroyNow`, were of the "looks like it's working" kind ——
> the page's polling hid the hanging request, and the button's mere presence hid the fact that it did nothing.

### ④ A fourth one I found myself while re-checking: refusing write permission was silently swallowed

The user asked "what does the native save dialog mean", and reading that code turned up a problem **nobody had reported, but which is more dangerous**:

```js
// the way it used to be written
} catch (e) {
  if (e && e.name === 'AbortError') { return cancelled = true, finished(true); }
  dirHandle = null;    // the user refused, or the environment doesn't support it → degrade to asking per file
}
```

Three **completely different** failures were merged into a single "degrade":

| The actual situation | Before | Now |
|---|---|---|
| The user clicks 「cancel」 (AbortError) | clean abort ✓ | unchanged |
| The user clicks 「deny」 (NotAllowedError) | **silently falls back to memory mode** | see below |
| The environment doesn't support it | falls back ✓ | unchanged |

Why the "deny" row is dangerous: the browser **does support** streaming writes, so the warning
"your browser doesn't support writing to disk while receiving" **does not** trigger; but permission was not granted, so the page actually
**receives everything into memory and then assembles it**. Small files survive that, but tens of GB will blow up the browser **halfway through** ——
and by then the user has waited a long time and has no idea what they did wrong (they only clicked the wrong button).

**The fix** (two ways, both based on the same threshold constant `MEMORY_MODE_LIMIT`):

- **Small files** (< about 900 MB): continue, but change `#go-note` to a warning style,
  stating clearly "you did not allow writing files just now, so what follows will be received into memory first and saved afterwards"
- **Large files**: **stop outright** and report `NO_WRITE_PERMISSION`, with copy telling the user
  "click retry and choose allow in the folder window" —— **stopping now beats crashing halfway through**

**Criteria**:
- `test/receiver-page.test.js`: the three failures must be distinguished separately; the large-file branch must throw
  `NO_WRITE_PERMISSION`; the small-file branch must warn; both paths must share the same constant;
  the error code must be registered in `KNOWN` (otherwise the interface degrades to "unknown error" and the key guidance is invisible);
  and it **must not be marked fatal** (one click on "allow" makes it succeed, so a retry button is needed).
  Verified in reverse: change this back to the old form and the cases go red immediately.
- `_lab/rehearsal-lan.mjs` gained rehearsal three (run by default): make the folder window
  throw `NotAllowedError` in a real browser, then assert that the page **really does show the warning**, and that **the file still transfers completely and byte-for-byte identically**.

> The "large files must warn" criterion in `test/protocol-facts.test.js` was changed along the way:
> it used to pin the literal `900 * 1024 * 1024`, so my change extracting it into a constant **turned the test red**.
> A criterion should watch behaviour (compare against the constant + the constant's value being in a sensible range), not the literal value ——
> otherwise an improvement like "extract the magic number into a constant" gets pushed back by the tests.

## 11. The most serious one: the single-file artifact **is not single-file at all** (2026-10, found by the user's real testing)

### Symptom

The user copied `dist/flicker-0.1.0-windows-x64.exe` to the desktop and double-clicked it:

> "CMD pops up for a moment and immediately disappears" (the same when run as administrator)

Running the same exe inside the project directory was **completely normal** —— including my own smoke script and the whole 415-case suite.

### Root cause

**The artifact contained only 5 modules; the rest were looked up on disk at runtime.**

```
5 modules before bundling: assets.js · suite/flicker1.js · destroy.js · rate.js · bin/flicker.js
```

The other modules (`gui.js`, `run.js`, `server.js`, `prepare.js`, `trust.js`, `relay/*` …)
were all loaded through **dynamic `import()` with relative paths**, and the bundler only follows **static** imports through the module graph ——
so those `import('../src/gui.js')` calls were left in the artifact untouched.

At runtime the single-file artifact has no `src/` on disk, so it resolves relative to the exe's directory:

| Where it runs | `import('../src/gui.js')` resolves to | Result |
|---|---|---|
| The source directory (`dist/`) | `D:\闪传\src\gui.js` | **happens to exist** → everything normal, all tests green |
| The desktop | `C:\Users\…\src\gui.js` | `Cannot find module` → the console flashes and disappears |

**All verification was done inside the source tree**, so this problem could hide indefinitely.

### The fix (layer upon layer, each one forced out by a build-time self-check)

| Layer | Problem | Fix |
|---|---|---|
| 1 | 5 dynamic imports with relative paths (`flicker.js`, `gui.js`) | All changed to **static imports** |
| 2 | The bundler refuses on seeing duplicate names: `OID_SERVER_AUTH` / `selfCheck` / `support` / `toPem` / `probe` **each had two implementations** | Each was consolidated into one: the OID constants moved into `x509.js`; trust's "throw if not qualified" wrapper was renamed `selfCheckOrThrow` (a different contract shouldn't share a name anyway); the `support()` in `session-cert.js` was dead code and was deleted; `toPem` is kept only in `x509.js`; the private `probe` in `session-cert-check.mjs` was renamed `tlsProbe` |
| 3 | The CLI section of `session-cert-check.mjs` had **top-level await** | Wrapped in `runHandshakeSelfCheck()` (not allowed in a CommonJS artifact) |
| 4 | After concatenation `import * as D from './x509.js'` left `D` undefined | The bundler generates a namespace object `const D = { toPem, SEQUENCE, … }` |
| 5 | Built-in modules had only a small hard-coded fallback require list | **Derive the bindings from the source**: named import → `{ a, b }`, default import → `const path = …`, with `as` → `{ original: local }` |
| 6 | The `as` alias on a relative import (`version as pkgVersion`) broke the link | Add `const pkgVersion = version` (needed at the entry too; a test caught that one) |
| 7 | `createServer` came from both `node:http` and `node:https` | Renamed in the source to tell them apart (`createHttpServer`); the bundler now refuses to build outright on the same name from different sources |

In the end the artifact went from **5 modules to not missing a single one (23 modules, 314 KB)**.

### Criteria (three, all verified to be able to fail)

1. **The bundler refuses dynamic imports with relative paths** (`gen/bundler.mjs`) —— the build fails on sight,
   explaining that "there is no source on disk at runtime". Verified in reverse: create a dynamic import and the build fails immediately.
   The pit of "a dynamic import mentioned in a comment tripping its own documentation" was handled along the way too.
2. **Smoke must run outside the source tree** (`gen/smoke-sea.mjs`) —— all the checks used to run directly inside `dist/`,
   and `dist/` is inside the source tree. Now **every artifact is copied to a temp directory first**, then
   `--version` / `--help` / `send --dry-run` / `--assets` /
   **whether the GUI comes up (12 seconds without exiting)** are verified. That last one is exactly the criterion for the path the user double-clicks.
3. **6 new bundler tests** (`test/bundler.test.js`): a dynamic import must fail, a comment must not be misjudged,
   an `as` alias must get a binding, a namespace must generate an object, the same name from different built-in modules must fail,
   and built-in bindings must really be generated. One of them, "allow and skip node: built-in modules", said
   *"built-in modules are globally available"* —— **that belief was itself half of this bug**, and it has been rewritten to the new contract.

> **Lesson**: this time it wasn't "some branch wasn't tested", it was that **the entire verification environment was inside the source tree**.
> For anything to do with "the artifact / deployment form", verification must happen in **the environment where it is actually used** ——
> for a single-file artifact, that means "copy it to another directory and run it". That is now written into the smoke script.

**The result after the fix (confirmed by the user's real testing)**: copy `dist\flicker-0.1.0-windows-x64.exe` to the desktop and double-click it,
and the GUI comes up normally —— the user's words: "it's fine now". Together with the earlier confirmation that "the native save dialog is normal",
the two human-only stretches of release criterion ② are closed too.

### Why there is a "pairing check" (`gen/check-doc-pairs.mjs`)

Two copies of a document drift by nature: **nobody ever reads both** —— Chinese readers read the
Chinese one, English readers the English one. Change a sentence in one and forget the other, and
no one notices. That is the same class of problem as the "two implementations" this project keeps
getting burned by, so it gets the same treatment: turn it into a machine criterion. It checks two things:

1. **File names match one-to-one** (it names the side that is missing)
2. **Structure matches**: the number of `#`/`##`/`###` headings, code fences, and table rows ——
   a translation may reword, but it must not drop a section, a code block, or a table row

> ⚠️ **Deliberately not comparing body line counts**: translations differ in length by nature, and
> pinning line counts only pushes people to pad. Structure parity plus valid links
> (`check-doc-links.mjs`) is the reasonable approximation of "the two say the same thing".
> Measured: all 10 pairs match structurally (verified pair by pair during translation, not by luck).

The check runs in `npm run check`, in CI, and in `test/docs-pairing.test.js`
(so `npm test` catches it too —— "added a Chinese doc, forgot the English one" is exactly what
happens during development).

### The gift: EXE + source + docs (`src/gift.js`)

It used to send **one** file: the exe in single-file mode, the `.fkz` source pack in source mode.
Now single-file mode sends **two**:

```
🎁 Bundled program: flicker-0.1.0-windows-x64.exe (94 MB)
🎁 Bundled source and docs: flicker-0.1.0-source.fkz (1.1 MB)
```

**The key implementation point**: at runtime a single-file artifact has **no `src/` and no docs on
disk**, so it cannot pack a source archive on the spot. So the build (`gen/build-sea.mjs`) packs the
source plus both documentation sets into `source-pack.fkz` and **embeds it in the artifact**
(36 files, 20 documents, ~1.1 MB —— which is why the artifact grew from 89.9 MB to 91.0 MB).
At runtime it is read from the embedded asset and handed to the other side —— so **the artifact is
complete wherever it is copied**, with no dependency on the source tree. Same lesson as chapter 11.

- There is only one packing implementation (`buildSourcePack()`), shared by the build and by source
  mode, so the two cannot produce different archives
- If not a single document made it into the pack → **a hard error**, rather than silently sending a
  "source pack without docs"
- An older artifact without that asset → send the program alone and **say so clearly**
  (silently sending less than promised is worse than an error)
- Source mode still can only send the source pack (it runs off the source on disk; it cannot
  conjure an exe) —— and the sentence shown in the UI is written per runtime fact, not shared
  (see `giftNoteForUser()` in `gui.js`)
