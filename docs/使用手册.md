## 1. What Flicker is

Flicker is a **one-shot** file transfer tool.

- You run it on your own computer, pick the files, and set a password
- The other side **installs nothing**: they open a link in a browser and type the same password
- The files go straight across, and when it is done the password, the keys, the link and the server are **all destroyed immediately**

How it differs from a cloud drive or from sending files over WeChat:

| | Flicker | Cloud drive / WeChat |
|---|---|---|
| Whose server the files pass through | LAN: **nobody's**; across networks: through a relay, but **only ciphertext** — the relay cannot decrypt it and cannot see the file names | Someone else's server, and readable in the clear |
| Are the files still there afterwards | **No** — the server is closed, the keys are zeroed, the room on the relay is destroyed | They stay on someone else's server forever |
| Do you need an account | No | Yes |
| Is there a size limit | No (only the limit of your disk) | Usually yes |
| Does the other side have to install anything | **No** | No (but an account is required) |

> **That sentence about across-networks mode is worth reading twice**: the relay handles **every single byte** of your files,
> but those bytes are AES-256-GCM ciphertext, and the key exists only on your computer and the other side's.
> The relay can tell that "someone is transferring, roughly this big"; it cannot tell "what is being transferred".
> If you do not accept even that, host your own relay (`中继部署.md` — one command deploys it to your own account),
> or use LAN mode instead (your data never leaves the local network).

## 2. Installing

### 2.1 Which side are you?

| What you want to do | Do you need to install anything |
|---|---|
| **Just receive files** | ❌ **Nothing at all.** They give you a link and you open it in a browser |
| **Send files to someone else** | ✅ You need Flicker |

### 2.2 How to install on the sender (choose one of three)

**Option A: single-file build (recommended, simplest)**

1. Download the file for your system from [GitHub Releases](https://github.com/). Each platform ships **two**:
   **the `.zip` is the recommended download** (62% smaller: 94 MB → 36 MB) and unpacks to the executable below;
   if you would rather not unzip, download the executable itself (tens of MB more).
   - Windows: `flicker-x.x.x-windows-x64.exe` (or the same name with `.zip`)
   - macOS: `flicker-x.x.x-macos-arm64` (Apple silicon) or `-macos-x64` (Intel)
   - Linux: `flicker-x.x.x-linux-x64`
2. Put it in any folder and **double-click to run** (on macOS/Linux the first time may need right-click → Open, or `chmod +x`)
3. Done. **No Node.js and no installation process**

**Option B: from source (needs Node.js)**

1. Make sure the computer has Node.js 24 or newer:
   ```powershell
   node --version      # 应该显示 v24.x.x 或更高
   ```
   If it does not, download and install it from <https://nodejs.org> (pick the LTS version)
2. Download the project folder and **double-click `启动.cmd`** (Windows) or `启动.command` (macOS)
3. If double-clicking does nothing, Node.js is not installed properly

**Option C: install with npm (for people who live in a terminal)**

```powershell
npm install -g flicker-transfer
flicker --gui
```

### 2.3 The first run shows a firewall prompt

**On Windows, the first run pops up a "Windows Security Alert" asking whether to allow network access.**

This is normal, and it is necessary — Flicker has to listen on a network port so the other side can connect.

- **Please tick "Private networks"** (home/office networks)
- "Public networks" can be left unticked (unless you really are going to use it on a public network)
- Then click "Allow access"

> ❌ If you click "Cancel", the receiver cannot connect and will sit on "connecting" forever.
> To fix it, run this once as administrator: `netsh advfirewall firewall add rule name="Flicker" dir=in action=allow protocol=TCP program="<闪传的完整路径>"`,
> or go to "Windows Security → Firewall & network protection → Allow an app through firewall" and tick it by hand.

**macOS**: the first run asks "Do you want the application to accept incoming network connections?" — choose "Allow".
**Linux**: usually no prompt; if you use `ufw`/`firewalld` you have to open the port yourself.

## 3. Three connection modes: pick one first

For the two computers to connect, **at least one** of the following has to hold. The program probes for this automatically, but you need to know which case you are in.

### Case 1: both computers are on the same WiFi / the same router ⭐ most recommended

- **Advantages**: the fastest (tens to hundreds of MB per second), no internet needed, no extra configuration, nothing to deploy
- **How to tell**: both devices are on the same WiFi name, or on cables from the same router
- **Typical cases**: two computers at home, one office network, a phone on the home WiFi transferring with a computer
- **What the sender does**: see §4 or §5, **no extra options needed**

### Case 2: the two computers are in different places (one at home, one at the office or elsewhere)

- **Requirement**: first **deploy a free relay once** (about 3 minutes, see §5.5)
- **Cost**: free. One transfer uses only a single-digit number of requests, and the free allowance is 100,000 a day
- **What the sender does**: add `--relay=https://你的地址.workers.dev`

### Case 3: one side has a public IP

- Most home broadband **does not** have a public IP (the ISP puts you behind a large private network, which is called CGNAT); the program detects this automatically and tells you
- If you do have one, you can use `--public=你的公网IP:端口` and no relay is needed
- **How to tell**: the program probes automatically at startup and prints the conclusion in the terminal

> If you are not sure which case you are in: **just use case 1**. When both devices are on the same network, the experience is best and the speed is highest.
> If they cannot connect, the program tells you the reason and what to try; it will not leave you guessing.

The graphical interface is for people who are not used to the command line. **It is the same interface on every platform.**

### 4.1 Opening it

- **Single-file build**: just double-click the Flicker program
- **From source**: double-click `启动.cmd` / `启动.command`
- **Command line**: `flicker --gui`

The program opens a window (or a browser tab), and what you see is the **site page**.

All three actions can be started within a single screen. **That is what "site" means here** — you can both send and receive.

The difference between the two panels is worth spelling out (this is easy to misread):

- **Send files**: you **start** sending something out, and then you set a password.
- **Or, let someone send to me**: after you click "Receive files", the computer starts a service that lives only on this
  machine and shows a **QR code and a link**; the phone scans it, types the password shown on the computer screen, and
  pushes the photos over. **Nothing on the computer side asks for a password** — the password is the one **the phone** types.
- **Or, receive from a link**: use this when **the other side also has Flicker**. Paste the link and the one-time password
  from their screen → click "Connect and show the fingerprint" → check that the 8 characters match their screen → start.
  **This computer's own program** downloads the files, verifies every chunk and the whole-file hash, saves them into the
  folder you pick, and notifies the other side to destroy the session when it is done. Relay links belong in a browser
  (their receiving end lives in a web page).

The **🌐 language button** in the top right is on both the sender and the receiver: one click switches between Chinese and English,
and the button carries the name of **the other language** (if the interface says `English`, clicking it turns the interface English).
It is deliberately made rather conspicuous — the people who need it are often exactly the people who cannot read the current interface.
Your choice is remembered, so next time it opens in the same language. To change the language on the command line, add `--lang=en`.

### 4.3 The complete flow for sending files

**Step 1: pick the files**
Drag the files into the "Send files" area, or click "Choose files". You can pick several at once, or pick a whole folder directly.

**Step 2: confirm the manifest**
The program shows:

```
📄 合同扫描件.pdf                892 KB
🎬 旅行记录 2024.mp4             2.31 GB
📁 照片/（3 个文件）             8.4 MB
──────────────────────────────────────
共 4 个文件                      2.32 GB
```

**The manifest is grouped by "the things you added"**: add a folder and it is one row (showing the folder name,
how many files are inside, and how big it is), and one click expands it to show what is in there. Even hundreds of thousands of files will not make it stutter —
the details are only read when you open them.

**Added something by mistake? You do not have to start over**: move the mouse onto that row and an `✕` appears on the right;
clicking it removes **only that item**, and everything else stays. Remove every item and the interface goes back to the very first screen
(the same as when it was first opened). To clear everything in one go, use "Clear all".

**Step 3: set the password**
The program generates a password automatically, like this:

```
correct-horse-battery-staple
```

- **You can use it as it is** (recommended)
- Or type one of your own
- There is a "Copy" button next to it

> **Why is the default password a few English words?** Because you have to **read it out loud** to the other person or type it over by hand.
> That kind of password is easy to say and easy to type, yet about as strong as `aB3#xK9!`.

**Step 4: choose the transfer options**

```
☑ 顺便把「闪传」也送给对方     ← 对方收到后也能把文件发给别人
☐ 限制传输速度
```

**Step 5: start the transfer**
Click "Start transfer", and the page shows a **QR code** and a **link**.

**Step 6: give the other side the link or the QR code**
- Face to face: have them **scan the QR code** (fastest)
- Remotely: send the link and the password over WeChat / SMS / any channel
- ⚠️ It is safer to send the link and the password **separately** (the link over WeChat and the password by phone, for example)

**Step 7: wait for them to type the password**
Once they type the same password you see "the other side has connected", and the transfer starts.

**Step 8: it is finished**

```
✓ 传输完成     4 个文件 · 2.32 GB · 用时 21 秒

会话销毁清单
✓ 密码与会话密钥已清零
✓ 服务已关闭
✓ 一次性链接已失效
✓ 证书已从系统中移除
```

**That is the end of it.** Just close the window. Your original files **were not touched at all** (Flicker only reads, it never writes).

### 4.4 The complete flow for receiving files

There are two ways to receive. Figure out which one is yours:

**Way 1: they give you a link and you open it in a browser** (the only option when they have not installed Flicker)

**Step 1**: the other side gives you a link.
**Step 2**: open it in a browser.
**Step 3**: you see the list of files they want to send you (names and sizes only — you cannot see the contents).
**Step 4**: type the password they told you.
**Step 5**: click "Start receiving". The files are written to disk as they are downloaded.
**Step 6**: when it finishes, the program tells you where the files are.

**Way 2: both sides have Flicker — receive right in the site page** (no browser needed)

**Step 1**: on the home screen, click "Receive from a link".
**Step 2**: paste the **link** and the **one-time password** from their screen, and pick the folder to save into
(the default is your Downloads folder).
**Step 3**: click "Connect and show the fingerprint". This only connects once and computes their certificate
fingerprint — **no data is transferred**.
**Step 4**: check that the 8 characters shown match their screen. If they do, click "Fingerprint matches — start".
**Step 5**: **this computer's own program** downloads the files, verifying every chunk and then the whole-file
hash. The progress is right on this page.
**Step 6**: when it finishes, "Open the save folder" shows you the files. To stop early, click "Stop receiving" —
files already received stay on disk.

> **Who is "Skip the check and start" for**: it is the equivalent of `--insecure` on the command line — it skips
> certificate verification, so a fake service impersonating their address would get through. Only use it when you
> are sure it is your own LAN. The password and the data are still end-to-end encrypted; what this check stops is
> "am I really talking to their machine".

> **Relay links do not work here**: links of the form `https://<relay>/room/…` receive inside a web page, so open
> them in a browser (the `flicker recv` command tells you to add `--browser` when it sees one).

> **For large files, it is best to open the link in Edge or Chrome.** Firefox downloads into memory first,
> so anything over about 1 GB may fail. The page detects the browser automatically and warns you.

> **Cannot read the interface?** The **🌐 button** in the top right switches between Chinese and English,
> and it is on both the receiver and the sender. The button is labelled with the language you get when you click it.

### 4.5 "Pinning" Flicker to the Start menu (optional)

If you will use it often, you can turn it into a real desktop app icon, **with no installer**:

**Edge / Chrome**: open Flicker's graphical interface → top-right menu → **Apps → Install this site as an app**
(or look for the "Install" icon at the right of the address bar)

After that, "Flicker" appears in your Start menu; it opens in its own window with no address bar, and it looks like an ordinary piece of software.

```powershell

```

This **opens the graphical interface** directly. That way you can always double-click the program without remembering any command.

### 5.4 Plain text only (no QR code)

Some terminals render the QR code as garbage, or you are in a remote SSH session:


### 5.5 Across networks: deploy a relay once (about 3 minutes, free)

> For a more detailed explanation (the protocol, what the relay can see, quotas, troubleshooting) see **`中继部署.md`**.

**You only need this step when the two computers are not on the same network. Do it once and it keeps working from then on.**

**Step 1: sign up for a Cloudflare account**
Go to <https://dash.cloudflare.com/sign-up> and sign up with your email address. **No credit card needed.**

**Step 2: install the deployment tool**
First make sure Node.js is installed, then:

```powershell
npm install -g wrangler
```

**Step 3: log in**

```powershell
wrangler login
```

The browser opens a page; click "Allow", then come back to the command line.

**Step 4: deploy**

```powershell
cd flicker\relay
wrangler deploy
```

On success the terminal prints a line with an address, something like:

```
https://flicker-relay.你的用户名.workers.dev
```

**That is your relay address — write it down.**

**Step 5: how to use it from now on**

```powershell
flicker send "D:\文件.zip" --relay=https://flicker-relay.你的用户名.workers.dev
```

Then give that address to the other side (they open it in a browser as well):

```
https://flicker-relay.你的用户名.workers.dev/#/7f3a9c1e
```

> **Can the relay server see my files?**
> **No.** The relay's only job is to let the two computers find each other, and **the file data does not pass through it at all**.
> It cannot even see the file names or the file sizes. See §10 for details.

### 5.6 Phone → computer (`flicker recv`)

Photos and videos on your phone, going to the computer. A phone **cannot** be the server
(browsers do not allow it), so it is the other way round — **the computer starts a service
and the phone pushes the files up in its browser**:

```powershell
flicker recv
```

The screen shows a link, a QR code and a one-time password:

```
  ┌ Let the phone open this link ────────────────────┐
  │  https://192.168.1.5:54713/?k=r-hGTJ4D2GRWGINLL │
  │  ██ ▄▄ ██▀▄▀█ ▄▄ ██  (QR code)                     │
  └──────────────────────────────────────────────────┘

  One-time password  k7m-3fq   (typed into the phone page)
  Saving to          C:\Users\you\Downloads
  ⏳ Waiting for the other side… (auto-destroyed after 10 minutes)
```

**Step 1**: the phone joins the **same WiFi** (same router as the computer).
**Step 2**: scan the code (or send the link to the phone and open it). The first time you get a
"Not secure" warning → tap **Advanced → Proceed** (the certificate can only live on the computer;
the data is still encrypted).
**Step 3**: type the one-time password shown on the screen and tap "Connect".
**Step 4**: tap "**Choose photos / videos**" (or "Choose other files" below it); you can select
several at once. The page then computes a checksum for every file first (slower on a phone, but it
is what lets the computer verify integrity).
**Step 5**: tap "Start sending". **Do not switch to another app and do not let the screen sleep** —
the browser freezes background pages (the page asks for "keep the screen awake" when it can; when
you come back it resumes).
**Step 6**: it shows "Everything sent", the save folder opens on the computer, and the terminal
prints the destroy list.

Common options:

| Option | What it does |
|---|---|
| `--dir=<path>` | Save somewhere else (default: this computer's Downloads folder) |
| `--password=<pw>` | Set the password yourself (default: a 6-character code, easy to read out loud) |
| `--no-ask` | Same-name files are always renamed, no three-way prompt |
| `--no-open` | Do not open the save folder when it finishes |
| `--timeout=30m` | How long to wait before destroying (default 10 minutes) |
| `--no-qr` | Do not show the QR code (for guiding someone remotely) |

> **Same-name files**: by default it **stops and asks** — rename / overwrite / skip this file —
> and after 5 minutes without an answer it takes the safest choice (rename). `--no-ask` turns the
> question off.

> **The phone-side limits, stated plainly** (browser limitations, not laziness):
> · a phone **cannot pick a whole folder** — only individual files (or a whole album), so the
>   computer receives file names with no directory structure;
> · a phone **cannot choose where the files land** (the computer decides) and **cannot push files
>   into another App**;
> · iPhone photos are HEIC and are sent **as-is** (no conversion), so the computer may not be able
>   to preview them;
> · during a large transfer **the phone must stay awake**: the browser freezes a backgrounded page
>   (the page asks for "screen wake lock" where it exists; iOS Safari has no such API, so keeping
>   the screen on is on you);
> · afterwards, to hand a received file to another App from the *receiver* page, use its "Share"
>   button (Web Share) — that is the only way a browser can hand files to another App.

> **The graphical interface has the same entry**: on the home screen, further down, is
> "**Or, let someone send to me**" → click "Receive files" → choose the save folder → "Start receiving".
> The same QR code and one-time password appear; the save folder opens once when the transfer finishes,
> and "Open the save folder" is there whenever you want it.
> Same-name files are handled the same way (it stops and asks: rename / overwrite / skip).

### 5.7 Receiving with another computer that also has Flicker (`flicker recv <link>`)

Scenario: **both machines have Flicker**. The other side runs `flicker send` and sends you the link (and
the password) from their screen. You can hand the link to a browser, or let the program receive:

```powershell
flicker recv "https://192.168.1.5:8443/?k=7f3a9c1e" --password=correct-horse-battery-staple
```

It does the following, and **says each step on screen**:

1. Connects and computes their **certificate fingerprint** (say `A3F9C1D2`), then asks you "does their
   screen show this?" —— only continues if you agree. That is the only backing a self-signed certificate
   has: **do not trust a CA, trust that both sides see the same certificate.** Agree once, then rerun with
   `--fingerprint=A3F9C1D2` to stop being asked; if you are sure it is your own LAN you can use `--insecure`
   (the screen will say plainly "not checked").
2. Decrypts the manifest, verifies **every chunk** (each has its own hash), then the **whole-file hash**,
   and only then gives the file its real name.
3. **Never overwrites**: a name collision becomes `name (1).ext`, and it tells you what it renamed.
4. Tells the other side "I am done" —— that is what makes the sender destroy the keys and the link
   (the "gone when it's done" promise lands here).

**How it differs from the browser path**:

| | Browser path | `flicker recv <link>` |
|---|---|---|
| Does the receiver need the program? | No | **Yes** (the one you are on) |
| Writing to disk | Chrome/Edge stream; Firefox/Safari buffer in memory | Node always writes straight to disk, **no memory cost** |
| Large files | May fail in Firefox/Safari | Any size (disk-bound) |
| The "not secure" warning | Yes (their certificate is installed on their machine) | No, replaced by **you checking the fingerprint** |

> **The graphical interface has exactly the same path**: on the home screen, "**Or, receive from a link**" →
> paste the link and password → click "Connect and show the fingerprint" → check the 8 characters → start
> (see §4.4 Way 2). Behind the interface it calls **the very same** `src/pull.js`, so verification, renaming
> and destruction behave identically.

> ⚠️ **Relay links cannot use this path**: `https://<relay>/room/…#<room>:<salt>` receives inside the web
> page (the relay serves you the page, the page pulls from the room), and the program does not implement
> that. Add `--browser` and open it there —— a relay uses a proper HTTPS certificate, so the browser path
> has no hurdle anyway.

#### About `--rate` (rate limit)

Use it to **avoid saturating your office/home uplink** — filling the uplink while transferring tens of GB makes video calls stutter and web pages fail to open.

```powershell
flicker send "D:\电影.mkv" --rate=2M      # 限到约 2 MB/s
flicker send "D:\备份.zip" --rate=500K    # 限到约 500 KB/s
```

- Syntax: `500K` / `5M` / `2G`, or give the number of bytes directly (such as `1048576`). K/M/G are powers of 1024.
- **Getting it wrong makes it exit with an error**, it does not quietly become "no limit" — that kind of misunderstanding only surfaces when a colleague complains that the network is slow.
- There is about one second of "burst allowance" at the start (the bucket is full), so **the beginning is slightly faster**, after which it settles at the rate you set.
  Measured steady-state deviation is 1–4%.

> ⚠️ **This one used to be "in the docs but not in the program"** — `--rate` was silently ignored as an unknown option, so
> users thought they had limited the speed while the uplink was in fact saturated. It is now really implemented, and tests watch it in both modes
> (`test/rate.test.js` checks the accuracy of the rate, and `test/e2e.test.js` together with `test/relay-e2e.test.js`
> check respectively that the LAN and relay paths are genuinely wired up).

**You can set it in the graphical interface too** (added 2026-10): double-click `启动.cmd` to open the interface → pick your files →
**Speed limit** under "Options", where you can choose `不限速 / 1 / 2 / 5 / 10 MB/s`, or pick "Custom…"
and fill it in yourself (exactly the same syntax as the command line: `512K`, `5M`, `2G`).

If you get it wrong in the interface it **tells you the correct syntax on the spot** and leaves the previous setting unchanged — for the same reason as on the command line:
treating an "unreadable speed" as no limit is far worse than an error.

#### How to pick files in the graphical interface (without typing paths)

Clicking **Choose files** or **Choose folder** opens a browsing window: drives/folders are listed on the left,
you go into one, and whatever is selected is "what gets sent".

- **Multi-select works**: click the box on the right to select (click again to deselect), or hold **Shift** to select a run of them
- **You can gather files from different folders**: pick two in folder A, go into folder B and pick one more, then confirm them all together
- **Double-clicking** an item = send just that one (fastest when you are only adding one file)
- The two modes divide the work differently:

| Where you click | Choose files | Choose folder |
|---|---|---|
| A file's name | Selects it | — (only folders are listed) |
| A folder's **name** | Goes into it | **Selects** it |
| The **▸** at the left of a folder | Goes into it | Goes into it |
| The box on the right | Select/deselect | Select/deselect |

- Clicking **"Up"** repeatedly gets you back to "This computer" (the list of drives)

> **Why can't it pop up the system file dialog the way other web pages do**: browsers have a hard rule —
> a web page cannot get the **full path** of the file you selected. And this program's sender reads the original file directly
> (no copying, no memory use — that is the only way tens of GB can move at all), so the path is exactly what it needs.
> That is why the "choosing" is done by the program's own local service (which listens on the loopback address of this machine only).

**After you add a folder**, the manifest shows **that folder** (its name + how many files are inside + the total size),
and one click expands it to show what is inside (the sub-directory hierarchy is preserved too).

The "Type a path instead" button is still there — it is for people who "already know the path and just want to paste it",
not a step you have to go through.

### 6.5 What to set `--window` to

`--window` is the number of chunks in flight in **relay mode** (one chunk is 1 MiB). It decides "how much data is on the road at the same time":

| Value | When it fits |
|---|---|
| `1` | Stop-and-wait. Uses the least traffic and makes problems easiest to see, but it is slow (measured about 4.7 MB/s) |
| `8` (default) | The sweet spot for an ordinary network. Measured at about 18–24 MB/s across networks |
| `16` and above | **Usually unnecessary** — measured throughput saturates at 28–30 MB/s, which is already the link's ceiling |

> Measured conclusion (see `路线图.md`, section 5 supplement): going from window 8 to window 32 raises throughput by only about 18%,
> which shows the bottleneck has moved from "latency" to "the bandwidth between you and the relay".
> **Making the window bigger does not make a slow link faster**; it only costs a few more MiB of memory on the relay.
>
> Also note: the window counts **chunks**, so after `--chunk=2m` the same window carries twice as much data
> (see the next section).

### 6.6 Should `--chunk` be changed

Normally **leave it alone** (the default is `auto`). It solves one very specific problem:
the receiver waits one network round trip per chunk, so "how much data is in flight" decides the cross-network
speed. A browser opens at most 6 connections to one origin, so the condition for filling the link is:

```
6 × chunk size  ≥  bandwidth × round trip
```

Measured on this machine (256 MiB, 195 ms round trip, link capped at 29.5 MB/s):

| Chunk size | End to end |
|---|---|
| 1 MiB | 18.9 MB/s (6 MiB in flight, only just enough) |
| **2 MiB** | **26.3 MB/s** (12 MiB in flight, 89% of the link) |
| 4 MiB | 25.8 MB/s (**no extra gain, just more memory**) |

So the `auto` default picks **2 MiB** —— but it cannot simply be used: one message is one chunk, and the relay
has a per-message ceiling. The sender first asks the relay "how large a message can you accept"
(`maxMessageBytes` in `/health` and in the create response) and then takes the smaller of "what it wants" and
"what the other side allows".

| Your relay | What `auto` gives |
|---|---|
| Deployed with this program 0.1.0 or later (declares 2 MiB) | 2 MiB |
| **Deployed earlier** (no such field) | Falls back to 1 MiB automatically —— **no error, nothing corrupted** |

To pin it yourself use `--chunk=512k` / `2m` / `4m`; a value above the relay's ceiling is **clamped down**
(and the terminal says "clamped to the relay's ceiling") rather than being sent and rejected.

> ⚠️ **Do not raise it blindly on a slow link**: on a measured 5 MB/s link, 1 MiB and 4 MiB give **exactly the
> same** throughput, while progress updates go from once every 212 ms to once every 837 ms and losing one chunk
> costs 4× the retransmission. Past "bandwidth × round trip", extra chunk size only buys a coarser granularity.

> By the way: the receiver's prefetch buffer is 6 × chunk size, so 2 MiB chunks mean about 12 MiB of memory
> (still constant, independent of file size).

## 7. After the transfer

### 7.1 The sender

The program **does not modify, does not delete and does not move** your original files. It only reads.
Once the transfer has ended:

- If you used the terminal: the process exits and everything is over
- If you used the graphical interface: you can close the window, or leave it open for the next transfer

### 7.2 The receiver

The files are saved wherever you chose (in the graphical interface a "Save to…" dialog appears; on the command line the default is the download folder).

### 7.3 What "it is all gone" means

Once the transfer has ended, the following things **disappear immediately**:

| What disappears | Explanation |
|---|---|
| The password and the keys | Overwritten with zeros in memory |
| The transfer server | The port is closed and the link stops working |
| The one-time token | The link cannot be visited again |
| Temporary files | **They were never created in the first place** (that is a design goal) |
| The system certificate | The session certificate is removed from the trust store |
| The room on the relay | Deleted (and even if it were not, it expires automatically after a few minutes) |

**The only thing left behind is the files the receiver saved** — which is exactly what you wanted.

## 8. Troubleshooting

### 8.1 The other side cannot open the link

**Symptom**: their browser shows "This site can't be reached", or it spins forever.

Check in this order:

1. **Confirm you are on the same network** — are both devices on the same WiFi / router?
   - If they are on a phone hotspot, or on the WiFi next door, they cannot connect and you need `--relay` (see §5.5)
2. **Confirm the link is complete** — especially the string of one-time token after `?k=`; one missing character is enough to break it. Scanning the QR code directly is best
3. **Check the firewall** — did the sender allow network access when it ran the first time? (see §2.3)
4. **Isolated networks** — many office WiFi and hotel WiFi networks turn on "client isolation", so devices on the same WiFi cannot reach each other either.
   In that situation only `--relay` will work
5. **Confirm the program is still running** — you did not close the terminal window, did you?

### 8.2 Stuck on "waiting for the other side to connect"

It means the other side has not opened the link yet, or has opened it but not typed the password.

- Keep the sender's terminal running
- The default timeout is 10 minutes; after that everything is destroyed automatically and you have to start again
- To change the timeout: `--timeout=30m`

### 8.3 It says "passwords do not match"

The two sides did not type exactly the same password. **Note**:

- It is case-sensitive (`Abc` ≠ `abc`)
- **Spaces count too** — `correct horse` and `correcthorse` are not the same
- A Chinese input method may have turned the hyphen `-` into the full-width `－`

**Suggestion**: copy and paste the password directly, or let them read it themselves from the QR code/link.
After 5 failures in a row, this session is destroyed automatically (that is a security feature, not a bug).

### 8.4 The browser crashed or froze while transferring a large file

**Cause**: you are using Firefox or Safari, which cannot "write to disk while receiving" and has to hold the whole file in memory.

**What to do**:
- Open the receiving link in **Edge or Chrome** instead (the most effective fix)
- Or have the sender add `--one-file` and send in batches

### 8.4.1 The other side opens the link and sees "Not secure / Your connection is not private"

**This is expected, not a failure.** The reason is that the session certificate is only installed on the **sender's** computer,
and theirs is seeing that certificate for the first time (see §10.3 for details).

**Have them do this**:

1. Click **"Advanced"** on the page
2. Then click **"Proceed to <address> (unsafe)"**
3. After that it behaves normally — this only affects that one time

> The key distinction: the warning says "**the browser does not recognise this certificate**", not "the content is unencrypted".
> The file contents are still end-to-end encrypted, and neither the relay nor any bystander can see them.
>
> To avoid this step entirely: use `--relay` and go through a relay (that path uses the relay's proper HTTPS certificate, so neither end sees a warning).

### 8.4.2 While receiving, the browser asks "allow this site to modify files?"

**This is required in order to save the files; just click "Allow".**

On Chrome / Edge, Flicker **writes to disk while it receives** (which is why tens of GB does not fill up memory),
and writing to disk needs the browser's file-write permission, so it asks this question.

- Choose **Allow** → normal receiving (files are written into the folder you picked as they arrive)
- Choose **Deny** → two cases:
  - The files are not large (under about 900 MB): the page **tells you clearly** that "it will collect them into memory first and save afterwards",
    and then carries on to the end
  - The files are large: the page **stops and tells you to click again and choose "Allow"** —
    because tens of GB cannot be assembled in memory first, and forcing it just crashes the browser halfway through,
    by which point you have already waited a long time. **Stopping now is a better deal than crashing halfway**
- Clicking **Cancel** in the folder window → a clean stop; no transfer is started

- That "choose a save location" window is the same thing: it is asking "**where to save it**"

**Why not just download the way an ordinary web page does**: an ordinary download puts the file into memory first and then writes it to disk,
and tens of GB would blow the browser up outright (this is what §8.4 is about). Writing while receiving is the path we chose **on purpose**.

### 8.5 The transfer was interrupted

**The good news first**: brief link hiccups **no longer** interrupt a transfer.
A WiFi blink, a phone switching networks, a connection being reset — both ends reconnect automatically
(backing off to at most once every 8 seconds), and the interface shows "Connection unstable — reconnecting (n/max)".
These momentary failures are the most common cause of failure in long transfers, and they no longer ruin the whole transfer.

**And now the part that cannot be done** (this was written wrongly before and is corrected here):

| Situation | Can it carry on |
|---|---|
| A network hiccup mid-transfer that recovers by itself | ✅ **Continues automatically**, nothing for you to do |
| Clicking "Cancel" and starting again (the sender is still running, the room is still there) | ✅ With several files, **files already completed and verified are skipped** and not resent |
| **Closing the page/browser and opening it again** | ⚠️ **At chunk level it cannot be done — it starts from the beginning**. If some files were already fully received and verified earlier, those files are skipped |

**Why "closing the page" cannot work** — this is not laziness, it is a limit of the browser APIs:

- With **Chrome / Edge**, files are **written to disk as they are received**. But the
  "handle" used to write them becomes invalid once the page closes, and after reopening you cannot carry on from byte N
  (the browser's write API can only write in order, and every open clears the file).
- With **Firefox / Safari**, files are **collected entirely into memory first and saved in one go at the end**.
  Closing the page takes the received part with it — there is nothing left to "carry on" writing into.
  That is why on those two browsers we already tell you to switch to Edge or Chrome for large files.

> **Honest advice**: for a transfer of tens of GB, **do not close the page halfway through**.
> Network hiccups heal themselves now; but closing the page means giving up this run.
> If you really must stop, wait until a whole file has finished and then close — completed files are skipped next time.

If you need the ability to "close it and still resume", that requires a different approach (for example making the receiver a resident program
rather than a web page) — and that is no longer the "the other side installs nothing" shape;
it is a different trade-off. **And this project has explicitly decided not to do it (2026-10)**: squeezing it into a
browser would mean giving up three promises you have just read in this manual —— no IndexedDB bookkeeping, a link
that dies on its first visit, and the password and session keys being released with the page. The trade-off is written
up in `路线图.md` item 5 and §6.

### 8.6 It is slow

| Cause | Explanation |
|---|---|
| **You are going through a relay** | In across-networks mode the data has to make a detour through the relay, so the speed depends on **the link between you and the relay**, not on the theoretical bandwidth between you and the relay provider. The measured round-trip latency to Cloudflare is about 195 ms; the window has already been widened from 1 to 8 (measured 4.4×), but the latency itself cannot be saved |
| The relay is far away | Wherever the relay's region is decides how far the detour is. When hosting your own relay, pick a region near you |
| Poor WiFi signal | A network cable is a lot faster |
| A slow disk | With a mechanical hard drive and a lot of small files, the bottleneck is the disk, not the network |
| The other side is a phone | A phone's write speed is usually far below a computer's |

> To find out how fast it actually is going right now, watch the live rate display on the sender.
> In LAN mode the bottleneck is almost always the disk or the WiFi, not the program.

### 8.7 It says "no public IP, cannot connect directly"

This is **normal**, and it is how the vast majority of home broadband works (the ISP puts you behind a large private network).
The program is only telling you that "across networks needs a relay" — it is not a failure.

### 8.8 The QR code shows up as a pile of garbage

Some older Windows terminal fonts do not support the half-block characters the QR code is built from. Three ways out:

1. Add `--no-qr` and the program prints only the text link
2. Use Windows Terminal or PowerShell 7 (which render it correctly)
3. Use the graphical interface (`flicker --gui`), where the QR code is an image

### 8.9 Double-clicking does nothing on macOS / Linux

- macOS: Gatekeeper may have blocked it. Right-click the file → "Open" → then click "Open" again
- Linux: you need to add execute permission first: `chmod +x flicker-*-linux-x64`

## 9. Frequently asked questions

**Q: Does the other side have to install anything?**
A: **Nothing at all** — just a browser. Computer, phone and tablet are all the same.

**Q: Do the files go through your servers?**
A: **We have no servers.** In LAN mode the data never leaves the local network; the two computers connect directly.
In across-networks mode it goes through **the relay you specified yourself** (you can host your own, see `中继部署.md`) —
and this is a point that has to be stated clearly: **the relay handles every byte of the files**, but all of it is AES-256-GCM ciphertext,
and the manifest itself (file names, directory structure, sizes) is encrypted as well.

So the accurate way to put it is:

| The relay can know | The relay cannot know |
|---|---|
| That someone is transferring, and when | What the content being transferred is |
| How big each message is, and how many there are in total | What the files are called, and how many files there are |
| The IPs of both ends | Your password (**the password never goes on the wire**) |

**Q: So what about the relay not being trustworthy?**
A: The encryption does not depend on the relay being trustworthy. The key is derived from the password through PBKDF2 + HKDF
and exists only on your computer and the other side's; even a relay that wanted to do harm could only "deny service" or "look at metadata",
it **cannot change the file contents** (every chunk carries an authentication tag, and one changed byte is rejected by the receiver).
See `行为与运行.md` §2.3 and §10 for details.

**Q: Is there a size limit?**
A: No. How much you can transfer depends on your disk space and your network. Scenarios of tens of GB have been tested.

**Q: Can it send folders?**
A: Yes. A folder goes across together with its internal structure.

**Q: Can it send to several people at the same time?**
A: The current version is one-shot and one-to-one. For several people, please send several times.

**Q: Is a transfer history saved?**
A: The program **writes no log files at all**. The terminal output is gone once you close it (unless you redirected it yourself).

**Q: Can it resume?**
A: Three cases, and the wording has to be accurate:

- **A network hiccup** → ✅ reconnects and carries on automatically, nothing to do (this is the most common failure, and it now heals itself)
- **Retrying within the same page** → ✅ **files** already completed and verified are skipped and not resent
- **Closing the page and opening it again** → ⚠️ **at chunk level it starts from the beginning**. Browsers have no API for "carry on writing from byte N",
  so a file that was not finished when the page closed is void (see §8.5 for details).
  This capability is **explicitly not being done** (decided 2026-10): building it would mean giving up three promises,
  and the cost outweighs the benefit —— same reasons as above.

That is why we do not use the sweeping phrase "supports resuming" — it would make people think closing the page can resume too.

**Q: Can the files the other side receives be "altered"?**
A: No. Every file gets a SHA-256 checksum as it is transferred, the receiver verifies it chunk by chunk,
and finally the overall hash is compared. Any single wrong byte is detected and the transfer is stopped.

**Q: Can it automatically delete the sender's files once the transfer is done?**
A: **No, and this feature will not be built.** Flicker treats your original files as **read-only**.
Automatic deletion is dangerous behaviour; a mistaken deletion cannot be undone, and it is not something a transfer tool should do.

**Q: Why is the default password a few English words?**
A: Because it has to be easy to read aloud and easy to type by hand. `correct-horse-battery-staple` has about as much entropy as `aB3#xK9!`,
but you can read it to the other person over the phone instead of depending on copy and paste.

**Q: I do not want that "send the program to the other side as well" — can I turn it off?**
A: Yes. Untick it in the graphical interface, or add `--no-gift` on the command line.

**Q: Can a phone receive files, and where do they end up afterwards?**
A: Yes, it can (**verified on a real Android phone**: direct over the LAN, everything destroyed afterwards — see `路线图.md`).
But **"where did the file go" really is messy on phones**, and we should say so:

- **The destination is decided by the phone's browser, not by this program** —— phones do not support the
  "pick a folder for me" capability (desktop Chrome/Edge do, which is why on a computer the file is streamed
  straight into the directory you choose).
- **Android**: usually the browser's download directory (on most models the **Download** folder). Vendors'
  file-manager interfaces differ a lot, and some older models have no separate file manager at all —— so
  "where did it download to" often means digging through the browser's own downloads list.
- **iPhone**: expected to land in **Files app → Downloads** (**not verified** —— this project has never tested
  iOS on a real device, and nobody has reported back; if you try it, we would like to know).

**So the easiest thing on a phone is to tap 「分享 / 保存到…」(share / save to…) next to each file after receiving**,
then pick "Save to Photos / send over WeChat / save into Files" in the system sheet —— that step is **you choosing
the destination**, instead of guessing where the browser dropped the file.

**Q: Can a phone send files?**
A: A phone **sending** files is limited by the browser — browsers do not allow a web page to read files from arbitrary paths,
so you can only pick files by hand in the file chooser; there is no "pick a folder and it sends automatically".

**Q: Can I use it directly on the public internet?**
A: Yes, but you must use `--relay` (see §5.5), because the vast majority of home broadband has no public IP.

## 10. Security questions

### 10.1 How the password is protected

**Your password never leaves your computer.**

Each of the two computers computes locally from the password, and then they check each other that "the results they computed agree",
verified by exchanging the answer to a random challenge — what travels over the network cannot be turned back into the password,
and it cannot be reused either (every challenge is new).

Even if someone captures packets on the network, they get neither the password nor the file contents.

### 10.2 What the relay server can see

| Can see | Cannot see |
|---|---|
| That two devices are communicating | The file contents |
| A random room ID | The password |
| When the communication happens | The file names |
| The IP addresses of both ends (unavoidably visible at the network layer) | The file sizes |

**And this information is deleted immediately once the transfer is complete.**

### 10.3 About the system certificate

So that the other side does **not** get a red "this connection is not secure" warning when they open the link, Flicker:

1. Generates a certificate at startup that **belongs to this session only**
2. Installs it into the **current user's** certificate trust store (**no administrator rights are needed**, and it does not affect other users on the system)
3. **Removes it automatically** once the transfer has ended

> ⚠️ **This step only helps on the initiator's own computer.**
> The certificate is installed on **your** computer and does not travel to theirs — so:
>
> | Which computer opens the link | What is seen |
> |---|---|
> | **The sender's** (local preview, testing it yourself) | Zero warnings, the page renders normally |
> | **The other side's** (the first time) | One "**Your connection is not private / Not secure**" notice |
>
> What they have to do is click **"Advanced" → "Proceed to <address> (unsafe)"**, and then it behaves normally.
> This only affects the first time they open it, and **the data is still end-to-end encrypted** — the warning says
> "the browser does not recognise this certificate", not "the content is unencrypted".
>
> Why not make it so that "the other side does not have to click either": that would require **installing one of our root certificates on their computer**,
> and "asking a user to install an unfamiliar root certificate" is far more dangerous than "clicking Proceed once"
> (it amounts to handing over the trust of all their HTTPS traffic). That trade-off is deliberate.
>
> To avoid this step entirely: use `--relay` and go through a relay — that path uses the relay's own proper HTTPS certificate,
> so neither end sees a warning (the cost is that the data is forwarded through the relay, see §10.2).

> ✅ **The zero-warning-on-this-machine mechanism has been verified by real testing on Windows 10 + Edge 155**.
> The tests covered three browser modes (background mode, a visible window, and an app window with no address bar) and two addresses
> (`127.0.0.1` and a real LAN IP), and used a set of control cases that "deliberately do not install the certificate" to confirm
> that the test method really can detect the security warning page — in other words, this "pass" is not an illusion caused by tests that are too lax.

**The certificate itself is generated in pure JS** (it does not call `openssl`, does not call PowerShell, and depends on no external program),
so the generation step runs the same code on every platform; and it has one hard acceptance test:
**start an HTTPS server and really connect to it once, using the generated CA as the trust root**.
If it cannot connect, it fails — no API return value is consulted.

> ⚠️ **But the "install it into the system trust store" step has only been done on Windows**; the other platforms are **not verified on real hardware**.
> And this is not a case of "we have not got round to it" — each of the two platforms has a hard reason of its own:
>
> - **macOS**: the built-in `security add-trusted-cert` can do it, with no extra software needed;
>   but Apple's documentation is explicit — changing user trust settings **requires going through an authentication dialog**,
>   and changing the system domain requires root. In other words **there is no "install it silently" path**,
>   and Flicker's positioning is "usable the moment it starts, with no dialog asking for your password".
> - **Linux**: **there is no zero-dependency way to do it**. On Linux, browsers do not read the system certificate directory;
>   Chromium reads the NSS database (since M146 `~/.local/share/pki/nssdb`,
>   before that `~/.pki/nssdb`), and writing to it needs `certutil`, which comes from `libnss3-tools`/`nss-tools`
>   and is **not installed by default**; Firefox additionally uses its own database.
>   Source: [Chromium's official documentation](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/docs/linux/cert_management.md).
>
> So on those two platforms please use `--no-cert-install`, which means the "trust it by hand" route below.
> At startup the program **prints the command you need to type exactly as it is**, but it will not run it for you —
> popping up dialogs and installing software packages are two things that should not happen on a program's startup path.

If you do not accept any program touching your trust store, add `--no-cert-install`:

```powershell
flicker send "D:\文件.zip" --no-cert-install
```

In that case the other side sees one security notice when they open the link and has to click "Proceed" by hand. Everything works exactly the same; it is just one extra click.

**It can be left behind in abnormal cases**: if the program is force-killed mid-transfer (Task Manager "End task", a power cut, a blue screen),
the certificate may not have been removed in time and will stay in your trust store. The program **scans for and cleans up** this kind of leftover **the next time it starts**.
You can also check by hand: `certmgr.msc` → "Trusted Root Certification Authorities" → look for an entry whose issuer is `Flicker Session`.
(On macOS the equivalent is "Keychain Access → System/Login → look for `Flicker Session`",
and on Linux it is the entry listed by `certutil -L` above.)

### 10.4 What someone who does not have the password can see

Only a page asking for the password, and **no file information at all** — not even the file names or the number of files
(the manifest is encrypted).

### 10.5 What this program does not protect against (an honest note)

- It does not protect against **weak passwords**. If you set `123456` yourself, someone may guess it. The password the program generates by default is safe
- It does not protect against **your computer already being under someone's control** (keyloggers, trojans)
- It does not protect against **traffic analysis**: it can be seen that "you are transferring something", but not what is being transferred
- It does not protect against **you yourself sending the link and the password together to someone who should not have them**

### 10.6 If you want to verify it yourself

- The terminal prints the certificate fingerprint at startup, so you can compare it by hand
- The receiver page can expand "security details", showing the cipher suite in use and the checksums
- The code is fully open source, and the cryptography is gathered into a separate module, which makes it easy to audit

## 11. Uninstalling

Flicker is a **portable program**: it writes nothing to the registry, installs no services and leaves no background processes. Uninstalling is minimal:

| How it was installed | How to uninstall |
|---|---|
| Single-file build | **Just delete that file** and it is gone |
| From source | Delete the whole folder |
| npm install | `npm uninstall -g flicker-transfer` |

**Also check the following** (normally the program has already cleaned these up automatically):

- **Windows**: `certmgr.msc` → "Trusted Root Certification Authorities" → look for an entry issued by `Flicker Session` and delete it if there is one
- **macOS**: Keychain Access → System → look for `Flicker Session`
- **If you deployed a relay**: `cd relay && wrangler delete` (or just leave it — you will never use up the free allowance)
