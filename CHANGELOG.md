# Changelog

This file records **what happened in each public release**.
Version numbers follow [Semantic Versioning](https://semver.org/), and the format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

> **0.1.0 is the first release** —— nothing was published before it,
> so that single entry below covers the whole development process.
>
> Every fix says **how it was found**, because looking back, the most expensive lessons in this
> project were almost never "we wrote it wrong" but "**it looked right**":
> tests green, smoke green, and the document reads smoothly, while the thing is wrong.

## [0.1.0] — 2026-10

### Added

- **One-shot file transfer**: both machines must type the same password, and everything is destroyed once the transfer ends —— keys zeroed, service closed, link dead.
- **Two paths**: direct LAN (the default) and relay forwarding (across networks; needs a relay you deploy once).
- **Zero install on the receiving side**: the other side just opens a link in a browser. On Chromium it **streams to disk** while receiving (no memory growth); other browsers buffer in memory and save at the end.
- **Receiver prefetch**: fetching chunks is no longer "one round trip per chunk" (measured 4.0 → 13.9~17.0 MB/s at a 195 ms cross-network round trip).
  Only the network half runs in parallel; decryption, per-chunk verification, sequential disk writes and "ack only after the write" are unchanged.
- **The whole-file hash moved into a Web Worker**: it is the largest single piece of CPU on the receiver's main thread
  (pure-JS SHA-256, measured at 252 MiB/s). Moving it took the LAN from **123 to 208.7 MB/s** (fetch phase 293 MB/s ≈ 2.35 Gbps,
  already against the 2.5 GbE line rate). When no Worker is available it falls back to the main thread automatically,
  and progress repaints are throttled to once per 100 ms.
- **Chunk size and capability negotiation**: the sender first asks the relay "how large a message can you accept"
  (`maxMessageBytes`) and then takes the smaller of the two —— the default chunk grew from 1 MiB to **2 MiB**, taking the
  same link from 18.9 to **25.5 MB/s** end to end (256 MiB, 195 ms round trip, link capped at 29.5 MB/s).
  **A relay that declares nothing makes it fall back to 1 MiB automatically**, so upgrading the client cannot kill an
  already-deployed old relay. The receiver's prefetch buffer becomes 6 × chunk size (about 12 MiB, still constant).
- **Two interfaces**: a graphical one (opened by passing no options) and a command line (`send` / `recv`).
- **Relay**: a Cloudflare Worker implementation plus a local relay (the same code) and a deployment document.
- **Rate limiting `--rate`**: works on both paths, with 1–4% steady-state deviation.
- **Automatic reconnection**: exponential backoff (from 400 ms, doubling, capped at 8 s, with jitter), so a brief network hiccup no longer destroys the whole transfer.
- **Bilingual interface (Chinese / English)**: 373 strings side by side, switchable in both UIs; plus a QR code and a PWA (installable, with the system share sheet).
- **Self-gifting**: when sending files it also sends **the program itself** (the single-file exe) plus a **source pack** (source and every document), so the receiver can pass it on to the next person.
- **Plugin system (v1, four planes)**: optional, and **loaded only when you ask explicitly** (`--plugin=<path>`, repeatable; or the `FLICKER_PLUGINS` environment variable; the receiver page uses the explicit manifest `web/page-plugins.json`) —— it never scans a directory or discovers anything by itself. The **sending-side plane** offers four events (`run/start`, `manifest/scanned`, `ui/message`, `transfer/complete`) and one contribution point (`gift/items`: attach a file to this transfer, which the receiver saves like any other file). The **relay plane** offers three events (`relay/route` fires **before any routing** and may return `{status, body}` to end the request; `relay/room-created` / `relay/room-destroyed` report the real room lifecycle) and one contribution point (`relay/health`: add fields to `/health`, but core fields win —— a plugin cannot override `maxMessageBytes`). The **receiver-page plane** offers four events (`page/ready`, `recv/verified`, `recv/file-done`, `recv/complete`) and one contribution point (`page/actions`: add buttons to the "receiving complete" panel). The **receiving-side plane (2026-10)** offers nine events (`receive/ready`, `receive/peer`, `receive/auth`, `receive/manifest`, `receive/collision`, `receive/file-done`, `receive/file-failed`, `receive/complete`, `receive/closed`) and **no contribution points** —— the on-disk path rules and per-chunk verification are the receiving side's safety floor, so a plugin may only *know what happened*. Event payloads **never carry the password or the one-time link token**; a plugin error **does not interrupt receiving** (the other side is pushing files), but it is recorded in `plugins.errors` and printed at the end. Criterion: `test/plugin-recv.test.js` (12 cases: event order and contents, failures sending `file-failed` instead of `file-done`, files still arriving when a plugin throws, both directions rejecting a wrong plane on the spot, the example plugin covering every hook of its plane, and the destroy-chain step). Page plugins can only be **inlined at build time** (the page must stay self-contained and the CSP forbids external scripts), which has a pleasant consequence: **any page plugin changes the page fingerprint**, so "who changed the page the other side received" cannot be hidden; with an empty manifest the page only gains two marker comments, so nobody pays for a feature they do not use. Every side effect in a plugin must go through `ctx.effect()`, and the sender's destroy chain, the relay's shutdown or the page's unload cleans it up. An `apiVersion` mismatch, a misspelled hook name or a hook from the wrong plane, and an illegal or colliding attached file name all **fail on the spot** instead of "doing their best". One deliberate **exception**: a page plugin's errors **do not interrupt the transfer** (at that moment the other side is receiving files, and a broken plugin should not be their problem) —— they are swallowed, recorded honestly, and the transfer carries on. Six runnable examples ship with it (`examples/plugins/`), plus two documents (`中文文档/插件.md`, `docs/插件.md`) and three machine checks (`gen/check-plugin-doc.mjs` compares the three planes' hook tables against both documents; `gen/inline-plugins.mjs --check` keeps the page's inlined block in sync with the manifest; 59 test cases in total — 15 + 7 + 12 + 4 + 5 + 4 + 12 — plus one real-CLI end-to-end case). **Plugins may split out helper files (measured 2026-10)**: inside the single-file artifact `require('./helper.cjs')` **works** —— the docs previously said "unverified, so plugins must be self-contained". Criterion: `_lab/probe-plugin-require.mjs` (a self-contained control plus the helper case; both must pass, which proves the require really returned the helper's exports instead of being ignored). **The GUI supports plugins too (2026-10)**: launching the GUI with `--plugin` used to be **explicitly refused**; now it really works —— the GUI hands the same registry to `runSend`, so events, contribution points and the destroy step all take effect, and `ctx.log()` output is re-routed into the GUI's log panel (writing to stderr, as it does by default, would be invisible there, i.e. "thrown away"). **Wrong-plane hooks now really fail (2026-10)**: previously only *mistyped* names were caught, so a relay plugin subscribing to `run/start` silently did nothing; the registry is now built per plane (sending / relay / receiving / both for the GUI) and a hook from another plane **throws on the spot**, listing the names this plane does have. Criteria: `test/plugin-gui.test.js` (4 cases: really start the GUI with a plugin, plugins in receive mode really work, the wiring, the log re-routing) and two plane cases in `test/plugin-recv.test.js`. **The relay can swap its storage backend (2026-10)**: at start-up the relay reads the `relay/store` contribution point once, and a contributed storage object moves "where rooms live" out of process memory into disk or object storage; one missing member **fails immediately and names both the plugin and the missing method**, and when several plugins contribute, the first one wins. Example: `examples/plugins/relay-disk-store.cjs`; criterion: `test/plugin-relay-store.test.js` (5 cases, including "the contribution is really used" and the example backend's write-to-disk / delete-on-ack).
- **Unpacking the gifted source package (2026-10)**: when "also send them Flicker" is ticked, the other side receives a `.fkz` (source plus all documents) —— and until now **nothing in the product could open it**: they got a file that would not open, with no command to unpack it, a gap that sat in the handover notes for a year. Now `flicker unpack <file.fkz>` unpacks it with **the program you were given** —— no Node, no other tool —— and what comes out is a source tree that actually runs (the criterion really executes `node bin/flicker.js --version`). Unpacking **does not trust the package**: path traversal, absolute paths, Windows reserved names, two entries landing on one file, invalid UTF-8 names, truncation and trailing bytes are all refused explicitly, and a refusal writes no file at all. Criterion: `test/unpack.test.js` (21 cases). Two hand-written FKZ parsers (`gen/check-source-pack.mjs`, `test/docs-pairing.test.js`) were also unified onto the single reader in `src/gift.js`.

- **Receiving with Flicker itself (2026-10)**: `flicker recv <link>` used to be nothing but "open it in a browser" —— so "both machines have the program" made no difference; the receiving side was always a web page. Now the default is the other way round: the program consumes the token, authenticates both ways, **verifies every chunk**, checks the whole-file hash, writes to disk under the same path rules, and tells the other side when it is done. The self-signed certificate is crossed by a human comparing a **fingerprint** (the sender prints 8 characters; the receiver asks you to confirm they match; `--fingerprint=` skips the prompt and `--insecure` gives it up explicitly, saying "not checked" on screen) —— that step guards "someone impersonating the other address", while content safety never depended on it (password-derived keys + AES-GCM + per-chunk hashes). Criterion `test/pull.test.js` (13 cases): a real sender plus the real CLI, byte for byte; reverse checks for a tampered chunk, `../x` in the manifest, two paths landing on the same file, a wrong whole-file digest (no final file, the partial one stays), a fingerprint mismatch and a wrong password —— all of them must **refuse**, and not write a single byte. Relay links still go through a browser (receiving happens in the page).

- **Receiving from a link in the GUI (2026-10)**: the path above used to be command-line only; now the station page has "**Or, receive from a link**": paste their link and the one-time password → click "Connect and show the fingerprint" → check those 8 characters against their screen → start. When it finishes you see the file count, size and elapsed time, can "Open the save folder", and can "Stop receiving" mid-transfer (files already received stay; the rest is left as a `.flicker-part` so it is obvious nothing is finished). **Why the page does not fetch by itself**: the station page lives at `http://127.0.0.1:<port>` while the other side is on a LAN IP with a **self-signed certificate** —— cross-origin plus certificate would both block the browser's `fetch` (`src/server.js` sends no CORS headers). So the page only posts to the local service (`/api/pull/probe|start|stop|open`) and Node does the actual fetching, through **the same** `src/pull.js` as the command line (one source, not a second implementation). That turns the certificate hurdle from "change the trust store" into "a human compares 8 characters": without a confirmation, a typed fingerprint, or an explicit "Skip the check", the API refuses (`NEED_CONFIRM`) and writes not a single byte. Criterion `test/pull-gui.test.js` (4 cases): a real sender plus the real GUI, byte for byte, with the sender exiting on `/api/done`; no check → refused; wrong fingerprint → refused; stop under a rate-limited sender → phase `stopped` and **no final file**.

- **Phone → computer: receive mode (`flicker recv`)**. A phone cannot be the server (browsers do not allow it), so it is the other way round —— the computer starts an HTTPS service and the phone **pushes** files up from its browser; the phone side is still a zero-install web page.
  Password verification, key derivation, manifest encryption and the per-chunk IV/AAD binding are **all the same code** (`role: 'receiver'` in `src/session.js` only turns the direction around); what is new is just how the bytes flow:
  `POST /up/session` → `/up/auth` → `/up/manifest` (the encrypted manifest arrives **first**) → `PUT /up/chunk` (**idempotent**, written straight to `<name>.flicker-part` at an offset) → `GET /up/status` (after a dropout the phone asks what is missing and sends only that) → `POST /up/finish` (re-reads the `.part` file **in disk order** to compute the whole-file SHA-256, and only renames it into place if that matches).
  Every file name still passes the twelve path-safety rules before anything is written, and any violation **aborts the whole session**; because the manifest comes first, "not enough disk space / too many files / too large / same name" are all decided **before work starts** (insufficient space answers 507 and says by how much).
  The default password became a **six-character code** (`k7m-3fq`, with the look-alike characters 0O1lIo removed) —— it has to be typed on a phone keyboard, and there are only five attempts; a name collision **stops and asks** (rename / overwrite / skip this file, and after five minutes without an answer it takes the safest choice, rename; `--no-ask` turns the question off).
  ⚠️ **The phone-side upload page is not built yet** (that is the next step), so scanning the code today only shows an explanatory page; to exercise the protocol on the computer, run `node _lab/sim-phone.mjs` to play the phone (`node _lab/recv-selftest.mjs` is the automated version of the same thing).
  The whole command-line path is tested end to end: 14 protocol/disk-layout unit cases plus 4 cases that spawn a **real child process over TLS** (including the negative verification "flip one byte of a chunk's ciphertext and it must be refused").
- **The phone upload page (`web/phone.html`)**: the page a phone sees after scanning the code — type the one-time password → pick photos/videos (or other files) → whole-file checksums are computed → encrypted upload → "Everything sent".
  The page is **self-contained**: the protocol core (PBKDF2 / HKDF / HMAC / AES-256-GCM / incremental SHA-256), the twelve path-safety rules and the bilingual strings are all **inlined at build time** (three generators plus their `--check` guards), so once the phone has the page it asks us for nothing else — the only shape that survives a weak network.
  Three chunks of 2 MiB in flight: peak memory is independent of total file size, so a 4 GB video cannot blow the page up.
  Several things that are easy to get wrong on a phone are handled: **checksums are computed before the manifest** (otherwise the computer cannot verify the whole file), file names are **checked on the phone against the same rules first** (collisions and illegal names are explained there instead of aborting the session on the computer), coming back to the foreground asks the computer which chunks are still missing and resumes, and the page requests a screen wake lock where it exists while saying plainly "do not let the screen sleep".
  How it is verified: 19 core cases compared **byte-for-byte** with the Node suite (`test/phone-page.test.js`) + 3 self-containment/inlining guard cases (`test/phone-inline.test.js`) + **the whole path in a real browser** (`_lab/e2e-phone-browser.mjs`: headless Edge against a real HTTPS service, three files injected, byte-for-byte comparison on the computer, including an empty file and a chunk-boundary case).
  Both traps it hit are written down in `_lab/设计草稿-手机发送端.md` chapter 11: the **chunk-size quote was missing a number** (the page declared `maxChunkBytes` while the server rejected it as `+17`; both numbers are quoted now, and the default plain chunk went from 1 to 2 MiB), and the **verification script read `input.files` too late** (the page clears the input after taking the files; the check now looks at the page's own list).
- **Single-file artifact**: packed with Node SEA, about 94 MB, double-click to run (no Node install needed); it supports **reproducible builds** (same source → byte-identical binary).
- **Release packing script**: produces every artifact plus a **zip** per artifact (the recommended download) plus `SHA256SUMS` and `RELEASE.md` (download table, usage, known limitations, checksums) in one go.
- **zip distribution (download 62% smaller)**: of the 94.3 MB artifact, **89.2 MB is the Node runtime itself** (it cannot be removed; our own content is only 5.1 MB), so what can be compressed is the **download**, not the size: a zip is shipped alongside (**36.0 MB**), and the raw artifact still ships too.
  The ZIP writer is **our own** (`gen/zip.mjs`, zero dependencies —— `node:zlib` gives you deflate but not a container), held up by three criteria: a real extraction tool can open it byte-for-byte (`_lab/verify-zip.mjs`), an independently written parser reads it back with a CRC matching `zlib.crc32`, and the same input zipped twice is **byte-identical** (the timestamp field is pinned to 1980-01-01, otherwise reproducible builds would be destroyed).
- **Personal-information pass before going public (2026-10)**: the user plans to open a new public repository, so everything that would be published along with it was scanned again. This round found **network identity**, not credentials: `设计文档.md` and `中继部署.md` (Chinese and English) still contained the author's **home egress public IP** and a **carrier hop** from a `tracert`, and a one-off refactor script carried the router/computer/phone **real LAN addresses** in its replacement table. Fixes: the egress IP and hop became neutral text ("redacted", `100.64.x.x`) with **no conclusion changed** (CGNAT, no global IPv6 and double NAT all still hold), and that script was deleted (its only value was the replacement table, which was itself the personal data). `gen/check-pack-pii.mjs` therefore gained a **"public IPv4"** rule: no routable address may appear in anything we ship (private ranges, loopback, CGNAT, the documentation ranges and ASN.1 OIDs do not count), and the rule itself is held up by 5 cases in `test/pack-pii.test.js` (it catches what it should and does not misfire).

- **Things the docs reference must actually exist (2026-10)**: `gen/check-doc-paths.mjs` guards three kinds of references —— repository paths (`src/…`, `_lab/…`; **836 places**), `npm run <script>` (66) and `FLICKER_*` environment variables (20). On its first run it caught two real problems: the roadmap cited `_lab/probe-relay-preempt.mjs` (the probe behind that measurement) which **was not in the repository** while the protocol document used it as evidence —— it is now rewritten from the documented three-row table and runs (`node _lab/probe-relay-preempt.mjs` reproduces "squatted → ROOM_TAKEN, lost create response → manifest re-posted, normal start → seq 0"); the other was a one-off script still cited after deletion. Only two exceptions exist and both state their reason (npm's own `bin/npx-cli.js`, and the "this file is a credential and must not be committed" counter-example). To keep the criterion from becoming decoration, `test/doc-paths.test.js` (8 cases) exercises every branch in reverse —— including the **extension boundary** (`web/page-plugins.json` must not be truncated to `.js`) and a trap that was actually hit: the first version excluded backticks from the character before a path, yet docs put almost every path inside backticks, so "144 paths" really only picked up the few outside backticks —— green criterion, almost nothing examined.

- **`_lab/` cleanup (2026-10)**: 28 one-off scripts that **nothing in the repository referenced** were deleted (`audit-*`, single-use `verify-*`/`probe-*`, `qr-*`, `doc-find`, `list-ui-strings`, `bench-browser-sha256`, …); their conclusions already live in the docs. Before deleting, a script listed every reference to each file; what remains is referenced by docs or criteria (`e2e-*`, `bench-*`, `verify-*`, `sim-phone`, `push-via-api`, `rehearse-ci`, `verify-fresh-clone`). The rule for future one-off scripts: **either leave the sentence that cites it, or delete it** —— `check-doc-paths.mjs` now enforces this.

- **Numbers in the docs now have a machine watching them (2026-10)**: a family of "current fact" numbers in the docs expires over time —— the i18n string count, the number of `npm run check` criteria, documents per language, the version in sample output, the minimum Node version. Before 2026-10 **not a single machine check watched them**, so they relied on a human re-reading the docs (one pass surfaced four kinds at once: 171→319, 89.5/91→94 MB, ten→twelve documents, v1.0.0→0.1.0). `gen/check-doc-numbers.mjs` now **computes** each one and compares it with the docs; it runs in `npm run check` and in CI, while artifact size is checked by the Windows CI job after `build-sea.mjs` (`--artifact`, ±0.1 MB —— the gift source pack carries the docs themselves, so every doc edit moves it). It also insists that **every fact has at least one claim**: if that sentence is deleted the check reports "no claim found" instead of quietly switching itself off —— an always-green check is no check. On its first run it caught six stale numbers: 171→373 in 7 places, `319 条` in the handover, four `flicker-1.0.0-…` file names in the architecture notes, and the English sentence `twelve each` (spelled-out numbers cannot be checked, so it became `12 each`). Reverse verification: `test/doc-numbers.test.js` (8 cases) —— a broken number must be reported **with file and line**, a deleted sentence must fail, and touching the old numbers inside a **historical** sentence (e.g. "171 → actually 319" in the changelog) must **not** react, otherwise it would degrade into a bad "scan every number" check.

- **Two sets of documents**: Chinese in `中文文档/`, English in `docs/`, 12 each, with their structure kept in step by a machine check.
- **Twelve path-safety rules**: absolute paths, drive letters, UNC, `..` traversal, NUL, reserved names, illegal characters… all rejected, from a single implementation.
- **Cross-platform session certificates**: X.509 encoded in pure JS (no openssl needed), measured to give **zero warnings** once installed into the Windows trust store.
- **Progress kept within a session**: at file granularity —— pressing "retry" does not re-send files that are already on disk.

### Fixed (each one says how it was found)

| Symptom | Root cause | How it was found |
|---|---|---|
| The relay was **deployed but could never be reached**, while the docs mentioned it in one sentence at the very bottom | The `*.workers.dev` domain is **blocked outright** on some networks (measured 2026-10: it resolved to `199.16.156.103` —— **not** a Cloudflare address —— and port 443 timed out, while Cloudflare's **API** host stayed reachable, so "deployment succeeded" and "cannot be reached" hold at the same time). The deploy script used to end with a cheerful "✅ done, your relay address is …", leaving the user to retry forever | Walked through on a real machine by the user (email verification → the dashboard only opened in Edge → no `workers.dev` subdomain → then stuck on exactly this). Three changes: ① the deploy script now **probes that address itself** right after deploying and prints the cause plus two ways out when it cannot be reached; ② the note "the default address may be unreachable" moved to **the top of chapter 2** of the deployment doc (it used to sit in chapter 7), together with a three-step "bind a domain of your own"; ③ a Windows path-with-spaces bug in the deploy script was fixed (previous row). Negative verification: `node _lab/verify-remote-relay.mjs <address>` runs a full transfer against the real relay, compares byte for byte and asserts the room disappears afterwards |
| LAN mode **never worked at all**: a correct password still reported "password mismatch" | The page computed the handshake MAC without the domain prefix (the sender uses `flicker/1/recv\n`; the page signed the bare challenge) | A real-browser LAN rehearsal was written (`_lab/rehearsal-lan.mjs`); every earlier verification had a Node receiver standing in, which bypassed the page |
| Relay mode **never worked in a browser** (four defects stacked) | ① the message type byte was not stripped ② the page never sent an ack ③ the ack sequence was off by one ④ the starting chunk number was only computed on the "gift" branch | Running the relay with a **real browser** (`_lab/e2e-relay-browser.mjs`): the Node stand-in receiver did all three things for the page, so all four defects slipped through |
| The files were not actually complete, yet the sender reported "transfer complete" | After the loop `break`, the function **unconditionally** returned success (measured: it returned success after 148 ms while the ack count was still 0) | The missing-ack reproduction script `_lab/repro-no-ack.mjs`; **"a failure reported as a success" is classified as the least acceptable kind of error in this project** |
| The single-file artifact, copied to the desktop and double-clicked, flashed a console window and vanished | Only 5 modules were packed in; the rest were loaded by relative **dynamic** `import()` from the source tree —— which always works while you are inside the source tree | Reported by the user after real testing; the bundler now refuses to build on a relative dynamic import, and smoke **copies the artifact outside the source tree** before running it |
| Pressing "destroy now" did nothing | The condition was written as `if (!S.run && …)`, and `S.run` exists exactly while a transfer runs —— so the button did nothing at the very moment it mattered most; and even when the phase changed, the session and certificate were untouched | Reported by the user after real testing; the criterion is now "after destruction that link must not answer" |
| The interface looked frozen after pressing "start" | `/api/start` awaited the end of the transfer before responding (minutes for a large file) | Surfaced while fixing the destroy button |
| The receiver computed checksums slowly and held the whole transfer back | The pure-JS SHA-256 in the page allocated a fresh 256-byte array every 64 bytes (33.55 million allocations for a 2 GiB file) and only reached 92 MiB/s | `probe-network` brought it out sideways: the NIC is 2.5 GbE while loopback measured only 187 MiB/s, so the bottleneck was the implementation; optimised to 252 MiB/s (2.7×) |
| `--rate` **silently did nothing** (the user thought 5 MB/s was set while it ran at full speed) | The token top-up formula was wrong (`Math.min(n, capacity) - tokens`) | Measured against the criterion "the user believes the limit is in force" rather than by reading the code |
| The browser always showed an "insecure" warning | The generated CA was missing the CA flag (`basicConstraints` must carry `ca=1`) | Real interactive verification (three window modes × two address forms); we nearly wrote "browsers do not trust self-signed CAs" into the docs as a platform limitation |
| The same source produced a different binary | The temporary build directory name contained `Date.now()` | Noticed while the release script compared checksums; after the fix, two consecutive builds are byte-identical |
| The artifact sitting in `dist/` was days old | The build script does not re-run just because you changed a page, and the tests read the page from disk | A near-miss where a changed page was about to ship; the build now records asset fingerprints inside the artifact and smoke compares them against disk |
| The docs said `POST from:"i"` could squat a room name, while the implementation **silently skipped the manifest** | The document's reasoning was wrong (the room name cannot be *guessed*, but it **is in the link**); the implementation conflated two opposite meanings of "the room already exists" | `_lab/probe-relay-preempt.mjs`; it now reports `ROOM_TAKEN` explicitly and tells the user to start again |
| The manifest fields in `PROTOCOL.md` §6.1 **did not exist in the implementation at all** | The document and the implementation were each written on their own, and nobody compared them | Found while translating the docs into English, sentence by sentence; a machine check now compares "the manifest generated by the real code" against the document |
| A chunk size larger than the protocol default leaves the sender's read buffer too small | On the LAN side it **silently truncates** (whatever was not read goes out as zero bytes —— the file arrives corrupted with nothing reporting an error); on the relay side it reports "the file changed during transfer", blaming the user's file | Walked into while measuring "how much is a bigger chunk worth": both resident buffers were hard-coded to `PARAMS.chunkBytes`. They now allocate from **the largest chunk actually used in the manifest** |
| With `PSModulePath` polluted by a tool higher up, the **leftover-certificate scan silently stops working** | Reading the certificate store needs PowerShell's `Cert:` drive; once a different version of that module wins the lookup, the old form **exits 0 while "finding 0 certificates"** —— so the CA left behind by an abnormal exit stays in the user's trust store while the program looks perfectly clean | A full test run suddenly failed en masse with "no such drive: Cert"; tracing it showed this session's environment put PowerShell 7's module directory ahead of 5.1's. The child process now puts 5.1's own module directory first, and **every command that reads a certificate store carries `-ErrorAction Stop`** (if it cannot be read, that is reported honestly instead of looking clean) |
| After opening "receive from a link" there was **no way back to the previous page** | The Back button sat in the bottom row: with a shorter window (a browser window, or the app-style window) it fell below the fold, so users never saw it and would not think of scrolling | Reported by the user after trying it on a real machine. Back now sits **at the top** of both the "paste the link" and "check the fingerprint" panels; `test/pull-gui.test.js` asserts it comes before the inputs/fingerprint |
| Clicking "Choose folder" produced **no system dialog** (the page just seemed to hang) | The dialog **was** created, but the PowerShell process that owns it has no foreground window, so Windows' foreground rules pushed it behind the browser. The user could not see it and would never think to look in the taskbar | Reported by the user after retesting on a real machine. ### Security

- **The handshake MAC now binds the suite id (downgrade protection, groundwork for a second crypto suite)**: the MAC input
  carries the suite identifier, so the negotiation result itself is authenticated. The old construction is kept for
  interoperability with 0.1.0 peers and distinguished by an **echo**: a peer that sends no echo continues on the old
  construction with an **explicit warning**; "I offered the new one, the other side echoed the old one" **aborts**
  (a sign the negotiation was tampered with — it must not degrade into "password mismatch").
  Relay mode has no challenge-response, but there the **room name is derived from suite-dependent KDF labels**, so the
  suite is implicitly bound.
- **The password never goes on the wire**: it only takes part in computation inside each machine's memory (PBKDF2-SHA-256, 600,000 iterations).
- **File contents are end-to-end encrypted**: AES-256-GCM, 1 MiB per chunk; each chunk's AAD binds "file index + chunk sequence + total chunks + plaintext length", so swapping a chunk, reordering or truncating is rejected.
- **File names and directory structure** travel encrypted with the manifest and are invisible on the network.
- **The relay only sees**: that two devices are talking, the room name, the timing, the size and count of each message, and both IPs; it cannot see content, password or file names.
- **One-shot**: when the session ends every key is overwritten with `fill(0)`, the service closes, the link dies; a certificate installed into the system trust store is **removed again afterwards** (both install and removal were measured, and the run asserts the user's certificate stores are back to their previous state).
- **Path safety**: before writing to disk the receiver applies twelve rules (rejecting absolute paths, drive letters, UNC, `..`, NUL, Windows reserved names, illegal characters, trailing spaces or dots…); failing any one of them aborts the whole session.

**A few lessons that were paid for:**

- **When the verification script does not behave like the real client, you have verified a different path.**
  On the relay path the Node stand-in receiver did three things the real page did not (strip the type byte, send acks,
  compute chunk numbers), so four defects slipped through while every check stayed green.
- **"A failure reported as a success" is the least acceptable kind of error.** It is worse than a crash: the user
  believes the transfer finished and deletes the source files. So the completion criterion is now "every chunk was
  confirmed by the other side", not "the loop ended".
- **On a benchmark that swings by ±65%, a difference under 20% is not a conclusion.** One optimisation meant to
  "save the extra round trip per window" measured slightly slower than the original, so it was reverted —— only the
  parts with evidence behind them were kept.
- **The dangerous state is "it looks right".** Certificates, destruction and reproducible builds all went through
  "tests green while the thing is wrong", so this project's rule is: **nothing counts as done until it is measured**,
  and every criterion must be falsifiable (negative-verification scripts live in the repository alongside the checks).
- **"All green but the process never exits" is the most expensive kind of failure.** There is no failure message,
  only "it hangs": one cleanup function that returns `undefined` prevents every later cleanup from running, a child
  process holds the pipe, and the node test process never exits (locating it took a quarter of an hour).
  Two lessons —— ① **search the whole repository for the same class of fix**: this lesson had been written down in
  `gui.test.js` long before, yet only that one file was fixed while five others kept the landmine;
  ② a form that easily comes back deserves a machine check (`gen/check-test-cleanup.mjs`), and the check itself
  needs a case that proves "deliberately writing it wrong fails".
- **"Completeness" cannot rely on memory.** The gift's source package was a **hand-written allow-list** that missed core
  modules such as `src/run.js` and `src/assets.js` —— so "source plus every document, so the other side can read it,
  change it and build it" was factually false, while tests, smoke runs and rehearsals stayed green: none of them ever
  asked "can the receiver actually run this". Two lessons —— ① the question to judge is **whether the other side can
  use it** ("build a real package, unpack it, run something inside it"), not "does the list contain the files I
  thought of"; ② allow-lists drift, whereas **a tree walk plus a deny list** does not (a new module is picked up
  automatically).
- **A third-party tool's error can point at the wrong place.** postject said "the sentinel occurs multiple times in
  the binary", while the real cause was inside **the blob being injected** (the source package had pulled in
  `gen/build-sea.mjs` itself, a file that writes the sentinel literal). For this class of misdirected failure the
  right move is not to memorise it but to add a check **on our own side**: the misleading sentence is replaced by one
  a person can act on (the build now prints exactly which files brought the sentinel in).
- **"The path the tests take" must be the path users take by default.** The gift is on by default while every relay
  test passed `--no-gift`; so "relay + default gift" had been 100% broken since release while tests, smoke runs and
  rehearsals stayed green —— they were exercising a **narrower** path than the user's. This is the third instance of
  the same bias in this project (the first two: a Node-side receiver doing three things the real page did not; the
  artifact only ever being run inside the source tree). The new criterion therefore uses **defaults** and asserts
  quantities that "a big object stuffed into the manifest" would break, such as how large the manifest is.
